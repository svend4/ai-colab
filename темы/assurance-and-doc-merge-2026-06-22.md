# Два вопроса: гарантии инструкций и слияние документации

> **proposed** — материал для котла (D-018). Два вопроса Stefan, разобранные структурно (текущие механизмы → пробелы → варианты с pros/cons/effort/where → рекомендация). Чистые формулировки вынесены в `questions/` как Q-XXX.

## A. Гарантии инструкций — применение, актуальность, поток вверх (L4→L1)

**Переформулировка:** Вопрос о трёх проблемах гарантирования инструкций: 1. ПРИМЕНЕНИЕ: как убедиться, что инструкции не просто существуют, а агент их реально учтённых в действиях (existence ≠ applied)? 2. АКТУАЛЬНОСТЬ: как предотвратить дрейф (drift) и устаревание документов; как автоматически выявлять несоответствие docs↔факт? 3. ПОТОК ВВЕРХ: как обеспечить, чтобы информация снизу (L4=sandbox, L3=collab) доходила до верхушки (L2=portals, L1=core) и там реально использовалась?

### Варианты решения

**Preflight + Required evidence** (effort: low)

- *Что:* Расширить tools/instructions.py так, чтобы preflight не только ПОКАЗЫВАЛ правила, но и требовал check-report: read-only verify на отчёт в outbox/done, и reject если `Applied instructions` неполна или формальна (пусто, одна строка, содержит только AGENTS.md без конкретики).
- *Плюсы:* Немедленная feedback: агент видит требования до работы, не после.; Проверяемая дисциплина: формальный отчёт не пройдёт gate.; Низкий overheard: read-only, не блокирует работу, только требует честности.
- *Минусы:* Может быть перфекционистским: если требовать слишком много details в evidence, агент потратит время на отчёт вместо работы.; Зависит от того, как сформулировать критерии: что считать 'достаточной' доказательством?
- *Где:* tools/instructions.py: cmd_check_report должен проверить не только наличие заголовка, но и минимальное количество пунктов per правилу; top.py должен добавить scenario `check-done <path>` перед тем как позволить pipeline.py done.

**Currency gate (freshness index на docs)** (effort: medium)

- *Что:* Добавить в front-matter каждого ключевого документа: `last_verified`, `status`, `applies_to`, `supersedes`, `superseded_by`. Создать tools/instruction_freshness_check.py, который прыгает через docs/ и ловит: старые docs без `last_verified`, docs которые ссылаются на отменённое решение D-NNN, docs лежащие в зоне L2 portal но ссылающиеся на устаревшую L4 информацию.
- *Плюсы:* Не требует переписания всех docs сейчас; можно добавлять метаданные incrementally.; Выявляет ОДНУ-ИЗ-ГЛАВНЫХ проблем: что инструкция есть, но устарела.; Помогает новому агенту фильтровать: 'этот doc status=draft, можно пока пропустить'.
- *Минусы:* Требует дисциплины при обновлении docs: каждый раз нужно stamp `last_verified`.; Может быть слишком шумно если много docs без метаданных: нужен plan миграции.
- *Где:* docs/*.md (добавить метаданные), tools/instruction_freshness_check.py (новый скрипт), docs/drift_check.py (интегрировать как часть дрейфа), top.py health (добавить currency check).

**Promotion coverage check (обратный поток вверх)** (effort: high)

- *Что:* После того как материал поднялся из L3 в L2 (portal), провести ОБРАТНУЮ проверку: действительно ли L2 workflow/docs ИСПОЛЬЗУЕТ L1 знание или L2 портал начал жить своей жизнью независимо? Создать tools/promotion_coverage.py: для каждого L1 артефакта показать, в скольких L2 портал он используется (grep refs); для каждого L2 портала показать, как он напрямую ссылается на L1 vs. переопределяет правила заново.
- *Плюсы:* Решает ROOT проблему: выявляет, дошло ли знание вверх не просто как текст, а как используемое руководство.; Помогает обнаружить дублирование и divergence в L2 портала.; Поддерживает L1 чистоту: если L1 правило не используется ни в одном L2, может ли оно быть в L1?
- *Минусы:* Требует чёткого определения 'использования': что считается использованием? ссылка, цитата, встроенное правило, или всё вместе?; Может быть слишком детектором проблем, не решением: 'L2 не ссылается на L1' — но что делать?
- *Где:* tools/promotion_coverage.py (новый скрипт), docs/promotion-coverage.md (правила), top.py coverage (новый сценарий).

**Capability manifest как retrieval engine** (effort: high)

- *Что:* Вместо статического JSON, system-capabilities.json должна быть retrieval index: для заданного задачи/agent/context система автоматически выдаёт не только commands и docs, но и rules_applicable, decisions_relevant, frictions_known. Это фактически 'query capability manifest' вместо 'read capability manifest'.
- *Плюсы:* Решает проблему 'как выбрать релевантные инструкции' через машинное query вместо текстовых heuristics.; Масштабируется: когда docs станет ещё больше, preflight будет выдавать ТОЛЬКО relevant правила.; Возможность связать capability с decision/friction: 'эта команда есть потому что decision D-020'.
- *Минусы:* Требует более структурированный metadata в docs (tags, category, depends_on).; Может стать over-engineering если просто интегрировать текущий preflight (уже работает).
- *Где:* tools/capabilities.py расширить с query-интерфейсом и routing logic. Например: `python tools/capabilities.py query --task T-123 --context 'code/commit'` выдаст не только команды, но и `['D-022', 'F-016', 'docs/parallel-work-policy.md', ...]`. tools/instructions.py preflight может использовать это engine.

**Required evidence in report gate** (effort: low)

- *Что:* Когда агент делает `python tools/pipeline.py done <agent> <T-id> --claim ...`, система требует параметра `--applied` с явным списком инструкций которые были used (например `--applied 'D-022,F-016,validate'`), или альтернативно, не даёт close задачу если outbox report не содержит `Applied instructions` блок. Это создаёт АРХИВИРУЕМУЮ запись что было учтено.
- *Плюсы:* Самый прямой механизм гарантирования: не закроешь задачу без доказательства применения.; Создаёт машиночитаемую запись (в YAML фронт-матер) для будущего анализа.; Не требует новых инструментов: использует существующий pipeline.py и инструкции.; Улучшает трейсинг: можно потом спросить 'какие инструкции применялись в T-150-T-160?'
- *Минусы:* Может быть percieved как бюрократия; агент может написать `--applied all` и готово.; Нужны чёткие критерии когда `--applied` обязателен (for system tasks? for reports?).
- *Где:* tools/pipeline.py: cmd_done должен проверить либо --applied флаг, либо вызвать instructions.check_report на соответствующий outbox файл перед записью в done/.

**Consensus synthesis + tracking** (effort: high)

- *Что:* Специфично для вопроса 'как выявить что разные агенты согласны на инструкцию': создать tools/claims.py с форматом claim-карточки (claim_id, thesis, source, agent, confidence, status). Когда несколько агентов пишут про одно и то же (например, 'targeted claim нужен'), система группирует это как Common Ground и выкладывает `synthesis/<topic>/<claim-id>.md`. Это документирует не только решения, но и консенсус процесс.
- *Плюсы:* Решает проблему многоагентности: документирует не только 'решение', но и 'кто и когда согласился'.; Улучшает trust: когда видишь что three agents independently пришли к одному выводу, это сильнее.; Помогает выявить расхождения рано, а не потом как конфликты.; Возможность связать claim с инструкцией: 'consensus G-001 требует применения D-022'.
- *Минусы:* Требует изменения культуры агентов: нужно учить писать структурированные claims, а не просто документы.; Может быть слишком надинженерингом для текущего проекта (3 агента, не 30).
- *Где:* tools/claims.py (новый скрипт), templates/claim.md (шаблон), synthesis/ (новая папка), tools/synthesis_helper.py расширить интеграцией.

**Рекомендация:** ## Стратегия в три волны  **Волна 1 (ближайшие 2-3 дня) — Укрепить текущий preflight (LOW EFFORT, HIGH CERTAINTY):**  1. **Required evidence gate в pipeline.py** (Вариант 5): расширить `pipeline.py done` требовать проверку `Applied instructions` или `--applied` флаг. Это создаст архивируемую запись и предотвратит формальные отчёты. Effort: ~4-8 часов. Выигрыш: гарантирует что evidence оставляется, не просто требует его наличие.  2. **Расширить check_report в tools/instructions.py** (Вариант 1): вместо проверки только наличия заголовка, требовать минимум N пунктов; проверять что не все пункты это просто AGENTS.md; интегрировать как gate в top.py перед done. Effort: ~4-6 часов. Выигрыш: заметает формализм.  **Волна 2 (неделя 2-3) — Добавить freshness detection (MEDIUM EFFORT, MEDIUM CERTAINTY):**  3. **Instruction freshness check** (Вариант 2): добавить metadata `last_verified`, `status`, `applies_to` в ключевые docs; написать tools/instruction_freshness_check.py; интегрировать в drift_check.py. Effort: ~2-3 дня. Выигрыш: выявляет устаревание, помогает отфильтровать неактуальные docs в preflight.  4. **Интегрировать freshness с capabilities.json** (Вариант 4 partial): когда capabilities.py генерирует JSON, добавить field `freshness_status` для каждого doc/command. Effort: ~1 день (piggyback на Волна 2). Выигрыш: агент видит сразу 'этот doc draft, используй осторожно'.  **Волна 3 (неделя 4+) — Закрыть поток вверх (HIGH EFFORT, HIGH LEVERAGE):**  5. **Promotion coverage check** (Вариант 3): написать tools/promotion_coverage.py для ОБРАТНОЙ проверки: действительно ли L2 портал использует L1 знание. Это решает ROOT проблему: 'доходит ли информация снизу вверх'. Effort: ~3-5 дней. Выигрыш: обнаруживает divergence в L2, поддерживает L1 чистоту.  6. **Consensus tracking для многоагентности** (Вариант 6): если проект масштабируется, tools/claims.py + synthesis tracking будет критичной. Effort: ~3-4 дня. Выигрыш: документирует консенсус, помогает новым агентам быстро понять что согласовано.  ## Почему такой порядок?  - **Волна 1** адресует НЕМЕДЛЕННУЮ проблему: инструкции не применяются, потому что нет гарантии, что evidence оставляется. Это quick win. - **Волна 2** адресует ВТОРИЧНУЮ проблему: даже если evidence есть, оно может быть про устаревшие инструкции. Freshness detection предотвращает это. - **Волна 3** адресует СТРАТЕГИЧЕСКУЮ проблему: данные идут снизу вверх в пирамиде, но используются ли? Coverage check это выявляет и помогает поддерживать L1 в актуальном состоянии.  ## Для каждой волны нужна минимум одна проверка  - Волна 1: `python tools/pipeline.py done` выдаст error если нет evidence; `python tools/instructions.py check-report` будет более строг. - Волна 2: `python tools/drift_check.py` будет ловить stale docs; `system-capabilities.json` будет помечать docs as draft/legacy. - Волна 3: `python tools/promotion_coverage.py` будет показывать divergence в L2; synthesis board будет документировать консенсус.  ## Ответ на три под-проблемы Stefan'а:  1. **ПРИМЕНЕНИЕ** (exist ≠ applied): Волна 1 требует evidence в отчёте и checking его в gate. Не 100% гарантия, но проверяемая.  2. **АКТУАЛЬНОСТЬ** (drift): Волна 2 добавляет metadata и freshness detection. Не идеально (требует дисциплины при обновлении docs), но лучше чем сейчас.  3. **ПОТОК ВВЕРХ** (L4→L3→L2→L1 и обратно): Волна 3 + Волна 1 вместе: Волна 1 гарантирует evidence идёт ввысь; Волна 3 проверяет что это знание реально используется в L2. Если нет — это signal что L1 правило либо не актуально, либо нужна переработка L2 workflow.

**Открытые под-вопросы:**
- Как определить критерий 'достаточное' в check_report — сколько пунктов в Applied instructions нужно? Относительный % per правилу или абсолютный минимум?
- Когда `--applied` обязателен в pipeline.py done — только для system tasks? для всех? только для commit? Нужен ли whitelist/blacklist?
- Для promotion_coverage check: что считать 'использованием' L1 в L2? ссылка, цитата, встроенное правило, или всё вместе? Какой минимальный % coverage требуется?
- Metadata `last_verified` — кто и когда её обновляет? Автоматически при коммите? ручным просмотром? Есть ли SLA (например, каждые 3 месяца)?
- Нужна ли feedback-петля: если freshness_check выявит что doc устарел, автоматически понизить статус в capabilities.json или требовать manual review?
- Для многоагентного consensus tracking — нужен ли отдельный реестр claims (files), или достаточно парсить synthesis/<topic>/ documents как source-of-truth?

## B. Слияние документации разных агентов — консенсус + структурированные разногласия

**Переформулировка:** Stefan запрашивает инструмент/процесс для сканирования нескольких тематических документов разных агентов, выделения: (1) консенсусных пунктов с указанием, в каких файлах встречаются; (2) структурированных разногласий в виде подструктуры (под-файлы/под-пункты/таблицы); логически и грамматически корректно оформленных. Сейчас это делается вручную (примеры: opinion-synthesis-2026-06-21.md, friction-subsystems-synthesis-2026-06-22.md). Нужна инструментация.

### Текущие механизмы и их пробелы

| Механизм | Что делает | Пробел |
|---|---|---|
| variants.py (D-018) | READ-ONLY реестр форк-вариантов по всему репо. Сканирует темы/*.md, docs/*.md, streams/, queues/outbox и строит индекс тема→[варианты] с фильтром по agent, status, kind. Только дискавери (поиск ВСЕХ вариантов одной темы). | Не сравнивает содержание документов, не выделяет общие пункты, не структурирует разногласия. Это только реестр, не синтез. |
| synthesis_helper.py (D-017/D-018) | Собирает форк-варианты темы в СКЕЛЕТ синтеза. Выводит скелет markdown с таблицей вариантов, outline каждого файла (##/### заголовки), шаблоны для заполнения консенсуса и расхождений. Инструмент подготавливает материал, но не принимает решение и не анализирует содержание. | Не парсит СОДЕРЖАНИЕ документов (только заголовки), не ищет общие пункты, не противопоставляет расхождения логически. ### Варианты решения

**1. Специализированный инструмент doc-consensus** (effort: high)

- *Что:* Новый tools/doc-consensus.py (2000-3000 строк) сканирует N документов по теме, парсит структуру (заголовки, таблицы, списки), ищет семантические совпадения (общие фразы, синонимы, структурные параллели), выделяет: (A) shared-bullets с cross-reference file:line; (B) divergences как таблица или подструктура с позициями сторон и доказательной базой.
- *Плюсы:* Полностью автоматизирует первый pass сравнения — экономит часы manual work.; Выводит готовый скелет с file:line references → легко отслеживать источники.; Может регулярно пересканировать при обновлении документов → выявит дрейф.; Интегрируется с variants.py: variants.py list --topic X → doc-consensus topics/X/*.md → синтез.md.; Формирует основу для дальнейшей ручной доработки (уточнение смысла, слияние близких пунктов).
- *Минусы:* Семантический анализ многовариантен: что считать «общим»? Нужно калибровать heuristic (threshold для similarity, исключения ложных совпадений).; Парсинг структуры Markdown нетривиален (nested lists, tables, code blocks). Требует robust parser или regex-инвестиций.; Divergence-выявление может быть неточным (пропустит скрытые несогласия, найдёт ложные конфликты).; Требует явного указания «по каким критериям» считать пункты общими (substring match? semantic embeddings? structural parallelism?).; Инструмент сам по себе не гарантирует корректность синтеза — результат нужно проверять человеком.
- *Где:* Новый tools/doc-consensus.py, опционально расширение synthesis_helper.py. CLI: `python tools/doc-consensus.py compare --docs docs/a.md docs/b.md docs/c.md [--out synthesis-report.md]` или `--topic opinion-synthesis` (автоматически найти варианты через variants.py).

**2. Формат вывода: консенсус в mainline, разногласия в streams/forks** (effort: low)

- *Что:* Процесс (не инструмент): при синтезе двух/трёх документов — консенсусные пункты остаются/пишутся в основной документ (docs/main.md) как unified description; расхождения выносятся в отдельные файлы streams/<topic>/<agent>-divergence.md (по агенту) или streams/<topic>/divergence-table.md (центральная таблица). Инструмент: расширить synthesis_helper output format с автогенерацией этих файлов + перекрёстные ссылки.
- *Плюсы:* Чистая архитектура: одна версия истины (консенсус в mainline), divergences изолированы → никогда не будут случайно совместно закомичены.; Divergence-файлы остаются в истории git → можно вернуться и проверить, как был разрешён спор.; Масштабируется: если через месяц вернёмся к теме — все divergence-аргументы уже документированы.; Структура streams/ уже понятна проекту (D-017 предусматривает fork-и-synthesize в streams).; Лёгкое расширение synthesis_helper.py: добавить генерацию stream-файлов вместо шаблона.
- *Минусы:* Требует дисциплины: писатель консенсуса должен явно указать, какие пункты consensual, какие остаются в divergence.; Mainline документ становится тоньше → риск потерять контекст для новичков (решение: перекрёстные ссылки на streams/).; Если divergence долго не разрешается, mainline документ может стать неполным (решение: docs-drift-check должен включить streams-ссылки в проверку).; Не автоматизирует выделение консенсуса — по-прежнему требует ручного разбора.
- *Где:* Расширение tools/synthesis_helper.py (функция generate-streams-for-divergences) + документация в docs/parallel-work-policy.md (как структурировать divergence-файлы). Не требует нового инструмента, только смена формата output.

**3. Процесс/протокол (D-019 Decision)** (effort: low)

- *Что:* Формальное описание в decisions/D-019.md: когда появляется несколько вариантов документа (через D-017 fork-and-synthesize), ОБЯЗАТЕЛЕН синтез-шаг с структурированным выводом (таблица консенсус/расхождения, file:line references, запись в DECISIONS.md о разрешении). Требование: author synthesis document (в темы/ или docs/), указать источники, явно обозначить consensus vs divergence. Валидатор (tools/validate.py расширение): check-synthesis-references (если в документе упомянуты варианты, должен быть синтез в список; если в синтезе ссылка на файл, файл должен существовать).
- *Плюсы:* Фиксирует правило на уровне governance (D-017 — почему, D-019 — как и обязательность).; Легко встроить в workflow: pre-commit hook может проверять наличие synthesis документа при коммите fork-вариантов.; Дешево реализуется: небольшие расширения validate.py + документация.; Не требует AI/ML — только логические проверки (ссылка на источник существует? упомянут ли все варианты?).; Встраивается в существующие инструменты (variants.py, synthesis_helper.py).
- *Минусы:* Требует изменения культуры/дисциплины: агенты должны помнить о синтез-шаге, не пропускать его.; Не автоматизирует сам синтез — только обязывает его делать и проверять структуру.; Валидация может быть ложноположительной (не всякий форк требует полного синтеза; маленькие fix-пакеты можно просто адопциировать без таблиц).; Если синтез неверен или неполон, валидатор это не поймёт (проверяет форму, не суть).
- *Где:* Новое decisions/D-019.md (2-3 страницы) + расширение tools/validate.py (функция check_synthesis_references, 50-100 строк). Опционально: расширение pre-commit hook. Активация: флаг в settings.json или явный вызов `python tools/validate.py --check-synthesis`.

**4. Расширение synthesis_helper.py (эволюционно)** (effort: medium)

- *Что:* Постепенное расширение synthesis_helper.py от «готового скелета» к полусамостоятельному синтезатору. Добавить функции: (A) parse-content (парсинг заголовков, списков, таблиц из Markdown); (B) find-common-bullets (поиск семантически близких пунктов); (C) extract-divergences (выделение пунктов, которые противоречат друг другу); (D) generate-report (шаблон отчёта с cross-refs). Версия 2: обогащение file:line references, версия 3: автоматическое слияние близких пунктов с user-query на разрешение конфликтов.
- *Плюсы:* Эволюционный путь: no big bang, постепенная добавка функций в уже известный инструмент.; Единая кодовая база с variants.py (оба живут в tools/, обмениваются парсерами).; Низкий порог входа: начать с простых heuristics (substring match), потом усложнить.; Встаёт на плечи существующего инструмента (синтез-скелет уже генерирует synthesis_helper, добавляем анализ).; Рефакторинг кода: _canon.py уже парсит front-matter, можно туда добавить _content_parser.
- *Минусы:* Рискует разбух инструмент: synthesis_helper.py сейчас ~200 строк, при добавке анализа станет 500+.; Boundary с variants.py станет нечётким (кто за что отвечает? дискавери vs анализ).; Тестирование heuristics сложно: много edge cases (таблицы? списки? вложенные заголовки?).; Если парсинг Markdown будет неточным, весь синтез сломается → требует серьёзных тестов.; Не решает проблему семантического совпадения (два пункта написаны по-разному, но означают одно).
- *Где:* Расширение tools/synthesis_helper.py + рефакторинг tools/_canon.py (добавить _content_parser). Новая опция: `python tools/synthesis_helper.py analyze --topic X [--deep]` (глубокий анализ контента). Предварительно: инженерное решение в tools/test_synthesis_helper.py (тесты на edge cases).
