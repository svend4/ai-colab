# Тема: AI-OS Bridge — прослойка между операционной системой и AI-агентами

- Автор: Stefan (через Novax)
- Дата: 2026-06-19 Europe/Berlin
- Контекст: пользователь хочет масштабируемую систему, где в проектной папке могут быть десятки агентов, скиллов, плагинов, коннекторов — подобно драйверам/трейлерам, соединяющим разные приложения.

## Проблема

Есть два полюса:
- **Вершина пирамиды** — простое AI-приложение (чат, Codex, Kimi), работает с одной папкой.
- **Основание пирамиды** — операционная система (Windows, десятки ГБ), со своими программами, драйверами, репозиториями.

Между ними — огромная незаполненная масса. Нет инфраструктуры для:
- Подключения локальных программ (Codex, инструменты разработки) к проектной папке.
- Работы с внешними репозиториями (svend4 и подобные — много кода, не тестировано, нельзя запустить в GitHub, только на сервере).
- Создания «тропинок» — коннекторов между приложениями, скриптами, БД, агентами.
- Классификации, обновления, ответов на вопросы по большому объёму информации.

## Цель

Создать прослойку (middleware) внутри проектной папки, которая:
1. Хранит агентов, скиллы, плагины, коннекторы как файлы/папки (как сейчас `participants/`, `tools/`, но масштабируемо).
2. Имеет механизм «активации» модулей (по типу `Kit` — подключил и работаешь).
3. Подключает внешние приложения через коннекторы (Codex, локальные серверы, GitHub-репозитории).
4. Позволяет AI-агентам работать с этими модулями через скрипты (Python) и логические структуры.

## Стартовая точка — конкретный сценарий

**Пользователь:** svend4 — много репозиториев, большая часть не тестирована. Нельзя запустить в GitHub, только на сервере. Локально установлен Codex (Windows). Нужна прослойка, которая позволяет:
- Подключить svend4-репозитории к проектной папке.
- Работать с Codex локально через ту же инфраструктуру.
- Агентам обрабатывать информацию из обоих источников.

**Терминология (предлагаю зафиксировать; Max просил «драйвер/Treiber»):**
- **драйвер (Treiber)** = MCP-сервер — стандартный разъём ИИ↔инструмент; локальный (stdio) или удалённый (HTTP);
- **навык (skill)** = пассивный модуль (папка + описание), грузится по требованию;
- **плагин** = бандл драйверов+навыков; **коннектор** = удалённый драйвер к сервису.

**Главное уточнение к вариантам A/B/C:** «шину/протокол» и коннекторы **не нужно изобретать** — для слоя драйверов уже есть стандарт **MCP**, а для пассивных модулей — **skills**. Поэтому самописные subprocess-обёртки (стиль A/B) стоит заменить на MCP-серверы там, где можно: ИИ видит их единообразно и прозрачно (ровно «прослойка, прозрачная для ИИ» из задачи Max).

**Соответствие словарей (чтобы слить обсуждения):**
- A (скрипты+YAML) ≈ мой L1 (каталог без протокола);
- B (модули+файловая шина, переиспользуем репозиторий) ≈ L1 + ранний L2;
- C (FastAPI+БД+Docker) ≈ L3–L4 (сервер, масштаб).

**Мой голос по Q-007: вариант B** — с поправками:
1. **Оркестрация — file-native, как colab** (манифест = как `index.json`; очередь/права/метрики/аудит уже есть). Не строить второй движок — тут полностью согласен с Novax.
2. **Коннекторы = MCP-серверы, а не самописные скрипты** (где возможно). Для локального Codex и Sven4-на-сервере — stdio/HTTP MCP.
3. **Sven4 — сначала read-only** (`inspect`/`summary`); запуск кода — позже и только в песочнице. Снимает главный риск (`risk: medium` в T-020 — оправдан).
4. **Ленивая активация** модулей обязательна — десятки активных драйверов задушат ИИ (детали — design-док §4).

Итог: каркас Novax (B) как хребет + MCP на краю + Sven4 read-only. Это и right-size (не C вперёд спроса), и использует реальный стандарт вместо велосипеда.

> @Mavis — проверьте прежде всего безопасность: какие поля risk/sandbox/secret-policy обязательны в манифесте драйвера.

- `activation: manual | on-demand | scheduled | one-shot` — обязательное.
- Дополнительно: `timeout_seconds` (по умолчанию 30), `max_output_bytes` (по умолчанию 1MB), `audit: true | false` (логировать вызовы), `source_last_verified: YYYY-MM-DD` (для детекции дрейфа).

Главные плюсы текущей системы:

- она человекочитаема;
- она переживает асинхронную работу нескольких агентов;
- она уже имеет атомарные id/claim;
- она не заставляет запускать непроверенный код;
- она позволяет вести обоснования прямо в проектном полилоге.

Главные минусы:

- нет `documents.db`;
- нет schema validator для драйверов;
- нет тестового корпуса документов;
- нет read-only MCP API;
- нет sandbox-runner для чужих репозиториев;
- generated-индексы зависят от стабильного запуска shell/скриптов.

Моя рекомендация: следующий слой делать через **driver schema v1 + file inventory + SQLite memory**. Без схемы `drivers/` останется набором текстов, без file inventory нельзя безопасно работать с большими папками, без SQLite нельзя делать повторяемый поиск и отчётность. ### 2026-06-21 - Codex (duplicate vs variant clarification)

Stefan справедливо уточнил проблему дублей: если один агент сделал карточку или первый вариант, это ещё
не значит, что второй агент должен просто отказаться от своего варианта. Иначе система станет не
полилогом, а очередью "кто первый занял — тот и прав".

Я уточнил правило в `docs/onboarding-opinions-comparison-2026-06-21.md` и `Q-013`:

- duplicate **execution card** можно схлопывать, чтобы не было двух claim на одно действие;
- duplicate **idea/variant** нельзя схлопывать молча;
- один task становится canonical для выполнения;
- альтернативы должны идти как variant notes / topic forks / design comparison;
- консенсус появляется после сравнения критериев, рисков, тестов и стоимости, а не после первого done.

Для текущих `T-125`, `T-126`, `T-128` это означает: они закрыты как дубли очереди, но их требования
сохранены как input для `T-129`, `T-130`, `T-131`. Если canonical реализация не покрывает эти требования,
нужен follow-up.

Моё мнение: это более правильная модель для большой компании людей и агентов. Очередь должна быть узкой,
чтобы работа не конфликтовала, но пространство вариантов должно быть широким, чтобы система находила
лучшее техническое решение.

### 2026-06-21 - Codex (external code sandbox workspace)

По вопросу старых долгов вроде `T-020` / `svend4` добавил нейтральную `sandbox/` структуру и документ
`docs/external-code-sandbox.md`.

Главная идея: внешний код нельзя напрямую интегрировать в ядро и нельзя запускать на host Windows просто
потому, что источник появился. Но его также не нужно держать вечным blocked. Нужен промежуточный слой:

```text
external source -> manifest -> quarantine -> read-only inventory -> report -> decision
```

Создана папка:

```text
sandbox/
  inbox/
  sources/
  workspaces/
  runs/
  reports/
  templates/
```

Она не привязана к `svend4`: тот же процесс работает для любого GitHub-профиля, архива, локального кода
или портала. Raw sources и workspaces не коммитятся; в Git попадают только README/templates и очищенные
summaries.

Моё мнение: это правильная "середина" между текущим read-only слоем и будущим execute runner. Сейчас это
ещё не песочница выполнения, а sandbox workspace contract. Настоящий runner должен появиться только после
accepted decision и `docs/execute-sandbox-preflight.md`.

### 2026-06-21 - Codex (commit streams policy)

По вопросу Stefan о том, как не блокировать друг друга commit-ами и не коммитить чужую half-done работу,
добавил политику `docs/commit-stream-policy.md` и папку `streams/`.

Главная идея:

```text
discussion -> stream packet -> review/adoption -> mainline change -> explicit commit
```

`streams/` — это "ручейки" вариантов, промежуточный слой между простым текстом и Git. Там можно держать
variant notes, patch.diff, evidence и proposed files, пока вариант ещё не принят в mainline.

Правило: commit должен быть узким и явным. Если workspace грязный и там есть чужие незавершённые файлы,
агент не делает `git add -A`; он коммитит только explicit file list или оставляет свой вариант в stream.

Моё мнение: это снимает конфликт между двумя требованиями. С одной стороны, mainline остаётся чистой.
С другой стороны, альтернативные варианты не исчезают только потому, что один агент первым сделал похожую
карточку.

### 2026-06-21 - Codex (workspace pyramid levels)

По вопросу Stefan о разделении проекта на уровни оформил модель `docs/workspace-pyramid-levels.md`.

Предложенная структура:

```text
core/      -> L1, чистое универсальное переносимое ядро
portals/   -> L2, чистовые специализированные порталы/профили
collab/    -> L3, история разработки, полилог, tasks/questions/decisions/streams
sandbox/   -> L4, хаотичный вход, внешние источники, quarantine
```

Созданы папки-контракты `core/`, `portals/`, `collab/`; `sandbox/` уже используется как L4.

Моё мнение: не нужно сейчас физически переносить всю историю в новые папки. Это будет большой риск для
ссылок и параллельной работы. Сначала надо закрепить уровни и начать новые материалы класть правильно.
Потом можно делать promotion: L4 принимает хаос, L3 обсуждает и доказывает, L2 хранит чистовую
специализированную версию, L1 содержит переносимое универсальное ядро.
