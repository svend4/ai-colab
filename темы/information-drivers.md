## Проблема

Текущая архитектура AI-агента (Codex / Claude / Mavis / локальный LLM) выглядит как пирамида с пустой серединой:

```
        [AI-агент]              ← вершина: одна точка входа, один контекст
           │
           │ ← ПУСТАЯ ЗОНА: нет инфраструктуры для навигации к
           │   данным, классификации, обновления, ответа на вопросы
           │
        [ОС + данные]           ← основание: десятки ГБ, 50+ репозиториев,
                                  Docker-контейнеры, базы, сервисы
```

Сейчас AI видит только одну папку проекта (`STATUS.md` и вниз). Всё остальное — невидимо, даже если оно лежит на том же диске или доступно по сети. Это **structural blind spot** современных AI-инструментов: модель «знает» только то, что попало в её контекст.

Stefan поднял вопрос 2026-06-20 (чат): можно ли заполнить эту зону **информационными драйверами** (он же «трайберы», от нем. *Treiber* = driver) — пассивными компонентами в файловой системе проекта, активируемыми по запросу AI.

## Терминология

**Информационный драйвер (трайбер)** = пассивный компонент в файловой системе проекта, который:

- Оборачивает сырой ресурс (репозиторий, базу данных, сервис, контейнер) в формат, понятный AI.
- Активируется по запросу через унифицированный интерфейс.
- Содержит манифест (front-matter), точку входа, документацию, тесты.
- Может быть локальным (Python-скрипт) или удалённым (HTTP-endpoint).
- Аналогии: device driver в ОС (оборачивает железо); capability в capability-based security; skill/plugin в agent framework.

## Аналогии (от Stefan)

- **Тропы в муравейнике** — появляются там, где часто ходят, укрепляются от использования. Lazy + emergent.
- **Дорожки на чипе** — физическая инфраструктура, проложенная заранее под определённые нужды.
- **Тропы в лесу** — неформальные маршруты, созданные повторяющимся использованием.

Эти три образа объединяет одна идея: **инфраструктура не строится сразу целиком, а прорастает по мере реальной потребности**. Драйверы должны появляться там, где AI часто нуждается в доступе к данным.

## Варианты реализации (от простого к сложному)

### Вариант A. Каталог в YAML/JSON (минимум)

Один файл `trailers.yaml` со списком всех драйверов:

```yaml
trailers:
  - name: svend4-repo-1
    type: code-search
    source: github.com/svend4/repo-1
    input_schema: {query: string, limit: int}
    output_schema: {results: list}
    location: trailers/repo-1/search.py
```

**Плюсы:** ноль инфраструктуры, детерминировано, легко понять.
**Минусы:** ручное обновление, нет интроспекции, нет валидации, плохо масштабируется на 100+ драйверов.

### Вариант B. Файловая система с манифестами (наш канон) ⭐ рекомендация

Каждый драйвер = папка с front-matter-манифестом + код + тесты + документация:

```
trailers/
  svend4-repo-1/
    manifest.md       # front-matter: name, capabilities, deps, schema
    index.py          # скрипт индексирования
    search.py         # точка входа (поиск)
    test_search.py    # самопроверка
    README.md         # документация для AI и человека
```

Главный `trailers/CATALOG.md` — генерируется из манифестов (как `STATUS.md` из front-matter тем). `tools/trailers_validator.py` проверяет manifests (по аналогии с `validate.py`).

**Плюсы:** модульно, воспроизводимо, дебагабельно, совместимо с тем, что уже построено; каждый драйвер = отдельная папка с тестами.
**Минусы:** требует дисциплины (как наш канон), manual catalog maintenance.

### Вариант C. Capability-based runtime

Вроде Plan9 / Capsicum: каждый ресурс = capability (URL: `trailer://svend4/repo-1?q=...`). Runtime маршрутизирует, sandbox изолирует, считает вызовы.

**Плюсы:** безопасность, единообразие, формальная модель, isolation.
**Минусы:** нужен свой runtime, сложно, высокий порог входа.

### Вариант D. Distributed fleet

Драйверы на сервере (svend4 server), AI локально подключается через API/WebSocket. Подходит для случая, когда код не запускается в Docker, только на сервере.

**Плюсы:** масштабируется, server-side данные остаются на сервере, единый source of truth.
**Минусы:** latency, нужен server-side runtime, security (креденшалы, сетевая атака).

### Вариант E. Гибрид B + D

Каталог в формате варианта B (front-matter + manifest). Часть драйверов локальная (Python), часть — удалённая (HTTP). AI читает общий каталог, вызывает нужный. **Протокол, который мы построили, становится «ОС для AI» — middleware между моделью и ресурсами.**

**Плюсы:** все плюсы B + D, естественная эволюция от B к D по мере роста.
**Минусы:** сложнее, чем чистый B или чистый D; требует абстракции «локальный vs удалённый драйвер».

## Плюсы и минусы концепции в целом

**Плюсы:**
- Модульность и линейное масштабирование (добавил 10 репо → добавил 10 драйверов).
- Lazy activation — не ест контекст, пока не вызван.
- Совместимость с современными LLM (function calling / tool use).
- Прозрачность — открыл папку и видишь, какие драйверы есть.

**Минусы:**
- **Discovery** — AI должен знать, что драйвер существует; на 100+ драйверов это съедает контекст.
- **Maintenance burden** — больше компонентов = больше точек отказа.
- **Security surface** — каждый активируемый драйвер = исполняемый код.
- **Quality control** — если данные в источнике не тестированы, то и драйвер ненадёжен.
- **YAGNI risk** — если реальных пользователей пока нет, переинжиниринг.

## Пошаговый план (при выборе B)

1. **Зафиксировать schema манифеста** (front-matter поля):
   - `id` — уникальный ID драйвера
   - `name` — человекочитаемое имя
   - `type` — категория (code-search, data-query, file-walker, и т.д.)
   - `source` — что оборачивает (URL репо, путь к БД, имя сервиса)
   - `capabilities` — список доступных операций
   - `input_schema` / `output_schema` — JSON-schema для аргументов и результатов
   - `runtime` — local / remote (URL)
   - `depends_on` — другие драйверы или инструменты
   - `risk` — low / medium / high
2. **Создать `trailers/` папку** — корневой каталог драйверов.
3. **Сделать `tools/trailers_validator.py`** — по аналогии с `validate.py`: проверить, что у каждого драйвера есть manifest, схема валидна, тесты проходят.
4. **Расширить `generate.py`** — добавить генерацию `trailers/CATALOG.md` (или `index.json` уже подходит, можно использовать).
5. **Сделать `tools/trailer_dispatch.py`** — runtime для активации драйвера по имени: принимает запрос → маршрутизирует к нужному драйверу → возвращает результат. Аналог `queue.py`, но для драйверов.
6. **Один первый драйвер** — для конкретного репозитория svend4 (нужен выбор Stefan).
7. **Тест end-to-end:** AI → `trailer_dispatch.py` → драйвер → результат → AI.
8. **Документация:** `docs/information-drivers.md` — описание концепции и API для новых пользователей.

## Связь с существующим каноном

Большая часть нашей инфраструктуры подходит:

| Инструмент | Как используется для драйверов |
|---|---|
| `front-matter` (канон) | Манифесты драйверов в том же формате |
| `index.json` / `generate.py` | Каталог драйверов генерируется аналогично |
| `validate.py` | Может проверять manifests (наличие `id`, `name`, корректность `input_schema`) |
| `permissions.py` | Может ограничивать, какие драйверы агент может активировать |
| `queue.py` | Может очередь запросов к драйверам |
| `dispatch.py` | Может выбирать драйвер по `depends_on` / `capability` |
| `risk_gate.py` | Может автоматически выбирать режим AUTO/REVIEW/HUMAN по полю `risk` |

**Не хватает:** schema manifest для драйверов + runtime для активации (`tools/trailer_dispatch.py`).
