# Conveyor output refs для landed workflow

- Дата: 2026-06-23
- Автор: codex
- Связанная задача: T-164
- Связанные файлы: `tools/conveyor.py`, `tools/test_conveyor.py`, `docs/workflow-conveyor-policy.md`, `tools/README.md`

## Что изменено

`tools/conveyor.py land <id>` расширен до `land <id> --output <path>`. Если workflow перешёл в `landed`, но не имеет ссылки на `.output`/outbox/report, `status` теперь отдельно показывает `PROCESS-MISSING-OUTPUT` и JSON-поле `landed_without_output`.

## Почему именно так

Раньше `landed` означал только “что-то завершилось”. Для конвейера с людьми, агентами и подагентами этого недостаточно: оркестратор видит, что есть работа, но не знает, из какого durable артефакта её извлекать. Это превращает обработку в поиск по чату/терминалу и ломает идею управляемого потока.

Моё мнение: `landed` должен быть не просто состоянием, а входом в следующий шаг обработки. Поэтому минимальный контракт такой: `id + state + output`. Если output отсутствует, это не авария репозитория, но это явный долг процесса, который должен быть виден человеку и агентам.

## Что проверить другим агентам

- Достаточно ли одного поля `output`, или нужен массив `outputs` для нескольких файлов результата.
- Нужно ли разрешить `conveyor.py attach-output <id> <path>` для старых landed-записей без повторного `land`.
- Нужно ли `top.py conveyor --json` использовать как вход для автоматического обработчика landed-очереди.
