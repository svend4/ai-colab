# Agent capacity methodology — отчёт Codex

По запросу Stefan оформлена методология динамической ёмкости агентов.

Главное решение: не фиксировать один «магический максимум», а разделить пределы на три слоя:

1. **Жёсткие потолки инструмента:** до 16 одновременных `agent()` на один workflow-прогон, до 1000
   агентов за жизнь одного прогона, один уровень вложенного `workflow()`.
2. **Практические потолки проекта:** полоса commit/review, бюджет токенов, CPU машины, качество синтеза.
3. **Операционный регулятор:** `conveyor.py target <N>`, который повышается только когда очередь здорова,
   и понижается/замораживается при `PROCESS`, missing output, build-конфликте или governance-решении.

Практический стартовый режим для текущей стадии:

- `target 2-4` для конвейера;
- `3 workers -> 1 conductor -> chief` для пилота;
- `9 producers -> 3 integrators -> chief` как первая широкая read-only волна;
- `27+ producers` только после стабильных handoff/result шаблонов и проверенного synthesis-gate.

Почему так:

- read-only анализ почти не конфликтует и может масштабироваться широко;
- build-потоки конфликтуют через общий git-tree и должны идти через worktree/merge-gate;
- governance/accepted decisions не параллелятся и требуют человеческого утверждения.

Добавлено в методологию:

- лестница динамической ёмкости: solo, pair review, pilot 3:1, small wave, medium tree, large tree;
- динамический регулятор `target`;
- команды активации верхнего слоя;
- связь между локальным handoff и внешним platform sub-agent launcher.

Моё мнение: сейчас правильный максимум для реальной работы — не технические 1000 агентов, а маленькие
управляемые волны. Сначала нужно несколько раз провести `3:1` и `9->3` на read-only задачах, только потом
поднимать флот. Иначе система будет создавать больше незавершённых результатов, чем верхний слой успеет
проверить, синтезировать и безопасно закоммитить.
