## Текст Lagrange

Проектная папка может работать как маленькая операционная среда для людей, AI-агентов, подагентов, скриптов и драйверов. Главная идея: агенты не общаются только через чат, а оставляют проверяемые следы в файлах: задачи, решения, вопросы, отчёты, сообщения, индексы и результаты проверок.

Система строится слоями. Человек задаёт цель и утверждает важные решения. Главный агент помогает держать контекст, читать репозиторий, формулировать задачи и проверять результат. Координатор распределяет работу между несколькими агентами или подагентами. Worker-агенты делают конкретные задачи. Sub-agent'ы запускаются внешним orchestrator'ом для узких параллельных подзадач. Скрипты автоматизируют рутину: claims, индексы, проверки, merge-gate. Драйверы дают безопасный доступ к данным, git, файлам или памяти. Память хранится не "в голове агента", а в каноне проекта: `tasks/`, `docs/`, `topics/`, `queues/`, `reports/`, `index.json`, runtime-логах и поисковых индексах.

Важно разделить две вещи: repo flow и platform orchestration. Repo flow готовит задачу, claim, worktree, инструкции и gate. Platform orchestrator запускает реальных sub-agent'ов во внешней среде. Репозиторий не должен притворяться платформой запуска; он должен выдавать понятный handoff: кто работает, над какой задачей, где рабочий каталог, какие правила применить, куда вернуть отчёт.

## Уровни

1. Человек: ставит цель, утверждает `accepted` решения, назначает права, принимает спорные изменения.
2. Главный агент: читает канон, проектирует систему, делает scoped-правки, запускает проверки, формирует задачи и отчёты.
3. Координатор: делит большую цель на независимые подзадачи, выбирает L0/L1 режим, создаёт claims/worktrees, собирает результаты worker'ов.
4. Worker-агент: берёт одну задачу, работает в своей зоне, оставляет отчёт, не трогает чужую незавершённую работу.
5. Sub-agent: короткоживущий исполнитель, запущенный внешним orchestrator'ом; обычно read-only analysis или узкая build-задача в отдельном worktree.
6. Скрипт: строго выполняет процедуру: `pipeline.py`, `flow.py`, `cohort.py`, `validate.py`, `generate.py`, `merge_gate.py`.
7. Драйвер: безопасный адаптер к возможностям: файлы, git, база, поиск, corpus, sandbox.
8. Память: канонические Markdown-файлы, generated indexes, отчёты, логи, FTS/SQLite.

## Как может работать агент Lagrange

Сначала Lagrange должен быть зарегистрирован в `AGENTS.md`: ID, роль, разрешённые зоны записи, ограничения. До регистрации его лучше считать внешним sub-agent'ом: читать можно, писать только в явно выделенный outbox/worktree.

Типовой цикл:

```text
1. Прочитать AGENTS.md, PROTOCOL.md, задачу и релевантные docs.
2. Запустить top.py agent-start lagrange --context "<тема>".
3. Взять задачу через pipeline.py next lagrange или получить handoff от координатора.
4. Проверить work-mode: shared tree или отдельный worktree.
5. Работать только в разрешённых файлах.
6. Не делать git add -A; добавлять только свои файлы.
7. Оставить отчёт в queues/outbox/ или теме.
8. Запустить validate/generate --check/тесты по масштабу.
9. Закрыть задачу через pipeline.py done с кратким evidence.
```

Что Lagrange может читать: весь канон проекта, задачи, решения, вопросы, docs, темы, отчёты, индексы, разрешённые данные и результаты драйверов.

Что может писать: только то, что указано в `AGENTS.md`. Обычно это `docs/`, `code/`, `tasks/`, `queues/outbox/`, свои topic messages, proposed questions and decisions. `accepted` решения без человека он не принимает.

Как не конфликтовать: брать claim, проверять `cohort.py guard`, уходить в worktree при hot files, чужих dirty-файлах, stale-index или same-file риске, писать отдельные сообщения вместо переписывания чужой истории.

## Плюсы

- Параллельная работа без постоянного конфликта в одном файле.
- Видно, кто что делает и почему.
- Sub-agent'ы могут масштабировать анализ, не ломая общий канон.
- Проверки превращают правила из договорённости в рабочий процесс.
- Память проекта переживает отдельные сессии и агентов.

## Риски и ограничения

- Слишком много слоёв может создать бюрократию.
- Без claims и worktree агенты будут смешивать чужие изменения.
- Sub-agent'ы могут вернуть шум, если не задать схему результата.
- Скрипты не должны автоматически принимать governance-решения.
- Память в файлах требует дисциплины: устаревшие docs надо обновлять или помечать.
- Внешний orchestrator должен быть явно отделён от repo tools.

## Пошаговый план внедрения

1. Зафиксировать роли в `AGENTS.md`, включая Lagrange.
2. Добавить короткий документ "repo flow vs platform orchestrator": repo готовит, orchestrator запускает.
3. Ввести handoff-manifest: agent, task, claim_id, branch, worktree_path, allowed files, report path, checks.
4. Добавить dry-run команду вроде `top.py subagent-handoff <agent> <task> --json`.
5. Использовать `cohort.py plan --json` для раздачи независимых задач.
6. Для build-подагентов создавать `flow.py start <agent> <task> --worktree --run`.
7. Для read-only analysis разрешить работу без worktree, но с отчётом в `queues/outbox/`.
8. Требовать structured result: summary, files read, findings, proposed changes, risks, checks.
9. Интегратор собирает результаты, запускает gate, принимает или отклоняет.
10. После 2-3 успешных циклов автоматизировать только повторяющиеся части, не весь процесс сразу.

Итоговая модель: люди принимают смысловые решения, главный агент держит контур, координатор готовит работу, platform sub-agent'ы выполняют изолированные куски, а репозиторий остаётся проверяемой общей памятью и системой правил.
