# D-022 — Политика параллельной работы (детализация 4 решений Stefan)

## Статус

`accepted`. Stefan ратифицировал 4 решения (D-006) и потребовал детализировать под-случаи. Полная
детальная политика с 50 под-случаями и матрицей «ситуация → механизм» — в
`docs/parallel-work-policy.md`. Двойная перепроверка D-018 (техн.+гуман.) — в конце. Закрывает
вопрос `Q-015` и развивает `D-021`.

Цель — убрать «ожидание другого агента» (остановку) и потерю работы при коллизиях: дать однозначное
правило на каждую конкретную ситуацию.

## Решения

1. **Уровень-1 (worktree-на-агента) — ОБЯЗАТЕЛЕН ПО ТРИГГЕРАМ** (Q-015 вариант B). Триггеры
   (детектор — `python tools/cohort.py guard`): **A** чужие незакоммиченные source-файлы; **B** STALE
   индекс не от моих staged-изменений; **C** правка hot-файла (`TASKS.md`/`index.json`/генераторы/
   `top.py`/`portal.py`/…); **D** явная параллельная работа/форк над одной темой; **E** предсказанная
   same-file коллизия. Нет триггеров → **Уровень-0** (selective-add + `commit_lock`, дефолт).

2. **STALE-индекс — авто-регенерация + коммит своих, НЕ ждать** (стандарт = `cohort ship`). Под-случаи:
   STALE от МОИХ источников → стейджить источники+индексы, коммитить; STALE от ЧУЖИХ незакоммиченных →
   регенерировать, индексы оставить НЕ-staged (их закоммитит владелец), коммитить только своё — либо, по
   п.1, уйти в worktree. «Ожидание чужого коммита» как способ — запрещено.

3. **Генерируемые файлы — разделить канонические/волатильные.** Канонические (коммитить при смене
   источников, входят в гейт): `TASKS.md`, `QUESTIONS.md`, `DECISIONS.md`, `board.md`, `STATUS.md`,
   `index.json`. Волатильные (рантайм-снимки — НЕ включать в обычный коммит, gitignore): `LIVE.md`,
   `PIPELINE.md`, `logs/heartbeat.json`, `logs/pipeline.json`. Снижает «ложные» STALE и шумные diff.
   *Механика (untrack `git rm --cached` + gitignore + не валить гейт на волатильных) — координированный
   follow-up: трогает то, что пишет pipeline, делать не соло (см. T-148).*

4. **Same-file параллелизм — три варианта по ситуации** (детально в политике):
   - **Вариант 1 (worktree + git merge)** — КРУПНАЯ/содержательная правка (≳500 строк, code, архитектура):
     каждому свой приток, `merge_gate` + 3-way merge сводит. Это случай LS-2 (`text_extract.py` — должен
     был быть Вариант 1, а не «кто последний перезаписал»).
   - **Вариант 2 (один-файл-один-claim, форк рядом)** — РЕВЬЮ/мелкие правки: второй не пишет в тот же
     файл, кладёт `docs/<file>-<agent>-review.md`, owner интегрирует.
   - **Вариант 3 (принять перезапись + обязательный синтез после)** — только узкий случай: маленький draft
     с заранее одобренной синтез-последовательностью, либо экстренный hot-fix с post-hoc синтезом. Вне
     этого — вреден (теряет работу).

## Перепроверка (D-018)

- **Техническая:** триггеры детектируются `cohort guard` (построен, протестирован, вживую сработал);
  Уровень-1 набор готов (`worktree.py`/`flow.py --worktree`/`merge_gate`); `cohort ship` уже реализует
  авто-регенерацию (п.2). Остаток (untrack волатильных, авто-эскалация в worktree по триггеру) — в T-148.
- **Гуманитарная:** политика устраняет потерю времени на «ожидание» и потерю работы при перезаписи; даёт
  человеку и агенту читаемую матрицу «ситуация → механизм» вместо догадок; не повышает поверхность риска.
