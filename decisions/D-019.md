## Context

T-136 asks to resolve the commit policy for many humans and AI agents working in one repository:

- how not to commit another agent's half-done work;
- how not to block every other participant;
- what the intermediate "semi-commit" format should be;
- whether worktree-streams and a merge-gate are needed.

Evidence already exists in `docs/commit-stream-policy.md`, `streams/commit-policy/2026-06-21-codex-streams-policy/STREAM.md`, `темы/commit-policy-streams-2026-06-21.md`, and the live T-133 case.

## Proposed Decision

1. **Accept Level 0 immediately as current practice:** use `tools/commit_lock.py` before `generate + git add + git commit`, and use explicit selective-add only. Do not use `git add -A` in a dirty shared worktree unless this is an explicitly named integration commit.
2. **Keep `streams/` as the semi-commit format:** a stream packet is the file-native middle layer for variants, evidence, draft patches and adoption notes. It is more structured than chat, but not yet mainline.
3. **Adopt Level 1 as the next target, pending Stefan approval:** one git worktree per active agent/task, with branch names such as `codex/<agent>/<task>`. This physically isolates dirty files and generated indexes.
4. **Add a merge-gate before mainline adoption:** the integration path should run `generate.py`, `validate.py`, focused tests, and a scoped diff review before merging a stream/worktree into mainline.
5. **Treat `changeset` files as evidence, not as a second VCS:** if a stream contains a patch, it should still be adopted through normal git review/merge. Avoid inventing a parallel version-control system inside Markdown.

## Technical Rationale

Level 0 solves two immediate problems: serializing `git index` writes and preventing accidental broad commits. It is cheap and already tested in practice.

Level 0 does **not** solve generated-index coupling. In the shared worktree, `TASKS.md`, `index.json`, `PIPELINE.md`, and other generated artifacts can reflect another agent's half-done task. The T-133/T-136 live case proved this: a second agent correctly avoided committing because the generated files would have mixed its own finished evidence with Codex's active T-133 state.

Therefore the technically cleaner solution is worktree-per-agent/task. Each stream has its own dirty tree and generated indexes; mainline only sees an integration commit after the merge-gate.

## Human / Collaboration Rationale

For people, Level 0 is understandable today: "commit only your files, take a short lock, explain the scope". It does not require new folders or new launch habits.

For a larger company of agents, Level 1 is the sustainable model: participants can work in parallel without constantly asking whether somebody else is halfway through `TASKS.md` or `index.json`. It also supports Stefan's "small streams flow into a larger river" metaphor without making mainline chaotic.

## Risks

- Worktrees add operational complexity: agents must know their worktree path and branch.
- A merge-gate can become a bottleneck if only one human can approve every merge.
- Streams can become a graveyard unless every stream has `status`, `adoption`, and a link to the deciding task/decision.
- If agents overuse streams for trivial changes, process overhead will grow faster than product value.

## Acceptance Criteria

D-019 can become `accepted` when Stefan or an explicitly appointed integrator confirms:

- Level 0 is mandatory in the shared worktree.
- Level 1 worktree-streams are allowed for parallel agents.
- Merge-gate ownership is clear: who may merge, under which checks, and how conflicts are resolved.

Until then, T-136 should remain blocked/waiting, not falsely done.
