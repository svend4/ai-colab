# Тема: Динамический конвейер агентов

- Автор: Stefan (через Novax)
- Дата: 2026-06-20 Europe/Berlin
- Контекст: пользователь хочет, чтобы процесс разработки был более динамичным, управляемым и живым. Агенты должны быстрее выполнять задачи, параллельно работать через единый конвейер, иметь единый файл отчёта и общаться более активно.

## Проблема текущей системы

Сейчас работает, но статично:
- Агенты пишут в `dialog.md` или темы — это полилог, но медленный (асинхронный, human-paced).
- `queue.py` есть, но только claim/complete/fail — нет пула, нет приоритетов, нет авто-назначения.
- `dispatch.py` показывает готовые задачи, но не назначает.
- Все сущности — Markdown, нет JSON для машинного быстрого взаимодействия.
- Агенты не знают, что делают другие, без чтения всего `dialog.md`.

## Что хочется

1. **Конвейер (pipeline):** единый файл, где видно все задачи, кто взял, кто делает, что блокирует.
2. **Пул заданий (stack/queue):** агент берёт следующее незанятое задание автоматически или по команде.
3. **Параллельность:** несколько агентов работают одновременно, не мешая друг другу.
4. **Живое общение:** агенты видят статус друг друга без чтения всего полилога.
5. **Отчётность:** один файл отчёта, который обновляется в реальном времени.
6. **Не только Markdown:** JSON/скрипты для быстрого машинного взаимодействия.

## Стартовая точка

На основе уже реализованного (`queue.py`, `dispatch.py`, `next_id.py`, `tasks/`):
- Улучшить queue.py (приоритеты, авто-назначение, heartbeat).
- Или создать новый слой (pipeline.md + JSON-логи + heartbeat).

## Решение

Принято D-011: комбинированный вариант A+B+C.

Не заменяем `queue.py`/`dispatch.py`, а добавляем поверх них слой `tools/pipeline.py`:

```text
agent -> pipeline.py next -> task claim -> work -> pipeline.py done/fail -> snapshot
```

Человек смотрит `PIPELINE.md`, агенты и скрипты читают `logs/pipeline.json`.

### 2026-06-20 - Codex

Продолжил слой визуального и машинного отчёта. Добавил в `tools/pipeline.py` команду:

```bash
python tools/pipeline.py snapshot
```

Она пишет два снимка:

- `PIPELINE.md` — один файл отчёта для людей;
- `logs/pipeline.json` — быстрый машинный срез для агентов и скриптов.

**Почему именно так:** текущий проект уже имеет правильные низкоуровневые детали: `tasks/*.md` как источник задач, `depends_on` для DAG, `queue.py`-подобный claim через `O_CREAT|O_EXCL`, `next_id.py` против коллизий номеров. Поэтому не нужно строить отдельную систему “с нуля”. Нужен тонкий слой, который соединяет готовность задачи, атомарный захват и отчёт в одну командную форму.

**Моё мнение:** это хорошая первая ступень “живости”. Полностью live-чат/heartbeat пока рано делать демоном: сначала надо проверить, что pull-модель задач удобна. Если она работает, следующий слой — `heartbeat.json` и короткая “комната разработки” `LIVE.md`, обновляемая агентами при начале/прогрессе/завершении.

**Вопрос к агентам:** нужно ли на следующем шаге делать heartbeat как обязательный протокол или оставить его добровольным до появления 3+ одновременно работающих агентов?

### 2026-06-20 - Codex (heartbeat)

Продолжил Q-012 и принял D-012: heartbeat делаем **добровольным**, не обязательным.

Почему не обязательным сразу:

- для 1-2 агентов это создаст больше служебного шума, чем пользы;
- обязательный live-протокол без нагрузки станет дисциплинарной бюрократией;
- преждевременный общий live-файл был бы горячим файлом и источником конфликтов.

Что сделано:

```bash
python tools/pipeline.py heartbeat codex T-028 --progress 80 --note "работаю" --eta "10m"
```

Дизайн записи:

- каждый агент пишет свой `logs/heartbeat/<agent>.json`;
- агрегированный машинный снимок — `logs/heartbeat.json`;
- человекочитаемая live-комната — `LIVE.md`.

Моё мнение: это правильный баланс между “живостью” и управляемостью. Если позже одновременно будут работать 3+ агента, можно вернуться к вопросу и сделать heartbeat обязательным.

### 2026-06-20 - Codex (совместимость queue.py check)

При перепроверке после heartbeat обнаружилось предупреждение:

```text
WARN: claim без задания и без done: T-024
```

Это не была настоящая потерянная задача. `T-024` существует в `tasks/T-024.md` и находится в работе у Novax, но старый `queue.py check` проверял только старую очередь `queues/inbox/<task>.md` и маркеры `queues/done/<task>.done.md`.

Что изменено:

- `tools/agent_queue.py check` теперь признаёт claim валидным, если существует `tasks/<task>.md`;
- старая логика для `queues/inbox/` сохранена;
- `tools/README.md` получил короткое пояснение, почему pipeline-claim живёт рядом с `tasks/*.md`.

Моё мнение: это важная совместимость между Queue 2.0 и новым pipeline-слоем. Без этой правки агенты будут видеть ложную тревогу, хотя фактически система работает правильно: pipeline берёт задачи из канонического каталога `tasks/`, а не из старого inbox.
