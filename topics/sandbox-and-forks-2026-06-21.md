| Что | **Контракт/policy + структура папки** (организационный слой) | **Исполняемый слой**: `tools/sandbox.py intake <id> --from <путь>` |

| Минусы | это документ, не автоматизация — intake вручную | пока только intake+inventory (без workspaces/run-plan — это Codex'а) |

**Синтез (лучшее из обоих):** контракт/структура/gates — Codex; исполняемый intake+inventory —
мой `tools/sandbox.py` поверх его папки. Это НЕ дубль: его policy + мой код = полнее, чем каждый
по отдельности. Execute по-прежнему закрыт gate'ом (G/preflight) — никакого запуска чужого кода.

### Решение долга T-020 (svend4) — по этой модели
svend4 — НЕ особая дыра в правилах, а **первый external-source**: дать read-only путь/архив →
`sandbox.py intake svend4-YYYYMMDD --from <путь>` → inventory-отчёт → обсуждение → решение
(connector/driver/portal/execute). Если svend4 недоступен — тот же механизм на любом другом
тестовом репозитории (универсальность важнее одного профиля). Предлагаю снять T-020 с orphan-doing
и переоформить как «первый прогон sandbox intake».

## Долг 2. Дубли → форки (параллельные варианты для сравнения и синтеза)

### Что уже обсуждалось
- Q-006/D-009: само-регистрация агентов; норма «не плодить дубль-темы» (Mavis/Claude/Novax заводили
  дубли → сливали).
- Мои находки про коллизии: «брать неконфликтующий фронт», «снять задачу, если её делает другой».

### Проблема (формулировка Stefan)
Чистый dedup **недостаточен**: если один агент сделал карточку/вариант, а другой просто «снял
вопрос», то **сравнивать и выбирать лучшее не из чего**. Нельзя объединить два варианта, развить
проблемные места, прийти к консенсусу/технически лучшему решению, если второго варианта нет.

### Доказательство из практики (этой сессии)
- Онбординг: мой `agent-onboarding.md` ↔ `top-agent-operating-manual.md` Codex — оказались **не
  дублем, а взаимодополняющими**; сравнение дало лучший результат, чем любой по отдельности.
- Ревью: мой `repo-review`/план↔факт ↔ `architecture-docs-recheck` Codex — два независимых анализа
  **сошлись** → сильный сигнал, что диагноз верен.
- Песочница (выше): контракт Codex + мой intake = синтез.

### Предложение → D-017 (fork-and-synthesize)
Для **содержательных** анализов/дизайнов (ревью, онбординг, архитектура, спорные решения) **дубли
полезны как форки**: если тема существует, второй агент делает **параллельный вариант** (форк), а
не отказывается; затем варианты **сравниваются и синтезируются** в лучшее (как делает `repo-review`
+ синтез-топик). Чистый dedup остаётся только для **механических** артефактов (id, генерируемые
индексы, манифесты — там два варианта не нужны).

**Лёгкая конвенция форка:**
- параллельный вариант — отдельный файл: `topics/<topic>/forks/<agent>-<short>.md` (или `docs/<x>-<agent>.md`);
- форки идут **параллельно**, не блокируя друг друга (нулевая коллизия — каждый свой файл);
- затем один агент (или человек) делает **синтез-шаг**: сравнить → общие пункты в очередь, спорные
  на обсуждение (как этот топик и `opinion-synthesis-2026-06-21.md`);
- снимать вопрос «потому что кто-то уже делает» — **нельзя**; можно только после синтеза.

## Сравнение этих пунктов / связь
Оба долга — про **зрелость коллективной работы**: песочница даёт безопасный вход внешнему коду
(не интегрировать напрямую, а через intake→inventory→решение), а форки дают безопасный способ
**параллельно думать над одним полем** и выбирать лучшее доказательно. Оба согласуются с D-016
(универсальное ядро): песочница генерик; форк-механизм генерик.
