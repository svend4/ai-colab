# 0. Визитка
> Беседа про `.inf` (заходы 5–7) искала «сервис совместной разработки»: среда, где несколько агентов+людей
> работают над проектом, оффлайн, без merge-ада. Главный вывод: **наш репо — это уже такой сервис**,
> и недостающий CRDT-слой мы только что построили. Здесь — архитектура «субстрат + governance», сравнение
> с Zed/infon-board/чистым git, и что осталось.

# 1. Видение из беседы (что искали)
- **MP-1 «формат есть платформа»** — общее состояние (документ/канон), тонкие клиенты (артефакт/терминал/IDE).
- **Web2-переход для ИИ = мульти-писательство** — несколько агентов+людей пишут в общее состояние.
- **Дыра, которую назвали:** координация через git (СТРОЧНЫЕ конфликты на хот-файлах) или проприетарные
  доски; провалы — merge-конфликты + изолированные окна, не видящие правок друг друга. Никто не даёт
  block-level merge + verify-once + glass-box-аудит. Zed решает, но коллаборация **облачная**.

# 2. Наш репо УЖЕ это — двухслойно
**Субстрат (общее состояние):**
- канон = файлы (tasks/decisions/questions/topics/docs) + YAML-front-matter + `[[ссылки]]` (≈ их блоки+рёбра);
- git = транспорт/история; queues/ = асинхронные сообщения между агентами; portals/view = срезы контекста;
- **CRDT-слой (построен этой сессией) — закрывает их дыру:**
  - `crdt_merge.py` — field-level 3-way (related/tags union, скаляры 3-way);
  - `seq_merge.py` — построчный diff3 тела (непересекающиеся правки сливаются);
  - `git_reconcile.py` — git merge-driver: коллизия канон-файла → авто-мёрж на уровне ПОЛЯ/СТРОКИ, не строки-каши.
  → Два агента правят РАЗНЫЕ поля/строки одного файла → сливается без конфликта (то, чего git-строки не дают).

**Governance (чего у их видения НЕТ):**
- `PROTOCOL.md` + `decisions/` — правила координации, ратификация человеком;
- адверсариальная валидация: `red_team_gate` + `oracle_quorum` (verify = пережил кворм, не подпись одного);
- провенанс: `seal_verified` + `provenance_independence` (целостность+порядок по git);
- независимый-first + сверка по смыслу (D-028/D-030, kotel).
→ Их «verify-once = подпись» — проблема оракула; наш governance-слой её смягчает.

# 3. Сравнение
| | Zed | infon-board | чистый git | НАШ репо |
|---|---|---|---|---|
| мульти-писатель | ✅ | ✅ (2 агента) | ⚠ строки | ✅ агенты+люди |
| конкурентная запись | CRDT (облако) | разбиение Q6-территорий | СТРОЧНЫЙ конфликт | **field+line merge (наш CRDT-слой)** |
| оффлайн коллаборация | ❌ (relay) | локально | ✅ | ✅ (git+файлы) |
| governance/валидация | — | verify-once=подпись | — | **red-team+кворум+провенанс** |
| glass-box | ✅ | ✅ | ✅ (текст) | ✅ (канон plain-text) |

**Вывод:** мы ближе к их идеалу, чем Zed (которому для коллаборации нужно облако): file-native + git + наш
field/line-merge + governance. Их infon-board избегал конфликтов разбиением территорий — мы их **сливаем**.

# 4. Что осталось
- **Sequence-CRDT на body (Automerge/Yjs)** — для ИСТИННО асинхронного (без merge-base) посимвольного
  мёржа. Наш `seq_merge` — diff3 (нужна merge-base); Automerge снимает это ограничение (P2P/оффлайн).
- **Тонкий клиент-доска** (как infon-board, но над нашим каноном) — view/level навигация + оркестратор.
- **Проблема оракула в governance** — семантические шаги (кворум/канонизация) остаются LLM-зависимы (kotel §10).

# 5. Итог
«Сервис совместной разработки» из беседы = **наш репо (субстрат) + CRDT-merge-слой (построен) + governance-слой
(построен) + тонкий клиент (TODO)**. T-263 (хот-файлы) решён инструментально. Следующий рубеж — Automerge-путь
для оффлайн-async и тонкий клиент-доска.
