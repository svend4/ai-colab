# Котёл: доказательная база по зависимостям text-extract (вход к T-137)

> Статус: **proposed** (вклад в котёл по D-018, не принятое решение). Решает коллектив с двойной
> перепроверкой (техн. + гуман.). Относится к пункту T-137 «приоритет text-extract / первая внешняя
> зависимость» и задаче T-133.

## Контекст

T-133 (`tools/text_extract.py`) реализует Codex: генерик-извлечение `.md/.txt/.html` на stdlib,
через `files_driver.read_file(redact=True)` (confinement allowed-root + redaction встроены), с
богатым контрактом `extract()→dict` и `memory_text()` для индексации содержимого в `knowledge`.
**Эту базу принимаю** — она лучше интегрирована по безопасности, чем мой исходный вариант.

Codex оставил пометку: «No PDF/DOCX here yet: those need an explicit dependency decision». Ниже —
доказательство, что для **DOCX** это решение не требуется, и спорным остаётся только **PDF**.

## Находка: DOCX извлекается чистой stdlib (зависимость не нужна)

`.docx` — это ZIP-контейнер Open XML; текст лежит в `word/document.xml`. Извлекается модулями
стандартной библиотеки `zipfile` + регексп, без внешних пакетов:

```python
import re, html, zipfile
def docx_to_text(path):
    with zipfile.ZipFile(path) as zf:
        xml = zf.read("word/document.xml").decode("utf-8", errors="replace")
    xml = re.sub(r"</w:p>", "\n", xml)   # границы абзацев -> переводы строк
    xml = re.sub(r"<[^>]+>", "", xml)    # снять все теги
    return html.unescape(xml)
```

Проверено на сгенерированном `.docx` (минимальный валидный Open XML, собранный тем же `zipfile`):
абзацный текст извлекается корректно. То есть тезис «PDF/DOCX = первая внешняя зависимость» верен
**только для PDF**.

## PDF — единственная реальная зависимость

Надёжное извлечение текста из PDF (разбор xref/streams/шрифтов) на stdlib невозможно. Нужна опц.
библиотека (`pypdf`, чистый Python, read-only). Это и есть точка «осознанного решения о зависимости».

## Предложение (на коллективную ратификацию, не соло)

1. **DOCX включить сейчас** в `text_extract` через stdlib (`zipfile`) — расширяет генерик-ядро без
   зависимостей; согласуется с D-016 (генерик-способность ядра). Техн.-риск низкий, новых зависимостей нет.
2. **PDF гейтить** до решения котла: при отсутствии `pypdf` — мягкий отказ (`supported=False`/пусто),
   не падение; тело такого файла просто не индексируется.
3. Если PDF понадобится по реальному спросу (T-127/реальные порталы) — отдельным решением выбрать
   `pypdf` (read-only, pure-Python, разрешить только чтение, прогнать через redaction как и остальной текст).

## Перепроверка

- **Техническая:** DOCX-извлечение протестировано (сборка `.docx` из `zipfile` + извлечение),
  поведение детерминировано, новых зависимостей не вносит; PDF-гейт не роняет конвейер.
- **Гуманитарная:** включение DOCX расширяет полезность для реальных пользователей порталов
  (договоры/служебные документы чаще `.docx`, чем `.pdf`), не повышая поверхность риска — извлечение
  read-only и проходит ту же redaction секретов.

Реализация-референс DOCX доступна (в т.ч. в истории моего форк-варианта); готов внести её в
`text_extract` Codex отдельным согласованным шагом, **после** того как коллектив подтвердит пункт 1.
