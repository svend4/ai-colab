**Доказательная рекомендация:** принять точный набор из 10 файлов; подтвердить семантику COPY (риск битых ссылок = 0); knowledge/drivers отложить на Q3. Четыре под-вопроса НЕ блокируют решение Q2, а уточняются при реализации: (a) генерировать ли core-специфичный README вместо копии 24KB `tools/README.md`; (b) запускаются ли тесты в изоляции или нужна адаптация путей; (c) `dispatch.py` отдельно или в паре с `pipeline.py`; (d) нужен ли уже сейчас безопасный (без зависимостей) путь `text_extract` в Q2, если реальный корпус потребует.

**Технический чек:** все 10 файлов — только stdlib + `_canon.py`, нет внешних зависимостей; фокус-тесты зелёные; copy-семантика подтверждена тестом; нет циклических импортов и хардкод-путей к доменам.
**Гуманитарный чек:** сторонняя команда может взять только координационное ядро без всего корпуса/истории — реальная ценность; контракт объясним человеку; копирование консервативно (источник цел) — строит доверие к независимой эволюции ядра.

## 2. portal-location-q4 — где жить порталам?

**Что решить:** разделять порталы между `portals/` (чистый L2: identity + current-state + workflows + links) и `data/portals/` (операционный корпус + .db, gitignored) — Вариант A; либо унифицировать всё под `portals/` — Вариант B.

**Стороны (кратко):**
- *Вариант A (split)*: чистый L2 + ссылка `corpus_ref` на операционные данные; уже реализован в `portals/example` и работает.
- *Вариант B (unified)*: один корень проще понять, но затаскивает бинарный `.db` и корпус в версионируемый чистый слой.
- *`tools/portal.py` сейчас*: рассчитан на `data/portals/`; рефактор на `portals/` требует переноса корпуса+`.db` и риска загрязнения L2.

**Доказательная рекомендация:** принять Вариант A (split). Соответствует контракту L2 (`workspace-pyramid-levels.md`: чистая конфигурация, без сырых данных); `corpus_ref` даёт семантическое единство без физического смешения; рефактор `portal.py` аддитивный (чтение identity из `portals/<name>/portal.md`, резолв корпуса через `corpus_ref` → `data/portals/`, с обратной совместимостью). Рефактор `portal.py` — горячая зона (Codex), поэтому только после синтеза, не соло (D-017).

**Технический чек:** Вариант A не ломает текущий `portal.py` (новый путь аддитивный); L2-файлы — чистый Markdown; `.db` остаётся gitignored в `data/`; пример-портал демонстрирует работоспособность.
**Гуманитарный чек:** человек видит `portals/` как чистую точку входа, а не спрятанную в `data/`; разделение «что я пишу» vs «что система генерирует» проясняет ментальную модель; нет риска случайно закоммитить `.db`/корпус.

**Кросс-чек vs Codex: partial.** Прямой позиции Codex по portal-location в просмотренных файлах нет (его STREAM — про commit-policy/worktrees, ортогонально). Совпадение структурное: принцип Codex в `workspace-pyramid-levels.md` («не реорганизовывать резко; уровни как контракты; держать `portals/` чистыми») сильно поддерживает философию Варианта A, но это согласие по принципу, не прямое подтверждение.
**Уверенность: высокая.**

## 5. docx-dependency — включать ли DOCX сейчас, гейтить ли PDF?

**Что решить:** включить ли DOCX-извлечение сейчас через stdlib `zipfile` (без зависимости), а реальную зависимость PDF (`pypdf`) гейтить до доказанного спроса.

**Стороны (кратко):**
- *Stefan (`topics/text-extract-deps-evidence-2026-06-21.md`)*: DOCX = ZIP-контейнер Open XML, текст в `word/document.xml` извлекается stdlib; PDF на stdlib невозможен. DOCX — сейчас; PDF — отдельно; при отсутствии `pypdf` — мягкий отказ (`supported=False`), не падение.
- *Codex (D-020 §6)*: text-extract инкрементален; DOCX — «next low-risk no-dependency step»; PDF — отдельное решение после реального корпуса.

**Доказательная рекомендация:** включить DOCX сейчас через stdlib (`zipfile` + `ElementTree`, без внешних зависимостей + один тест); PDF гейтить до реального спроса (T-127 или корпус Stefan). Поведение без `pypdf` — мягкий отказ (graceful degradation: индексируем остальное). DOCX — часть генерик-ядра (D-016), служебные документы чаще `.docx`, чем `.pdf`. PDF остаётся первой осознанной зависимостью — решается отдельно.

**Технический чек:** DOCX = валидированный стандартом ECMA-376 ZIP; `zipfile` + `ElementTree` (stdlib), gracefully обрабатывает некорректный файл; контракт `extract()` не меняется (те же поля path/type/supported/text/chars/truncated); redaction уже встроена в `read_file()`. Подтверждено чтением `tools/text_extract.py`: SUPPORTED не включает DOCX/PDF — это точка решения, не препятствие.
**Гуманитарный чек:** реальные (особенно юридические/социальные) порталы работают с `.docx` чаще; нет нового вектора риска (читаем текст, не исполняем макросы); меньше friction («работает» вместо «unsupported»); для тех, кому DOCX не нужен — нулевая цена.

**Кросс-чек vs Codex: partial.** Codex в D-020 предложил DOCX как «next low-risk step», но без деталей и без конкретного «сейчас vs позже». Stefan дал полный технический разбор и предложил «сейчас». Независимое чтение кода подтверждает: структура `extract()` позволяет добавить DOCX без breaking changes, мягкий отказ PDF реалистичен. Вывод согласен со Stefan и уточняет Codex.
### Implementation follow-up — T-142 / Codex

DOCX low-risk path реализован как `tools/text_extract.py` + тест `tools/test_text_extract.py`. Реализация использует stdlib `zipfile` и `xml.etree.ElementTree`, читает только `word/document.xml`, применяет canonical redaction и не добавляет PDF-зависимость. Отчёт: `docs/docx-text-extract-result-2026-06-21.md`.
**Уверенность: высокая.**
