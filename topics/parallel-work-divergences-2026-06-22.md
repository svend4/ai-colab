# Расхождения и одностороннее покрытие

> Структурированные разногласия по модели Stefan «разногласия выносим, детализируем, обосновываем». Сначала — расхождения по общим пунктам (как у Claude / как у Codex → verdict → что выбрать). Затем — расхождения **между двумя проходами** сведе́ния (D-015 перепроверка). В конце — что уникально покрыто только в A или только в B.

## Часть 1. Разногласия по содержанию (point → A / B → verdict → решение)

### 1. Основной механизм изоляции / таймлайн worktree — КОНФЛИКТ (firmest)
- **Claude (A):** worktree (Уровень-1) — это текущий обязательный стандарт **сейчас**: при срабатывании любого триггера (чужие незакоммиченные source, STALE-индекс, hot-file, same-file) worktree обязателен немедленно. См. `parallel-work-policy.md:30`, `:159-161`.
- **Codex (B):** worktree признан нужным и хорошим, но позиционирован как **будущая** модель (`stream packet → agent branch/worktree → review → integration commit`); текущая дешёвая ступень — `streams/`. См. `commit-stream-policy.md:236-254`.
- **Verdict:** **conflict.** Оба независимых прохода (PASS1 и PASS2) пометили именно этот пункт как conflict — самое надёжное разногласие.
- **Что выбрать / как совместить:** это разные временны́е горизонты, а не взаимоисключающие правила. Сводим так: `streams/` — текущий лёгкий слой для вариантов/полилога и мелких правок; worktree+merge-gate — обязателен **сейчас** для тяжёлых случаев (hot-files, same-file substantive, чужой незакоммиченный source, STALE от чужой работы). Целевая модель Codex (stream → worktree → integration) принимается как направление; пороги перехода берём из A. То есть «не либо-либо, а по триггеру»: лёгкое → stream, тяжёлое/конфликтное → worktree.

### 2. Обнаружение триггеров эскалации — COMPLEMENT
- **Claude (A):** явная матрица триггеров (A–F) с количественными порогами, детектируется `cohort.py guard`: M-код в source-dirs, STALE exit≠0, hot-file, >5 файлов, same-file, таймаут активности >10 мин, `commit_lock` BUSY >120с/>2 раз, цикл `generate.py` >5 раз. `parallel-work-policy.md:44-54`, `:159-161`.
- **Codex (B):** явного детектора нет; решение применить worktree — ручное и контекстное (размер задачи, риск, вероятность конфликта). `commit-stream-policy.md:240-246`.
- **Verdict:** **complement.** Берём количественные триггеры A как операционализацию общего намерения B. B даёт «когда вообще нужен branch», A даёт «как это автоматически детектировать».

### 3. Ответственность за коммит генерируемых индексов — РАСХОЖДЕНИЕ МЕЖДУ ПРОХОДАМИ
- **Claude (A):** правило «commit-your-own» — изменил `tasks/*.md`, обязан в том же changeset регенерировать и закоммитить `TASKS.md`; владелец источника = владелец индекса. `parallel-work-policy.md:88`, `:93`, `:102`.
- **Codex (B):** индексы коммитятся, **только если** прямо нужны задаче и не содержат чужого half-done; иначе — отложить, попросить коллегу завершить, или сделать integration commit. `commit-stream-policy.md:118`, `:121-125`.
- **Verdict:** **спорный — проходы разошлись.** PASS1 пометил это `conflict`; PASS2 — `emphasis`. Это и есть «расхождение между проходами», требующее пометки (D-015).
- **Что выбрать / как совместить:** реального противоречия нет — это разные ветки одного дерева решений. Объединённое правило: *по умолчанию* commit-your-own (A) — владелец источника регенерирует и коммитит индекс **со своей** работой; **но** если регенерированный индекс захватывает чужой незакоммиченный source (B), вступает условие B: не коммитить сейчас / дождаться / integration commit. То есть A описывает чистый случай, B — загрязнённый. Помечаем как «emphasis с граничным условием», не как жёсткий conflict.

### 4. Стратегия вариантов same-file (V1/V2/V3 vs stream-forks) — EMPHASIS
- **Claude (A):** три явных Варианта по размеру правки — V1 (worktree+merge для крупного/архитектурного), V2 (adjacent forks для мелких ревью, <3 файлов/<5 правок), V3 (overwrite+synthesis, только с approval Stefan). Прескриптивные пороги. `parallel-work-policy.md:90-92`, `:99-101`, `:154-156`.
- **Codex (B):** stream-forks как плоские параллельные «ручейки» со ссылками `parent_stream`/`variant_of`; структура есть, но порогов выбора нет; делегирует к D-017. `commit-stream-policy.md:205-223`.
- **Verdict:** **emphasis.** Совместить: структура форков B (плоские ручейки + метаданные) + пороги выбора A (размер/тип/риск → V1/V2/V3). B отвечает «как уложить варианты», A — «когда какой вариант».

### 5. Семантика integration commit — EMPHASIS
- **Claude (A):** integration commit — исключительный случай при сведе́нии нескольких worktree-веток / сборе adoption на merge-gate; не первоклассный инструмент. `parallel-work-policy.md:108`.
- **Codex (B):** integration commit — регулярный именованный инструмент: после review собирает несколько streams/изменений в mainline. `commit-stream-policy.md:37`, `:121-125`, `:153`.
- **Verdict:** **emphasis.** Согласованно: integration commit допустим только при явном именовании; различие — в частоте. Совместить: разрешён как штатный, но всегда явно помеченный механизм (общий пункт 4 mainline это уже фиксирует).

### 6. Hot-file contention — EMPHASIS / COMPLEMENT
- **Claude (A):** hot-файлы перечислены явно (`TASKS.md`, `tools/top.py`, генераторы, `index.json`, …); любая планируемая правка → Level-1 обязателен (триггер C). `parallel-work-policy.md:47`, `:152`, `:161`.
- **Codex (B):** hot-файлы признаны источником конфликтов, но проактивного триггера нет — рекомендация worktree «при высоком риске». `commit-stream-policy.md:244`.
- **Verdict:** **emphasis** (PASS2) / в PASS1 проходит как часть `level-escalation-triggers` (complement). Совместить: явный список hot-файлов и обязательный триггер A — поверх общего намерения B.

### 7. Stale-индекс от чужого незакоммиченного source — COMPLEMENT
- **Claude (A):** если STALE из-за чужого незакоммиченного source — НЕ регенерировать-и-коммитить (захватишь half-done); ждать <5 мин ИЛИ эскалировать в Level-1. `parallel-work-policy.md:85`, `:104`, `:117`.
- **Codex (B):** если generated мешаны с чужим — три опции: не коммитить сейчас / попросить коллегу завершить / integration commit с явным scope. `commit-stream-policy.md:121-125`.
- **Verdict:** **complement.** Опции согласованы и дополняют друг друга; A добавляет временной порог (<5 мин) и путь эскалации, B — путь «попросить коллегу».

## Часть 2. Расхождения между двумя проходами сведе́ния (D-015 перепроверка)

- **Пункт «ответственность за индексы» (см. 1.3):** PASS1 = `conflict`, PASS2 = `emphasis`. **Помечено.** Разрешено в пользу `emphasis` с граничным условием (чистый случай — commit-your-own; загрязнённый — условие B). Не твёрдый conflict.
- **Пункт «таймлайн worktree» (см. 1.1):** оба прохода = `conflict`. **Твёрдый conflict** — единственное разногласие, подтверждённое обоими проходами.
- **Якорь B для аварийного обхода (mainline п.9):** PASS1 относит к consensus (`emergency-override-approval`), PASS2 — к divergence (`emergency_fast_track`, verdict complement: «B не упоминает явно»). **Помечено.** Вывод: принцип в mainline оставлен, но B-покрытие слабое — фактически уникально для A. Перепроверено по тексту: в `commit-stream-policy.md` явного аварийного обхода нет; ближайшее — `:240-246` (CI-проверка до mainline). Поэтому аварийный сценарий ниже также числится в «уникально в A».
- Все прочие пункты verdict'ы совпали между проходами (selective-add, foreign-work, atomic-scope, volatile, stream-first, generated-index-coupling, isolation-required — устойчивый consensus; trigger-detection, same-file-strategy, hot-file — устойчивые complement/emphasis).

## Часть 3. Уникальное покрытие

### Уникально в A (`docs/parallel-work-policy.md`)
- **Количественная матрица триггеров A–F** с порогами: M-код в SOURCE_DIRS, STALE exit≠0/'устарел', hot-file, >5 файлов / >3 директорий + активный claim <5 мин, same-file под разными claim, таймаут активности >10 мин, цикл `generate.py` >5 раз, `commit_lock` BUSY >120с. Пористая граница Level-0/Level-1 с количественными условиями входа (`:44-54`).
- **Merge-gate как обязательный интегратор:** после merge перегоняет `generate.py` для канонических индексов; детектит конфликты между worktree-ветками; 3-way merge; требует approval; worktree-локальные индексы **отбрасываются**, не сливаются вручную; gate-poison (`validate ERROR`) блокирует ВСЕ коммиты (`:16`, `:57`, `:114`, `:166`).
- **Жизненный цикл STALE/регенерации:** свой-vs-чужой STALE, разделение каноническое (`TASKS.md`/`DECISIONS.md`/`index.json`) vs волатильное (`LIVE.md`/`PIPELINE.md`/heartbeat/logs), идемпотентная регенерация, retry 2-3 с против false-positive, топологический порядок каскада индексов (`:139-149`, `:158-167`).
- **Три Варианта same-file с явными порогами:** V1 (>500 строк/архитектура → worktree+merge), V2 (<3 файлов/<5 правок → adjacent forks), V3 (overwrite+synthesis, только approval Stefan) (`:90-92`, `:154-156`).
- **16 edge-cases и 9–10 анти-паттернов:** вложенные stale, регенерация-во-время-commit race, коллизия имён worktree-веток (авто-суффикс), конфликты в генерируемых индексах, одновременные merge-gate запросы, висящие ветки (cron-очистка >7 дней), CRLF vs LF, orphan-claim (`:56-64`, `:110-120`, `:170-191`).
- **Инфраструктура и метрики:** `cohort.py guard`, `flow.py start … --worktree`, `worktree.py remove`, ветка `agent/<agent>/<task>`, `top.py preflight`, отслеживание claim'ов (`queues/claimed/*.claim.md`), `merge_gate.py --with-tests` (`:30`, `:150-156`, `:166`).
- **Аварийный пост-фактум-синтез:** approval Stefan + URGENT merge + документированное решение `D-XXX` (`:42`) — фактически уникально A (см. Часть 2).

### Уникально в B (`docs/commit-stream-policy.md`)
- **Иерархия фиксации L0–L4:** L0 Message → L1 Variant note → L2 Stream packet → L3 Mainline change → L4 Git commit. Прогрессивное «отвердевание» предложения; объясняет, **зачем** существует промежуточный слой (`:39-84`).
- **Структура и метаданные stream packet:** front-matter `STREAM.md` (`id`, `topic`, `status`, `author`, `related`, `adoption`); тело (Проблема/Вариант/Почему лучше/Риски/Проверка/Условия adoption); статусы `draft → ready-for-review → adopted / superseded / rejected / archived` (`:155-203`).
- **Stream-forks как плоские ручейки:** параллельные варианты в `streams/<topic-id>/` со ссылками `parent_stream`/`variant_of`, без глубокого дерева; несколько агентов авторят варианты в одной теме (`:205-223`).
- **Поток adoption (8 шагов):** создать stream → сравнить → adoption note → задача на перенос → mainline-правки → проверки → selective-commit → отметить `adopted` + ссылка на commit/task. Явная точка решения (adoption note) до изменения mainline (`:225-234`).
- **C-правила как социальный контракт (C1–C6):** selective-add, проверка трёх списков, своя задача, не трогать чужое, stream-first, одна мысль на commit — оформлены как дисциплина агентов, а не техническая архитектура (`:86-153`).
- **Позиция/обоснование Codex:** `streams/` как середина между «слишком жёстким Git» и «слишком слабым Markdown»; агент не обязан бросать идею, если другой первым сделал похожую карточку; mainline не превращается в свалку. Девиз: **«много ручейков, одна проверенная основная линия»** (`:256-262`).
