## 1. ХРОНОЛОГИЯ механизмов «ручейки/потоки/форки»

Каждый механизм — что это, где задокументировано, статус. Статусы: ПРИНЯТО (governance accepted) / ПРЕДЛОЖЕНО (proposed) / ПОСТРОЕНО-НО-НЕ-ВКЛЮЧЕНО (код есть, по умолчанию не активно) / ОТКЛОНЕНО.

### Слой дисциплины общего дерева (Уровень 0)

1. **Selective-add (вариант A)** — коммитить ТОЛЬКО явный список своих файлов, никогда `git add -A` в грязном общем дереве.
   - Где: `docs/commit-stream-policy.md:86-100` (правило C1), `topics/commit-policy-streams-2026-06-21.md:36-42`, `decisions/D-019.md:30`.
   - Статус: **ПРИНЯТО**, обязательное правило по умолчанию (D-021 п.1, `decisions/D-021.md:23-24`).

2. **commit_lock (вариант B)** — атомарный короткоживущий advisory-лок (`O_EXCL`, TTL≈120с) перед `generate+add+commit`, сериализует git-операции.
   - Где: `tools/commit_lock.py`, `topics/commit-policy-streams-2026-06-21.md:39-41`.
   - Статус: **ПОСТРОЕНО и протестировано** (`tools/test_commit_lock.py`), **ПРИНЯТО** как часть Уровня 0 (D-021).

3. **Ветка-на-агента, `flow.py` (вариант C)** — каждый агент в ветке `agent/<agent>/<task>`, но в ОБЩЕМ рабочем каталоге; merge через гейт делает человек/maintainer.
   - Где: `tools/flow.py:1-15` (docstring: «Этап F из scaling-design»), таблица сравнения `topics/commit-policy-streams-2026-06-21.md:30`.
   - Статус: **ПОСТРОЕНО, но фактически вытеснено вариантом D**. В таблице помечен как «⚠ общий рабочий дир → checkout-хаос при параллели». Сам `flow.py` сохранён и переиспользован как обвязка для worktree (`flow.py --worktree`).

### Слой изоляции исполнения (Уровень 1)

4. **Worktree-на-агента (вариант D)** — отдельный рабочий каталог + ветка `agent/<agent>/<task>`; `git add -A` видит только свою работу, `index.lock` не пересекается. Это и есть канонический «ручеёк/приток».
   - Где: `tools/worktree.py:1-15` (docstring дословно: «„маленький ручеёк“, впадающий в основную линию через merge-gate»), `topics/commit-policy-streams-2026-06-21.md:43-48`, `decisions/D-021.md:20-24`.
   - Статус: **ПОСТРОЕНО и протестировано** (`test_worktree`) + **ПРИНЯТО как явный режим `--worktree`** (D-021), но **НЕ ВКЛЮЧЕНО по умолчанию** — Уровень 0 остаётся дефолтом (`decisions/D-021.md:23-24`).

5. **merge_gate** — оркестратор-гейт перед вливанием: `validate.py` + `generate.py --check` + `permissions.py` + опционально тесты; exit 0 = зелёный, exit 1 = блок; dry-by-default.
   - Где: `tools/merge_gate.py`, `decisions/D-019.md:33`, `decisions/D-021.md:22`.
   - Статус: **ПОСТРОЕНО и протестировано** (`test_merge_gate`). Владелец гейта (Stefan/назначенный интегратор) — `decisions/D-021.md:45-46`.

### Полу-формат «ручеёк» (между текстом и git)

6. **streams/ (Stream packet, Уровень L2)** — папка `streams/<topic>/<stream-id>/` с `STREAM.md` (YAML front-matter) + опционально `notes.md`, `patch.diff`, `files/`, `evidence/`. Файловый слой для форк-вариантов.
   - Где: `docs/commit-stream-policy.md:53-66, 155-203`, `streams/README.md`, `tools/stream.py`, `PROTOCOL.md:186-206`.
   - Статус: **ПОСТРОЕНО и работает** (`tools/stream.py`, `test_stream`), **ПРИНЯТО как полу-формат** (D-021: «`streams/` остаётся полу-форматом видимости и синтеза, но не становится отдельной VCS», `topics/commit-policy-streams-2026-06-21.md:97`). Реально используется: см. ниже список живых пакетов.

7. **Change-set «полу-формат» (вариант E)** — отдельный Markdown/патч-changeset формат, который интегратор применяет в main.
   - Где: таблица `topics/commit-policy-streams-2026-06-21.md:32, 50-56`, обсуждение `decisions/D-019.md:34`.
   - Статус: **ОТКЛОНЁН как отдельная VCS**. Дословно: «A Markdown changeset is useful as evidence inside `streams/`, but not as a second VCS. Once code changes are involved, git already provides diff, merge, conflict resolution and history.» — `streams/commit-policy/2026-06-21-codex-t136-synthesis/STREAM.md:53-56`; «Avoid inventing a parallel version-control system inside Markdown» — `decisions/D-019.md:34`. Компромисс: changeset допустим как `patch.diff` ВНУТРИ stream-пакета (как evidence), не как второй контроль версий.

### Политика форков (содержательные дубли)

8. **Fork-and-synthesize (D-017)** — для содержательных работ (ревью, архитектура, спорные решения) дубли ПОЛЕЗНЫ как параллельные форки в отдельных файлах; после параллельной разработки — обязательный синтез-шаг. Снимать вопрос «потому что кто-то уже делает» запрещено.
   - Где: `decisions/D-017.md` (полностью), `topics/commit-policy-streams-2026-06-21.md:58-62`.
   - Статус: **ПРИНЯТО** (Stefan, 2026-06-21).

### Очередь и пайплайн (нижний атомарный слой)

9. **queue.py / pipeline.py — атомарный claim (O_EXCL) + TTL + fencing-token** — предотвращает гонку за задачу; «8 параллельных вызовов → 8 разных id, ноль дублей».
   - Где: `tools/queue.py`, `tools/pipeline.py`, `tools/next_id.py`, эмпирика в `dialog.md:593`.
   - Статус: **ПОСТРОЕНО и протестировано** (T-009/T-026/T-082).

### Хронология решений (governance)

## 2. «Уже не текст, но ещё не git» — вопрос полу-формата для черновиков

Это прямая формулировка Stefan: нужен слой «не просто текстовые правки, но ещё не git, особый формат» (`topics/commit-policy-streams-2026-06-21.md:50-51`).

**Что было предложено** (три кандидата):
- (а) **streams/ packet** — структурированная папка-пакет (STREAM.md + patch/evidence). Принято.
- (б) **git-ветка/worktree с дисциплиной готовности** — «по сути это git-ветка с дисциплиной готовности» (`topics/commit-policy-streams-2026-06-21.md:55`). Принято как Уровень 1.
- (в) **отдельный Markdown-changeset формат (вариант E)** — отклонён как «второй VCS».

**Что реализовано:**
- `streams/` — РЕАЛИЗОВАНО и работает. Формат STREAM.md: YAML front-matter `id / topic / agent / status / created`, опц. `adopted_commit / parent_stream / variant_of`; жизненный цикл `draft → ready-for-review → adopted/superseded/rejected/archived` (`docs/commit-stream-policy.md:155-203`).
- Инструмент `tools/stream.py`: `create / list / adopt` (атомарное создание `O_EXCL`), протестирован (`test_stream`).
- Определение полу-коммита закреплено в каноне: «Stream — это „полу-коммит“: уже структурированный вариант, но ещё не mainline. Он нужен, чтобы разные агенты могли вести параллельные ручейки решений, сравнивать их и только потом вливать выбранный вариант…» — `PROTOCOL.md:205-206`; и принцип «Mainline должна быть узкой и проверенной. Streams могут быть широкими и параллельными» — `streams/README.md:42`.

**Что НЕ реализовано / открытый дефект формата:**
- Нет `stream.py check` (валидатор статуса/adoption/срока жизни) — предложен в `docs/parallel-streams-problems-review-2026-06-22.md:185-198` и `streams/commit-policy/20260622-0555-codex/STREAM.md:68`.
- Риск «кладбища потоков»: stream без `status/adoption/related` превращается в архивный шум (`decisions/D-019.md:54`, P5 в `…parallel-streams-problems-review…:99-106`). Нет TTL/архивации.
- Ключевое: **streams решает видимость ВАРИАНТОВ, но не убирает связку через общий генерируемый индекс** — поэтому для черновиков КОДА полу-формат не снимает «ожидание» (см. раздел 5).

## 3. Merge-back / отдельные ветки — как (не) решена проблема

**Принятая модель:**
```
stream packet -> agent branch/worktree -> review -> integration commit
```
(`docs/commit-stream-policy.md:248-254`). Технически: worktree-приток → `merge_gate` (validate+generate --check+permissions зелёные) → integration commit в main. Stefan «маленькие ручейки впадают в большую реку».

**Что РЕШЕНО:**
- Изоляция исполнения: worktree физически разводит грязные деревья и генерируемые индексы (`decisions/D-019.md:40-42`).
- Гейт-проверка перед вливанием реализована (`merge_gate.py`, dry-by-default).
- Владелец merge определён консервативно: Stefan или назначенный интегратор (`decisions/D-021.md:45-46`).

**Что НЕ решено (открыто):**
- **Активация.** Worktree+merge-gate РАТИФИЦИРОВАНЫ и ПОСТРОЕНЫ, но НЕ включены по умолчанию — агенты по-прежнему делят одно дерево на master, поэтому связка сохраняется на практике (`decisions/D-021.md:23-24`; live problem #8 этой сессии).
- **Bottleneck гейта.** Если один человек вливает все притоки — скорость снова падает; есть риск, что «при медленном/непоследовательном merge-gate агенты обойдут Уровень 1» (P7 в `…parallel-streams-problems-review…:119-121`).
- **Роль интегратора не определена.** «роль уточняется при первом реальном Уровне-1» (`decisions/D-021.md:46`). Можно ли ротировать? Кто, кроме Stefan?
- **Разрешение конфликтов при merge двух worktree в master** — политика не описана.
- **Триггеры обязательности.** D-021 говорит «явно `--worktree` при реальной параллельной нагрузке», но порог не задан — это и есть открытый Q-015 (вариант B: обязателен при чужих незакоммиченных файлах / stale index / hot files).
- **Нет интеграционного теста на 2+ одновременных агента** в Level 1 (реальная контенция не наблюдалась; тесты dry/одиночные).

## 5. Почему «ожидание другого агента» возвращается, несмотря на построенные механизмы

Все механизмы Уровня 0 (commit_lock + selective-add) решают **гонку за git-операцию** и **захват чужих файлов**, но НЕ решают связку через общее состояние. Корень — три совмещённых фактора:

1. **Общий генерируемый индекс (shared generated index).** `TASKS.md`, `QUESTIONS.md`, `index.json`, `PIPELINE.md`, `LIVE.md` генерируются из ВСЕХ `tasks/*.md` в общем дереве. Любая чужая незакоммиченная карточка делает индекс STALE для всех. Дословно: «Уровень 0 закрывает риск half-done кода, но не устраняет связку через общий генерируемый индекс… мой коммит вынужден либо ждать (hook STALE), либо тащить чужое состояние» — `topics/commit-policy-streams-2026-06-21.md:84-89`. Это ровно LS-1/LS-3 этой сессии.

2. **Общее рабочее дерево (shared working tree).** Уровень 0 сериализует commit, но не изолирует workspace: «пока один агент думает, другой видит его незакоммиченные файлы» (P3 в `…parallel-streams-problems-review…:91-93`). Отсюда LS-5 (нет видимости) и LS-4 (BUSY-ожидание лока).

3. **Форки на ОДНОМ файле (same-file forks).** D-017 предполагает, что форки живут в РАЗНЫХ файлах (`topics/<topic>/forks/<agent>-*.md`), «нулевая коллизия» (`decisions/D-017.md:24`). Но в этой сессии агенты столкнулись на ОДНОМ файле (`tools/text_extract.py`, `portals/example/*`) — LS-2. Для same-file параллелизма D-017 защиты не даёт; нужен именно worktree (отдельная ветка) + merge, а не отдельный файл.

**Сухой итог:** «ожидание» — не дефект Уровня 0, а его граница. Уровень 0 необходим, но недостаточен по построению. Единственное построенное средство, физически разрывающее все три связки, — Уровень 1 (worktree-на-агента: свой индекс, своё дерево, своя ветка), сводимый merge-gate. Он **ратифицирован и протестирован, но по умолчанию выключен** (`decisions/D-021.md:23-24`), поэтому на практике агенты остаются в общем дереве и «ожидание» воспроизводится. Это организационный, а не технический разрыв — что и зафиксировал follow-up: «старый дефект не закрыт полностью организационно… ожидание чужого commit из-за stale generated indexes остаётся потерей времени» (`topics/commit-policy-streams-2026-06-21.md:103`).

Незакрытый под-вопрос (Q-015): сделать ли Level 1 ОБЯЗАТЕЛЬНЫМ при трёх триггерах (чужие незакоммиченные source-файлы / stale generated index / hot files) — рекомендация Codex = вариант B, статус `open` (`questions/Q-015.md`).
