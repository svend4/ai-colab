## 2. Ответы на старые открытые вопросы

### 2.1. Q2.3.1 - Что стало бы другим, если бы проект начинался заново?

Короткий ответ: начинать нужно было бы не с большого количества документов, а с малой активной поверхности.

Если бы проект начинался заново, порядок был бы таким:

1. `START_HERE.md` как human/agent entrypoint.
2. `tools/top.py status` как первая команда.
3. `tasks/`, `questions/`, `decisions/`, `queues/` как минимальные рабочие контуры.
4. `topics/` только для длинных обсуждений, а не для всего подряд.
5. `sandbox/` как обязательная зона для внешнего, спорного и экспериментального материала.
6. Сразу ввести правило: любой большой текст должен иметь карточку файла, статус зрелости и следующий action.
7. Сразу ввести правило: если совет повторился 2-3 раза, он становится playbook; если playbook повторился 2-3 раза, он становится tool или check.

Что было правильным с самого начала:

- Markdown как общий формат для людей и агентов.
- Append-only полилог: не удалять чужую историю.
- Разделение задач, вопросов, решений и отчетов.
- Идея среднего слоя между чатом и операционной системой.

Что было бы сделано иначе:

- Меньше ранних длинных документов без машинного индекса.
- Раньше сделать `top.py` главным входом.
- Раньше вводить статусы `draft`, `proposed`, `accepted`, `historical`, `superseded`.
- Раньше проверять, что каждая инструкция реально используется инструментом или человеком.

Уточняющий вопрос 2.1.A: какой минимальный набор файлов должен увидеть новый агент за первые 10 секунд?

Предложенный ответ: `START_HERE.md`, `AGENTS.md`, `PROTOCOL.md`, `TASKS.md`, `QUESTIONS.md`, `DECISIONS.md`, `PIPELINE.md`, `tools/top.py`.

### 2.2. Q5.3.1 - Нужно ли физически переносить файлы?

Короткий ответ: по умолчанию нет. Физический перенос - это поздняя операция, а не первый шаг санации.

Безопасная лестница санации:

1. Добавить статус и карточку файла.
2. Добавить индекс или включить файл в существующий индекс.
3. Показать файл через верхний слой или скрыть из активной поверхности.
4. Создать заменяющий summary/portal/core-документ.
5. Только после этого решать, нужен ли физический перенос.
6. Если перенос нужен, делать manifest: old path -> new path -> reason -> rollback note.

Почему так: физический перенос ломает ссылки, привычки людей и возможные скрытые зависимости. Виртуальная навигация дешевле, безопаснее и лучше подходит для живого репозитория, где параллельно работают люди и агенты.

Уточняющий вопрос 2.2.A: какие папки считаются активной поверхностью, а какие историческим архивом?

Предложенный ответ: активная поверхность - `core/`, `portals/`, `tasks/`, `questions/`, `decisions/`, `tools/`, `PIPELINE.md`, `STATUS.md`. Исторический слой - старые `queues/outbox/`, длинные topic-ветки без current summary, старые intake-файлы и временные runtime-логи.

### 2.3. Q6.3.1 - Может ли верхний слой перегрузиться метаданными?

Короткий ответ: да. Метаданные полезны только тогда, когда они управляют действием.

Хорошие метаданные:

- помогают выбрать следующий шаг;
- показывают статус зрелости;
- показывают owner/agent/role;
- показывают связи с задачами, решениями и вопросами;
- читаются инструментом или хотя бы человеком в первые секунды.

Плохие метаданные:

- существуют только для красоты;
- не проверяются;
- не используются в `top.py`, `validate.py`, `generate.py` или другом workflow;
- дублируют смысл тела документа;
- требуют ручного обновления, но никто не отвечает за актуальность.

Правило: metadata budget должен быть ограничен. Для обычного документа достаточно 5-9 ключей. Для технических machine-layer файлов можно больше, если есть проверяющий инструмент.

Уточняющий вопрос 2.3.A: какие metadata-поля должны быть обязательными для активных файлов?

Предложенный минимум: `id`, `type`, `status`, `owner`, `related`, `next`.

### 2.4. Q7.3.1 - Какие метрики использовать?

Короткий ответ: метрики должны измерять не количество текста, а способность системы быстро превращать хаос в проверяемое действие.

Предлагаемые метрики:

1. `question_unknown_count`: сколько вопросов ещё без явного статуса.
2. `open_question_count`: сколько вопросов признаны открытыми.
3. `requires_decision_count`: сколько вопросов ждут governance.
4. `active_surface_size`: сколько файлов нужно открыть новому агенту для старта.
5. `top_command_coverage`: сколько важных workflows доступны через `tools/top.py`.
6. `instruction_activation_rate`: сколько повторяющихся советов стали tools/checks/skills.
7. `outbox_entropy`: сколько outbox-отчетов не сведены в summary/decision/task.
8. `consensus_coverage`: сколько спорных тем имеют consensus/divergence breakdown.
9. `human_start_time`: сколько шагов нужно человеку до понимания текущего состояния.
10. `agent_start_time`: сколько команд нужно агенту до безопасного начала работы.
11. `stale_runtime_noise`: сколько runtime-файлов меняются без смысловой ценности.
12. `proof_ladder_maturity`: сколько рекомендаций имеют цепочку evidence -> test -> decision/tool.

Уточняющий вопрос 2.4.A: какие из этих метрик должны стать advisory, а какие strict?

Предложенный ответ: на Alpha-2 почти всё advisory. Strict только синтаксис, ссылки, уникальность id, безопасность sandbox и запрет silent history rewrite.

## 4. Методы обработки большого объема информации

### 4.1. Проверенные современные методы

1. MapReduce для агентов: много scout-агентов собирают факты, observer сводит, integrator принимает решение.
2. Event sourcing: не переписывать историю, а добавлять события и строить актуальные projections.
3. Medallion architecture: raw -> reviewed -> accepted -> core.
4. ADR/decision log: каждое устойчивое архитектурное решение хранится отдельно.
5. CI для знаний: generate/validate/drift-check превращают документацию в проверяемую систему.
6. Faceted search: один документ может входить в несколько классификаций без физического копирования.
7. Attention budget: ограничивать активную поверхность вместо бесконечного расширения корня.

### 4.2. Исторические и “средневековые” методы как инженерные аналогии

1. Scriptorium: один пишет, второй сверяет, третий делает краткую копию для каталога.
2. Scholastic disputation: consensus и objections должны храниться отдельно, а не смешиваться в один текст.
3. Guild apprenticeship: новый агент сначала выполняет read-only задачи, потом advisory, потом code tasks.
4. Cathedral building: разные мастера работают над частями, но есть master plan и проверка совместимости.
5. Monastic rule: простой устав важнее тысячи разрозненных советов.

### 4.3. Инновационные и экспериментальные методы

1. Semantic elevator: любой большой документ должен иметь уровни 10 секунд, 1 минута, 10 минут, полный текст.
2. Memory compost: старые отчеты не удаляются, а перерабатываются в summary, decision, task или historical archive.
3. Proof ladder: мнение -> пример -> повторение -> playbook -> tool -> validator -> decision.
4. Agent parliament: scout, critic, synthesizer, implementer, reviewer, human approver.
5. Idea particle accelerator: спорная идея идёт в sandbox, получает 2-3 независимых варианта, затем synthesis.
6. Semantic traffic lights: green = consensus/ready, yellow = partial/open, red = conflict/risk, grey = historical/no-action.
7. Living index: индекс не просто список файлов, а список действий, которые система может выполнить.

## 5. Предлагаемая топология большой группы

### 5.1. Минимальная рабочая ячейка

```text
3 scouts -> 1 observer -> 1 integrator
```

- Scout: ищет факты, документы, старые долги, противоречия.
- Observer: сравнивает 3 отчета, выделяет consensus/divergence.
- Integrator: превращает вывод в task, decision, tool или code change.

### 5.2. Средняя группа

```text
3 cells x (3 scouts + 1 observer) -> 1 coordinator -> 1 human/integrator
```

Такой режим полезен для read-only исследования большого корпуса, но опасен для прямых правок кода. Для кода нужен worktree/merge-gate, иначе верхний слой захлебнется в конфликтующих изменениях.

### 5.3. Правило масштабирования

Не увеличивать число агентов, если:

- нет синтезатора;
- нет формата отчета;
- нет правила landing;
- нет способа отличить consensus от disagreement;
- нет верхней команды для просмотра состояния;
- нет человека или назначенного integrator для accepted-решений.
