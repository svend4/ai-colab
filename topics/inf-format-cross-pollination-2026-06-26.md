# 1. Провенанс
Беседа (2026-06-26, ~10 заходов) построила: `.inf`-формат + `infon.py` (парсер/граф/Hamming/render, 19
тестов) → слои `@ref`/`&name`/`!macro`/`↑rollup↓drill`/`type:portal|view|recipe` → `infon board` (React-
артефакт, оркестратор 2 суб-агента) → `inf_crdt.py` (CvRDT: LWW+OR-Set, SEC) → `inf_falsify.py`/
`inf_accuracy.py` (измеренная фальсификация: 76.5%→43% сокращение контекста по Hamming-радиусу).

# 2. Конвергенция (две независимые ветки Claude → одно)
| `.inf` (та беседа) | наш репо (эта сессия) |
|---|---|
| блоки = типизированные инфоны + метаданные | канон: файлы + YAML-front-matter, типы task/decision |
| Q6-адрес → Hamming-кластеризация | `portals.py` (контент-кластеры, средний слой И-8) |
| content-hash «verified = проверяемый ФАКТ» | `seal_verified` (тело==первый коммит) + `provenance_independence` |
| «LLM-генерация недетерминирована → что значит verify-once?» | **проблема оракула** (kotel §10) |
| CRDT для конкурентной мульти-агентной записи | cross-agent commit-координация (T-263), reconcile |
| falsification harness (мерить, не заявлять) | red-team → self-repair → quorum |

# 3. Что ЗАИМСТВОВАТЬ (приоритет) и в какой форме
- **B-1 (высокий) — view-слайсы.** Именованная проекция «какие блоки/файлы раскрыты под задачу»: `!frozen`
  (копия, самодостаточный срез) / `!live` (ссылки). У нас НЕТ. Форма: тула `view.py` — собрать срез
  релевантного канона под тему/казус/агента (контекст как рабочее множество, не свалка). Бьёт нашу боль
  «агенту подать релевантное, а не весь репо».
- **B-2 (высокий) — CRDT блок-мёрж для конкурентности.** `inf_crdt`: правки сливаются на уровне БЛОКА
  (LWW-регистры + OR-Set для ссылок → ничего не теряется), а не git-строк. Прямой ответ на T-263
  (хот-файлы Codex, broad-commit, merge-конфликты). Форма: прототип block-level reconcile поверх
  наших файлов (или per-секция). Но: field-level LWW тихо теряет конкурентные правки ОДНОГО тела —
  нужен sequence-CRDT для текста.
- **B-3 (средний) — `level:`-лестница / progressive disclosure (L0..L5).** Наш FILE-ID-CARD + front-matter
  + секции = зачаток; явные уровни дали бы агенту «в окно только L0, ниже по требованию».

# 4. Что у НАС СИЛЬНЕЕ (не заимствовать — предложить им)
- **verify-once.** `.inf` смешивает целостность (hash) и доверие (`verified: by max` = подпись ОДНОГО).
  Мы РАЗДЕЛИЛИ: `seal_verified` = целостность; `red_team_gate`+`oracle_quorum` = доверие через
  адверсариальную выживаемость и кворум N судей. «verified» у нас = «пережил кворм», а не «max подписал».
- **Адверсариальная валидация.** `.inf` одно-авторский, не прошёл независимую панель (его falsification —
  частичный само-red-team). Наша сессия показала: одно-авторская конвергенция ПЕРЕ-принимает.

# 5. Общий открытый КОРЕНЬ (обе ветки): проблема оракула
- `.inf`: Q6 = 6 бит = 64 корзины, и конвертер ставит **q6 = хеш типа** → «Hamming меряет хеш, не смысл».
- `.inf`: «verified» = подпись/hash ≠ истина.
- Обе держатся на LLM/подписи, не на проверяемом смысле — ровно наша проблема оракула. Наш слой
  (кворум/red-team/провенанс) — кандидат закрыть её для `.inf`.

# 6. Рекомендованный синтез
`.inf`-сила (блоки/адресация/CRDT/view/glass-box) **+** наш адверсариально-валидирующий слой (кворум
вместо одиночного `trust.led`). Конкретный первый шаг — **B-1 (view.py)** как самостоятельная польза для
наших агентов, ИЛИ **B-2 (CRDT блок-мёрж)** как ответ на T-263. Перед заимствованием — атаковать claim'ы
`.inf` нашей панелью (red-team Q6-семантики и verify-once-безопасности), чего тому диалогу не хватало.
