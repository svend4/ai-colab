# Обзор разделов (расширенная середина)

**§1.** Ядро — file-native движок координации агентов: единицы знания живут как самостоятельные Markdown-файлы с YAML-front-matter (tasks/decisions/questions/topics/drivers), а агрегаты (TASKS.md, index.json) детерминированно генерируются. Канон держат три сущности — generate.py (сборка навигации), validate.py (инварианты), pre-commit hook (гейт) — поверх 4-слойной пирамиды L1 core → L2 portals → L3 collab/history → L4 sandbox.

**§2.** Каждый файл (docs И scripts) обязан нести единую «визитную карточку» вверху — тот же фрактал, что card.py (top→середина→основание), но на уровне файла: машино-парсимый блок ключ:значение (как RFC822/HTTP) с тремя уровнями детализации, поля совпадают с ключами index.json, чтобы шапки автоматически собирались в индекс.

**§3.** Репо сейчас полностью плоский каталог (tasks/=216, docs/=110, tools/=116, topics/=43); это работает для машины-с-grep, но за пределами человеческой навигации и git-производительности — нужны числовые пороги шардинга и переносимая схема имён.

**§4.** Файл — не плоский текст, а дерево: метаданные/ToC сверху, расширенная середина, полный хвост; каждая секция получает стабильный абсолютный адрес (outline 1.2.3 + якорь), чтобы на любую деталь можно сослаться и нарастить под-случай, ничего не выбрасывая.

**§5.** Развитие идёт по двум осям: (1) детализация больших файлов вглубь общее→частное с нумерацией; (2) код кластерами по темам + ссылки на кластеры из обзорных доков/порталов. Обе оси частично реализованы (3 портала, своды), но связь «портал↔кластер кода↔кластер доков» неполна.

**§6.** Все 17 Q-файлов формально answered, но «стадия ответа» неравномерна: организационные вопросы закрыты на 90–100%, тяжёлые архитектурные (драйверы, assurance existence!=applied, docmerge) — лишь как «решение принято», реализация отстаёт. Плюс 5 фундаментальных вопросов Stefan не заведены как Q-карточки.

**§7.** Репо интуитивно собрал верные методы (пирамида=Википедия, порталы=фасеты, ID-ссылки=Zettelkasten), но применяет непоследовательно: ось «вширь» не существует как объект, дублирование L2↔L3 не запрещено, навигация частично ручная, пирамида частично фиктивна, core почти пуст.

**§8.** Главная незакрытая идея — сделать ссылку таким же first-class объектом, как документ, и дать обеим осям расти независимо над одним неизменным атомарным ядром; плюс decay/самоочистка, полииерархия, emergent-кластеризация, обратимость L2→L3.

# 1. Ядро-архитектура и правила канона

## 1.1. Девять конститутивных правил канона

### 1.1.1. ОДИН ФАЙЛ = ОДНА ЕДИНИЦА ЗНАНИЯ (file-native канон)
Каждая задача/решение/вопрос — отдельный `tasks/T-NNN.md`, `decisions/D-NNN.md`, `questions/Q-NNN.md` с обязательным YAML-front-matter (id, type, title, status, …). Почему так, а не одна большая таблица: закреплено D-002 («для больших тем — отдельный файл на сообщение») и снимает класс конфликтов слияния при параллельной работе — два агента, трогающих разные задачи, никогда не пишут в один файл. Основание: прямой аналог content-addressable / one-record-per-file (Maildir, git objects, Jekyll `_posts/`), где append вместо edit убирает write-write races.

### 1.1.2. FRONT-MATTER — ЕДИНСТВЕННЫЙ ИСТОЧНИК ПРАВДЫ; агрегаты ВСЕГДА генерируются
`TASKS.md`, `DECISIONS.md`, `QUESTIONS.md`, `STATUS.md`, `board.md`, `index.json` не редактируются руками — `generate.py` пересобирает таблицы между маркерами `<!-- GEN:… START/END -->` (а index.json целиком) из front-matter каждого файла. Из докстринга generate.py: «один источник правды на тему — нет ручной синхронизации, значит нет класса дрейфа». Основание: derived-artifact / single-source-of-truth (Makefile-таргеты, codegen) — производное никогда не авторитетно.

### 1.1.3. ЕДИНЫЙ ПАРСЕР `_canon.py` — устранение дублирования логики
`parse_front_matter` (синоним `parse_fm`) вынесен в `tools/_canon.py` как единый источник вместо 8 идентичных копий по `tools/*.py` (T-085, ревью-находка L). 8 копий = 8 мест расхождения поведения; консолидация делает канон-парсинг детерминированным для generate/validate/pipeline/dispatch/metrics. Основание: DRY и rule-of-three — повторяющийся инвариант принадлежит одному модулю.

### 1.1.4. ВАЛИДАТОР `validate.py` КОДИФИЦИРУЕТ ИНВАРИАНТЫ
Проверяет: уникальность id и совпадение имени файла с id; наличие/валидность status по реестру (tasks: todo/doing/blocked/review/done; questions: open/answered/closed; decisions: accepted/proposed/rejected/superseded); целостность ссылок (`depends_on` → существующая задача, «где обсуждается» → существующий файл); свежесть драйверов (>30 дней → WARN); запрет `mode: execute` до реализации всех гейтов D-014; обязательные секции отчётов синтеза (D-018). Разделение ERROR vs WARN: ERROR валит коммит (целостность), WARN — advisory (кириллические имена по D-007 при постепенной миграции не блокируют). Основание: схема-валидация как контракт (JSON Schema, DB-констрейнты) + «fail закрыто на нарушении инварианта, открыто на стилистике».

### 1.1.5. PRE-COMMIT HOOK — МЕХАНИЗМ ПРИНУЖДЕНИЯ канона (две фазы)
`tools/githooks/pre-commit` запускает `validate.py` (ERROR → коммит отклонён) и `generate.py --check` (навигация устарела → отклонён, нужно перегенерировать и `git add`). Канон, который не принуждается машинно, дрейфует; хук превращает «договорённость» в исполняемый инвариант на границе записи. Особенность: хук устойчиво ищет рабочий Python 3 на Windows (обходит нерабочий App-Execution-Alias из Microsoft Store), `--no-verify` — явный аварийный обход. Основание: shift-left валидация / quality gate.

### 1.1.6. АТОМАРНОЕ ВЫДЕЛЕНИЕ ID + ЛОК — фундамент multi-agent безопасности
`next_id.py` (выдача T-/D-/Q-NNN), `commit_lock.py`, `pipeline.py`, `dispatch.py`, `merge_gate.py` образуют «атомарный котёл + лок + гейт» (core/engine-manifest.md). При N агентах коллизия id и одновременная запись в очередь — главный класс гонок; модули покрыты тестами (`test_commit_lock.py`, `test_merge_gate.py`). Основание: распределённая координация через файловые локи и атомарную аллокацию (ticket-lock / lease).

### 1.1.7. ПИРАМИДА L1→L4 как ось чистоты/доверия (D-016)
`core/` (L1: переносимое универсальное ядро, проверено тестами, не привязано к домену) → `portals/` (L2: чистовые present-tense специализированные области, домен как плагин) → `collab/`+`topics/tasks/questions/decisions/streams/` (L3: история, споры, evidence) → `sandbox/` (L4: хаотичный вход, quarantine). Главное правило потока: `raw input → sandbox manifest → read-only inventory → report → decision → portal/core`; ничего из L4 не поднимается выше автоматически. Основание: явная модель-аналог Википедии (ядро/порталы/talk-история/черновики) и trust-tiers/quarantine из security.

### 1.1.8. ПАССИВНЫЕ (docs) vs АКТИВНЫЕ (scripts) — чёткое разделение по расположению
Активные: `tools/*.py` — генераторы, валидаторы, пайплайны, гейты; они ИСПОЛНЯЮТ канон. Пассивные: `*.md`-файлы канона — декларативное состояние, читаемое и человеком, и машиной (через front-matter). Декларация состояния отделена от обработки — markdown остаётся git-diff-able и human-readable, логика в одном месте (tools/). Основание: data-as-code / declarative-state + separate processor (Terraform-state vs CLI, k8s-манифесты vs controller).

### 1.1.9. СТАТИКА vs ДИНАМИКА: канон детерминирован и без таймстампов
`build_index()` строит index.json как «детерминированный, без таймстампов» — это позволяет `generate.py --check` сравнивать байт-в-байт и ловить дрейф. Недетерминированный генератор делает `--check` бесполезным (всегда «устарело»); reproducible build — предусловие для гейта. Основание: reproducible builds / idempotent codegen.

## 1.2. Проверенные практики (основание правил §1.1)
1. Single-source-of-truth + derived artifacts (Makefile/codegen): front-matter авторитетен, TASKS.md/index.json генерируются.
2. One-record-per-file для устранения write-write конфликтов (Maildir, git loose objects, Jekyll `_posts`) — аналог D-002.
3. Schema/contract-валидация на границе записи (JSON Schema, DB-констрейнты) — validate.py как исполняемый контракт, ERROR/WARN.
4. Shift-left quality gate в pre-commit; явный аварийный обход `--no-verify`.
5. DRY / rule-of-three: единый `_canon.py` вместо 8 копий парсера (T-085).
6. Reproducible/idempotent codegen: детерминированный index.json без таймстампов.
7. Trust-tiers / quarantine: L4 sandbox изолирует непроверенный вход.
8. Atomic id allocation + file locks для multi-agent координации, покрытые юнит-тестами ядра.

# 2. Стандарт визитки-файла: заголовок-метаданные для каждого файла

## 2.1. Одиннадцать правил единой шапки (card→middle→base)

### 2.1.1. ЕДИНЫЙ КОНТРАКТ ПОЛЕЙ, ДВА СИНТАКСИСА-НОСИТЕЛЯ
Один словарь полей (id, type, title, gist, status, owner, level, risk, related, detail_ref…), но для docs он живёт в YAML front-matter (`---`…`---`), а для scripts — в первом docstring/комментарии (`# key: value` или structured docstring). RFC 822 / HTTP / MIME доказали: заголовок отделяется от тела пустой строкой и парсится отдельно — но носитель должен быть НАТИВНЫМ для парсера тела (YAML не ломает Markdown-рендер; `#`-комментарий не ломает Python). Контракт один, обёртка разная.

### 2.1.2. ТРИ УРОВНЯ ВНУТРИ ОДНОЙ ШАПКИ: card → middle → base (НЕ три файла)
- **card** = 4–6 обязательных полей (id, type, title, gist, status) — «строка каталога», 5 секунд.
- **middle** = семантические поля содержания (what, why, contains, inputs/outputs, related) — 30–60 секунд.
- **base** = ссылки-в-основание (detail_ref, spec, tests, decisions) — НЕ сам текст, а указатели.

card.py уже доказал фрактал top→середина→основание ВНУТРИ единицы; agent-onboarding.md делает то же (§0→§1-4→§5-8). Три файла = три точки рассинхрона. Локальность важнее: визитка ТАМ ЖЕ, где артефакт (как `package.json` рядом с кодом).

### 2.1.3. ПОРЯДОК ПОЛЕЙ = ОБЩЕЕ→ЧАСТНОЕ (пирамида подачи)
Сверху вниз: идентификация (id/type/title) → суть (gist) → статус-жизнь (status/owner/date) → содержание (what/contains) → связи (related/depends_on) → основание (detail_ref/spec/tests). И человек, и AI читают сверху и могут ОСТАНОВИТЬСЯ на нужном уровне (progressive disclosure). OpenGraph/`<head>` ставят `og:title`/`<title>` первым именно потому, что краулер берёт первые N байт.

### 2.1.4. МАШИНО-ПАРСИМОСТЬ КАК ПЕРВИЧНОЕ ТРЕБОВАНИЕ
Поля = `ключ: значение`, значения типизированы, словарь полей КОНЕЧЕН. Никакого свободного текста в значениях card-уровня (кроме gist). RFC 822 победил строгим `Field: value`, парсящимся одним сплитом по `:`. Для AI: шапку можно извлечь БЕЗ запуска LLM (дёшево, детерминированно), сложить в эмбеддинг-индекс, отфильтровать по status/owner/risk. Контролируемый словарь (enum для type/status/risk) = валидируемость.

### 2.1.5. ПОЛЯ ШАПКИ ОБЯЗАНЫ СОВПАДАТЬ С КЛЮЧАМИ index.json
index.json уже хранит per-секцию: tasks{id,title,status,owner,priority,risk,depends_on,topic,next}, drivers{…,level,mode,risk,interfaces,inputs,outputs,sandbox,related}, decisions{id,title,status,date,file}. Шапка ДОЛЖНА использовать те же имена — иначе нужен переводчик header↔index, который рассинхронизируется. Если имена совпадают — индекс СОБИРАЕТСЯ из шапок автоматически (header как SSOT, index как производная проекция). Это разворачивает текущую инверсию (сейчас index ведётся вручную).

### 2.1.6. РАЗНЫЕ type → РАЗНЫЕ обязательные поля (как card.py CARD_TYPES)
У doc обязательны {id,type,title,gist,status,related}; у script добавляются {entrypoint/cli, inputs, outputs, side_effects, mode (read-only|write), deps}; у driver — {level,mode,sandbox,secrets,activation}. Единый каркас + тип-специфичные слоты избегают и жёсткости, и хаоса. MIME делает так же: общий Content-* каркас + Content-Transfer-Encoding не всем.

### 2.1.7. ДЛЯ SCRIPTS ШАПКА ОБЯЗАНА НЕСТИ side-effects/mode/inputs/outputs — это и есть «активность»
Активный скрипт должен заявить: что читает, что пишет, нужна ли песочница, идемпотентен ли. driver-safety-policy.md требует read-only-по-умолчанию и dry-run; человеко-гейт D-006 — для high-risk. Если mode/side_effects в шапке, гейт-проверка (как friction.py gate-poison) становится статической: можно отказать в запуске write-скрипта без явного решения, НЕ читая тело. Заголовок = контракт безопасности.

### 2.1.8. detail_ref / base-уровень = ССЫЛКИ, не дублирование
base содержит указатели: spec→docs/…, tests→tools/test_*.py, decisions→[D-NNN], topic→topics/…. Дублирование детали в шапке = гарантированный дрейф. Гиперссылочная модель (HTML `<link rel>`, HTTP `Link:`) масштабируется; копипаст — нет. Шапка — ИНДЕКС файла, а не его сжатие.

### 2.1.9. ОБЯЗАТЕЛЬНОЕ ПОЛЕ updated/date + опц. checksum-тела для anti-drift
Чтобы машина видела свежесть и предупреждала «шапка старше тела». HTTP Last-Modified/ETag решают ровно это. В present-tense-чистовиках дата-в-шапке — гейт доверия: устаревшая визитка ОПАСНЕЕ отсутствующей, потому что ей верят.

### 2.1.10. ИНСТРУМЕНТ-ОБВЯЗКА: header.py (lint + extract + render-card) поверх card.py
Один скрипт: (a) валидирует шапку по схеме типа, (b) извлекает все шапки → пересобирает index.json, (c) рендерит card-уровень через card.py. Шапка-card и card.py-карточка — ОДИН фрактал на разных масштабах (файл vs сообщение). Один рендерер → один язык на всех уровнях. Подключить как gate в top.py/friction.py: «нет валидной визитки → friction».

### 2.1.11. МИГРАЦИЯ — НЕ big-bang, а gate-on-touch + бэкафилл по приоритету
Новый файл без шапки = friction-флаг (мягкий гейт). Существующие: сначала активные scripts (там side_effects=безопасность) и held-doc'и. Насильная массовая правка = шум в git и риск; постепенный гейт-на-касание (как F-020) даёт сходимость без стоп-мира. Сначала ценность там, где шапка работает гейтом (scripts), потом косметика.

## 2.2. Проверенные практики (основание §2.1)
1. RFC 822 / HTTP / MIME заголовки: строгий `Field: value`, отделён от тела, парсится независимо.
2. YAML front-matter (Jekyll/Hugo/Obsidian/Pandoc) — частично применён (concept-map.md, card-standard.md).
3. OpenGraph / HTML `<head>`+`<meta>` / `<link rel>` — связи вместо дублирования.
4. Python module docstring (PEP 257) + Javadoc/JSDoc/Doxygen `@param/@return` — аналог для scripts.
5. HTTP Last-Modified/ETag — дешёвое обнаружение рассинхрона.
6. package.json / Cargo.toml / pyproject.toml — локальная визитка рядом с кодом.
7. Контролируемый словарь + схема-валидация (lorenzo validate_doc, JSON Schema).

## 3.2. Десять правил организации с порогами

### 3.2.1. ПОРОГ ФАЙЛОВ В ОДНОЙ ПАПКЕ: цель 7–50, мягкий потолок 100, жёсткий 200
Для человека граница от Miller 7±2 (рабочая память) — 7±2 ОСМЫСЛЕННЫХ группы на уровне; выше ~50 элементов глаз перестаёт сканировать и начинает искать (Hick's law: время выбора растёт логарифмически). Для машины — git/FS: git status/diff stat'ит весь каталог, plain-каталоги в ext4/NTFS теряют локальность. tasks/=216 уже за потолком — главный долг.

### 3.2.2. ШАРДИНГ ПО ДИАПАЗОНАМ ID, а не по семантике
tasks/T-001..T-050/, T-051..T-100/ (бакеты по 50–100). ID T-NNN монотонный и иммутабельный → диапазонный шардинг детерминирован, не требует перемещения файла при смене темы (семантические папки требуют — задача меняет тему и ломает путь, ломая cross-links). Так git хранит объекты (.git/objects/ab/cdef… — 2 hex = 256 бакетов), так Maven/npm раскладывают артефакты. При 216 задачах: 3 бакета по ~72.

### 3.2.3. РАЗМЕР ОДНОГО ФАЙЛА: цель 1–8 КБ, потолок ~20–30 КБ, тревога >50 КБ
task-файлы: median 1.4 КБ / max 7.5 КБ — идеально, «one concern per file». docs/: max 135 КБ, mean 10.7 КБ — есть монстры. Файл >30 КБ для машины не помещается в один read без offset/limit и раздувает контекст; для человека — листать, а не оценить. Основание: Unix «do one thing» + практика монорепо.

### 3.2.4. ЦЕНТРАЛЬНЫЙ index.json (136 КБ) — антипаттерн единой точки
Растущий индекс линейно дорожает на каждую запись (merge-конфликты при параллельных агентах гарантированы — видно в git status: M index.json), а 136 КБ JSON надо целиком распарсить ради одной ссылки. РЕШЕНИЕ: пер-папочные манифесты (tasks/INDEX.json, docs/INDEX.json) + тонкий корневой index.json со ссылками (двухуровневый каталог). Так устроены Cargo.lock-в-крейте, package.json-per-workspace, FHS-раскладка.

### 3.2.5. ГЛУБИНА ВЛОЖЕННОСТИ: ровно 2–3 уровня, не больше
Каждый лишний уровень — +1 решение «куда положить» для человека и +1 join для машины. UDC/Дьюи доказали обратное: 10-уровневая иерархия не масштабируется, библиотеки перешли к фасетной. Правило: глубина = ceil(log_B(N)), B=бакет (50–100). Для N=216, B=72 → глубина 2. Не делать tasks/2026/06/done/T-001 (4 уровня ради 216 файлов).

### 3.2.6. ШИРИНА ПРОТИВ ГЛУБИНЫ — балансируй по формуле
При N файлов оптимум — ширина B≈sqrt(N)..N^(1/3). Для tasks N=216 → sqrt≈15 папок по ~15, или плоско-с-шардами 3×72. Слишком широко бьёт по человеку; слишком глубоко — по машине лишними stat(). Основание: B-tree fanout — узел читается одним блоком; здесь «блок» = один человеческий взгляд / один ls.

### 3.2.7. 21 КОРНЕВАЯ ПАПКА — на верхней границе
Корень — самый дорогой уровень (его видят все при онбординге). 21 за Miller-комфортом; сгруппировать в ~7 кластеров: knowledge/ (docs, topics, decisions, questions), work/ (tasks, queues, streams), runtime/ (logs, reports, tmp-work, sandbox), agents/ (skills, participants, collab, drivers), code/, core/, portals/. FHS держит / коротким (~15 каталогов) именно потому что корень — контракт.

### 3.2.8. ПЕРЕНОСИМОСТЬ (portable)
(а) только относительные пути в index.json (уже так); (б) имена файлов ASCII-safe, kebab-case, без пробелов/кириллицы в ИМЕНАХ (содержимое кириллица — ок) — иначе ломается на case-insensitive NTFS vs case-sensitive ext4 и в URL/git; (в) zero-padding ID до фикс. ширины: T-001 не T-1 (уже так — сортировка строкой = числом); (г) никаких путей >255 байт и Windows-резерв (CON, NUL, PRN). Основание: POSIX pathname portability + Windows reserved names.

### 3.2.9. МАШИННЫЙ vs ЧЕЛОВЕЧЕСКИЙ оптимум РАЗНЫЙ — обслуживай оба разными механизмами
Машине-с-grep плоские 216 файлов почти безразличны (ripgrep одинаково быстр), ей важны стабильные пути и манифесты; человеку — навигация ≤50/уровень. РЕШЕНИЕ: физическая раскладка под МАШИНУ (плоско+шарды+padding), а под ЧЕЛОВЕКА — ВИРТУАЛЬНЫЕ виды (board.md, STATUS.md, фасетные теги by-status/by-owner). Библиотечная наука разделила физическую полку (shelfmark) и каталог (фасеты).

### 3.2.10. ИЗМЕРЯЙ И СТАВЬ GATE
Добавить в tools/top.py/линтер health-метрики с порогами-алертами: max_files_per_dir>200 → FAIL, >100 → WARN; max_file_size>50KB → WARN; index.json>200KB → WARN; root_dirs>15 → WARN. Правила без автопроверки деградируют (энтропия каталога монотонно растёт с каждым агентом). Основание: перенос lint/CI-gate на структуру репо — «структура как код».

## 3.3. Проверенные практики (основание §3.2)
1. git .git/objects/ — шардинг по 2-символьному префиксу хэша (256 бакетов); прецедент для tasks/T-0XX/.
2. Unix FHS — короткий стабильный корень + локальные кэши на уровне вместо одного гигантского индекса.
3. Монорепо Google/Meta (Bazel/Buck) — per-directory BUILD/OWNERS вместо мегафайлов, меньше blast-radius merge.
4. Library science (Дьюи→фасеты) — физика под машину, виды под человека.
5. Maven/npm/Cargo — артефакты по префиксу координат, lock/manifest на workspace.
6. Miller 7±2 и Hick's law — эмпирическая база порога ≤50.
7. B-tree fanout — формула баланса ширина/глубина (узел = один блок чтения).

# 4. Внутрифайловая навигация и абсолютная нумерация (общее→частное, расширяемость вглубь)

## 4.1. Восемь правил файла-как-дерева

### 4.1.1. Трёхфазный закон «общее→частное» в каждом файле
(a) head — front-matter + краткое содержание/ToC; (b) body — расширенное изложение; (c) tail — полные детали/приложения; при перерастании фаза (c) выносится в отдельный файл (summary.md / README.md / messages/, уже в PROTOCOL.md). И человек, и парсер тратят дешёвый первый экран на решение «читать дальше». Это BLUF (bottom-line-up-front) из перевёрнутой пирамиды и man-page (NAME/SYNOPSIS/DESCRIPTION). STATUS.md уже декларирует «читается первым» — сделать дисциплину обязательной для ВСЕХ длинных файлов.

### 4.1.2. Обязательная метаданная шапка + машиночитаемое поле sections:/авто-ToC
YAML front-matter ПЛЮС поле `sections:`. Это единственное место, которое Markdown-рендер прячет, а парсер читает детерминированно (O(1) до первого `---`); index.json уже строится из front-matter — канал «машина читает шапку» доказан, расширить с уровня файла на уровень секций.

### 4.1.3. Абсолютная outline-нумерация 1, 1.1, 1.2.3 (Dewey/LaTeX) в длинных файлах
Плоская сквозная (1..N как в PROTOCOL.md) ломается при вставке (вставить между 5 и 6 нельзя без перенумерации хвоста); 5.1 вставляется без сдвига — прямой ответ на «расширяемо вглубь, каждая деталь развивается в под-случай». LaTeX/DocBook/RFC десятилетиями держат стабильные перекрёстные ссылки так.

### 4.1.4. Разделить ДВА вида идентификаторов: позиционный номер vs стабильный якорь
(a) позиционный outline-номер (1.2.3 — ГДЕ в дереве) и (b) стабильный immutable-якорь (slug/Zettelkasten-ID — ЧТО это). Ссылаться ВСЕГДА на якорь. Перенос пункта рвёт ссылку на «п.7», но `#gate-poison` переживает перенумерацию. В репо уже есть стабильные ID-пространства (T-/Q-/D-/F-/L-) — опустить тот же принцип ВНУТРЬ файла.

### 4.1.5. Расширяемость вглубь = «ничего не выбрасывать»
Исключение/уточнение становится под-пунктом (был 4.2 → стал 4.2 + новый 4.2.1), а не переписыванием 4.2. Сохраняет аудит-трейл рассуждения (видно, что общее правило породило под-случай), повторяет рост newsgroup-дерева, совместимо с semi-commit/stream-подходом репо.

### 4.1.6. Inline-ToC в начале каждого длинного файла (>~150 строк)
`[1.2 Заголовок](#anchor)`. Порог по длине: для T-168 (20 строк) ToC — шум, для dialog.md (167KB) и TASKS.md (66KB) отсутствие ToC — реальный дефект НАВИГАЦИИ. ToC генерируется инструментом (generate.py с GEN-маркерами), а не руками — иначе протухнет.

### 4.1.7. Машинный «оглавление-сайдкар» в index.json
Генератор кладёт дерево секций каждого крупного файла в index.json (section-id, anchor, level, line). Агент не должен парсить 167KB markdown ради оглавления — читает index.json (паттерн уже для topics/tasks). Навигация ВНУТРИ файла = такой же дешёвый машинный lookup, как между файлами.

### 4.1.8. Рекурсивный порядок метаданные→краткое→среднее→полное ВНУТРИ каждой секции
Фрактальная перевёрнутая пирамида: читатель/агент останавливается на любой глубине с консистентным уровнем детализации — как оглавление книги полезно на каждом уровне вложенности, а не только сверху.

## 4.2. Проверенные практики (основание §4.1)
1. Перевёрнутая пирамида / BLUF (журналистика, военные сводки).
2. man-page (NAME/SYNOPSIS/DESCRIPTION) — фиксированный порядок от сводки к деталям.
3. LaTeX/DocBook/RFC numbering + \label/\ref — позиционная нумерация + независимые метки.
4. Dewey Decimal — десятичная расширяемость (510→510.1→510.15) без перенумерации соседей.
5. Zettelkasten ID (1a, 1a1, 1b) — ветвление без переписывания.
6. Markdown anchors / URL fragments — дешёвая адресация точки внутри документа.
7. Outline-процессоры (org-mode, Workflowy) — контент читаем на любой глубине.
8. Авто-ToC инструментом (Sphinx/doctoc) — generate.py с GEN-маркерами не даёт протухнуть.

# 5. Два направления развития: детализация вглубь + кластеры-ссылки

## 5.1. Семь правил кластеризации и портал-навигации

### 5.1.1. Канонизировать ПОРТАЛ как универсальный информационный кластер (не только код)
portals/README.md определяет портал как «present-tense слой поверх core, привязанный к теме/домену/workflow» с машинным `l1_basis`. Это Facade (GoF) + Bounded Context (DDD): один вход в подсистему, скрывающий N файлов. bridge-knowledge/portal.md имеет `l1_basis: [knowledge.py, text_extract.py]` — ссылка-на-кластер в шапке документа, путь «код кластерами + ссылка из обзора» реализован для одного домена.

### 5.1.2. Порталы на РАЗНЫЕ универсальные темы, а не на разные данные
Текущие 3 портала (example, bridge-knowledge, repo-inventory) опираются на ОДИН движок knowledge.py и различаются лишь корпусом данных — обобщён ОДИН кластер, не покрыты остальные 5. Универсальная тема (canon-движок, safety, drivers) переиспользуема многими задачами; тема-под-данные одноразова. Single Responsibility на уровне подсистемы: один портал = одна ось ответственности, переносимая между проектами.

### 5.1.3. Tools/ (~52 non-test) кластеризуются в 6 порталов по реальным импортам и именам
- **(a) CANON-движок**: _canon.py, validate.py, generate.py, card.py, next_id.py, templates.
- **(b) ОРКЕСТРАЦИЯ**: top.py, pipeline.py, dispatch.py, flow.py, conveyor.py, agent_queue.py, stream.py, onboard.py.
- **(c) PYRAMID/PORTAL**: portal.py, promote.py, knowledge.py, text_extract.py, repo_search.py.
- **(d) FRICTION/SAFETY**: friction.py, ownership.py, cohort.py, commit_lock.py, merge_gate.py, worktree.py, drift_check.py, reconcile_state.py, race_test.py.
- **(e) BLOCKS/decisions**: blocks.py, decision_menu.py, decision_propagation.py, doc_consensus.py, advice.py.
- **(f) BRIDGE/drivers/execute**: drivers_catalog.py, capabilities.py, sandbox.py, execute_*.py, risk_gate.py, result_intake.py.

engine-subsystems-overview-2026-06-23.md уже сводит (d)+(f) в две из трёх подсистем со списком «Ключевые файлы» — кластеризация подтверждена авторитетным доком.

### 5.1.4. Docs/ (110) кластеризуются в ~10 тем по префиксам имён
agent-* (6), runtime-* (5), top-* (4), pipeline-* (4), mcp-* (4), knowledge-* (4), friction-* (4), driver-* (4), parallel-* (3), files-* (3) + execute/engine/portal/gateway по 2. Именная конвенция уже действует — кластеры ЕСТЬ де-факто, не хватает явного индекса. Каждый docs-кластер маппится на tool-портал из §5.1.3.

### 5.1.5. Связывать кластеры ССЫЛКАМИ двух типов
(a) машинная опора `l1_basis` в шапке портала (уже есть) — для assurance.py coverage; (b) человекочитаемый раздел «Ключевые файлы» + `related:` front-matter в обзорном доке (уже в engine-subsystems-overview). Машинная ссылка проверяема (orphan-L1 детектор в README), человеческая навигируема. Разделение index-vs-prose как book TOC vs hyperlink graph.

### 5.1.6. Путь 1 (детализация вглубь) применять к ОБЗОРНЫМ файлам-сводам, не ко всем
engine-subsystems-overview уже структурирован как 1→1.1→слой-1/2/3 с нумерацией контур→файл:строка. Большие файлы (TASKS.md, доки-своды) детализируются вглубь; маленькие L3-артефакты (tasks/T-NNN) остаются атомарными — иначе теряется зернистость claim/fencing из pipeline.

### 5.1.7. Ввести один КОРНЕВОЙ портал-индекс со ссылками на 6 тематических порталов
21 корневая папка + 52 tool + 110 docs дают комбинаторный взрыв точек входа; индекс-портал — единственная «вершина пирамиды», совпадающая с top.py facade. Один индекс → N порталов → N кластеров файлов: трёхуровневая навигация = O(log) вместо O(N).

## 5.2. Проверенные практики (основание §5.1)
1. Facade (GoF): top.py группирует pipeline/validate/generate/knowledge в «кнопки-сценарии».
2. Bounded Context (DDD): один портал = одна подсистема; l1_basis — карта контекста.
3. Package-by-feature vs package-by-layer — антидот «god-folder» из 52 файлов.
4. Documentation pyramid / Diátaxis: overview→reference→how-to.
5. Index/TOC + hyperlink graph: l1_basis + related front-matter.
6. SBOM / inventory portal: repo-inventory — read-only инвентарь как первоклассный артефакт.

# 8. Инновационные методы организации больших объёмов информации

> Репо уже неявно собрал «лучшие хиты» истории организации знаний: пирамида L1-L4 (Википедия), фасетные L2-порталы (Ранганатан), ID-перелинковка T/D/Q (Zettelkasten/гипертекст). Но методы применены частично и без единой модели «оси-вглубь + оси-вширь».

## 8.1. Десять направлений (главная идея: ссылка — first-class объект; обе оси растут над неизменным атомарным ядром)

### 8.1.1. Разделить ДВЕ ортогональные оси физически
Ось A — «вглубь» (containment: L1→L2→L3→L4, topic→task→claim). Ось B — «вширь» (ассоциативные ссылки, теги, граф). Смешение дерева и графа — корневая причина того, что папки одновременно навигация И классификация, что даёт переразрастание дерева или хаос тегов. Фасетная классификация Ранганатана (PMEST) и Usenet big-8 явно отделяли иерархию от множественных признаков. Ось A построена (workspace-pyramid-levels.md), ось B живёт только как inline-ID.

### 8.1.2. ССЫЛКА как first-class typed/directed объект
Каждая связь = (from, to, тип: refines|cites|contradicts|supersedes|derives|duplicates, direction). Ненаправленное упоминание T-137 не отличает «вытекает из» от «противоречит», нельзя обойти граф машинно или обнаружить orphan/битую ссылку. Ted Nelson Xanadu (двусторонние видимые typed-links + transclusion), RDF-триплет subject-predicate-object. tools/knowledge.py + assurance coverage + L2-портал bridge-knowledge — готовая точка для рёберной таблицы (edges) рядом с FTS5.

### 8.1.3. Инвариант «один атом — одно место»; копии заменять transclusion
pyramid-doc прямо называет риск дублирования L2↔L3; дубль убивает доверие. Zettelkasten Лумана (одна мысль = одна заметка) и нормализация 3NF. Портал хранит corpus_ref/ссылку, а не копию текста (D-021/T-145 уже это делает для portal.py — обобщить как общий закон).

### 8.1.4. КАЖДОМУ узлу — стабильный, непрозрачный, сортируемо-ветвящийся ID
Опционально Luhmann-style под-ID (T-168, T-168a, T-168a1) для детализации вглубь без новой папки. Перемещение файла L3→L2 не должно ломать ссылки. ID = адрес, путь = текущая раскладка («location-independent addressing» memex/Xanadu).

### 8.1.5. Навигация — ГЕНЕРИРУЕМАЯ проекция графа, а не ручная правда
index.json/board.md полностью пересобираются из узлов+рёбер. Ручной board.md при 110 docs/216 tasks неизбежно расходится — рассинхрон = тихая ложь. wiki «What links here», Obsidian/Roam backlinks вычисляются. Расширить generate.py/validate.py до полной перегенерации обеих осей + отчёт «orphan/dangling/cycle».

### 8.1.6. Множественный вход в один узел (полииерархия), а не одно дерево
Один task живёт одновременно в «security», «portal:bridge-knowledge», «sprint». Навязанное единственное дерево заставляет дублировать или терять (Dewey vs фасеты). UDC/фасеты: одна сущность — несколько координат. Реализация: фасеты как typed-edges, а не новые папки.

### 8.1.7. Явная PROMOTION-механика между уровнями с критерием и тестом на границе
L4→L3 (report), L3→L2 (clean summary), L2→L1 (повтор+тесты). Без правил продвижения материал застревает; ядро преждевременно абстрагируется. data-pipeline staging→curated→published (medallion bronze/silver/gold), редакционный цикл Википедии draft→article. tools/promote.py (открытый вопрос pyramid-doc) — недостающее звено, превращающее статичные уровни в живой конвейер.

### 8.1.8. «Температура»/распад узлов (decay) — самоочистка, а не только рост
Узел без обращений и свежих рёбер за N времени → cold, предлагается к архиву/сжатию. 216 задач и 110 docs будут расти; без обратного давления портал устаревает. forgetting curve / spaced-repetition, LRU-кэш, апоптоз. В deferred-инструментах виден decay_card — сделать общим законом для всех узлов.

### 8.1.9. EMERGENT-кластеризация поверх embedding-графа, ТОЛЬКО по реальному спросу
Кластеры (ось B) не назначаются заранее, а вычисляются: похожие узлы стягиваются «similar», сообщества графа дают авто-темы. Предзаданные категории устаревают; emergent следует за содержанием. self-organizing maps, community detection (Louvain), Zettelkasten «структура вырастает снизу». Осторожно: D-010 «без vector/RAG до спроса» — опциональный слой над FTS5, не ломая детерминизм.

### 8.1.10. Инвариант ОБРАТИМОСТИ: каждый L2-узел хранит ссылку вниз на L3-evidence
Чистовой портал без trace до спора/решения запрещён. Иначе теряется «почему так, а не иначе» — требование PROTOCOL.md. Научная цитируемость и audit-trail; instruction trace (D-NNN база→вершина, коммит 53e6d61) — ровно этот механизм, сделать обязательным для всех уровней.

## 8.2. Проверенные практики (основание §8.1)
1. Фасетная классификация Ранганатана (PMEST) и UDC — полииерархия/теги поверх одного дерева.
2. Zettelkasten Лумана — атомарность, ветвящийся ID, структура снизу через ссылки.
3. Гипертекст и backlinks (wiki «What links here», Obsidian/Roam) — вычисляемая проекция графа.
4. Реляционная нормализация (3NF) и SSOT — устранение дубликатов через transclusion.
5. Data-pipeline staging (bronze/silver/gold) и редакционный цикл Википедии — контролируемое продвижение.
6. Модель Википедии (статья/портал/talk-page+история/черновик) → L1/L2/L3/L4.
7. Usenet big-8 и Dewey/DNS — иерархическое именование как стабильная адресация.
8. Community detection (Louvain) и SOM — эмерджентные кластеры из реальных связей.

## 8.3. Фантастические, но проработанные направления (innovative)
1. **Ссылка как first-class typed/directed объект** в духе Xanadu: двусторонние видимые связи + transclusion вместо односторонних голых ID — машинный обход графа и обе оси одновременно.
2. **Memex-тропинки Буша**: сохранять не только узлы, но именованные ТРОПЫ (последовательности переходов агента) как переиспользуемый артефакт онбординга — «как пройти от вопроса к решению».
3. **Голографический/фрактальный инвариант**: каждый узел любого уровня имеет одинаковую мини-структуру (identity / current-state / links-up / links-down / evidence), так что zoom-in и zoom-out одинаковы — портал, задача и claim самоподобны (стыкуется с §0 этого документа).
4. **Memory-palace / пространственная раскладка**: граф со стабильными 2D-координатами (embedding-проекция) — агенты и люди запоминают «где» лежит знание пространственно.
5. **ДНК-метафора**: неизменное атомарное L1-ядро = геном, L2-порталы = экспрессия генов под контекст (один движок «экспрессируется» в порталах по-разному через corpus_ref) — переносимость без копирования.
6. **Decay/апоптоз и «температура» узлов**: самоочищающаяся система, холодные узлы автоматически к сжатию/архиву — объём управляем при росте до тысяч узлов.
7. **Emergent self-organizing навигация**: board.md/портал-кластеры не пишутся, а кристаллизуются Louvain-сообществами поверх typed-edge графа по реальному спросу (с уважением к D-010).
8. **File-native как «локальная БД на git»** (из §1): front-matter + генераторы = read-model/materialized-view над event-log из коммитов; довести до CQRS, где index.json — проекция, git-история — неизменяемый журнал.
9. **Self-describing canon → авто-сборка index.json** (из §2): шапка как SSOT, индекс как ВЫЧИСЛЯЕМАЯ проекция (header.py extract) — устраняет дрейф index по построению.
10. **Self-balancing каталог** (из §3): tool при превышении порога АВТО-ре-шардит папку и переписывает ссылки — каталог как самобалансирующееся B-дерево, человек никогда не видит переполнения.
11. **Атомарный аллокатор ID на Lamport/CRDT** (из §6, ФУНД-D): превратить ручное разрешение Q-008/009/010-коллизий в распределённо-корректную нумерацию без центрального сервера.
12. **Семантический 3-way docmerge документации** (из §6, Q-017): автонахождение общих пунктов с cross-reference file:line, консенсус в mainline, разногласия в структурированные под-версии — нерешённая в индустрии задача; реализация = прорыв.
13. **«Котёл» как evidence-based синтез вместо голосования** (Q-013/Q-016/Q-017): разногласия разрешаются доказательной базой (тесты/риск-анализ/cross-reference), а не большинством — формальный механизм «доказательного консенсуса» для смешанных human+AI команд.
