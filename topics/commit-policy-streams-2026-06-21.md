# Политика коммитов: «ручейки» в основную линию

Форк-вариант Claude (по D-017) на вопрос Stefan: как агентам коммитить, **не блокируя друг друга**
и **не коммитя чужую полу-готовую работу**; нужен промежуточный слой между текстовыми правками и git.

## Проблема (наблюдалась прямо в этой сессии)

Несколько агентов работают в ОДНОМ рабочем дереве на ОДНОЙ ветке (`master`):
1. **Блокировка:** `git commit` фейлится/ждёт из-за `index.lock`, удерживаемого другим агентом; мои
   коммиты несколько раз отскакивали (stale-hook / lock), приходилось retry-loop'ом.
2. **Чужая полу-готовая работа:** `git add -A` хватает ВСЁ незакоммиченное, включая файлы другого
   агента, который ещё в середине правки → риск закоммитить чужой недоделанный код.
3. Pre-commit hook падает на «устаревшей навигации», когда другой агент сменил источники между моим
   `generate` и `commit`.

## Сравнение вариантов (модель «ручейки → основная линия»)

| Вариант | Блокировка | Чужая half-done | Инфра | Это «ручеёк»? |
|---|---|---|---|---|
| **A. Selective-add** — коммитить ТОЛЬКО свои файлы (`git add <свои пути>`, не `-A`) | не решает | ✅ решает | нулевая | нет |
| **B. Commit-lock** — атомарный короткоживущий лок перед `generate+add+commit` | ✅ сериализует | не решает | мини-инструмент | нет |
| **C. Ветка-на-агента** (`flow.py`: `agent/<name>/<task>`) | ✅ (свой коммит) | ⚠ общий рабочий дир → checkout-хаос при параллели | средняя | да (ветка) |
| **D. Worktree-на-агента** — отдельный рабочий каталог + ветка | ✅ полностью | ✅ полностью (`-A` видит только своё) | средняя (git worktree) | **да (приток)** |
| **E. Change-set «полу-формат»** — агент пишет draft-патч/changeset в `streams/<agent>/`, интегратор применяет в main | ✅ | ✅ | новый формат | да (ручеёк) |

## Рекомендация — слоями

### Уровень 0 (сейчас, дёшево, без инфры) — A + B
- **Selective-add (правило):** агент коммитит ТОЛЬКО файлы своего завершённого юнита (он их знает),
  **никогда `git add -A`** в общем дереве. Это снимает риск чужой half-done.
- **Commit-lock (инструмент):** перед `generate+add+commit` агент берёт атомарный короткоживущий лок
  (`tools/commit_lock.py acquire <agent>`), после — `release`. Коммиты **сериализуются** (нет драки
  за `index.lock`, нет отскоков). TTL снимает лок упавшего агента.

### Уровень 1 (следующий, реальная модель «ручейки→основная линия») — D
- **Worktree-на-агента:** каждый агент работает в своём `git worktree` на ветке `agent/<name>/<task>`
  (свой рабочий каталог). `git add -A` видит ТОЛЬКО его работу → чужой half-done физически недостижим,
  index.lock не пересекается. Это и есть «маленький ручеёк/приток».
- **Merge-gate в main:** приток вливается в основную линию через гейт (`validate` + `generate --check`
  зелёные → fast-forward/merge). `tools/flow.py` уже частично это каркасит.

### «Полу-формат» (между текстовыми правками и git) = Уровень E (опционально)
Идея Stefan «не просто текстовые правки, но ещё не git, особый формат» → **changeset-ручеёк**: агент
готовит юнит как структурированный draft (набор файлов + манифест изменения `streams/<agent>/<id>.md`:
что/зачем/тесты/готовность %), **предварительно**, до вливания. Интегратор (агент/человек/CI) сводит
готовые ручейки в основную линию. Это даёт «полуготовое видно, но в main не попало». По сути это
git-ветка с дисциплиной готовности — но можно сделать и как лёгкий файловый changeset поверх текущего
file-native канона, без полноценного git-flow.

## Живой кейс-доказательство (2026-06-21, Claude)

Проверка Уровня 0 на реальной контенции в этой же сессии:
1. Я взял T-133 (text-extract), но Codex параллельно его **заclaimил** и почти доделал
   (`tools/text_extract.py`, обёртка в `knowledge.py`, тесты). Claim-файл показал держателя `codex` —
   я **отступил**, не барджась в чужую активную задачу (commit-lock ранее тоже корректно отказал мне,
   пока лок держал codex). Механизм сериализации/владения сработал как задумано.
2. Когда понадобилось закоммитить **свои** готовые файлы (заметка-доказательство + указатель в T-137),
   `generate --check` показал STALE `TASKS.md`/`index.json` — но устаревание шло от **незакоммиченного
   `T-133.md` Codex'а**, а не от моих правок. Регенерация+commit зашили бы half-done состояние Codex в
   индекс. По правилу Уровня 0 я **не делал `git add -A` и не регенерировал** — оставил свои 2 готовых
   файла в дереве до чистого окна / ближайшего sweep.

**Вывод (доказательная база к T-136):** selective-add + «не коммить чужой half-done» **необходимы**, но
их **недостаточно** при общем дереве — общий генерируемый индекс (`TASKS.md`/`index.json`) всё равно
связывает работу агентов: мой коммит вынужден либо ждать (hook STALE), либо тащить чужое состояние.
Это эмпирически усиливает аргумент за **Уровень 1 (worktree-на-агента)**, где индекс генерится в своём
притоке и сводится merge-gate'ом, а не делится в реальном времени. Уровень 0 закрывает риск half-done
кода, но не устраняет связку через общий генерируемый индекс.

## Closeout 2026-06-21 — D-021 / T-143

Stefan ратифицировал котёл-пакет в `D-021`. Итог по этой теме:

- Уровень 0 (`selective-add` + `commit_lock`) остаётся дефолтом для общего рабочего дерева.
- Уровень 1 (`git worktree` на агента/задачу + `merge_gate`) принят как явный режим для реальной параллельной нагрузки.
- `streams/` остаётся полу-форматом видимости и синтеза, но не становится отдельной VCS.
- Merge подтверждает Stefan или назначенный интегратор.
