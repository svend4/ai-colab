# Context-graph RAG (статья TDS) ↔ наш канон

> Источник: «Vector RAG isn't enough — I built a context graph layer for multi-agent memory»
> (towardsdatascience.com, 2026). Разбор по запросу Stefan + сопоставление с нашим репо. Вывод: автор
> НЕЗАВИСИМО описал архитектуру, которую мы уже построили (типизированный граф рёбер поверх FTS), и в
> нескольких местах мы впереди. Взято: бенчмарк-метод (`tools/retrieval_bench.py`).

# 1. Тезис статьи
Вектор-RAG структурно недостаточен для мульти-агентной памяти — не из-за окна, а потому что **join-запросы**
(ответ = склейка ДВУХ раздельных фактов) невозможны для similarity: факт A в чанке A, зависимый B в чанке B,
эмбеддинг их не «соединяет». Решение — **context-graph**: память как направленный мультиграф типизированных
троек `(subject, predicate, object)` (`AuthModule —DEPENDS_ON→ RateLimiter`); в граф входят только ФАКТЫ,
болтовня отброшена; запросы direct (1 узел) / distant (обход) / **join (2-hop walk)**. Бенчмарк (18 запросов,
0 LLM): context-graph **89%** vs vector-RAG 50% vs raw 61%; решающий разрыв — **join 80% vs 20%**.

# 2. Сопоставление: мы это УЖЕ построили
| Статья | У нас |
|---|---|
| тройки `(subj, pred, obj)` | front-matter `related/depends_on/superseded_by` + inline `[[id]]` → `edges.py build_edges` |
| типизированные предикаты | `edges.py DIRECTED = depends/superseded/basis/in_topic/cites/detail/source` |
| направленный мультиграф (NetworkX) | `edges.py` (свой, stdlib) |
| **join = 2-hop walk** | `edges.py path(a,b)/neighbors/impact`; `view.slice_ids` BFS |
| тройка с типом связи | `text_mux` ячейка `links:[{rel:supports\|contradicts\|derived_from, target}]` |
| вектор-слой (дополняет граф) | `canon_index.py` (FTS5/BM25) |
| отбрасывать дистракторы | канон = только факты (tasks/decisions/...), не каждое сообщение |

# 3. Где мы ВПЕРЕДИ статьи
- **Fact supersession** — их «серьёзный баг» (старое ребро возвращалось с полной уверенностью). У нас тип
  `superseded` + **supersede-целостность** в `edges.py check` (`A superseded_by B → A терминален`). Тот же
  класс, что R7 (no-resurrection) из [[defect-class-formula-2026-06-26]].
- **Разрешение алиасов** — их «постоянная инженерная цена на write-time». У нас **явные id** (`[[D-031]]`) →
  entity-resolution не нужен вовсе.
- **Неограниченный рост сущностей** — их нерешённое ограничение. У нас `fold.py` (C-II fold-not-delete).
- **Персистенция** — им нужен Neo4j-экспорт; у нас канон нативно персистентен (git-файлы).

# 4. Что ВЗЯЛИ: бенчмарк-метод → `tools/retrieval_bench.py`
Единственное, чего у нас не было — ИЗМЕРЕНИЕ retrieval по типам запросов. Адоптировал метод статьи
(детерминированно, без LLM) на НАШИ инструменты — граф (`edges.py`-модель) vs FTS (`canon_index`):

| тип | ГРАФ | FTS |
|---|---|---|
| direct | 100% | 0% |
| distant | 100% | 100% |
| **join** | **100%** | **0%** |
| ИТОГО | **100%** | 33% |

(токенов/запрос: граф 1.0 · FTS 5.7). Воспроизводит вывод статьи **на нашем коде**: FTS проваливает join
(ответ не в тексте запроса), граф решает 2-hop walk'ом; FTS силён на distant (контент) — его зона. Тест
`test_retrieval_bench.py` пинит главное (граф join=100%, FTS join=0%).

# 5. Открытое (общее с автором)
- **Описательные ссылки** («датасет с аномалией» вместо id) — не решены ни у автора, ни у нас (у нас mitigated
  явными id, но запрос-по-описанию всё равно требует FTS+оракул).
- **Извлечение сущностей в проде** — у автора LLM (цена+недетерминизм); мы обходим явными id в каноне, но
  для свободного текста (треды/ячейки) тот же вопрос остаётся.

# 6. Вердикт
Статья — внешняя независимая валидация нашей архитектуры: «граф типизированных рёбер поверх FTS» — правильный
ответ на мульти-агентную память, и join — его киллер-фича. Мы это построили (`edges.py`+`canon_index`+`text_mux`),
местами опередив (supersession/алиасы/рост/персистенция), и теперь **измерили** (`retrieval_bench`: граф 100% vs
FTS 33% на join-наборе). Брать дальше из статьи нечего — ядро у нас сильнее; держать как точку внешней сверки.
