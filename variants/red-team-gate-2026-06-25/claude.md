# 0. Визитка
> Выходная симметрия к ripeness_gate. На ВХОДЕ вариант должен быть зрел+запечатан; на ВЫХОДЕ
> консенсус-claim не попадает в канон, пока не ПЕРЕЖИЛ попытку опровержения (red team против итога,
> не против вариантов). «По смыслу» = «пережил атаку», а НЕ «набрал голоса». Опровергнутый → в
> negative-set С ПРИЧИНОЙ (апоптоз, не молчаливое стирание). Опровержение — подключаемый агент, гейт
> детерминирован.

# 1. Условия применимости
Гейтит CORE-claim консенсуса ПЕРЕД промоушном в канон. Требует red-team-записей (опровержение —
агент, подключаем). НЕ для механики. НЕ для миноров (их не промоутят, а хранят — отдельный путь).

# 2. Проблема
Даже консенсус «по смыслу» бывает правдоподобно-НЕВЕРНЫМ. Голоса этого не ловят (много кто согласен ≠
правда). Нужна адверсариальная проверка ИТОГА. Две линзы (наука: red-team; коллективы: red-team против
своего консенсуса) пришли к этому ПОРОЗНЬ → высокий мерит.

# 3. Дизайн
- **3.1. Red-team-запись:** {claim, attack (лучшая попытка опровержения), verdict: survived|refuted|open,
  reason}. Живёт в `redteam/<topic>.md`.
- **3.2. Гейт (детерминирован):** `gate(core_claims, records)` →
  - **cleared** (verdict=survived) → можно промоутить в канон;
  - **rejected** (verdict=refuted) → в negative-set С ПРИЧИНОЙ (НЕ молчаливо), связь immune.py;
  - **pending** (нет записи / open) → не промоутить, нужен red team.
- **3.3. Опровергатель ПОДКЛЮЧАЕМ** (агент-LLM) — как канонизатор стены №1. Гейт лишь проверяет записи.
- **3.4. Симметрия:** ripeness_gate(вход) ↔ red_team_gate(выход). Оба — структурное принуждение.

# 4. Уникальный вклад
- **Структурное принуждение «пережил опровержение» на ВЫХОДЕ** — замыкает «по смыслу не числом» с
  обратного конца (вход: независимость; выход: адверсариальная выживаемость).
- **Опровергнутый → negative-set С ПРИЧИНОЙ** (апоптоз, INV-NO-SILENT-APOPTOSIS) — претензия не
  исчезает, причина смерти становится антигеном (связь immune.py).
- **Замена голосования адверсариальным тестом** — конкретный механизм для «по смыслу».

# 5. Evidence
Котёл: red-team-консенсуса — merit-промоция, 2 линзы порознь. immune.py имеет INV-NO-SILENT-APOPTOSIS
(дом для negative-set). ripeness_gate даёт паттерн «детерминированный гейт + подключаемый смысловой шаг».

# 6. Риски
- Опровержение LLM-зависимо → подключаемо, гейт детерминирован (как стена №1).
- Слишком агрессивный опровергатель убьёт хорошие claim → verdict обязан нести reason (аудит); калибровка.
- «open» может застрять → нужен срок устаревания.

# 7. Инварианты
- **RT-1** Нет промоушна без записи survived.
- **RT-2** Refuted → negative-set С ПРИЧИНОЙ (никакого молчаливого отброса).
- **RT-3** Опровержение подключаемо (агент), гейт детерминирован.
- **RT-4** Verdict аудируем (reason записан).

# 8. Открытые вопросы
1. Нужно ли N независимых опровергателей на claim (как adversarial-verify), или один?
2. Кто калибрует силу опровергателя (чтобы не убивал верное)?
3. Когда «open» считается устаревшим?
