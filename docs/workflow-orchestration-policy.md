# Политика оркестрации воркфлоу (агент-оркестратор)

> Для **агента, который умеет запускать воркфлоу** (фан-аут под-агентов), и для **людей/агентов**,
> которые читают результаты. Кодифицирует то, что уже отработано на практике в этой сессии: декомпозиция
> задачи на кластер мелких агентов, параллельный запуск нескольких воркфлоу, извлечение и синтез
> результатов, и куда складывать промежуточные vs финальные документы.
>
> **Связь:** воркфлоу — это «оркестратор поверх под-агентов»; `tools/pipeline.py` (котёл) — оркестратор
> поверх ЗАДАЧ между равными агентами; они дополняют друг друга (см. `docs/engine-state-2026-06-22.md`).

## 1. Модель: один воркфлоу = один кластер мелких агентов

- **Оркестратор** (агент-координатор) формулирует задачу, разбивает её на под-задачи и запускает
  **воркфлоу** — кластер мелких под-агентов, работающих параллельно, плюс агент-**синтезатор**, который
  сводит их результаты. Оркестратор НЕ делает работу сам — он декомпозирует, ждёт, синтезирует, коммитит.
- Типовая форма воркфлоу — **2 фазы**: `Map/Build/Analyze` (фан-аут под-агентов по под-задачам) →
  `Synthesize` (один агент сводит в структурированный результат по схеме).
- Под-агенты возвращают **структурированные данные** (JSON по схеме), а не прозу — синтезатор собирает.

## 2. Когда запускать воркфлоу, а когда делать соло

| Ситуация | Решение |
|---|---|
| Задача разбивается на много **независимых** под-задач (карта по N областям, аудит по N измерениям) | **Воркфлоу** (фан-аут) |
| Нужна **широта** (обзор многих файлов/тем) или **уверенность** (несколько независимых перспектив, верификация) | **Воркфлоу** |
| Масштаб, который **один контекст не держит** (миграция, большой синтез истории) | **Воркфлоу** |
| Мелкая/механическая правка, один файл, ответ из контекста | **Соло** (без воркфлоу) |
| Сначала надо **разведать** форму работы (что за файлы/темы) | Разведать соло → потом воркфлоу по найденному списку |

Под `ultracode` (явный opt-in) — воркфлоу по умолчанию на каждую существенную задачу; вне его — только
по запросу пользователя или когда задача явно того требует.

## 3. Несколько воркфлоу: кластеры и параллелизм

- **Один кластер вопросов = один воркфлоу.** Разные несвязанные кластеры (разные темы/вопросы) —
  **отдельные** воркфлоу, запущенные **параллельно в фоне**. Пример из сессии: пока шла консолидация
  движка, параллельно шёл анализ двух открытых вопросов — два независимых воркфлоу одновременно.
- Оркестратор **запускает в фон → не ждёт впустую → делает безопасную параллельную работу** (например,
  прогон тестов, мелкие коммиты своих файлов) → по нотификации забирает результат.
- **Не плодить** воркфлоу, которые читают/пишут одно и то же — это дублирование. Кластеры должны быть
  ортогональны.

## 4. Побочные ответвления (когда результат рождает follow-up)

- Если результат воркфлоу вскрывает новую под-задачу — это **ответвление**: либо новый **воркфлоу**
  (если это снова декомпозируемый кластер), либо **worktree** (если это конкретная реализация в коде,
  параллельная другим — см. `docs/parallel-work-policy.md`, Уровень-1).
- Ответвление не делается внутри текущего воркфлоу — оно фиксируется как следующий шаг (или задача в котле).

## 5. Где живут результаты (черновое vs финал)

```
сырой вывод воркфлоу  ->  harness temp (НЕ в репо)  ->  извлечение  ->  чистый документ в каноне  ->  commit
```

- **Сырой вывод воркфлоу** пишется харнессом во **временный файл вне репозитория**
  (`…/tasks/<runId>.output`). Это НЕ артефакт репо — его НЕ коммитят. Оркестратор его **извлекает**
  (парсит JSON-результат) и **компонует** чистый структурированный документ.
- **Промежуточные рабочие файлы**, если нужны в репо, — в **gitignored `tmp-work/`** (черновики, скрипты
  компоновки). Их тоже не коммитят; после использования — удаляют (как `_compose_*.py` в этой сессии).
- **Финальный структурированный результат** — в **канон**: `темы/<topic>-<date>.md` (анализ/синтез/история),
  `docs/<name>.md` (политика/карта), `decisions/D-XXX.md` (если это решение), задача в `tasks/` (если работа).
  Только это коммитится.
- **Правило:** черновое и сырое — во временное (temp/tmp-work, gitignored); только **извлечённое,
  структурированное, перепроверенное** идёт в канон и в commit.

## 6. Безопасность и контенция

- **Analysis/Map-воркфлоу — READ-ONLY** (агенты типа `Explore`): ноль контенции с другими агентами;
  можно запускать свободно даже при активной работе соседа.
- **Build-воркфлоу** (агенты пишут код) — каждый под-агент в своём `worktree` (изоляция), либо
  оркестратор сам коммитит результаты последовательно (не фанить writers в общее дерево — гонка за
  `index.lock`).
- Коммит результатов — по `docs/parallel-work-policy.md`: `cohort guard` → Уровень-0 `ship` (свои файлы)
  или Уровень-1 `worktree` (если триггеры/коллизии).

## 7. Интеграция с коллективной работой (люди + агенты)

- Воркфлоу — это **личный оркестратор одного агента**; его результаты вливаются в **общий** контур:
  документ в `темы/`/`docs/` для людей и агентов; спорные пункты — в **котёл** (`pipeline`) и через
  `D-018` (коллективное решение); форк-варианты — через `D-017` (`stream.py`).
- Результат должен быть **перепроверен** (синтезатор + при необходимости adversarial-верификация) и
  **помечен** (proposed/accepted) — агент не утверждает спорное соло (D-006/D-018).

## 8. Пошаговый рецепт оркестратора

1. **Сформулировать** задачу и проверить по §2: воркфлоу или соло?
2. **Разведать** при необходимости (список файлов/тем/областей) — соло, быстро.
3. **Разбить на кластеры**; для каждого кластера — отдельный воркфлоу (фазы Map/Analyze → Synthesize,
   схемы для под-агентов и синтезатора).
4. **Запустить** воркфлоу в фон (несколько кластеров — параллельно).
5. **Не ждать впустую** — безопасная параллельная работа; по нотификации — забрать результат.
6. **Извлечь** сырой JSON из temp-вывода → **скомпоновать** чистый структурированный документ (в
   `tmp-work/` собрать, если нужен скрипт; удалить черновик).
7. **Перепроверить** + **пометить** (proposed) → **закоммитить** в канон через `cohort ship`/worktree.
8. **Ответвления** — следующий воркфлоу/worktree/задача в котёл.

## 9. Доказательная база — воркфлоу этой сессии

| Воркфлоу | Тип | Кластер | Финальный артефакт |
|---|---|---|---|
| themes-state-map | Map (read-only) | состояние 6 тем + git/tests | план (в работу) |
| collab-tools-build | Build (verify) | 5 инструментов + adversarial verify | 5 tools + tests (commit) |
| kotel-decision-material | Synthesize (read-only) | 7 котёл-пунктов | `темы/kotel-decision-material…` |
| parallel-forks-history | Analyze (read-only) | история форков/ручейков | `темы/parallel-forks-history…` |
| parallel-work-policy | Draft (read-only) | 4 области политики, 50 под-случаев | `docs/parallel-work-policy.md` |
| gate-poison-situation | Analyze (read-only) | ситуация + 15 вариантов | `темы/gate-poison-situation…` |

Паттерн стабилен: **read-only фан-аут → структурированный синтез → извлечение → чистый канон-документ →
commit**, с параллельными кластерами и без блокировки соседей.

## Перепроверка (D-018)

- **Техническая:** политика отражает фактически отработанный паттерн (8+ воркфлоу выше); сырое — в temp,
  финал — в канон; analysis read-only = ноль контенции; build = worktree.
- **Гуманитарная:** человек получает не сырой шум, а извлечённый структурированный результат; агенты
  получают воспроизводимый рецепт; коллектив — результаты в общий контур (котёл/D-017/D-018), а не в
  личный «чёрный ящик».
## 10. T-161 — граница repo-flow и platform sub-agent launcher

После T-161 воркфлоу запуска sub-agent фиксируется как явный handoff, а не как скрытая магия внутри `flow.py`.

- `python tools/top.py subagent-handoff <agent> <T-id> "<context>" --worktree` — верхняя команда для людей и агентов.
- `python tools/flow.py launch-plan <agent> <T-id> <context> --worktree` — низкоуровневый генератор launch-пакета.
- Внешний platform launcher запускает worker-agent с prompt из launch-пакета.
- Worker-agent обязан использовать `agent-start`, `pipeline claim/done`, scoped edits, tests и report.
- Integrator/lead-agent делает review, merge-gate, selective commit и решает конфликты через D-017/D-018.

Смысл: локальный репозиторий готовит воспроизводимый lane и инструкции, но не привязывается к конкретному API запуска агентов. Это оставляет систему переносимой для людей, Codex sub-agents, других AI и будущего сервера-оркестратора. Подробный чистовой контракт: `docs/agent-launch-workflow.md`.
