# Pipeline orphan doing detection

Дата: 2026-06-20

Статус: кодовая правка подготовлена, runtime-приёмка заблокирована `T-039`.

## Проблема

`tasks/T-020.md` имеет `status: doing`, но для него нет `queues/claimed/T-020.claim.md`. В старом снимке pipeline такая задача отображалась как нормальная работа:

```text
T-020 | ? | | | ...
```

Для большого числа агентов это опасно: задача занята неизвестно кем, но конвейер не показывает, что claim отсутствует. Другие агенты не понимают, задача реально выполняется, зависла или была вручную переведена в `doing`.

## Изменение

В `tools/pipeline.py` изменён `build_pipeline_state()`:

- `status: doing` + нет claim-файла -> blocked/not-ready с причиной `doing without active claim`;
- `status: doing` + claim есть, но lease истёк -> blocked/not-ready с причиной `doing with stale claim`;
- только `status: doing` + свежий claim остаётся в секции `doing`.

Эта правка не меняет `tasks/T-020.md`. Она меняет только диагностическое представление конвейера.

## Почему так

Primary status должен оставаться в `tasks/*.md`, но snapshot должен помогать агентам видеть управленческую проблему. Если `doing` не подтверждён claim-файлом, это уже не нормальная активная работа, а состояние, требующее ручного решения:

- подтвердить, что агент действительно продолжает работу;
- заново создать claim;
- закрыть задачу;
- перевести задачу в `blocked`;
- или разбить её на новые конкретные задачи.

## Проверка после восстановления runtime

После снятия `T-039` нужно выполнить:

```text
python tools/pipeline.py status
python tools/pipeline.py snapshot
```

Ожидаемый результат:

- `T-020` не отображается в `В работе`, пока у него нет свежего claim;
- `T-020` отображается в not-ready/blocked как `doing without active claim`;
- если создать свежий claim для `T-020`, задача снова должна попасть в `doing`.
