# Масштабирование: сервер / NAS / GitHub — плюсы, минусы, доработка

> Повод: стресс-тест 2026-07-07 показал потолок ОДНОЙ машины (6 агентов на 4 ядрах →
> git-латентность 24–59с/таймаут). Отсюда стратегические вопросы Stefan: нужен ли сервер;
> имеет ли смысл онлайн-параллелизм; класть ли канон на сетевой накопитель или на GitHub;
> какие плюсы/минусы и доработки для обоих вариантов; стоит ли выкладывать ДО подключения
> множества агентов.

## 0. Ключевая рамка: потолков ДВА, они независимы

Стресс-тест смешивает два разных ограничения — их надо разделить, иначе выбор хранилища
не решит проблему.

| Потолок | Что это | Чем снимается |
|---|---|---|
| **A. Вычислительный (CPU/IO)** | N тяжёлых агентов требуют ~N ядер. Одна машина, даже мощная, конечна. | Больше ядер (вертикаль) ИЛИ много машин (горизонталь). |
| **B. Контеншн разделяемого дерева** | ВСЕ агенты сейчас в ОДНОМ рабочем дереве и ОДНОМ `.git` → дерутся за `index.lock`, nav-файлы, репак. Это и есть live-lock. | Клон/ветка на агента (у каждого свой `.git`), синхронизация push/pull/merge. |

**Важно:** потолок B — архитектурный, НЕ про мощность. Даже 64-ядерный сервер, если все агенты
сидят в одном дереве, ухудшит B (больше агентов на одном `.git` = больше гонок). Поэтому «купить
мощный компьютер» лечит только A и лишь частично. Настоящее решение — сменить модель: **клон на
агента** (git-нативно). А выбор «NAS или GitHub» — это по сути выбор, ГДЕ стоит центральный
репозиторий, в который клоны пушат.

## 1. Три модели размещения канона

### Модель 1 — сейчас: одна машина, одно общее рабочее дерево
- Все агенты на одном боксе, один checkout.
- Потолок = ядра бокса + контеншн дерева (B) растёт с числом агентов.
- Единая точка отказа, нет офсайт-бэкапа (bus-factor — подтверждён пилотом L2 и near-miss удалением ~11k строк).
- **Вывод:** не масштабируется дальше ~2 тяжёлых агентов на этой машине.

### Модель 2 — локальный сетевой накопитель (NAS / общий SMB/NFS-диск)
Два РАЗНЫХ подварианта — их часто путают:

- **2a. Рабочее дерево репозитория ЛЕЖИТ на сетевом диске, несколько машин его монтируют.**
  ❌ Худший вариант. Git поверх SMB/NFS при одновременном доступе с разных машин —
  печально известная поломка: гонки `index.lock` между машинами, разная семантика
  файловых локов, деградация скорости, риск повреждения `.git`. Это потолок B, умноженный
  на сеть. **Не делать.**

- **2b. На NAS лежит BARE-репозиторий; каждая машина клонирует ЛОКАЛЬНО, push/pull к нему.**
  ✅ Жизнеспособно. Это самодельный git-сервер в LAN (как GitHub, но у себя). Каждый агент
  работает в СВОЁМ локальном клоне (потолок B снят), синхрон через push/pull.

### Модель 3 — онлайн распределённо (GitHub/GitLab, приватный репозиторий)
- Центральный bare-репозиторий в облаке. Каждый агент/машина клонирует, работает в своём
  клоне/ветке, push/pull, слияние через PR или прямой пуш.
- Это **нативная модель git** — ровно то, для чего он создан (распределённые клоны + merge).
- Потолок B снят полностью (каждый клон изолирован). Потолок A снят горизонтально
  (агенты на любом числе машин / облачных раннеров).

## 2. NAS (2b) vs GitHub (3) — плюсы и минусы

| Критерий | Локальный NAS (bare, 2b) | Онлайн GitHub (приватный, 3) |
|---|---|---|
| **Скорость синхро** | ✅ LAN, быстро | ⚠️ сеть, но только в точках push/pull (не на каждую операцию) |
| **Изоляция агентов (B)** | ✅ клон на агента | ✅ клон/ветка на агента |
| **Горизонтальный масштаб (A)** | ⚠️ машины только в LAN | ✅ любые машины/облачные раннеры где угодно |
| **CI / серверный гейт** | ❌ надо самому поднимать раннер | ✅ GitHub Actions — наш `bulk-guard.yml` уже готов, сервер-сайд, необходимый |
| **PR-ревью, merge-queue** | ❌ нет UI, всё вручную | ✅ встроено (ветка→PR→CI→auto-merge) |
| **Офсайт-бэкап / bus-factor** | ❌ NAS = одна площадка, свой бэкап нужен | ✅ офсайт-копия + полная история из коробки |
| **Приватность** | ✅ всё локально | ⚠️ приватный репо (данные у вендора; для чувствительного — шифровать/не класть) |
| **Доступ вне сети** | ❌ нужен VPN | ✅ откуда угодно |
| **Стоимость/обслуживание** | железо + админство NAS | приватные репо бесплатны; CI-минуты лимитированы |
| **Единая точка отказа** | ⚠️ NAS | ✅ вендор реплицирует |

**Суть:** и 2b, и 3 делают ОДНО главное — переводят с «общего дерева» на «клон на агента +
push/pull». Это и есть фикс потолка B. GitHub — это 2b, где сервер держит вендор, ПЛЮС
бесплатный CI (серверный гейт, который мы уже написали), PR-UI и офсайт-долговечность.
NAS выигрывает только в LAN-скорости и полной приватности, но всё остальное (CI, бэкап, UI)
придётся строить руками.

## 3. Нужен ли «сервер» / мощный компьютер?

- Мощный компьютер поднимает потолок A (больше ядер = больше агентов), но: (1) не убирает B,
  если агенты всё ещё в одном дереве; (2) не чинит bus-factor; (3) конечен и дорог (вертикаль).
- Настоящее масштабирование — **горизонталь**: много клонов на многих машинах/раннерах.
  Это ровно облачно-git модель. Поэтому «онлайн» — не альтернатива «мощному ПК», а
  качественно другая ось (горизонт vs вертикаль) И заодно решает долговечность.
- **Вывод:** отдельный мощный сервер оправдан только если нужен приватный тяжёлый локальный
  compute. Для координации канона центральный сервер = git-remote (NAS или GitHub), а не
  «большая машина, куда все ходят».

## 4. Стоит ли выложить на GitHub ДО подключения многих агентов? — Да, это почти prerequisite

1. **Bus-factor.** Сейчас канон — на ОДНОМ диске. Near-miss с удалением ~11k строк и пилот L2
   показали хрупкость. GitHub = офсайт-копия + вся история. Это надо сделать в любом случае.
2. **Субстрат для распределённых агентов.** Codex + Antigravity + Claude в разных процессах/на
   разных машинах не могут безопасно делить состояние без настоящего remote. Общее дерево — нельзя
   (потолок B + стресс-тест). Значит remote нужен ДО, а не после подключения.
3. **CI активируется (мы его уже построили).** `bulk-guard.yml` (validate + generate --check +
   bulk_guard) на сервере = **необходимый гейт**: `--no-verify` обходит только локальный хук,
   серверный CI не обойти. Это финальный уровень защиты коммитов.
4. **Изоляция становится естественной.** Вместо worktree-поверх-общего-дерева — ветка/клон на
   агента (нативно). Гейт A из «форсируем worktree» превращается в «просто у каждого своя ветка».

## 5. Что мы уже построили — это ПОДГОТОВКА к распределённой модели

Большая часть слоя координации уже совместима с моделью «клон на агента + remote», её надо лишь
перенацелить с «одна машина» на «много клонов»:

| Что построено | Роль в распределённой модели |
|---|---|
| `git_reconcile` (полевой CRDT merge-драйвер) + `.gitattributes` | авто-слияние одновременных пушей (разные поля — без конфликта) |
| Принцип reconcile (не-удаление, precedence) | политика слияния при коллизии |
| `bulk-guard.yml` (CI) | серверный не-обходимый гейт (validate/bulk_guard/generate) |
| `worktree_gate` (Гейт A) | → «ветка/клон на агента» (на GitHub — естественно) |
| `work_admission` (Гейт B) | → ПО-МАШИННЫЙ кап (каждая машина ≤ ядра−2); межмашинную очередь на пуш держит merge-queue CI |
| `validate` / `generate` | шаги CI |
| `commit_lock` (nav-гонка) | внутри одного клона; при клон-на-агента почти не нужен (деревья изолированы) |

**Т.е. переход на GitHub не выбрасывает наработки — он их «включает».**

## 6. Доработка (конкретный чек-лист) — что нужно перед выкладкой

### Общее (для ОБОИХ вариантов — NAS 2b и GitHub 3)
- [x] **Скраб секретов — ПРОЙДЕН (сухой прогон 2026-07-07):** настоящих токенов/ключей НЕТ.
      Единственные совпадения `AKIA…/api_key=…` — тестовые фикстуры в `drivers/*/test_*.py`
      (фейковые секреты для проверки маскировки). Безопасно к пушу.
- [~] **PII/пути — низкий риск, стоит подчистить для переносимости:** 219 вхождений
      абсолютного `C:\Users\stefan\...` в 27 файлах (docs/reports; один историч. дамп даёт 172).
      Не секрет, но не-переносимо (на другой машине/агенте путь не разрешится). Для приватного
      репо не блокер; отдельным проходом заменить на относительные/`$COLLAB_ROOT`.
- [ ] **Полнота `.gitignore`:** убедиться, что ничего runtime/volatile не трекается
      (`logs/slots/`, `LIVE.md`, `PIPELINE.md`, heartbeat, `indexes/*.db`, `views/*` — уже есть).
      NB: рабочее дерево 119.5 МБ, но это в осн. gitignored-рантайм (`indexes/*.db`, `views/`,
      `logs/`, `__pycache__`) — проверить, что клоны остаются лёгкими.
- [x] **Размер репо — ПРОВЕРЕН:** `.git` = **18.5 МБ** (крошечный: первый пуш тривиален, клоны
      дёшевы). 13 104 файла в дереве — но `.git` мал → трекается немного; squash/фильтр не нужен.
- [ ] **Merge-драйвер закоммичен и активируется:** `.gitattributes` + инструкция
      `git config merge.reconcile.driver` (драйвер в репо, но config — локальный, нужен bootstrap-скрипт).
- [ ] **Модель веток:** ветка-на-агента (`agent/<id>/<task>`) → PR/merge; `main` защищён.
- [ ] **Гейт B перенацелить на ПО-МАШИННЫЙ кап** (`work_admission` уже читает `logs/slots/` —
      локально на каждой машине; глобальный кап на пуш заменяется merge-queue).

### Только GitHub (3)
- [ ] Приватный репозиторий; branch protection на `main` (require CI green, require PR).
- [ ] CI-раннер: `bulk-guard.yml` уже есть — проверить, что validate укладывается в лимит минут
      (при росте — кэш, только staged/дифф в PR).
- [ ] Политика auto-merge on green (merge-queue сериализует одновременные пуши — заменяет наш commit_lock на уровне сервера).
- [ ] Bootstrap-скрипт для нового клона/агента: `git config` merge-драйвера, установка хуков,
      `work_admission` reserve по числу ядер машины.

### Только NAS (2b)
- [ ] Bare-репо на NAS + доступ (SSH/файловый) для машин.
- [ ] Самому поднять CI (раннер на отдельной машине) ИЛИ жёсткий pre-push хук на каждом клоне
      (слабее CI — обходится). Без этого серверного гейта нет.
- [ ] VPN для доступа вне LAN.
- [ ] Бэкап самого NAS (иначе одна площадка = один риск).
- [ ] Межмашинный кап/сериализация пушей — руками (нет merge-queue).

## 7. Рекомендация

1. **Целевое состояние — GitHub (приватный) как источник истины + локальные клоны на машину/агента.**
   Это нативная git-модель: снимает потолок B, масштабирует A горизонтально, включает наш CI
   как серверный гейт, чинит bus-factor офсайт-копией. NAS-bare (2b) — разумный LAN-only/приватный
   запасной вариант, но в нём заново строишь то, что GitHub даёт даром (CI, долговечность, UI).
2. **Сделать до подключения многих агентов** (bus-factor + это субстрат для распределёнки).
3. **Порядок миграции (этапы):**
   - Э1: скраб секретов + `.gitignore` + проверка веса → первый пуш в приватный GitHub (бэкап уже есть).
   - Э2: включить `bulk-guard.yml` CI + branch protection на `main` → серверный гейт живой.
   - Э3: bootstrap-скрипт клона (merge-драйвер, хуки, `work_admission` по ядрам) → агент = свой клон/ветка.
   - Э4: перевести 1–2 агентов на модель «клон+ветка+PR», обкатать merge-драйвер на реальных
     одновременных пушах, затем расширять.
4. **Кап остаётся ПО-МАШИННЫМ** (`ядра−2`), а не глобальным: в распределёнке у каждой машины
   свой CPU, глобально сериализуется только СЛИЯНИЕ (merge-queue), не работа.

## 8. Минусы/риски честно
- GitHub: данные у вендора (для чувствительного — не класть/шифровать); CI-минуты лимитированы;
  сетевая задержка на sync; merge-конфликты при одновременных пушах (смягчает CRDT-драйвер, но
  не на 100% — семантические коллизии всё равно к человеку/оркестратору).
- NAS: строишь CI/бэкап/UI сам; одна площадка; вне LAN — VPN.
- Общее: переход на «клон на агента» — реальная смена модели эстафеты (D-036): worktree-гейт
  превращается в ветку-на-агента, а commit_lock почти не нужен. Это доработка, не «просто залить».

## 9. Что дальше (для агентов, без человека)
- Технически проработать bootstrap-скрипт клона (merge-драйвер + хуки + `work_admission`).
- Прогнать скраб секретов и посчитать вес `.git` (сухой прогон, без пуша).
- Оформить D-* о целевой модели «GitHub + клон на агента» на ратификацию Stefan.
- Стратегический выбор (GitHub vs NAS, приватность данных, бюджет CI) — за человеком.
