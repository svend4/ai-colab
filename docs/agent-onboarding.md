## §0. Метаданные — карточка на 30 секунд

- **Что это.** «Средний слой пирамиды»: ОС (низ) ↔ **этот слой** ↔ AI-агенты/люди (верх).
  Слой даёт безопасный read-only доступ к файлам, репозиториям, таблицам, БД, истории git и
  к памяти-корпусу — через единый набор драйверов (MCP-серверов) и файловый конвейер задач.
- **Ты подключился на вершину.** Ты — агент или человек. Снизу есть **9 драйверов**, **память
  с поиском**, **конвейер задач**, **переносимая MCP-приёмка**, **skills**.
- **3 команды, чтобы начать:**
  - `python tools/top.py buttons` — увидеть верхнюю панель сценариев/кнопок;
  - `python tools/top.py agent-start codex --task T-id --context "<тема>"` — старт агента + статус + assurance/advice + быстрый поиск по канону;
  - `python tools/demo_bridge.py` — увидеть слой в действии (6 способностей за один запуск);
  - `python tools/pipeline.py status` — что сейчас в работе/готово/заблокировано;
  - `python tools/validate.py` — здоров ли канон (должно быть `ERROR=0`).
- **Куда смотреть:** `STATUS.md` (состояние) · `docs/bridge-usage.md` (как пользоваться) ·
  `drivers/CATALOG.md` (драйверы) · `AGENTS.md` (правила агентов) · этот файл (онбординг).

## §1. Что ты можешь делать — карта возможностей (5 минут)

### Драйверы (read-only способности; все с allowed-root, лимитами, аудитом)

| Драйвер | Что даёт | Инструменты |
|---|---|---|
| `files` | чтение/инвентаризация файлов, поиск, маскировка секретов | list/read/search/summarize |
| `repo-runner` | инвентаризация репозитория (языки/тесты/риски), код НЕ запускается | inspect/summary/risks |
| `data` | таблицы CSV/TSV: колонки/срез/сводка | list_tables/columns/head/summarize |
| `sqlite` | инспекция/запрос любых SQLite-БД read-only (`mode=ro`, только SELECT) | list_tables/schema/head/query |
| `git-log` | история git: коммиты/авторы/история файла/сводка | recent_commits/author_stats/file_history/repo_summary |
| `workbench` | SQLite-память корпуса (documents + audit_log) | init/add/query/log |
| `gateway` | **композиция** — один MCP-сервер над files+repo+workbench | 6 инструментов сразу |
| `codex-local` | мост к локальной среде Codex (наличие/версия) | codex_available/codex_info |
| `file-inventory` | карта файлов проекта (draft) | scan |

### Память и знания (L6)
- `python tools/knowledge.py report <папка> [--query ТЕКСТ] [--out reports/x.md]` —
  ingest корпуса → состав по типам/рискам → ответ на запрос → markdown-отчёт.
- `python tools/knowledge.py search <db> <текст>` — **ранжированный поиск (FTS5 + bm25)**;
  `query` — простой LIKE.
- `python tools/top.py repo-search "<тема>" --limit 5` — быстрый поиск по канонической документации, решениям, вопросам, темам и задачам; runtime-БД в `logs/*.db` не версионируется.
- `python tools/text_extract.py summary <file>` — безопасное извлечение текста для `.md/.txt/.html`;
  `knowledge.py` использует его, чтобы искать по содержимому документа, а не только по первой строке.

### Конвейер задач (как агент выполняет работу)
- `pipeline.py next <agent>` (взять) → `done <agent> <T-id> --claim <id> --report "..."` (закрыть) →
  `generate.py` → `validate.py` → `snapshot`. Подробности — §3 и `skills/pipeline-operator/SKILL.md`.

### Параллельная работа без блокировки (вершина + Уровень-0/1)
Полная карта движка — `docs/engine-state-2026-06-22.md`; политика по ситуациям — `docs/parallel-work-policy.md` (D-022).
- **Вершина (одна кнопка):** `python tools/cohort.py board|plan|turn|self` (параллель+самохостинг) и
  Codex-панель `python tools/top.py` (одиночный агент/человек).
- **Перед работой — `guard`:** `python tools/cohort.py guard <agent>` — триггеры Уровня-1 (foreign-source /
  hot-tool / stale-index / gate-poison) через общий `tools/ownership.py` (mine|generated|volatile|foreign|unknown).
- **Уровень-0 (общее дерево):** `python tools/cohort.py ship <agent> <свои файлы> --message "..." --run` —
  `commit_lock` + selective-add + авто-регенерация (не блокируя других, не тащя чужое).
- **Уровень-1 (изоляция):** при триггерах — `python tools/flow.py start <agent> <task> --worktree --run` →
  работа в притоке → `flow.py finish ... --worktree` (`merge_gate` → merge → снять). Форк-пакеты — `tools/stream.py`.
- **Трение:** `python tools/friction.py status --agent <you>` — детектор повторяющихся проблем (F-XXX) + рецепты.

### MCP-приёмка (подключить драйверы к реальному AI-клиенту)
- `python drivers/mcp_sync_acceptance.py` — **переносимая** `tools/call`-приёмка всех серверов
  (работает там, где официальный async stdio падает Windows `WinError 5`).
- Подключение gateway к клиенту — в `docs/bridge-usage.md §3`.

### Skills (повторяемые процедуры, L3)
`skills/driver-acceptance`, `skills/pipeline-operator`, `skills/repo-review` — переносимые `SKILL.md`.

## §2. Роли — что делает человек, что делает агент

| | Человек (Stefan/Max) | Агент (claude/codex/…) |
|---|---|---|
| **Видение, приоритеты, бизнес-цель** | ✅ задаёт | ✗ не выдумывает |
| **Доступ к внешним данным** (svend4, секреты) | ✅ предоставляет | ✗ не имеет |
| **Архитектурные решения** (`DECISIONS.md` accepted) | ✅ утверждает (D-006) | предлагает `proposed` |
| **Технический статус** драйвера (`draft→ready`) | подтверждает или нет | ✅ меняет по **D-015** (код работает + сверка ≥2 агентами) |
| **Код/драйверы/тесты/документация** | ревью | ✅ пишет, тестирует, чинит |
| **Перепроверка/ревью/дрейф** | по запросу | ✅ ведёт (skill `repo-review`) |
| **Выполнение задач из пула** | ставит задачи | ✅ берёт через `pipeline.py next` |

**Граница (важно):** агент **предлагает** решения и **сам меняет только верифицируемый
технический статус**; он не утверждает архитектуру и не имеет внешнего доступа. Человек —
источник цели, данных и финального «да».

## §3. Как начать — пошагово

**Агент, который только подключился:**
1. Прочитай `STATUS.md` → `этот файл §0-1` → `AGENTS.md` (твои права/зона записи).
2. Если тема известна, подними контекст: `python tools/top.py agent-start <agent> --task <T-id> --context "<тема>"` или `python tools/top.py repo-search "<тема>" --limit 5`. `agent-start` теперь также показывает assurance/advice, чтобы существующие правила и рецепты не оставались пассивным текстом.
3. Зарегистрируй присутствие: `pipeline.py heartbeat <agent> <T-id> --note "..."`.
4. Возьми работу: `pipeline.py next <agent>` (или сделай то, о чём просил человек).
5. Сделай → закрой с fencing (`done ... --claim <id> --applied "AGENTS.md, PROTOCOL.md, Checks"`) → `generate && validate && snapshot`.
5. Значимые правки служебных файлов объясняй в `dialog.md` (формат D-003).
6. Не уверен — заведи вопрос в `QUESTIONS.md`, не меняй итоговые файлы молча.

**Человек:** `STATUS.md` (что происходит) · `PIPELINE.md`/`LIVE.md` (кто что делает) ·
поставить задачу — строкой через `next_id.py` + файл `tasks/T-XXX.md` · спросить агента — `@Claude`/`@Codex` в любом `.md`.

## §5. Вопросы и ответы — проблемы разработки и коллективной работы

> Это главный рефлексивный блок: реальные вопросы, с которыми сталкиваешься, мой ответ/решение,
> и **рекомендация-микроскилл** (короткое правило для следующего раза). Многие формализованы в `skills/`.

### Q1. Как несколько агентов работают над ОДНИМ полем, не мешая друг другу?
**Проблема:** общий рабочий tree + параллельные правки = потерянные изменения, гонки.
**Решение (работает):** (а) **append-only** для обсуждений (одно сообщение = один файл в
`topics/<topic>/messages/`); (б) **шардирование** реестров (задачи/вопросы/решения — по файлу,
агрегаты генерируются); (в) **атомарный claim** задачи (`O_CREAT|O_EXCL`) + **fencing-token** при
закрытии; (г) генерируемые индексы вместо ручной правки 6 файлов.
**Микроскилл:** *«Не редактируй общий длинный файл — пиши свой маленький; общий итог собирается
генератором. Перед началом задачи — `pipeline.py next` (атомарный захват), при закрытии —
`done --claim`.»*

### Q2. Гонка за номером (id) — два агента берут один T-номер.
**Решение:** `tools/next_id.py` выдаёт id атомарно (та же техника `O_CREAT|O_EXCL`).
**Микроскилл:** *«Новый id — ТОЛЬКО через `next_id.py`, никогда руками.»*
**Остаточная проблема (нашёл на практике):** между `next_id` (создаёт placeholder) и заполнением
есть окно, в которое чужой cleanup-sweep может «retired» твой placeholder. **Решение:** заполнять
задачу одной цепочкой сразу после выдачи id (`next_id … && cat > tasks/$id.md … && done`).

### Q3. Гонка КОММИТОВ с активным вторым агентом (pre-commit падает на «устаревшей навигации»).
**Проблема:** пока я готовлю коммит, второй агент меняет `tasks/*` → мой `TASKS.md`/`index.json`
устаревают → hook блокирует.
**Решение (работает):** коммитить **одной цепочкой** `python tools/generate.py && git add -A &&
git commit` — окно минимально; при блокировке просто повторить (hook сам подсказывает).
**Микроскилл:** *«Регенерируй → add → commit без разрыва. Не обходи hook (`--no-verify`) — он
защищает канон.»*

### Q4. Дрейф состояния (committed index/manifest/status ≠ источники).
**Проблема:** руками поменяли статус/манифест, забыли регенерировать → производные расходятся.
**Решение:** `generate.py`/`drivers_catalog.py` (производные из источников) + `validate.py`
(ловит ERROR) + `reconcile_state.py` (репортит дрейф, не чинит молча) + pre-commit hook.
**Микроскилл:** *«Источник правды — front-matter `tasks/*.md`/`drivers/*.md`; `TASKS.md`,
`index.json`, `CATALOG.md` — генерируемые. После правки источника всегда `generate → validate`.»*

### Q5. Как менять статус без бюрократического ожидания человека?
**Проблема:** «draft→ready требует подписи человека» тормозит, а человек — узкое место.
**Решение (D-015, принято в этой сессии):** технический статус меняется по **результату**:
код работает (тесты/приёмка) **+ перепроверка ≥2 агентами**, без обязательной подписи. (Архитектурные
решения по-прежнему утверждает человек — D-006.) На практике сработало: я сделал `sqlite`, Codex
независимо прогнал sync-приёмку и перевёл в `ready` за минуты.
**Микроскилл:** *«Статус = доказанный результат, а не церемония. Зафиксируй, КТО и ЧЕМ верифицировал
(`source_last_verified` + запись в манифесте).»* (skill `driver-acceptance`).

### Q6. Windows-специфика ломает рантайм (а инфраструктура должна продолжать работать).
**Столкнулся с тремя:** (1) cp1252 в выводе → крах на кириллице; (2) `asyncio` stdio MCP-клиент
падает `PermissionError [WinError 5]`; (3) `git`/subprocess внутри MCP-сервера виснет (наследует
stdin-пайп asyncio).
**Решения:** (1) `stdout.reconfigure(encoding="utf-8")` в каждом скрипте; (2) **синхронный** MCP-клиент
на `subprocess.Popen` (`mcp_sync_probe`/`mcp_sync_acceptance`) — переносим между средами; (3)
`subprocess.run(..., stdin=subprocess.DEVNULL)`.
**Микроскилл:** *«Не привязывай инфраструктуру к одному рантайму. Для subprocess под pipe-stdio —
всегда `stdin=DEVNULL`. Имей sync-fallback для MCP.»*

### Q7. Коллизии при правке одних и тех же файлов двумя агентами.
**Столкнулся:** Codex взял задачу T-088 на gateway, пока я уже сделал gateway-аудит; мой же
fencing корректно не дал мне закрыть его задачу.
**Решение:** (а) брать **неконфликтующий фронт** (новый файл/новая папка-драйвер = нулевая
коллизия); (б) проверять claim перед работой; (в) если уже пересеклись — громко отсигналить в
`dialog.md`, оставить закрытие владельцу claim; (г) **не править чужие манифесты/статусы молча**.
**Микроскилл:** *«Перед работой проверь `pipeline.py status`/claim. Предпочитай новый файл правке
чужого. Пересёкся — сигналь, не дублируй.»*

### Q8. Фантомные блокеры (задача `blocked` за уже снятой причиной).
**Столкнулся:** T-039 (среда зависала) держал каскад из 6 задач, хотя среда уже работала.
**Решение:** перепроверка фактом (прогнать тесты) → снять блокер → пересчитать снимок.
**Микроскилл:** *«`blocked` без свежей проверки причины — подозрителен. Сначала воспроизведи
причину, потом верь статусу.»* (skill `repo-review`).

### Q9. Перекос «мета-работа vs продукт» (система отчитывается о себе).
**Столкнулся (и сам усугубил):** docs/ переполнен отчётами о самой системе; инфраструктура
обгоняет спрос.
**Решение/рекомендация:** не заводить docs «о системе» как отдельные done-задачи; статус-отчёты
**генерировать**, а не писать руками; KPI сессии — закрытые продуктовые задачи и тесты, а не число
отчётов.
**Микроскилл:** *«Один срез статуса = одна генерируемая команда, не два рукописных файла. Спроси:
это двигает ПРОДУКТ или документирует ПРОЦЕСС?»*

### Q10. Как не потерять обоснование правок (асинхронный форум).
**Решение:** служебные правки сопровождаются записью в `dialog.md` (Изменил/Почему/Моё мнение/Что
нужно от других — D-003). Это даёт асинхронную трассируемость для людей и агентов.
**Микроскилл:** *«Меняешь служебный файл — оставь 4-строчное обоснование. Код объясняет КАК, запись
объясняет ЗАЧЕМ.»*

4. **Нумерация слоёв L0-L8 расходилась** между документами (находка J — закрыта канонизацией, но

5. **Движок развит, продукт — нет** (см. оценку план↔факт). → **Иначе:** заморозить дженерик-слой,
   развернуться к реальным данным/домену.

## §7. Насколько движок зрел и может ли он улучшать сам себя

**Зрелость (по слоям):** инфраструктура — высокая (TRL ~7-8 для малого масштаба): атомарная
конкуренция, генерируемый канон, валидаторы, переносимая MCP-приёмка, аудит, 9 read-only драйверов,
память+FTS5. Продуктовый слой (реальный корпус/домен/execute) — низкая (TRL ~2-3).

**Может ли работать над собой — да, и уже делает, в значимой степени:**
- **Самоописание:** генерирует свои индексы/каталог/навигацию из источников (`generate.py`,
  `drivers_catalog.py`) — самодокументируется.
- **Самопроверка:** `validate.py` (канон), `reconcile_state.py` (дрейф), `race_test.py`/
  `test_pipeline_fencing.py` (свои гарантии конкуренции), `mcp_sync_acceptance.py` (свои драйверы).
- **Саморефлексия как процесс:** агент может прогнать `repo-review` skill, найти свои же дефекты
  (как я нашёл A-N) и закрыть их задачами через свой же конвейер — этой сессией это и произошло
  (ревью → 14 находок → закрыты через `pipeline.py`).
- **Самоприёмка нового модуля:** новый драйвер проходит свой же `driver-acceptance` (unit + sync
  MCP-приёмка + манифест-сверка), и второй агент верифицирует по D-015 — **замкнутый цикл улучшения
  без человека** для технических изменений.

**Граница автономии (честно):** движок **не** может сам: поставить себе бизнес-цель, получить
внешние данные/секреты, утвердить архитектурное решение, запустить непроверенный код (нет песочницы).
То есть он автономен в **сопровождении и улучшении самого себя**, но не в **выборе, ЗАЧЕМ** он нужен —
это остаётся за человеком. Это правильная граница, а не дефект.

**Чего не хватает для более сильного self-improvement:**
- **Само-метрики качества** (покрытие тестами, доля мета vs продукт, дрейф) как генерируемый дашборд,
  по которому агент сам приоритизирует.
- **Авто-завод задач из находок:** `repo-review` мог бы сам создавать `tasks/*` из дефектов
  (сейчас это делает агент вручную).
- **Изоляция параллельных агентов** (worktree) — чтобы самоулучшение шло реально параллельно.

## §8. Инновационные идеи обработки больших массивов информации

От практичных к фантастическим:

1. **Capability manifest (`capabilities.json`)** — машиночитаемая карта «что умеет слой»
   (драйверы, инструменты, входы/выходы, риск), генерируемая из манифестов. Агент при подключении
   читает ОДИН файл и сразу знает свои возможности — без чтения истории. *(дешёво, высокая отдача)*
2. **«Тропы муравейника» буквально** (идея Stefan): счётчик использования драйверов/запросов;
   часто используемые пути «протаптываются» — кешируются, индексируются, поднимаются в подсказках.
   Инфраструктура **прорастает по факту использования**, а не строится вперёд спроса.
3. **Инкрементальный ingest по событию** (watch): новый/изменённый файл в корпусе → авто-ingest →
   обновление FTS5 → дельта-отчёт. Память «живёт» вместе с папкой.
4. **Слой объяснимости поиска:** к каждому ответу — «откуда» (документ:строка) + почему ранг
   (bm25-вклад термов). Для юр.домена — обязательная трассируемость источника.
5. **Гибридный поиск:** FTS5 (точные слова, важны для права) → при росте корпуса добавить
   локальные эмбеддинги (sentence-transformers + FAISS) как ВТОРОЙ ранкер, не заменяя первый.
6. **«Средневековая» идея — скрипторий/реестр писцов:** каждый агент-«писец» работает в своей
   изолированной келье (worktree), а «настоятель» (reconcile/merge-гейт) сводит копии в канон —
   масштабирование без гонок, как монастырская переписка.
7. **Граф знаний поверх documents** (`entities`/связи): сущности (термины SGB, даты, дела) →
   timeline и «дело целиком», а не отдельные файлы. *(план из исходного архитектурного документа)*
8. **Самоулучшающийся цикл:** ночной агент гоняет `repo-review` → находки → авто-задачи → утром
   человек видит дайджест «что слой починил/предлагает в себе». Движок, который дежурит над собой.
