# Средний слой пирамиды: инфраструктура «драйверов» и агентов между приложением и ОС

> Черновик-шпаргалка по вопросу Max (2026-06-20). Цель — заполнить «пустую середину»
> между одним приложением-агентом (Cowork/Codex) и большой статичной ОС (Windows)
> прозрачным для ИИ слоем возможностей: драйверов, коннекторов, навыков и агентов.
> Документ теоретический: он даёт карту, словарь, варианты и план, а не готовый код.

---

## 0. О чём вопрос (своими словами)

Есть две крайности:

- **Вершина пирамиды** — одно приложение (Cowork/Codex). Лёгкое, умное, но «слишком мало»: знает только то, что ему дали.
- **Основание пирамиды** — операционная система (Windows, десятки гигабайт). Огромная, статичная, «слишком много»: всё умеет, но непрозрачна для ИИ — нейросеть не «видит» её функции как инструменты.

Между ними — **огромная незаполненная масса**. Её надо заполнить слоем, который:

1. прозрачен для нейросети/агентов (ИИ видит возможности как набор инструментов);
2. состоит из множества разнофункциональных «информационных драйверов/трейлеров», навыков, плагинов, баз данных;
3. лежит в папках проекта (и подпапках/подтемах), активируется по требованию — «как тулкит»;
4. умеет подключать и внешние сервисы (через коннекторы по интернету), и локальные программы внутри компьютера;
5. служит одной цели — удобно работать с **большими объёмами информации**: обрабатывать, классифицировать, обновлять, отвечать на вопросы — силами ИИ и его агентов.

Конкретный кейс: у профиля **Sven4** много репозиториев с кодом, который в основном не тестирован и который **нельзя запустить на GitHub — только на сервере**. Локально стоит **Codex** (ОС Windows). Но **прозрачной прослойки между ними нет** — нет «троп в муравейнике», «дорожек на микросхеме». Их нужно проложить.

## 1. Главный вывод: ты описываешь реальный слой, и у него уже есть имя

То, что ты называешь «информационными драйверами» и «прозрачной прослойкой», в индустрии уже оформилось. Твоя интуиция точна — не нужно изобретать протокол с нуля, нужно собрать существующие кубики. Соответствие твоих метафор и реальных технологий:

| Твоя метафора | Реальная технология | Что это |
|---|---|---|
| «информационный драйвер / трейлер» | **MCP-сервер** (Model Context Protocol) | Стандартный «разъём» между ИИ и инструментом/данными. Драйвер именно в твоём смысле: ИИ не знает внутренностей, видит только функции. |
| «прослойка, прозрачная для ИИ» | **MCP как протокол** | Один протокол для всех источников. Нейросеть работает одинаково с локальной программой и облачным сервисом. |
| «коннектор к приложению по интернету» | **удалённый MCP-сервер** (HTTP/SSE) | Сервис в облаке, обёрнутый в MCP (Gmail, Drive, GitHub, Slack…). |
| «коннектор к программе внутри компьютера» | **локальный MCP-сервер** (stdio) | Локальный процесс-обёртка над программой/папкой/БД на твоей машине. |
| «пассивный агент, активируемый как тулкит» | **Skill** (папка `SKILL.md` + скрипты) или **субагент** | Лежит в папке, не грузится в память, пока не понадобится; активируется по описанию-триггеру. |
| «десятки агентов в папках проекта» | **реестр skills/MCP в репозитории** | Каталог возможностей внутри проекта — ровно то, что ты уже начал в `New project ai colab`. |
| «соединить как плагин» | **Plugin** (бандл MCP + skills + команд) | Упакованный набор драйверов и навыков, ставится одним куском. |

**Ключевая мысль:** твоя папка `New project ai colab` — это уже половина пирамиды. Слой **оркестрации агентов** ты построил (`queue.py`, `dispatch.py`, `permissions.py`, `risk_gate.py`, `metrics.py`, `index.json`). Не хватает **слоя драйверов** — обёрток над программами, репозиториями Sven4, базами данных и сервисами, чтобы ИИ видел их как инструменты. План ниже — как достроить вторую половину тем же стилем.

## 2. Архитектура слоёв — чем заполняем середину

> **Нумерация.** Схема ниже — иллюстративный набросок «снизу вверх» (4 концептуальных слоя),
> а НЕ каноническая нумерация. Канонический источник нумерации слоёв проекта — **`docs/layers-coverage.md`**
> (карта `L0–L7`) и `docs/middle-layer-guide.md`. Там `Оркестрация = L7`, `Драйверы = L2`, `Skills = L3`,
> `Память/RAG = L6`. Не путать «СЛОЙ 4» этого наброска с `L4` канона (ревью T-078, находка J).

Снизу вверх (от основания пирамиды к вершине):

```
            ┌─────────────────────────────┐
   ВЕРШИНА  │  Cowork / Codex (оркестратор)│  ← один агент-дирижёр
            └──────────────┬──────────────┘
                           │
        ┌──────────────────┴───────────────────┐
СЛОЙ 4  │  Оркестрация: queue, dispatch,        │  ← у тебя УЖЕ есть (colab)
        │  permissions, risk_gate, metrics      │
        └──────────────────┬────────────────────┘
        ┌──────────────────┴────────────────────┐
СЛОЙ 3  │  Агенты/навыки: subagents + skills    │  ← частично есть (skills)
        │  (пассивные, ленивая загрузка)        │
        └──────────────────┬────────────────────┘
        ┌──────────────────┴────────────────────┐
СЛОЙ 2  │  ДРАЙВЕРЫ (MCP-серверы):              │  ← ГЛАВНЫЙ пробел
        │  обёртки над кодом/данными/сервисами  │
        └──────────────────┬────────────────────┘
        ┌──────────────────┴────────────────────┐
СЛОЙ 1  │  Реестр/каталог + манифест драйверов  │  ← нужно сделать (как index.json)
        └──────────────────┬────────────────────┘
            ┌──────────────┴──────────────┐
ОСНОВАНИЕ   │  ОС, ФС, локальные программы,│  ← Windows, Codex, репозитории Sven4,
            │  репозитории, внешние API    │     БД, интернет-сервисы
            └─────────────────────────────┘
```

«Пустая масса» = **Слой 1 (реестр) + Слой 2 (драйверы) + Слой 3 (навыки/агенты)**. Слой 4 у тебя уже работает и его паттерны (манифест, права, очередь, метрики) переиспользуются для нижних слоёв.

## 3. Каталог «информационных драйверов» (черновик-шпаргалка)

Это словарь категорий — что вообще можно обернуть в драйвер. Каждый драйвер = «что делает» + «интерфейс (примерные инструменты)» + «где живёт» + «статус у тебя сейчас».

| # | Категория драйвера | Что делает (примерные инструменты) | Где живёт | Статус |
|---|---|---|---|---|
| 1 | **Файловый** | читать/писать/искать/переименовывать/дедуп файлы | локально (stdio) | частично (skills: organizer, renamer, dedupe) |
| 2 | **Данные** | SQLite/CSV/Parquet/векторная БД: запрос, классификация, обновление | локально | нужно |
| 3 | **Код/репозитории** | клонировать, читать, запускать, тестировать, линтить репозиторий | сервер (Sven4) + локально | нужно (ключевое для Sven4) |
| 4 | **Выполнение/песочница** | запустить Python/Node в изоляции, вернуть результат | сервер/Docker | нужно |
| 5 | **Внешние сервисы** | Gmail, Drive, GitHub, Slack, Notion… | удалённый MCP (коннектор) | доступно через реестр коннекторов |
| 6 | **Поиск/знания** | веб-поиск, RAG по локальным документам, эмбеддинги | локально + интернет | частично (web search) |
| 7 | **Оркестрация** | очередь задач, диспетчер по DAG, расписание | локально (colab) | **есть** (`queue/dispatch`) |
| 8 | **Наблюдаемость** | метрики, логи, аудит-трейл | локально (colab) | **есть** (`metrics`, `dialog.md`) |
| 9 | **Права/безопасность** | зоны доступа, секреты, политика песочницы | локально (colab) | частично (`permissions.py`) |
| 10 | **Связь агентов** | полилог, шина сообщений, призыв `@агент` | локально (colab) | **есть** (`dialog.md`, темы) |
| 11 | **Документы/форматы** | docx/pdf/xlsx/pptx: читать и создавать | локально (skills) | **есть** (skills) |
| 12 | **Домен-специфика** | напр. юр-драйверы, расчёт сроков, шаблоны | локально (skills/MCP) | частично (legal skills) |

Принцип: **«насколько богата ОС функциями — настолько обрастает функциями и слой»** — верно, но с оговоркой из раздела 4.

## 4. Критический принцип: ленивая активация (иначе слой задушит ИИ)

Самая частая ошибка такой архитектуры — «подключим все драйверы сразу». Это ломает систему: десятки-сотни инструментов одновременно → модель путается, контекст переполняется, качество падает. Поэтому **пассивность драйверов — не деталь, а центральное требование** (ты сам это почувствовал словами «пассивные агенты, активируемые как тулкит»).

Правильный паттерн (он же — то, как работают skills и отложенные инструменты):

1. **Манифест-каталог** (один лёгкий файл, как твой `index.json`): список всех драйверов с коротким описанием-триггером, но БЕЗ загрузки.
2. **Поиск/подбор по задаче**: оркестратор читает манифест, выбирает 1–5 релевантных драйверов.
3. **Активация по требованию**: только выбранные драйверы поднимаются и дают свои инструменты.
4. **Деактивация**: отработал — выгрузился, контекст чист.

Твой `index.json` + `dispatch.py` — это и есть зародыш такого каталога-активатора. Его надо расширить с «задач» на «драйверы».

## 5. Варианты решения — от простого к сложному

Лестница зрелости. Каждый уровень — рабочий сам по себе; можно остановиться на любом.

### Уровень 0 — то, что уже есть
Один репозиторий-проект + skills + ручной запуск скриптов (твой colab). 
**+** работает сегодня, ноль инфраструктуры. **−** драйверов нет, Sven4 и локальные программы не видны ИИ.

### Уровень 1 — папка-реестр драйверов (локально, без сервера)
Добавить в репозиторий папку `drivers/`, в ней — описания возможностей (по одному файлу на драйвер, с front-matter, как у задач) и манифест `drivers/index.json`. Пока БЕЗ настоящих MCP — просто каталог + Python-скрипты-обёртки, которые Codex запускает.
**+** дёшево, в стиле colab, сразу полезно как «шпаргалка» и точка роста. **−** ещё не «прозрачно для ИИ» в смысле протокола — обёртки вызываются скриптами, не как инструменты MCP.

### Уровень 2 — локальные MCP-серверы + хаб (прозрачность для ИИ)
Обернуть 2–3 ключевые возможности в настоящие локальные MCP-серверы (stdio): «репозиторий-раннер», «данные», «файлы». Добавить тонкий **MCP-хаб/роутер**, который поднимает их и отдаёт единый каталог.
**+** теперь ИИ видит драйверы как инструменты — это и есть «прозрачная прослойка». **−** нужен код MCP-серверов (есть skill `mcp-builder`), появляется эксплуатация (поднимать/гасить процессы).

### Уровень 3 — серверный оркестратор (гибрид локально+сеть)
На сервере (где живут репозитории Sven4) поднять MCP-серверы, оборачивающие каждый репозиторий как инструмент «запусти/протестируй/расскажи». Codex/Cowork с Windows подключаются к ним по сети. Локальные драйверы остаются локальными.
**+** решает твой главный кейс — Sven4-код, который «только на сервере». Чёткое разделение: тяжёлое — на сервере, лёгкое — локально. **−** нужен сервер, сеть, аутентификация, песочница для непроверенного кода (раздел 8).

### Уровень 4 — полноценная платформа драйверов
Реестр с версионированием, авто-дискавери, песочницы, права (как `permissions.py`), очередь (как `queue.py`), наблюдаемость (как `metrics.py`), пассивные субагенты по DAG (как `dispatch.py`) — но уже над драйверами, а не только над задачами.
**+** это и есть «заполненная пирамида»: масштаб на десятки драйверов/агентов. **−** большой объём работы и поддержки; строить это «вперёд спроса» — прямой путь к over-engineering (ты сам предупреждал об этом в `scaling-design.md`).

## 6. Привязка к твоей конкретной ситуации

Дано: **Cowork** (вершина), локальный **Codex** на Windows, репозитории **Sven4** на сервере (нельзя на GitHub), и уже построенный **colab-репозиторий** (оркестрация).

Кратчайшая тропа «из муравейника»:

1. **colab-репозиторий = реестр и дирижёр.** Он уже умеет очередь, права, метрики, полилог. Делаем его домом для каталога драйверов (`drivers/`).
2. **Один репозиторий Sven4 → один MCP-драйвер** на сервере: инструменты `inspect` (что внутри), `run` (запусти в песочнице), `test` (прогон тестов), `summary` (опиши код). Это превращает «мёртвый» непротестированный код в инструмент, видимый ИИ.
3. **Локальный Codex → драйвер-раннер**: MCP-сервер, который даёт ИИ выполнять задачи через локальный Codex (его сильная сторона — код в твоей ФС).
4. **Драйвер данных** поверх SQLite/векторной БД — чтобы «работать с большими объёмами информации»: классифицировать, обновлять, отвечать на вопросы (твоя главная цель).
5. **Каталог** `drivers/index.json` связывает всё: Cowork/Codex читают манифест и активируют нужный драйвер под задачу.

То есть: **не строить всё сразу**, а проложить три-четыре «тропинки» (Sven4-раннер, локальный раннер, данные, файлы) и связать их каталогом — остальное дорастёт по спросу.

## 7. Плюсы и минусы идеи в целом

**Плюсы:**
- Концептуально верно и совпадает с реальным направлением индустрии (MCP/skills/агенты) — не тупик.
- Переиспользует уже построенное: colab-паттерны (манифест, права, очередь, метрики) ложатся на драйверы один в один.
- Решает реальную боль: Sven4-код и локальные программы становятся видимыми ИИ.
- Масштабируется постепенно — можно остановиться на любом уровне.
- «Большие объёмы информации» — именно та задача, где слой драйверов + агентов даёт максимум.

**Минусы / риски:**
- Соблазн построить Уровень 4 сразу → over-engineering без спроса (ты сам это отмечал).
- Запуск непроверенного кода Sven4 — реальная угроза безопасности без песочницы.
- Эксплуатация: поднимать/гасить десятки MCP-процессов — отдельная работа.
- Слишком много активных драйверов → деградация качества ИИ (отсюда обязательная ленивая загрузка).
- Дрейф версий/описаний драйверов (тот же класс проблем, что ты уже ловишь валидатором).

## 8. Риски и предостережения (важно)

1. **Песочница для Sven4 — обязательна.** Непротестированный код нельзя запускать в открытой среде. Минимум — отдельный пользователь/контейнер на сервере, лимиты CPU/памяти/сети, никакого доступа к секретам.
2. **Секреты — вне репозитория.** Токены к серверу/сервисам — через переменные окружения/секрет-стор, не в `drivers/`.
3. **Права как у colab.** Драйверы получают зоны (как `permissions.py`): кто что может запускать. «Финансовые/разрушительные» действия — только с подтверждением человека (D-006).
4. **Right-size.** Строй драйвер только под реальную задачу. «Каталог на будущее» — нормально как черновик (этот файл), но не как код, который надо поддерживать.
5. **Наблюдаемость с первого дня.** Каждый запуск драйвера — в аудит-трейл (как `dialog.md`/`metrics.py`), иначе отладка станет невозможной.

## 9. Пошаговый план (фазы)

**Фаза A — каталог (Уровень 1), 1–2 захода:**
1. Создать `drivers/` и шаблон `drivers/_template.md` (front-matter: `id`, `title`, `kind`, `where: local|server|remote`, `status`, `activation`, `inputs`, `outputs`, `risk`).
2. Описать 5–8 драйверов из каталога раздела 3 как черновики (без кода).
3. Сгенерировать `drivers/index.json` тем же `generate.py` (добавить сбор `drivers/`).
4. Завести задачи в `tasks/` и тему `темы/drivers-layer.md` для обсуждения.

**Фаза B — первый настоящий драйвер (Уровень 2):**
5. Через skill `mcp-builder` обернуть «файлы» или «данные» в локальный MCP-сервер (самый безопасный старт).
6. Проверить, что Cowork/Codex видят его инструменты; записать результат в тему.

**Фаза C — кейс Sven4 (Уровень 3):**
7. На сервере поднять MCP-драйвер над ОДНИМ репозиторием Sven4 (`inspect`/`summary` сначала — только чтение, без запуска).
8. Добавить песочницу и только потом `run`/`test`.
9. Подключить с Windows, проверить сквозной сценарий «вопрос → драйвер → ответ».

**Фаза D — оркестрация над драйверами (Уровень 4, по спросу):**
10. Расширить `dispatch.py`/`risk_gate.py` на драйверы; права; метрики запусков. Только когда драйверов станет реально много.

## 10. Моя рекомендация

- **Начни с Уровня 1 → раннего Уровня 2.** Сделай каталог `drivers/` (дёшево, в твоём стиле) и оберни ОДИН безопасный драйвер (файлы или данные) в настоящий MCP. Это превратит идею из теории в работающую «тропинку» за один-два захода.
