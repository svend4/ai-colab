# MVP-roadmap: Information Workbench Layer

Дата: 2026-06-20
Связано: `docs/ai_middle_layer_architecture_ru.md`, `темы/ai-os-bridge.md`, `темы/agent-pipeline.md`, `tasks/T-025.md`

## Короткий вывод

Проект уже прошёл стадию "просто папка с Markdown" и находится на ранней инженерной стадии локального workbench:

- канон обсуждений, задач, вопросов и решений работает;
- есть генераторы индексов и валидатор;
- есть атомарные id, claim и pipeline;
- есть каталог `drivers/`;
- первый реальный драйвер `repo-runner` уже доведён до read-only реализации;
- появился добровольный heartbeat/live-слой для параллельных агентов.

Но это ещё не полноценная AI-OS, MCP-платформа или серверная система. Текущий правильный статус: **локальный прототип управляемой агентной инфраструктуры**. Его надо развивать не в сторону большого монолита, а в сторону маленьких проверяемых драйверов, индексов и правил безопасности.

## Моё мнение о текущей инфраструктуре

### Плюсы

- **Markdown как источник правды** удобен людям и агентам: можно читать, обсуждать, делать review, коммитить.
- **Шардирование задач/вопросов/решений** уже защищает проект от одного огромного конфликтного файла.
- **`next_id.py` и claim через `O_CREAT|O_EXCL`** решают реальную проблему параллельной работы: два агента не должны брать один номер или одну задачу.
- **`pipeline.py`** добавляет динамику: агент может взять следующую готовую задачу из общего пула.
- **`LIVE.md` + heartbeat** дают живость без горячего общего файла записи: каждый агент пишет свой heartbeat, общий вид генерируется сверху.
- **`drivers/`** правильно отделяет способности проекта от обычной документации. Это зародыш будущего слоя Treiber/Datenadapter/Konnektoren.
- **Read-only-first** хорошо подходит для непроверенного кода и больших корпусов: сначала карта, потом запуск.

### Минусы

- Пока нет настоящей базы корпуса: нет `documents.db`, таблиц документов, chunks, entities, audit_log.
- Нет общего driver schema validator: манифесты драйверов существуют, но обязательные поля и версии схемы ещё не зафиксированы.
- Pipeline уже есть, но нет нормального lease-refresh/heartbeat enforcement для долгих задач.
- Нет серверного или MCP-слоя: агенты работают через файлы и скрипты, а не через стабильный API.
- Нет единого тестового корпуса документов на 10-100 файлов, поэтому трудно проверять file/text/search/report драйверы.
- Нет профиля безопасности для запуска чужого кода: `repo-runner` сознательно read-only, и это правильно, но sandbox-runner ещё не создан.
- PowerShell/командная оболочка в текущей сессии нестабильна; это показывает, что инфраструктура должна уметь продолжать работу через файлы, а не зависеть только от одного runtime.

## Архитектурная стадия

| Слой | Состояние | Оценка |
|---|---|---|
| L0: папка проекта и правила | сделано | рабочее |
| L1: Markdown-драйверы и манифесты | начато | нужно стабилизировать schema |
| L2: локальные Python-драйверы | начато с `repo-runner` | нужен набор 3-5 драйверов |
| L3: SQLite/JSONL память корпуса | не сделано | следующий важный слой |
| L4: индексы поиска | частично только project index | нужен corpus index |
| L5: MCP read-only API | не сделано | после локального MVP |
| L6: plugin/skills distribution | концептуально | после MCP |
| L7: custom agents | частично через AGENTS.md | нужна дисциплина ролей |
| L8: сервер | рано | только после локальной пользы |

## MVP на ближайший этап

Не надо сразу строить большую AI-OS. Минимальный полезный MVP должен доказать одну вещь: агент может безопасно взять большой набор файлов/репозиториев, построить карту, извлечь текст/метаданные, найти информацию и сделать отчёт с источниками.

### MVP-драйверы

1. **`repo-runner`** - ✅ **DONE (T-024, Novax)**. Режим: read-only inventory непроверенных репозиториев. Скрипт `inventory.py` + тесты + fixture-report. Не запускает код.
2. **`file inventory driver`** - следующий. Карта файлов: путь, размер, тип, hash, дата, риск, можно ли читать. Можно строить на базе repo-runner.
3. **`text-extract` driver** - извлечение текста из `.md`, `.txt`, `.pdf`, `.docx`, `.html`; OCR позже.
4. **`search-index` driver** - SQLite FTS/BM25 по документам и фрагментам.
5. **`report` driver** - Markdown/CSV отчёты: что найдено, какие источники, какие пробелы, какие следующие задачи.

Остальное позже: `copy`, `dedupe`, `ocr`, `anonymization`, `timeline`, `evidence`, `portal`, `MCP`.

### Следующий технологический фокус (согласовано Novax + Codex)

1. **driver schema v1** — обязательные поля манифеста и проверка в валидаторе.
2. **file inventory driver** — no-deps Python, reuse repo-runner patterns.
3. **workbench.db schema** — SQLite `documents` + `audit_log`.

MCP и сервер — только после локального MVP.

## Минимальная структура данных

Предлагаю не создавать сразу сложную DDD-модель. Достаточно:

```text
data/
  inbox/
  originals/
  copies/
  text/
  chunks/
  indexes/
  reports/
  audit/
  workbench.db
```

Минимальные таблицы SQLite:

```text
documents(id, source_path, project_path, sha256, file_type, size, title, language, status, pii_level, imported_at)
chunks(id, document_id, chunk_no, heading, text, token_estimate)
entities(id, document_id, type, value, normalized_value)
audit_log(id, timestamp, actor, action, target, result, details)
```

Для начала можно сделать только `documents` и `audit_log`. `chunks` и `entities` добавить после первого extraction.

## Проверки безопасности

Любой новый драйвер должен иметь минимум:

- режим `read-only` по умолчанию;
- `--dry-run`, если он что-то меняет;
- запись в `data/audit/` или `audit_log`;
- тестовую fixture-папку;
- явный список запрещённых действий;
- отсутствие секретов в репозитории;
- понятный выход: Markdown/JSON/CSV.

Для непроверенных репозиториев:

- сначала inventory;
- потом dependency/risk report;
- только потом отдельное решение о sandbox-runner;
- никакого `install`, `test`, `run`, `docker compose up` без отдельной задачи и подтверждения.

## Следующие задачи, которые стоит завести через `next_id.py`

Когда shell снова будет стабилен, я бы завёл такие задачи:

1. `driver schema v1` - обязательные поля манифеста драйвера и проверка в валидаторе.
2. `file inventory driver` - no-deps Python-скрипт для карты файлов.
3. `workbench.db schema` - создать SQLite-схему `documents` + `audit_log`.
4. `text extract driver v0` - `.md/.txt/.html` сначала, PDF/DOCX потом.
5. `search index driver v0` - SQLite FTS по extracted text.
6. `report driver v0` - отчёт по корпусу с источниками и пробелами.
7. `repo-runner MCP design` - только read-only API, без запуска кода.

## Как это должно работать как конвейер

```text
agent -> pipeline.py next
      -> claim task
      -> driver reads/copies/indexes
      -> writes report + audit
      -> pipeline.py done
      -> generate.py
      -> validate.py
```

Если агентов много:

- каждый берёт одну задачу;
- пишет heartbeat при долгой работе;
- не редактирует чужие task/source-файлы без причины;
- большие результаты кладёт в `docs/`, `drivers/`, `data/reports/` или `queues/outbox/`;
- важные изменения объясняет в теме.

## Рекомендация

Следующий технологический фокус: **driver schema + file inventory + SQLite memory**.

Причина простая: без схемы драйверов `drivers/` останется набором хороших текстов; без file inventory невозможно безопасно работать с большим корпусом; без SQLite невозможно строить повторяемый поиск и отчётность. MCP и сервер стоит делать только после того, как локальный слой докажет пользу на реальных файлах.
