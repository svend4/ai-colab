# Политика конвейера воркфлоу

> **Конвейерный слой поверх `docs/workflow-orchestration-policy.md`.** Та политика описывает ОДИН воркфлоу (один кластер под-агентов: §1), запуск в фон и параллелизм нескольких воркфлоу (§3), маршрут результатов сырое→temp→канон (§5), безопасность read-only vs build (§6), пошаговый рецепт (§8). Здесь — то, что НАД ней: как держать **≥2 воркфлоу как конвейер** — ступенчатый запуск, возврат-к-первому по мере прихода результатов, упорядочивание зависимостей, трекинг внимания одним контекстом, восстановление при сбоях. Базовые вещи (что такое воркфлоу, куда коммитить) не повторяю — ссылаюсь.

## 1. Когда конвейер (≥2 воркфлоу) оправдан, а когда хватит одного

Один контекст-оркестратор = один последовательный планировщик с N фоновыми воркерами. Узкое место конвейера — НЕ под-агенты (они и так параллельны внутри воркфлоу), а **оркестратор, простаивающий между запуском и возвратом**, плюс сериализованный хвост (извлечение + коммиты). Конвейер оправдан, когда есть **несколько ортогональных кластеров**, чьи окна вычислений можно наложить друг на друга.

| Ситуация | Решение |
|---|---|
| Один большой вопрос, равномерно фан-аут-able (аудит N измерений, карта N областей), один синтезатор держит все N | **ОДИН воркфлоу** (политика §1). Дробить на N воркфлоу — лишние издержки формулировки/извлечения без выигрыша: под-агенты и так параллельны |
| ≥2 **ортогональных** кластера (разные файлы/темы, ни один не потребляет результат другого) | **Конвейер** — запустить ступенчато, наложить окна |
| Синтез — узкое место: N результатов слишком разнородны для одного синтезатора, или нужны разные схемы вывода | Конвейер: разбить по схеме/выводу, у каждого свой синтезатор |
| Кластеры читают/пишут одни и те же файлы | **НЕ конвейер** — схлопнуть в один воркфлоу (§3: ортогональность — предусловие дробления) |
| Мелкая правка, ответ из контекста | Соло, без воркфлоу (политика §2) |

**Честный предел:** один контекст деградирует на трекинге >2-3 параллельных async-сущностей. Ширина конвейера ограничена не параллелизмом воркеров, а **полосой извлечения+коммита** одного оркестратора. Невыгодно запускать больше, чем успеваешь обработать — непрочитанный результат на диске тратит wall-clock так же, как простой оркестратора.

## 2. Декомпозиция: один или несколько вопросов → ортогональные кластеры

Цель — нарисовать **DAG кластеров**, а не плоский список. Для каждой пары (Wi, Wj) до запуска решить, какая между ними связь (см. §5). Правила:

- **Ортогональны по входам И выходам** (разные файлы, разные схемы, общего ответа нет) → отдельные воркфлоу, запускаются на t0. Идеальные граждане конвейера.
- **Одна тема, но ответ одного НЕ меняет формулировку другого** → дробить. Тематическая связь ≠ связь по данным; примирять только на синтезе.
- **Большой вопрос, части НЕ независимы** (их надо сверять друг с другом) → ОДИН воркфлоу с широким фан-аутом и одним примиряющим синтезатором, а не N воркфлоу с ручной сверкой в голове (именно эту нагрузку конвейер и снижает).
- **Кластер смешивает read-only анализ и build-запись** → дробить по классу контенции: read-only часть — свободно-параллельный воркфлоу (ноль контенции, §6); build-часть — отдельный воркфлоу через worktree или сериализованный коммит. Не давать build-под-агенту и analyze-под-агенту делить кластер — build-половина заставит весь результат ждать `index.lock`.
- **Крупный кластер, где смерть одной ноги дорога** → дробить на больше мелких независимых ног: пере-запускаешь одну дешёвую, а не весь кластер. Мелкий фан-аут = дешёвый salvage.

## 3. Ступенчатый запуск (оркестратор не простаивает)

Формулировка воркфлоу (декомпозиция, схемы) — чистая CPU-работа оркестратора, результата не требует. Поэтому:

1. Запустить **W1** в фон → run id сохранён. **Не ждать.**
2. Сразу сформулировать и запустить **W2**, затем **W3** — всю независимую границу back-to-back.
3. Cap: ~2-4 read-only в полёте; **не более 1 build в общем дереве**, остальные build — через worktree. Стоп на cap или на первой не-выполнимой пока зависимости (барьер).

**Заполнить окно ожидания** приоритетно (строгий порядок против busywork):
1. обработать приземлившийся результат;
2. сформулировать следующий запуск;
3. **предзаготовить хвост**: скрипт извлечения/компоновки в `tmp-work/`, предвыделить канон-путь/ID (схема вывода известна на запуске — пост-результатная работа схлопывается до «прогнать-и-отгрузить»);
4. закоммитить уже извлечённую когорту;
5. read-only разведка под будущие воркфлоу.

**Только premise-safe заполнение:** не коммить в путь, который картирует in-flight анализ. Пока assurance-карта read-only идёт по `tools/`, рефактор-коммит в `tools/` сделает её возвращённую карту описанием дерева, которого уже нет (классический read-modify-write на уровне воркфлоу).

## 3-bis. Непрерывное пополнение — конвейер как ПОТОК, а не ПАРТИЯ (ключевой принцип)

Самая частая ошибка — относиться к конвейеру как к **одной партии из N**: запустил 3 → обработал 3 → пусто → остановка. Это не конвейер, это батч. Конвейер — **поток**: пока обрабатываешь готовый, следующие уже должны бежать. Правила потока:

- **Пополнять ЗАРАНЕЕ, а не после.** Запускать следующую ноду нужно в момент, когда **начинаешь обрабатывать** завершённую (на её RELEASE/REPLENISH-шаге), а не когда полностью её доделал. Иначе между «доделал» и «запустил следующую» — простой, и каждый такой зазор тратит wall-clock впустую.
- **Никогда не осушать in-flight до нуля.** Держать **цель N≥2-4 воркфлоу в полёте на перспективу** (read-only — свободно; build — через worktree). Если счётчик падает к 0 или 1, а полоса коммита позволяет — добить новыми нодами, не дожидаясь, пока дерётся последний.
- **Подтверждение порядка обработки:** завершившийся воркфлоу — **не повод бросать текущую работу** и мгновенно переключаться (это верно, §4 TRIAGE: blocking/топ-value → process, иначе PARK). Но «не переключаться» относится к ОБРАБОТКЕ, а не к ЗАПУСКУ: запуск следующих — дёшев (CPU оркестратора) и должен идти непрерывно, фоном к доработке предыдущего.
- **Источник будущих заданий должен работать постоянно.** Чтобы было чем пополнять, нужен **стоячий перспективный бэклог** — и его надо генерировать тем же конвейером. Держать **воркфлоу-сканер бэклога** (поверхности: открытые `Q-*`, `todo`-задачи, находки `assurance.py`/`drift_check`, разделы «Дальше» в доках, `TODO`/`FIXME`) как **рекуррентную ноду**: его выход — ранжированные launchable-брифы следующей волны. Так конвейер **сам себя кормит**: пока идёт текущая волна, сканер готовит следующую (out-degree сканера максимален — он гейтит все будущие запуски, поэтому идёт первым по топо-сортировке §5).
- **Граница потока — полоса КОММИТА, а не желание.** Запускать ровно столько, сколько успеваешь извлекать+коммитить (§6): непрочитанный `.output` на диске тратит wall-clock как простой. N подбирается под свою полосу обработки, а не под максимум воркеров.

```
ПАРТИЯ (плохо):   [W1 W2 W3]=====> обработка W1,W2,W3 -> ПУСТО -> новая формулировка -> [W4 W5 W6]...
                                                          ^^^^^ простой: конвейер встал

ПОТОК (хорошо):   [W1 W2 W3]==> W1.out -> process+RELEASE -> сразу [W4]   (in-flight снова 3)
                       [W2 W3 W4]==> W2.out -> process+RELEASE -> сразу [W5]   (снова 3)
                            сканер-бэклога всё время готовит W6,W7,W8...  -> очередь не пустеет
```

## 3-ter. Надзиратель конвейера (`tools/conveyor.py`) — внешний глаз

Оркестратор — ОДИН контекст; он сам может «забыть» дозалить, уйти в foreground-стройку и осушить
конвейер до 0-1 (реальный случай: за один ход осталась одна нода, конвейер встал). Дисциплины §3-bis
мало — нужен **внешний процесс-надзиратель**, который видит состояние и сигналит.

- **Реестр** (`logs/conveyor.json`, runtime, gitignored): `conveyor.py launch/land/ship/dismiss <id>`.
  Для `land` предпочтительно указывать `--output <path>`: путь к `.output`, outbox-отчёту или другому
  durable результату, из которого оркестратор сможет извлечь работу без поиска по чату/терминалу.
  На каждом действии пишется **heartbeat** оркестратора.
- **`conveyor.py status`** считает in-flight против цели и печатает ВЕРДИКТ + **exit-код** (1 = нужно
  действие — чтобы за конвейером можно было следить из hook/CI/wakeup):
  - **REFILL** — in-flight < цель (дозалей: `conveyor.py next` берёт кандидатов из перспективного бэклога);
  - **PROCESS** — есть приземлившиеся, ждущие обработки;
  - **IDLE** — heartbeat устарел > порога: оркестратор замолчал (завис или забыл тикнуть).
- **Дисциплина:** на КАЖДОМ пробуждении (нотификация о завершении воркфлоу ИЛИ сообщение) —
  `conveyor.py tick` + `status`; на REFILL — запустить. `land --output <path>` переводит inflight→landed
  (in-flight падает) и сохраняет машинную ссылку на результат; `land` без output допускается как аварийная
  отметка, но `status` поднимает `PROCESS-MISSING-OUTPUT`, пока результат не привязан или workflow не
  списан через `dismiss --reason`. Так «не осушать до нуля» становится **проверяемым**.

**Как держать оркестратора активным** (он событийный — просыпается на нотификациях воркфлоу и сообщениях):
1. **Нотификации сами ре-инвокируют** оркестратора при завершении каждого воркфлоу — на каждой запускать
   `status` и дозаливать. Пока ≥1 в полёте, петля само-поддерживается.
2. **Hook** (Claude Code, `.claude/settings.json`) — `Stop`-hook, печатающий вердикт после каждого ответа:
   ```json
   { "hooks": { "Stop": [ { "hooks": [ { "type": "command", "command": "python tools/conveyor.py status" } ] } ] } }
   ```
3. **`ScheduleWakeup` / cron** — таймерный heartbeat на случай, когда ВСЁ осушилось и нотификаций нет:
   разбудить, прогнать `status`, дозалить из бэклога. Это единственный путь пережить полное осушение.

Надзиратель не запускает воркфлоу сам (он read-mostly, граница observe) — он **сигналит**, а решение и
запуск остаются за оркестратором (как `friction.py` сигналит, а `cohort.py` исполняет).

**Масштаб флота — цель НЕ зашита в 2.** `conveyor.py target <N>` поднимает цель под надобность: при
многих открытых вопросах запускают **флот** — по воркфлоу на вопрос (5, 8, больше). Запуск дёшев и
параллелен, поэтому ПРОИЗВОДСТВО масштабируется свободно. **Но потолок — полоса ОБРАБОТКИ одного
оркестратора:** результаты приземляются в очередь `landed`, а извлечь/перепроверить/закоммитить их можно
только серийно. Поэтому target поднимают до уровня, который успеваешь обрабатывать; если `landed`-очередь
растёт быстрее обработки — надзиратель печатает `PROCESS: N ждут`, и это сигнал НЕ запускать ещё, а
разгребать (непрочитанный `.output` тратит wall-clock как простой, §6). Технические потолки фан-аута
(≈16 агентов на воркфлоу, 1000 на прогон) — высоко над реальной нуждой; первым упирается полоса коммита.

## 4. Конвейерная петля: возврат-к-первому

Ядро конвейера — обрабатывать тот воркфлоу, что **уведомил первым**, даже вне порядка запуска, пока остальные идут. Batch-wait (запустить N, ждать ВСЕХ, потом трогать) тратит всё окно вычислений ранних финишёров.

```
Цикл (на каждое уведомление .output):
  1. TRIAGE, не process: сопоставить label с реестром (§6).
     обрабатывать СЕЙЧАС если: (a) на нём кто-то заблокирован, или
     (b) это топ-value когорто-отгружаемый. Иначе → LANDED-PARKED, вернуться к safe-fill.
  2. RETURN+REDUCE: перед тем как трогать дерево — 3 строки (§6).
  3. GATE результат (§8): парс-схема, не-truncated, покрытие, adversarial-проверка.
  4. EXTRACT → tmp-work → канон-док (политика §5), пометить proposed.
  5. RELEASE dependents: если этот результат разблокировал отложенную ноду — сформулировать+запустить её сейчас.
  6. SHIP когортой (§7), не по-результатно.
  7. REPLENISH: освободившийся hot-слот добить новой нодой, если полоса коммита позволяет и нет невыполненной зависимости. Иначе держать.
```

Никогда не сливать к нулю in-flight: добивать счётчик к cap, пока граница зависимостей не исчерпана.

## 5. Упорядочивание зависимостей: барьер vs конвейер

Классифицировать КАЖДОЕ ребро **до** запуска, не во время. Тест формулировки: *потребляет ли payload запуска Wj (промпт/схема под-агентов) ЗНАЧЕНИЕ, которое производит Wi?*

- **BARRIER** — да: формулировка Wj должна содержать значение из результата Wi (напр. «проверь модули, которые Wi пометил рискованными»). НЕ ко-запускать. Запустить Wi сейчас, держать шаблон Wj, запустить Wj ровно на шаге extract, когда значение Wi в руках.
- **PIPELINE** — нет: Wj лишь тема-связан или может бежать по супер-множеству, которое Wi сузил бы. Запустить оба параллельно; обрезать результат Wj по Wi на синтезе. Размениваем немного лишней работы под-агентов на сэкономленное сериализованное ожидание.

**Дефолт — PIPELINE; барьер требует позитивного доказательства.** Над-объявление барьеров схлопывает конвейер обратно в одиночный воркфлоу, который базовая политика уже покрывает.

Порядок головы конвейера — по **out-degree** (фан-аут того, что результат разблокирует), не по важности: воркфлоу, чей результат — предусловие для бо́льшего числа других (или для рискованнейшего build), идёт первым. Это топологическая сортировка с одной исполняющей головой.

**Никогда не строить на не-вернувшемся результате.** Дренаж — в порядке ЗАВИСИМОСТЕЙ, не прихода: приземлившийся лист, чей ограничивающий родитель ещё бежит, НЕ готов — парковать до возврата родителя.

**Две сортировки раздельны:** информационная зависимость управляет ЗАПУСКОМ; контенция записи управляет КОММИТОМ. Конвейер широк на read-стороне, узок (или worktree-шардирован) на write-стороне. Два build, чьи анализы шли параллельно, но пишущие в один канон-путь, сериализуются или шардируются по worktree — даже если чтения были полностью параллельны.

**Побочные ответвления (политика §4) — НОВАЯ нода, не правка in-flight:** запущенный фоновый воркфлоу immutable, инжектировать follow-up в его замороженную формулировку нельзя. Маршрут по форме: декомпозируемый кластер → новый воркфлоу (в хвост, или вперёд, если он теперь гейтит ожидающие build); конкретный код параллельно другим → worktree (`parallel-work-policy`, Уровень-1); спорное/меж-агентное (трогает зону Codex, политика/архитектура) → котёл (`pipeline.py`-задача, D-018), НЕ соло-build. При вставке ноды, меняющей критический путь, — пере-топо-сортировать остаток.

## 6. Внимание/трекинг: реестр, порядок возвратов, когда СТОП

Один контекст не держит >2-3 in-flight интентов. Внешняя память обязательна.

- **Реестр in-flight** (одна строка на воркфлоу), обновлять на каждом запуске и приземлении. Колонки: `label | вопрос-кластера | схема | depends-on | действие-при-приземлении | state`. Машина состояний: `PLANNED → INFLIGHT → LANDED-PARKED → SHIPPED | DISCARDED`. Temp `.output`-файл (политика §5) — durable память; строка реестра — ключ регидрации.
- **Стабильный семантический label** на запуске (`verb-topic-type`, напр. `W2-assurance-map-RO`), один и тот же в реестре, в temp-имени, в коммите/доке. Никогда «первый/другой» — фоновые запуски возвращаются вне порядка, позиционные имена молча пере-привязываются.
- **Порядок возвратов: BLOCKING-FIRST → VALUE-FIRST → FIFO**, не порядок прихода. Порядок прихода случаен (фоновый планировщик); обработка по приходу максимизирует context-thrash.
- **Hot cap 3** «горячих» в голове; остальное — холодное, живёт строкой реестра + temp-файлом, регидрируется по требованию.
- **3-строчное landing-summary** ДО любого build/commit: (1) одно решение/число, что дал результат; (2) подтверждает/противоречит/расширяет соседа; (3) единственное следующее действие. Возврат к холодной ноде потом стоит 3 строки, а не пере-чтение JSON.
- **СТОП запускать**, когда: реестр достиг cap; новый вопрос зависит от не-приземлившегося результата; общее дерево всё равно заставит сериализовать коммиты. **Полоса КОММИТА, а не фан-аут, задаёт ширину.**
- **Cross-link после каждого возврата:** если результат сделал соседа избыточным/неверным — пометить его строку `DISCARDED`, чтобы его приземление игнорировалось, а не обрабатывалось вслепую в дубль/противоречие.

## 7. Маршрут документов сырое→temp→канон

Повторно используем правило политики §5 (не переопределяем):

```
сырой .output  →  harness temp (НЕ в репо)  →  извлечение  →  tmp-work компоновка  →  канон-док  →  commit
```

Конвейерные добавки: (1) предзаготовить компоновщик в `tmp-work/` в окне ожидания; (2) **отгружать когортой**, не по-результатно — несколько приземлившихся результатов в один commit, чтобы минимизировать churn `index.lock` против Codex; (3) коммит через `tools/cohort.py guard` → Уровень-0 `ship` (свои файлы, selective-add, НЕ `git add -A`) или Уровень-1 worktree + `merge_gate` (если guard флагнул hot/shared-файлы или это build).

## 8. Восстановление при сбоях и контенции

Приземлившийся `.output` — это **ПРЕТЕНЗИЯ, не факт.** Гейтить до канона/дерева (политика §7: перепроверка синтезатором + adversarial).

- **Parse-gate на возврате:** схема валидна? не truncated? покрывает спрошенное? adversarial-проверка (само-ревью синтезатора или дешёвая независимая verify-нога — независимая перспектива ловит уверенно-неверное лучше само-аттестации). Вердикт GOOD / PARTIAL / BAD.
  - **GOOD** → extract.
  - **PARTIAL** (часть ног мертвы/слабы) → salvage хороших ног в provisional-док + пере-запуск ТОЛЬКО недостающих ног. Схему синтезатора проектировать с полем `coverage/missing`, чтобы N-1 хороших ног давали partial-but-valid, а не fail-closed.
  - **BAD** → resume по runId: пере-запустить кластер; при второй смерти — сузить вопрос или соло-зонд разведать форму.
- **Идемпотентность по runId:** держать per-runId маркер (`launched/landed/extracted/committed`). Уведомление может пере-сработать, оркестратор может прерваться. На re-entry — пере-вывести state с диска (существует ли закоммиченный док?) и пропустить уже-committed run, не дублировать карту.
- **Сериализация коммитов TTL-локом:** `tools/commit_lock.py acquire <agent> --ttl <T> --wait <W>` — атомарный O_EXCL захват с `lease_epoch` TTL и stale-takeover (мёртвый держатель само-исцеляется по истечении lease; доказано `tools/test_commit_lock.py`). TTL > worst-case generate+add+commit, иначе подорвёшь свой же in-flight коммит. `release` после.
- **Изоляция > сериализация для контенди-работы:** когда под-агенты ПИШУТ код (build) или результат трогает hot-файлы (guard `cohort.py` срабатывает на `TASKS.md`/`generate.py`/`index.json`), эскалировать в Уровень-1 — каждый writer в своём worktree (`tools/worktree.py`) на `agent/<agent>/<task>`, слияние через `tools/merge_gate.py`. Изоляция убирает гонку, а не очередит на ней.
- **Зависимый — только на проверенном родителе:** если W_b нужен канон-док W1, запускать W_b ТОЛЬКО после gate+extract W1; иначе W_b фан-аутит по «яду». Провалившийся/partial родитель блокирует своих dependents, но не independents.

## 9. Сквозной пример (реальная сессия: три воркфлоу одновременно)

Запрос: (W1) карта instruction-assurance по `tools/` для Q-016; (W2) эта самая методичка конвейера; (W3) merge доков для Q-017. Все три — read-only анализ; W2 и W3 ортогональны W1, между собой тоже. Гипотетическое ребро для иллюстрации барьера: build-нога «закрыть найденный assurance-gap» зависит от W1.

```
t0   запустить W1-assurance-map-RO   (read-only фан-аут по tools/)   -> фон, runId, premise HEAD=9fa0e13
t0+  сформулировать+запустить W2-conveyor-methodology-RO              -> фон   (без ожидания)
t0+  сформулировать+запустить W3-docmerge-Q017-RO                      -> фон   (без ожидания)
     in-flight: {W1, W2, W3}   build-follow-up НЕ запускаем (барьер на W1)
[fill] tmp-work/compose_assurance.py, compose_methodology.py, compose_docmerge.py;
       предвыделить docs/instruction-assurance-2026-06-23.md и темы/q017-docmerge-2026-06-23.md;
       коммитить ТОЛЬКО premise-disjoint файлы (НЕ под tools/, которую картирует W1)

>> W1.output приземляется ПЕРВЫМ (W2/W3 ещё формулируются/бегут) -> RETURN-TO-FIRST
   triage: на нём заблокирован build-follow-up + топ-value -> process сейчас
   git diff 9fa0e13..HEAD -- tools/  (Codex трогал tools/? если да — ре-валидировать карту)
   parse-gate: схема ASSURANCE валидна, покрытие полное -> GOOD
   3 строки: (1) цепь metadata->preflight->evidence->gate; (2) независим от W2/W3; (3) extract->канон->ship
   extract -> tmp-work -> docs/instruction-assurance-2026-06-23.md (proposed)
   RELEASE: барьер снят -> сформулировать+запустить build-follow-up в СВОЁМ worktree (фон)
   in-flight: {W2, W3, build-follow-up}   (добит, не слит к 0)

>> W3.output приземляется, пока компонуется W2
   triage: не блокирует, не топ-value -> LANDED-PARKED, продолжить W2

>> W2.output приземляется -> reduce
   cross-link: W3 теперь вливается В раздел W2 -> W3 помечен DISCARDED-as-standalone (merge, не двойная отгрузка)
   cohort-guard -> Уровень-0 ship: assurance + methodology одним commit (минимум index.lock-churn против Codex)

>> build-follow-up.output приземляется
   parse-gate -> Уровень-1 merge_gate из worktree (commit_lock.py) -> ship build

LEDGER CLOSE: все label SHIPPED/DISCARDED, ни одного orphan .output. Когорта закрыта.
```
Итог: W2 и W3 полностью спрятались под критическим путём W1→build; оркестратор не простаивал — каждое окно держало извлечение, staging или коммит.

## 11. Краткий рецепт (step-by-step)

1. **DAG-first:** перечислить кластеры, нарисовать рёбра, разметить BARRIER vs PIPELINE (§5). Топо-сортировка по out-degree.
2. **Реестр открыть:** строка на каждый кластер (label, схема, depends-on, on-land, state=PLANNED) (§6).
3. **Ступенчатый запуск:** W1 в фон → не ждать → сформулировать+запустить W2, W3 — всю независимую границу. Cap ~2-4 RO, ≤1 build в общем дереве. Записать runId + premise HEAD.
4. **Заполнить окно** premise-safe приоритетом: предзаготовить компоновщики/канон-пути, коммитить только disjoint-файлы (§3).
5. **На уведомлении — TRIAGE:** blocking/топ-value → process; иначе PARK (§4, §6).
6. **RETURN-TO-FIRST + REDUCE:** 3 строки до дерева; parse-gate (GOOD/PARTIAL/BAD, §8).
7. **EXTRACT → tmp-work → канон** (proposed), idempotent-маркер по runId (§7, §8).
8. **RELEASE dependents** (барьер снят → запустить ноду), **REPLENISH** hot-слот.
9. **SHIP когортой** через cohort guard → Уровень-0 ship / Уровень-1 worktree+merge_gate; коммит-лок TTL self-heal (§7, §8).
10. **Cross-link соседей**, ответвления — новая нода/worktree/котёл, не правка in-flight (§5).
11. **LEDGER CLOSE:** все label SHIPPED/DISCARDED, ни одного orphan .output — тогда когорта закрыта (§6).
