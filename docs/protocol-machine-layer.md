# Машинный Слой Протокола (Machine Layer)

Документ описывает **детерминированные правила**, обязательные для исполнения всеми AI-агентами и скриптами. В отличие от базового `PROTOCOL.md`, эти правила лишены "гуманитарного" субъективизма (такого как "делай небольшие улучшения" или "остановись, если не уверен").

Каждое правило здесь может быть провалидировано парсером.

## 1. Запрет на "неуверенность" (Эскалация)
Агент не имеет права "взять паузу и ничего не делать". Если агенту не хватает контекста, прав, или он сомневается в решении, он **обязан** перевести задачу в статус `BLOCKED` и сформировать машиночитаемый блок эскалации:

```yaml
blocked_by: "Причина блокировки (например: не найден файл X)"
needed_input: "Что конкретно ожидается (например: утвердите план Y)"
last_attempt: "YYYY-MM-DD HH:MM"
next_unblock_check: "Ожидание ответа от User"
```
Этот блок пишется в конец отчета (в `queues/outbox/` или в рабочий claim).

## 2. Вопросы как Объекты
Если агенту нужно задать вопрос человеку или другому агенту, он не имеет права просто "оставлять комментарии в тексте".
Агент обязан создать в `QUESTIONS.md` объект по шаблоному формату:

* **ID:** `Q-XXX` (уникальный)
* **Owner:** Имя агента или `human`
* **Decision Needed:** Суть вопроса
* **Deadline:** Ожидаемый срок или `none`

## 3. Гранулярный трекинг (Action Items)
Любые предложения по коду, рефакторингу или изменениям (Action Items) внутри отчетов агента **обязаны** оформляться в виде Markdown-чекбоксов.
Запрещено писать действия сплошным текстом.
Пример правильного оформления:
```md
- [ ] Заменить функцию X на Y в файле Z.
- [x] Добавить тесты (Выполнено в коммите ABC).
```
Статус отчета вычисляется автоматически на основе отношения `[x]` к `[ ]` внутри файла.

## 4. Требования к Отчетам (Outbox)
Любой отчет агента в `queues/outbox/` или в `streams/` должен завершаться формальным подвалом из двух секций:

### `## Applied instructions`
Список скиллов (Skills) или инструментов, которые агент осознанно применил (например, `cauldron-synthesis`, `view_file`).

### `Checks:`
Список консольных команд, которые агент запустил для самопроверки, и их статус (`OK` / `FAIL`). Если агент ничего не запустил — он обязан написать `None`.
Пример:
```text
Checks:
- python tools/generate.py -> OK
- py -3 -m pytest tools/tests/ -> OK
```

## 5. Контроль побочных эффектов (Dry-run by default)
Любая служебная утилита (`tools/`), которая меняет Primary State (базовые файлы, задачи, индексы), обязана:
1. По умолчанию работать в режиме **`dry-run`** (только чтение и вывод плана изменений).
2. Применять изменения только при явной передаче флага `--apply` (или `--force`).
Исключением являются скрипты диагностики и чтения (`status`, `list`).

## 6. Изоляция Инструментов
При падении скриптов (`exit code != 0`), утилиты **обязаны** писать Traceback и любые человекочитаемые ошибки в `stderr`.
Поток `stdout` резервируется исключительно для чистых данных (например, JSON) и успешных ответов `--help` (exit code 0).

## 7. Безопасность Данных (Data Loss Guard)
Для предотвращения случайного обнуления или обрезки файлов при массовых изменениях (bulk edit):
- **ЗАПРЕЩЕНО** использовать сырой `open(filepath, "w").write(new_content)` для редактирования существующих файлов.
- **РАЗРЕШЕНО** использовать `from tools._ioutil import safe_write` и вызывать `safe_write(filepath, new_content)`.
- Если файл новый — `safe_write` запишет его штатно.
- Если файл существует, `safe_write` проверит объем удаляемых данных. Если удаляется более 15% ИЛИ более 20 строк, он выбросит `DataLossGuardException` и прервет операцию.
- Если массивное удаление строк было вашим **намерением**, явно укажите: `safe_write(..., force_truncate=True)`.
