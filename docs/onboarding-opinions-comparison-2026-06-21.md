## 2. Краткое различие позиций

### 2.1. Claude / `agent-onboarding.md`

Сильная сторона: документ хорошо подходит человеку и новому агенту, который впервые видит проект. Он не начинает с истории commit-ов, а объясняет настоящее состояние: карта возможностей, роли, рабочий цикл, Q&A, проблемы коллективной работы, свежая критика и идеи.

Основной акцент: сделать систему понятной и самопоясняющей. Важны вопросы типа: как несколько агентов не мешают друг другу, как не терять обоснование правок, как бороться с docs drift, как не застрять в мета-работе.

Риск: документ широкий. Если не поддерживать его проверками, он может стать ещё одним большим текстом, который устареет.

### 2.2. Codex / `top-agent-operating-manual.md`

Сильная сторона: документ больше похож на рабочую карту для агента. Он явно называет control plane, capability plane, dialog plane, safety plane; показывает команды; даёт micro-skills; предлагает автоматизацию середины пирамиды.

Основной акцент: агент должен не просто читать, а быстро понять, что можно делать, что запрещено, какие команды запускать и куда записывать результат.

Риск: частично пересекается с `agent-onboarding.md`. Без ясного разделения ролей два документа могут начать конкурировать.

### 2.3. Codex recheck / `architecture-docs-recheck-2026-06-21.md`

Сильная сторона: документ связывает раннюю идею "середины пирамиды" с текущим состоянием. Он честно фиксирует: система уже не просто папка с Markdown, но ещё не execute/AI-OS платформа.

Основной акцент: стадия реализации, плюсы/минусы, P0/P1/P2 предложения, read-only граница, T-020/svend4 как unresolved blocker.

Риск: это не onboarding и не инструкция. Он полезен для оценки зрелости, но новый агент не должен начинать только с него.

### 2.4. `bridge-usage.md` и `layers-coverage.md`

Сильная сторона: это короткая factual baseline. Они меньше философствуют и больше фиксируют, что прямо сейчас работает: 9 drivers, sync acceptance 27/27, L6 через SQLite/FTS5/reports, safety boundaries, execute forbidden until sandbox.

Риск: если эти документы устареют, они будут опаснее длинных дискуссий, потому что выглядят как актуальная справка.

## 3. Общий консенсус

Ниже пункты, где документы в целом сходятся.

### C1. Нужны оба уровня документации: человеко-читаемый вход и агентский manual

`agent-onboarding.md` лучше как первый вход для человека/агента.  
`top-agent-operating-manual.md` лучше как операционная карта действий и micro-skills.

Решение на сейчас: оставить оба, но явно связать роли и добавить drift-control. Не объединять прямо сейчас.

Очередь: связано с `T-126`.

### C2. Текущая стадия — read-only middle layer, не execute AI-OS

Система уже имеет control plane, pipeline, drivers, skills, L6 memory/reporting и validation. Но запуск чужого кода, svend4 execute, sandbox runner и автономная AI-OS ещё не реализованы.

Практический вывод: нельзя расширять read-only drivers до execute "по привычке". Любой execute требует отдельного accepted decision, sandbox, audit, limits и rollback.

Очередь: спорная часть по T-020 вынесена в `Q-013`.

### C3. `pipeline.py` должен быть главным task engine

Все свежие документы фактически говорят одно: живой конвейер уже строится вокруг `pipeline.py`, claims, done/fail, snapshot, heartbeat. Старые следы `queue.py` во входных инструкциях должны быть очищены или явно помечены как legacy/forum layer.

Очередь: `T-124`.

### C4. Нужен единый machine-readable capability manifest

Люди могут читать Markdown, но агентам нужен короткий машинный снимок: слои, drivers, команды, safety, maturity, ссылки на docs.

Это не замена документации, а индекс поверх неё.

Очередь: `T-129` уже реализовал этот пункт; `T-125` закрыта как merged/duplicate.

### C5. Нужна одна команда входа нового агента

Новый агент сейчас должен вручную читать несколько файлов и запускать несколько команд. Это медленно и создаёт ошибки.

Команда `tools/onboard.py` должна собрать короткий briefing: pipeline, blockers, docs, safety, актуальные capabilities.

Очередь: активная задача `T-131`; `T-128` закрыта как merged/duplicate.

### C6. Нужен docs drift detector

Проект уже сталкивался с устаревшими числами и статусами. В многоагентной среде drift опасен: следующий агент принимает устаревший документ за истину.

Очередь: активная задача `T-130`; `T-126` закрыта как merged/duplicate.

### C7. Следующий прирост ценности должен идти через реальные read-only данные

Мета-инфраструктура стала достаточно богатой. Теперь нужно проверить её на большем безопасном corpus или read-only источнике, иначе есть риск строить красивую систему вокруг самой системы.

Очередь: `T-127`.

### C8. T-020/svend4 нельзя держать как мутный полублокер

Все документы сходятся: без read-only источника или нового решения эта ветка не двигается. Нужно одно из трёх: дать безопасный read-only source, переформулировать задачу в generic repo inventory, либо закрыть/заморозить blocker.

Обсуждение: `Q-013`. Дополнительный вопрос Claude о домене vs generic — `Q-014`.

### C9. Worktree/изоляция агентов нужна, но сначала как эксперимент

Проблема реальна: несколько агентов могут конфликтовать при правке generated indexes, docs и tasks. Но обязательный worktree на всех сразу усложнит процесс.

Позиция: провести ограниченный эксперимент, измерить пользу, затем решать.

Обсуждение: `Q-013`.

### C10. L5 plugin packaging лучше отложить

Project-local skills уже полезны. Упаковка в plugin имеет смысл после повторного применения в нескольких проектах или если понадобится install/update lifecycle.

Обсуждение: `Q-013`.

## 4. Плюсы текущей системы

1. **Файловая прозрачность.** Люди и агенты видят одни и те же Markdown/JSON/manifest файлы.
2. **Append-only культура.** История обсуждения не переписывается, решения фиксируются отдельно.
3. **Pipeline claims.** Есть атомарное взятие задач, done/fail, snapshot, heartbeat.
4. **Разделение safety границ.** Read-only drivers не смешаны с execute.
5. **Самопроверка.** `validate.py`, generated indexes, driver acceptance и regression tests дают минимум инженерной дисциплины.
6. **Слои уже различимы.** L2 drivers, L3 skills, L6 memory/reporting, L7 orchestration не лежат в одной каше.
7. **Форумная модель работает.** `topics/`, `queues/outbox/`, `tasks/`, `questions/`, `decisions/` уже создают асинхронный полилог.

## 5. Минусы и риски

1. **Документов становится много.** Без navigation/drift-check новый агент может утонуть в правильных, но длинных текстах.
2. **Есть дублирование onboarding/manual.** Пока оно полезное, но может стать рассинхроном.
3. **Система всё ещё часто говорит о себе.** Нужен больший внешний или прикладной corpus.
4. **Один workspace плохо масштабируется на много агентов.** Append-only помогает, но не решает git/generate conflicts полностью.
5. **T-020 висит как шум.** Orphan/blocker в pipeline ухудшает картину готовности.
6. **Нет единого machine-readable state.** Есть `drivers/index.json`, `index.json`, logs, но нет одного system capability snapshot.
7. **Onboarding всё ещё ручной.** Новый агент должен знать, какие команды запускать.

## 6. Спорные пункты и как их решать

Спорные пункты вынесены в `Q-013`. Для каждого нужен не вкус, а доказательство:

| Спор | Что считать доказательством |
|---|---|
| Один документ или два | Новый агент должен найти нужные команды и safety boundaries быстрее; drift-check не должен ловить расхождения. |
| Worktree сейчас или позже | Тест с двумя агентами: меньше конфликтов и меньше ручного merge-time, чем в одном workspace. |
| Больше автоматизации или больше данных | Задачи T-124..T-128 должны уменьшить время входа/ошибки, а T-127 должен показать качество обработки корпуса. |
| Plugin packaging | Есть минимум 2-3 повторных применения skill/driver вне проекта или явная потребность install/update. |
| T-020/svend4 | Есть безопасный read-only source или человек выбирает reframe/close. |
| Доменный юридический workbench или generic-инструмент | Ответ Stefan в `Q-014` и типы реального корпуса: PDF/DOCX, Markdown/TXT, репозитории, базы. |

## 6.1. Уточнение: duplicate card != variant

После замечания Stefan важно уточнить правило. Закрытие `T-125`, `T-126`, `T-128` как `merged/duplicate`
означает только одно: в **исполнительной очереди** не должно быть двух одинаковых claim-слотов, чтобы два
агента не делали один и тот же файл/команду вслепую.

Это не означает, что альтернативный вариант решения исчезает. В многоагентной системе надо различать:

| Ситуация | Что делать |
|---|---|
| Две карточки описывают один и тот же исполнительный шаг | Оставить один canonical task, вторую закрыть как `merged/duplicate`, поставить ссылку на canonical task. |
| Два агента предлагают разные технические подходы | Не закрывать как простой duplicate. Оформить варианты A/B/C в теме, вопросе или design note. |
| Один агент уже реализовал первый вариант | Другой агент всё равно может добавить critique/alternative, но не должен параллельно менять тот же файл без claim/координации. |
| Вариант выглядит хуже | Зафиксировать почему: критерий, риск, тест, стоимость, влияние на safety. Не удалять молча. |
| Вариант выглядит лучше | Создать follow-up task или proposed decision, а существующую реализацию считать baseline для сравнения. |

Правильная модель ближе к "форкам под темы": общий вопрос остаётся один, но внутри него могут идти
параллельные ветки `variant-A`, `variant-B`, `variant-C`. Консенсус появляется не потому, что один агент
первым занял карточку, а потому что варианты сравнили по доказательным критериям.

Для текущего случая:

- `T-129` остаётся canonical execution task/result для capability manifest;
- `T-125` закрыта как дубликат **очереди**, но Codex-вариант требований к manifest сохранён в тексте `T-125` и в этом документе;
- `T-130` остаётся canonical execution task для drift detector;
- `T-126` закрыта как дубликат очереди, но его критерии drift-check остаются полезным input для `T-130`;
- `T-131` остаётся canonical execution task для onboarding command;
- `T-128` закрыта как дубликат очереди, но его ограничения "no state change by default" и "heartbeat/claim только явным флагом" должны быть учтены в `T-131`.

Вывод: дубли надо **схлопывать на уровне управления работой**, но **не схлопывать на уровне мышления**.
Очередь требует одного исполнителя на шаг; архитектура требует сохранения и сравнения вариантов.

Рекомендуемый порядок:

1. **T-124 — quickstart pipeline cleanup.** Убрать противоречие `queue.py` vs `pipeline.py` во входных инструкциях.
2. **T-129 — system capabilities manifest.** Уже сделано параллельно Claude: `tools/capabilities.py` и `system-capabilities.json`.
3. **T-130 — docs drift detector.** Закрепить актуальность ключевых чисел и статусов.
4. **T-131 — tools/onboard.py.** На основе manifest/docs дать одну команду входа нового агента.
5. **T-127 — larger safe corpus.** Проверить L6 workflow на 50-200 безопасных read-only файлах.

Это намеренно смешанный порядок: сначала убрать явные трения входа, затем дать агентам машинную карту, затем перейти к реальным данным.

## 8. Мнение Codex

Моя оценка: текущая система находится в хорошей инженерной точке для read-only middle layer. Она уже достаточно структурирована, чтобы несколько людей и агентов могли работать асинхронно, но ещё недостаточно автоматизирована, чтобы называть её самостоятельной AI-OS.

Самый сильный элемент — не конкретный драйвер, а цикл: задача -> claim -> работа -> report -> generate -> validate -> snapshot -> discussion. Это уже "движок" в минимальном смысле.

Самый слабый элемент — вход и актуальное состояние. Новый агент видит много документов, но не получает один проверенный briefing и один machine-readable state. Поэтому `system-capabilities.json`, `onboard.py` и drift detector важны не как украшение, а как следующая автоматизация середины пирамиды.

Второй слабый элемент — мало реальных данных. Без T-127 проект рискует стать системой управления собственными отчётами. Поэтому после малых инфраструктурных задач нужно обязательно перейти к corpus/report workflow.

Третья граница — execute. Здесь я бы не ускорялся. Read-only слой уже полезен; запуск чужого кода должен появиться только через отдельный sandbox design и accepted decision.

## 9. Как продолжать обсуждение

1. Общие пункты брать из `T-124..T-128`.
   После синхронизации с параллельной работой Claude актуальная очередь: `T-124`, `T-127`, `T-130`, `T-131`; `T-129` уже done; `T-125`, `T-126`, `T-128` закрыты как merged/duplicate.
2. По спорным пунктам отвечать в `Q-013` или в `topics/ai-os-bridge.md`.
   По цели проекта domain vs generic отвечать в `Q-014`.
3. Каждый ответ должен содержать: вариант, аргумент, проверку/пример, риск, рекомендацию.
4. После появления доказательной базы создать proposed decision. Accepted decision должен делать человек или явно назначенный сборщик.

Дополнительное правило после замечания Stefan: если "дубль" содержит самостоятельный технический вариант,
то он должен быть перенесён в design comparison, а не просто снят с очереди. Canonical task отвечает за
исполнение; variant note отвечает за качество выбора.

Итог: consensus есть на ближайшие практические шаги. Расхождения не блокируют работу, если держать их в `Q-013` и проверять через маленькие эксперименты.
