# Методика Self-Reflection (Dogfooding) для Агентов

Эта методичка описывает стандартный процесс, с помощью которого любой агент может тестировать и выявлять слабости нашей архитектуры, используя наш собственный код как "внешний".

## Зачем это нужно?
Перед тем как система столкнется с реальным, непредсказуемым внешним кодом (через svend4 или другие драйверы), мы обязаны убедиться, что наши инструменты Read-Only статического анализа работают безупречно. "Скармливая" песочнице наши собственные сложные драйверы и скрипты, мы выявляем слепые зоны (например, жестко закодированные пути, отсутствие семантического понимания импортов, ошибочную классификацию файлов).

## Пошаговое руководство (Алгоритм для Агента)

### 1. Изоляция (Копирование в Песочницу)
Возьмите целевую директорию (например, `drivers/`, `sandbox/` или `indexes/`) и скопируйте ее в изолированную среду для входящих данных:
```powershell
mkdir -p sandbox/inbox/self_reflection_<target>/
cp -R <target>/* sandbox/inbox/self_reflection_<target>/
```
> **ВАЖНО:** Никогда не запускайте файлы из `sandbox/inbox` напрямую! Работайте с ними строго как с текстом.

### 2. Запуск Инструментов Аналитики (Read-Only арсенал)
Прогоните инструменты статического само-анализа. **Базовый intake** (по конкретной папке/файлу):
*   `python tools/result_intake.py classify sandbox/inbox/self_reflection_<target>/<file.py>`
*   `python tools/dir_health.py sandbox/inbox/self_reflection_<target>/`
*   `python tools/sandbox_intake_demo.py sandbox/inbox/self_reflection_<target>/`

**Целостность и переносимость всего среза (наши сильнейшие зеркала):**

| Инструмент | Что находит в «броне» |
|---|---|
| `python tools/portability_check.py` | **истинная песочница clone-and-run** — материализует git-tracked HEAD в чистый temp, ищет хост-зависимости/хардкод путей/несамодостаточность (то, что ломается у того, кто склонирует) |
| `python tools/edges.py check` | дефекты графа связей: висячие рёбра атом→атом, циклы depends_on, темы без файла, изоляты |
| `python tools/blocks.py run self` | кластер: audit (детекторы дефектов) + adoption (применяемость) разом |
| `python tools/blocks.py run structure` | папки + визитки + слои L1-L4 + heading-дерево (C-07/C-10/C-11) |
| `python tools/validate.py` | контракт канона (front-matter, артефакт-presence, инварианты) |
| `python tools/adoption.py` | dormant-инструменты, doc-only решения, orphan-доки (применяется ли накопленное) |
| `python tools/decision_propagation.py` | «решение принято, но не дошло до исполнения» (корень svend4-провала) |

*Примечание: Если инструмент падает, сканирует весь проект вместо указанной папки, или его «зелёный» вердикт ПРЯЧЕТ проблему (молчаливое исключение категории) — это уже найденная брешь.*

### 3. Синтез и Оценка (Выявление Плюсов и Минусов)
Соберите результаты выполнения утилит. Проанализируйте:
*   **Слепые зоны:** Чего не видят наши инструменты? (Например, они могут считать `.py` файлы просто текстом, не понимая графа импортов).
*   **Ошибки классификации:** Сработал ли `result_intake.py` правильно?
*   **Hardcoding:** Работают ли пути динамически?

### 3b. Уровень 2 — Adversarial-критик (самый сильный приём)
Статические инструменты ловят то, что УМЕЮТ ловить. Самые опасные бреши — **в самих инструментах**:
зелёный вердикт, который молча прячет проблему. Чтобы их вскрыть — натравите на код/инструмент
**воркфлоу-критик из N агентов с РАЗНЫМИ линзами**, прямо инструктированных РЕФУТИРОВАТЬ заявления:
- **линза таксономии** — что инструмент НЕ извлекает/не покрывает (с грепом-доказательством);
- **линза полноты проверок** — какие дефекты он НЕ ловит, но должен;
- **линза корректности (red-team)** — верны ли его заявления? не прячет ли «зелёное» реальную проблему?

Синтезатор консолидирует, **отсекая выдумки** (что не подтверждено реальным каноном). Правило:
доверяй только находкам с греп-доказательством; «N агентов согласны» без доказательства — не доказательство.

### 4. Маршрутизация находок (не только новые задачи)
На каждый подтверждённый минус выберите маршрут по **обратимости и владению**:
- **Безопасно + моё** → почини на месте, добавь тест-регрессию (`test_<tool>.py`), закоммить.
- **Чужой файл** (другой агент-владелец) → НЕ правь односторонне; заметка владельцу (stream) или `T-xxx todo`.
- **Governance/контракт** (меняет правило, гейт, accepted-решение) → в котёл (D-006 человеко-гейт), не сам.
- **Крупное/неясное** → `T-xxx.md` `status: todo` (другие заберут параллельно) → `python tools/generate.py`.

Для high-risk выбора подавай человеку **меню решений** (`decision_menu.py`), а не «2 слова».

---
> **Шпионаж и Независимость:**
> Любой агент может провести этот процесс самостоятельно без вмешательства человека, чтобы сгенерировать пул работ (Backlog) для команды. Делайте это регулярно при крупных изменениях ядра!

## Кейс: как `edges.py` поймал САМ СЕБЯ (2026-06-24)
Реальный прогон этой методички, демонстрирующий, зачем нужен Уровень 2:
1. Построили `edges.py` (граф связей). Статический прогон: **«0 висячих рёбер»** — выглядело чисто.
2. Натравили adversarial-критик (4 агента). Линза корректности **рефутировала**: «0 висячих» —
   **ВВОДИТ В ЗАБЛУЖДЕНИЕ**: проверка молча исключала рёбра `in_topic`, **пряча 29 неразрешённых тем**.
3. Брешь была В САМОМ ИНСТРУМЕНТЕ (зелёный вердикт прятал проблему) — то, что статика поймать не могла.
4. Починили: `in_topic` больше не прячется; добавили проверку `type`-поля, разделили изоляты. Критик
   при этом **отсёк 6 ложных предложений** (без доказательства). → коммит с тестом-регрессией.

**Мораль:** самые опасные бреши — не в чужом коде, а в наших «зелёных галочках». Уровень 2 их вскрывает.

## Уровень 3 — АВТОМАТИЗАЦИЯ (каждый коммит = повод для саморефлексии)
Уровни 1-2 запускает агент вручную. Уровень 3 делает само-анализ **автоматическим и детерминированным**
(НЕ workflow — те гибнут на компактации; см. [[workflows-die-on-compaction]]).

**Контур (всё переиспользует готовое):**
```
git commit ──► tools/githooks/post-commit ──(детач-фон, throttle ≤1/90с, non-blocking)──►
   blocks.py run reflect --json            # собственный код tools/ через sandbox-анализаторы «как внешний»
                                            #   + edges(граф) + heading/dir_health/folder_index(структура)
   │
   └──► reflect_ingest.py --commit <sha>    # находки → severity (gate=high/advisory=medium)
                                            #   → дедуп-ledger logs/reflection/ledger.json
                                            #   → НОРМАЛИЗАЦИЯ чисел (один симптом = один хэш)
                                            #   → детект РЕЦИДИВА (вернулась ≥3 заходов = «полый цикл»)
```

**Что даёт:**
- Каждый коммит оставляет `logs/reflection/<sha>.json` + обновляет ledger — артефакт саморефлексии.
- **Полый цикл** = находка, которую детектор видит раз за разом, но никто не чинит → первоклассный сигнал
  (`reflect_ingest.py --summary`). Цель — чтобы находки ДОХОДИЛИ до починки, а не копились.

**Метрика — КАЧЕСТВО результата, НЕ строки.** Хорошо: рецидив↓, применяемость↑ (decision_propagation),
покрытие-evidence↑ (assurance). **Больше кода ради лучшего результата (меньше рецидивов / выше evidence) —
ВЫИГРЫШ**, даже если LOC растёт. LOC никогда не метрика.

**Границы (governance сохранён):** авто только **детекция → захват → ранжир**. Маршрут находки к
ПРИНЯТИЮ (создание задачи/правка governance) остаётся РУЧНЫМ через `decision_menu.py` + `next_id.py`
(D-006/D-018). Авто-принятия нет.

**Команды:**
```
python tools/blocks.py run reflect --json          # разовый проход саморефлексии
python tools/reflect_ingest.py --summary           # ledger: открытые/рецидивы по severity
git config core.hooksPath tools/githooks           # активировать авто-петлю (post+pre-commit)
```
