# Стандарт информационного рефакторинга и санации

> Отвечает на открытые мета-вопросы из `meta-sanation-questions-2026-06-24`. Это **концептуальный**
> стандарт (методология), операционализируемый инструментом `tools/sanation.py`.

## 1. Что такое «информационный рефакторинг» (ответ 4.1)

| | Классический рефакторинг | **Информационный рефакторинг** |
|---|---|---|
| Объект | код (структура) | **содержание + метаданные** канона |
| Инвариант | поведение неизменно | **история неизменна** (git, аудит) |
| Что меняем | внутреннюю структуру кода | **верхушку**: визитки, рёбра, статусы, индексы, навигацию |
| Что НЕ трогаем | внешний контракт | **тело и историю** артефактов |
| Цель | проще менять код | **дискаверабельность, свежесть, зрелость** информации |

**Определение.** Информационный рефакторинг — оздоровление **метаданного слоя** (как информация
представлена, связана, находится, оценивается), при котором **содержание и история сохраняются
неизменными**. Не «переписать», а «переосвежить верхушку».

## 2. Метафора поезда — жизненный цикл артефакта (ответ 4.2)

```
   [новые вагоны]→→→ ВЕДУЩИЙ СОСТАВ (live: open/doing/proposed) →→→ [отцепка в историю]
       прицепка спереди          ↑ санация ↑                     archived/superseded/done
                            омолаживаем верхушку              тело сохранено в git + (опц.) queues/archive
```
- **Прицепка** (спереди): новый артефакт входит в живой состав.
- **Ведущий состав** (live): активные атомы — их верхушку (визитку/рёбра/статус) **санируем** регулярно.
- **Отцепка** (назад, в историю): артефакт достигает терминального статуса (done/accepted/superseded)
  ИЛИ остывает (cold по `decay`) → уходит из «ведущего состава», НО **не уничтожается**.
- **Критерий отцепки** (4.2.1): терминальный статус ИЛИ `cold` + не-активный. Активное (даже старое) — не отцепляем.

## 3. Санация — оздоровить функционирующее, не удалить (ответ 4.3)

**Санация ≠ удаление.** Отцепленный, но функционирующий вагон (артефакт с ценным телом) **оздоравливается**:
- его **тело сохраняется** (в файле или перенос `move` в `queues/archive/`, НЕ truncate — D-026 П-3);
- его **верхушка обновляется**: визитка дополняется, статус ставится `archived`/`historical`, рёбра чинятся;
- он **выходит из активных метрик** (не считается «застоем»), но остаётся восстановимым и читаемым.

Анти-пример (инцидент 2026-06-24): вырезать тело при пометке `status: historical` — это НЕ санация, а
**стирание** (нарушение D-026). Санация сохраняет тело.

## 4. Верхушка vs тело — что омолаживаем (ответ 4.5)

«Метаданные = верхушка пирамиды/айсберга». Делим на **живое** (омолаживаемо) и **замороженное** (неизменно):

| Слой | Примеры | Санируемо? |
|---|---|---|
| **Живая верхушка** | визитка (title/gist), `status`, рёбра `edges`, температура `decay`, индексы навигации | ✅ омолаживается на лету |
| **Замороженное тело** | контент артефакта, дата создания, **git-история** | ❌ неизменно (аудит) |

**Правило (4.5.2):** омоложение трогает ТОЛЬКО живую верхушку, регенерируя её из текущего состояния
канона. Тело и историю не касается. «Пересобрать верхушку» (4.5.3) = регенерировать визитки + индексы +
граф одной командой санации — это безопасно (идемпотентно, из правды-канона).

## 5. Золотая середина: агенты ↔ операционная система (ответ 5.1)

```
   ОС / ИНФРА (детерминизм)        ←  ЗОЛОТАЯ СЕРЕДИНА  →        АГЕНТЫ (суждение)
   Windows, git, FS, generate,        средний слой:                синтез, решение,
   validate, гейты, атомарность       ВИЗИТКА + МЕНЮ РЕШЕНИЙ        роутинг, оценка
   «как хранить/принуждать»           «как ПОДАТЬ выбор»            «что выбрать/создать»
```
- **Сторона ОС** (5.2): то, что должно быть **детерминированным и принуждаемым** — хранилище (файлы/git),
  генерация агрегатов, гейты (validate/hook), атомарность (claim/lock). Машина не ошибается здесь.
- **Сторона агентов**: то, что требует **суждения** — синтез, выбор маршрута, оценка зрелости, решение.
- **Золотая середина** (5.3): **средний слой подачи** — визитка-карточка (`card-standard`) + меню решений
  (`decision-menu`). Не «2 слова» (ОС-уровень) и не «весь детейл» (агент-уровень), а ровно столько, чтобы
  агент↔человек приняли решение. Санация поддерживает именно этот средний слой свежим.

## 6. Санация на лету — качественно, не количественно (ответ 6.1, 6.2)

- **«На лету»** (6.1): санация — read-only анализ + идемпотентная регенерация верхушки; не блокирует
  работу агентов, встроена в петлю (post-commit reflect → кандидаты санации).
- **«Качественно, не количественно»** (6.2): цель — НЕ меньше файлов/строк, а **выше зрелость и свежесть**
  (визитка полна, граф цел, остывшее отцеплено, среднее `maturity`‰ растёт). Метрика — качество
  верхушки, не количество. Больше контента ради лучшего результата — норма (принцип D-026).
- **Непрерывность** (6.4): санация — петля, не разовая акция. Ритуал омоложения (6.5.1): одна команда
  `sanation.py --apply` пересобирает верхушку (индексы) + отчёт «что остыло → кандидат на архив (тело сохранить)».

## 7. Инструмент `tools/sanation.py`
Композит омоложения верхушки (read-only отчёт + одна безопасная регенерация):
- **отчёт:** визитка-покрытие (`header`), целостность графа (`edges`), остывшее (`decay`), зрелость (`maturity`);
- **кандидаты санации:** cold+terminal → архив (тело сохранить), атомы без визитки → backfill (через ROUTE);
- **`--apply`:** регенерирует индексы (`folder_index` — единственная безопасная идемпотентная запись);
  контент-санация (архив, backfill) — НЕ авто, идёт через ROUTE/человека (governance, D-006).
