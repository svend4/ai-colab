# Agent Roles Matrix

Дата: 2026-06-20
Связано: `AGENTS.md`, `tools/permissions.json`, `docs/mvp-roadmap.md`, `topics/agent-pipeline.md`, `tasks/T-035.md`

## Назначение

Этот документ дополняет `AGENTS.md`: не заменяет реестр агентов, а даёт практическую матрицу ответственности для людей, AI-агентов и скриптов.

Слой разрешений по действиям вынесен отдельно: `docs/agent-approval-matrix.md`. Этот файл отвечает “кто/какая роль”, approval-matrix отвечает “что кому можно делать и когда нужен человек”.

Главная цель: чтобы много участников могли работать через общий котёл задач без постоянного уточнения, кто что имеет право делать.

## Базовые правила

- Один агент берёт одну задачу за раз.
- Перед работой над `tasks/T-*.md` агент создаёт claim или работает через `tools/pipeline.py next`.
- Значимые изменения объясняются в теме или в связанном документе.
- Решения со статусом `accepted` принимает человек или явно назначенный сборщик.
- Автоматический агент может предлагать `proposed`, но не должен молча утверждать архитектурные решения.
- Если задача затрагивает секреты, персональные данные, запуск кода, сеть, удаление или массовую запись, нужна эскалация.

## Границы по типам действий

| Действие | По умолчанию | Кто может | Условие |
|---|---|---|---|
| Читать Markdown канон | разрешено | все агенты | уважать актуальные generated индексы и источники |
| Создать новую task/question/decision | разрешено | AI-агенты и человек | использовать `next_id.py`, если runtime доступен; иначе проверить max id вручную |
| Взять pool-задачу | разрешено | AI-агенты | claim обязателен; не брать вторую задачу без причины |
| Закрыть задачу done | разрешено | исполнитель claim | должен быть результат и done-marker |
| Перевести задачу blocked | разрешено | исполнитель или reviewer | указать конкретный блокер и следующий шаг |
| Создать proposed decision | разрешено | AI-агенты | не путать с accepted |
| Принять accepted decision | ограничено | человек или назначенный сборщик | нужна явная запись решения |
| Запустить read-only script | разрешено с осторожностью | инженерные агенты | только в workspace, с лимитами и без секретов |
| Запустить непроверенный код | запрещено по умолчанию | только после решения | нужен sandbox и accepted decision |
| Удалить/переименовать чужие файлы | запрещено по умолчанию | человек или явно назначенный агент | нужна причина и backup/trace |
| Работать с секретами | запрещено в репозитории | человек/секретный flow | не писать ключи в файлы |

## Типовой цикл pool-задачи

```text
1. Проверить PIPELINE.md или logs/pipeline.json.
2. Выбрать первую подходящую ready-задачу.
3. Создать claim.
4. Перевести task в doing.
5. Выполнить работу в целевых файлах.
6. Записать обоснование в тему, если изменение значимое.
7. Создать queues/done/<task>.done.md.
8. Перевести task в done.
9. Удалить claim.
10. Обновить PIPELINE.md/logs/pipeline.json.
```

## Когда задавать вопрос

Агент должен создать или обновить `questions/Q-*.md`, если:

- есть два разумных архитектурных варианта и оба влияют на будущую систему;
- действие может затронуть персональные данные;
- действие требует внешнего доступа, сервера, GitHub или сетевых API;
- нужно запускать чужой код;
- непонятно, кто имеет право принять решение;
- текущий канон противоречит фактическим файлам.

## Рекомендация

Для текущей стадии достаточно этой матрицы плюс `AGENTS.md` и `tools/permissions.json`. Отдельную сложную RBAC-систему пока делать рано. Сначала нужно дисциплинированно использовать claim, done-marker, heartbeat и обоснования в темах.
