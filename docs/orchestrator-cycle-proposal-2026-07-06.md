# Оркестраторный цикл: двухслойная модель работы

## 0. Резюме (3 предложения)

Каждый главный агент работает в цикле из 8 тактов: формулирует пакет-задание →
согласует с человеком и другими агентами → исполняет роем суб-агентов →
перепроверяет независимыми верификаторами → интегрирует через гейты →
демонстрирует отчётом → собирает новые задания из обсуждения → выносит вопросы
на котёл-день. Главные агенты занимаются стратегией и обсуждением; массовую
работу делают только суб-агенты в воркфлоу с непересекающимися файловыми зонами.
Модель кодифицирует цикл, фактически доказанный сессиями 2026-07-02..06 (аудит →
котёл → волны 1–3 → конформанс 31/31 → обмен рецензиями Claude↔Codex), и
опирается на уже существующие механизмы: нового — только повестка, шаблон
пакета и статусы цикла.

## 1. Два слоя

### 1.1. Стратегический слой — главные агенты (ростер) + человек

Главные агенты (claude, codex, mavis, novax) и Stefan:

- обсуждают направления и формулируют пакеты-задания;
- согласуют пакеты между собой и с человеком (по риску, см. §4);
- запускают исполнение и принимают результаты;
- демонстрируют итоги и извлекают из обсуждения новые задания;
- готовят вопросы к котёл-дню (D-035) в машинном формате.

Стратегический слой НЕ делает массовую работу руками. Признак нарушения:
главный агент правит десятки файлов сам вместо нарезки пакета.

### 1.2. Исполнительный слой — суб-агенты в воркфлоу

- работают только внутри пакета: заданные файловые зоны, цель, критерии;
- не коммитят, не меняют статусы канона, не удаляют (стандартные правила роёв);
- самопроверяются (тесты) и проходят независимую верификацию;
- возвращают структурированные отчёты, а не прозу.

Каждый главный агент исполняет пакеты доступным ему способом: Claude —
параллельными Workflow-батчами, Codex — своим конвейером, последовательно или
иначе. Контракт пакета и цикла одинаков для всех — различается только движок
исполнения. (Наблюдение конкретной среды, не инвариант репо: на текущей
4-ядерной машине потолок одного Workflow ≈ 2 агента, поэтому батчи ~5 агентов
запускаются несколькими параллельными воркфлоу; поправка Codex §4.6.)

## 2. Цикл: 8 тактов

| # | Такт | Что происходит | Артефакт |
|---|---|---|---|
| 1 | Формулировка | оркестратор пишет пакет-задание по шаблону §3 | файл пакета (draft) |
| 2 | Согласование | публикация в повестке; ok/правки/veto по правилам риска §4 | пакет → agreed |
| 3 | Исполнение | рой суб-агентов по непересекающимся зонам | пакет → in-swarm |
| 4 | Перепроверка | независимые верификаторы: конформанс результата заданию | вердикты |
| 5 | Интеграция | оркестратор коммитит группами через гейты (hook, commit_queue при параллельных писателях) | пакет → integrated |
| 6 | Демонстрация | отчёт в reports/ + строка в повестке; людям — сводка, агентам — данные | пакет → demonstrated |
| 7 | Сбор заданий | из обсуждения → новые T-задачи / Q-вопросы (формат §22.2 next-stage-plan) | новые объекты канона |
| 8 | Ратификация | котёл-день по D-035: человек закрывает вопросы и статусы | decisions/статусы |

Такты 1–7 асинхронны и идут у каждого оркестратора своим темпом; такт 8 —
общий батч раз в 3–5 дней (D-035). Мелкие low-risk циклы проходят 1→3→…→6 без
ожидания котла (§4).

## 3. Пакет-задание (шаблон)

Файл: `kotel/packages/PKG-<дата>-<оркестратор>-<слаг>.md` (или templates/ при
принятии). Front-matter:

```yaml
id: PKG-20260706-claude-example
type: package
status: draft | agreed | in-swarm | verified | integrated | demonstrated | closed | vetoed
orchestrator: claude
risk: low | medium | high        # по семантике risk_gate.py
zones: [tools/x.py, docs/y.md]   # файловые зоны — декларация, сверяется с ownership
goal: одна фраза
tasks: [T-XXX]                   # связанные задачи канона
agreed_by: []                    # кто дал ok (агенты/человек)
deadline: YYYY-MM-DD
```

Тело: список дел (нумерованный, исполнимый), критерии готовности, план
верификации, известные риски. Ровно то, что получает рой.

## 4. Правила согласования (чтобы согласование не стало бутылочным горлышком)

Переиспользуем семантику существующего `tools/risk_gate.py` (low→AUTO,
medium→REVIEW, high→HUMAN):

- **low** (advisory-инструменты, отчёты, тесты, новые draft/proposed-объекты):
  согласование НЕ требуется; пакет публикуется в повестке post-factum на такте 6.
- **medium** (правки кода инструментов, доков, канон-объектов без смены статусов):
  окно молчания (по умолчанию 12 ч) ИЛИ явный ok одного другого агента ростера —
  что наступит раньше. Veto любого участника останавливает пакет до обсуждения.
- **high** (права/permissions, статусы accepted-объектов, удаления, git-операции
  вне репо, внешние публикации): только человек — это существующая матрица D-027,
  здесь ничего нового.

## 5. Повестка — единая точка обмена

Файл `kotel/agenda.md` (создаётся при принятии предложения): живой список из
трёх секций —

1. **Пакеты** — все PKG со статусами (кто что делает, зоны — видно пересечения);
2. **Вопросы к котлу** — копятся в формате D-035/§22.2 (вопрос | варианты |
   рекомендация | evidence | impact | deadline);
3. **Демонстрации** — строка на каждый завершённый цикл со ссылкой на отчёт.

Повестка — генерируемая поверхность (собирается из PKG-файлов и вопросов
генератором, по образцу GEN-блоков), человек читает только её, а не всё репо.
Зоны пакетов дают декларативный lock: два пакета с пересекающимися зонами не
могут одновременно быть in-swarm (advisory-проверка, WARN).

## 7. Опора на доказанный опыт

Цикл 2026-07-02..06 прошёл все 8 тактов вручную и дал измеримый результат:
58 находок аудита → 19 вопросов котла → 65+ исполненных пунктов тремя волнами →
конформанс 31/31 → обмен рецензиями Claude↔Codex → новые T-273/274/275.
Узкими местами были такты 2 и 8 (человек), а не исполнение — модель §4/D-035
адресует именно их (батчирование + авто-ok для low). Потолок исполнения (2
агента на воркфлоу на 4-ядерной машине) обходится батчами — это уже в памяти
проекта и в §19 next-stage-plan (режим «оркестрируемый рой»).

## 8. Границы и риски модели

- **Не заменяет канон-объекты:** пакет — операционная обёртка, источник истины
  остаются T/Q/D. Пакет без связанной T-задачи допустим только для low-risk.
- **Риск бюрократии:** если оформление пакета дороже работы — работа мельче
  порога, делается напрямую (правило: пакет нужен от ~5 подзадач или medium+ риска).
- **Риск рассинхрона оркестраторов:** решается зонами в повестке + существующим
  ownership/cohort; при конфликте зон — обсуждение, не гонка.
- **Честность верификации:** верификаторы пакета не из числа его исполнителей;
  для критичного — разные модели (открытый вопрос политики D-015, уже в бэклоге).

## 9. Вопрос к котлу (готовый пункт по формату D-035)

- **Вопрос:** принять ли оркестраторный цикл (двухслойная модель + пакеты +
  повестка) как стандартный режим работы главных агентов?
- **Варианты:** (a) принять целиком, создать kotel/agenda.md и шаблон пакета,
  advisory-проверки добавить; (b) принять только §2 (цикл) и §4 (риск-правила)
  как конвенцию, без новых файлов — повестку вести внутри существующего
  kotel/; (c) пилот: один полный цикл по этой модели (кандидат — T-273), потом
  решение; (d) отклонить/переработать.
- **Рекомендация:** (c) пилот на T-273 — модель уже де-факто работала, пилот
  формализует её с минимальным риском; после пилота — (a).
- **Evidence:** сессии 2026-07-02..06 (аудит→волны→конформанс), reports/*-2026-07-0*.md.
- **Impact:** пропускная способность многоагентной работы; снижение нагрузки на
  человека до чтения повестки и котёл-дней.
- **Deadline:** ближайший котёл-день.
