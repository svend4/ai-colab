## 2. Концептуальная стадия: архитектура L0–L8 (детально)

### 2.1. L0 — Инструкции и протокол (✅ Стабильно)

**Что есть:**
- `PROTOCOL.md` (220 строк) — 7 уровней работы: статус, темы, сообщения, очереди, реестр агентов, запрет на перезапись, обоснование правок, сборщик итогов, git-режим.
- `AGENTS.md` (33 строки) — реестр 4 агентов (Codex, Claude, Mavis, Novax) с зонами ответственности.
- `DECISIONS.md` + `decisions/` — 14 принятых решений (D-001..D-014), формальный метод D-004 (варианты → голоса → итог).
- `permissions.json` — совещательный guard для зон записи.

**Что не хватает:**
- Автоматическое обнаружение нарушений протокола (сейчас только manual review).
- Динамические права (права меняются по ролям, а не hardcoded в JSON).
- Версионирование протокола (как отследить, что изменилось в PROTOCOL.md v2).

**Оценка зрелости:** 3/3. Система правил канонизирована, работает, проверяется валидатором.

---

### 2.2. L1 — Манифесты драйверов (✅ Работает)

**Что есть:**
- `drivers/SCHEMA.md` — draft schema v1 с 18 полями: `id`, `type`, `title`, `status`, `level`, `mode`, `owner`, `risk`, `activation`, `interfaces`, `inputs`, `outputs`, `sandbox`, `secrets`, `source_last_verified`, `timeout_seconds`, `max_output_bytes`, `audit`, `related`.
- `tools/drivers_catalog.py` — генератор `drivers/CATALOG.md` (человеческая таблица) + `drivers/index.json` (машинный срез).
- `tools/validate.py::check_drivers()` — проверка 6 манифестов по schema v1 (уникальность id, корректность enum, наличие обязательных полей).
- 6 драйверов в каталоге: repo-runner, files, codex-local, data, workbench, file-inventory.

**Что не хватает:**
- Schema v1 ещё draft — не принят как окончательный стандарт (Q-008/D-013).
- Нет валидатора mode+sandbox совместимости (например, `mode: execute` требует `sandbox: required`).
- Нет автоматического тестирования манифестов (например, проверка, что все `interfaces` реализованы в коде).
- Нет версионирования манифестов (как отследить, что `repo-runner` v1 → v2).

**Оценка зрелости:** 2.5/3. Система работает, но schema ещё draft.

### 2.3. L2 — MCP и инструменты (✅ PoC готов)

**Что есть:**
- **`files` driver** — L2, FastMCP, read-only. Скрипт `drivers/files/mcp_server.py` (~120 строк). Реализует 4 инструмента: `list_files`, `read_file`, `grep_files`, `file_summary`. Протестирован handshake (MCP-соединение устанавливается, инструменты регистрируются).
- **`repo-runner` driver** — L1/L2, read-only. Скрипт `drivers/repo-runner/inventory.py` (~180 строк). Сканирует структуру, языки, package-файлы, тесты, риски. Тесты `test_inventory.py` (4 теста, проходят). Демо-сканирование текущего репозитория: 141 файл, 0.71 МБ, 3 риска.
- **`data` driver** — L1, read-only. CSV/SQLite чтение. Манифест + базовый код.
- **`codex-local` driver** — L1, manual. Манифест коннектора к локальному Codex.

**Что не хватает:**
- MCP-gateway (untested) — общая точка входа для всех MCP-драйверов.
- Только 2 драйвера реально работают (files + repo-runner). Остальные — манифесты или прототипы.
- Нет автоматического тестирования MCP-handshake в CI.
- Нет документации по подключению нового MCP-драйвера (шаблон есть, но без инструкции).

**Оценка зрелости:** 2/3. PoC работает, но не production-ready.

---

### 2.4. L3 — Сервисы и сеть (🔄 В разработке)

**Что есть:**
- **`workbench.db` схема** — SQLite (дизайн). Таблицы: `documents` (метаданные артефактов), `fragments` (подразделы документов), `audit_log` (append-only журнал), `drivers` (статистика), `__meta__` (версия схемы).
- **`drivers/workbench-db/init.py`** — создание БД с версионированием (schema v1).
- **`drivers/workbench-db/query.py`** — базовые операции: insert document, search by LIKE, list by filters, log event, get audit, driver stats.
- **`drivers/workbench-db/test_db.py`** — 5 тестов (init, insert/search, list by risk, audit log, driver stats) — все проходят.

**Что не хватает:**
- Реальный сервер (FastAPI/Flask) — сейчас только Python-скрипты, не web-сервис.
- Docker-песочница для безопасного запуска кода.
- Сетевой доступ — сейчас только локальная SQLite, не shared БД.
- Масштабирование — SQLite не выдержит 10+ параллельных агентов с записью.
- Нет ORM/моделей — прямой SQL, что хрупко при изменении схемы.

**Оценка зрелости:** 1.5/3. Схема и базовые скрипты есть, но нет сервера и масштабирования.

- Нет интеграции с `repo-runner` — inventory.py выдаёт JSON, но не пишет в workbench.db автоматически.

**Оценка зрелости:** 1/3. Есть реляционный каркас, но нет поиска и связей.

### 2.8. L7 — Оркестрация (✅ Работает)

**Что есть:**
- **`pipeline.py`** — конвейер pull-next. Команды: `next`, `status`, `mine`, `done`, `fail`, `snapshot`. 6-задачный стресс-тест пройден (3 агента, 0 коллизий, DAG-зависимости работают).
- **`queue.py`** — legacy очередь (claim/complete/fail с TTL + fencing). Работает, но pipeline.py предпочтительнее.
- **`dispatch.py`** — диспетчер задач по DAG (показывает готовые/заблокированные).
- **`next_id.py`** — атомарная выдача ID (O_EXCL, предотвращает коллизии).
- **`flow.py`** — git-flow для агентов (ветка → гейт → merge).
- **`risk_gate.py`** — классификация риска (low/medium/high).
- **`metrics.py`** — сводка метрик канона.
- **`logs/pipeline.json`** — машинный срез конвейера.
- **`PIPELINE.md`** — визуальная Kanban-доска.
- **`logs/heartbeat.json`** — heartbeat агентов (добровольный).

**Что не хватает:**
- Heartbeat дисперсия 6.5 мин — агенты обновляются неровно, нет real-time.
- Нет авто-перезапуска failed-задач (если агент упал, задача остаётся failed, не переназначается).
- Нет приоритетной очереди (все задачи в пуле равны, нет `urgent` vs `normal`).
- Нет лимита на количество задач у одного агента (агент может взять все задачи и монополизировать пул).
- Нет таймаута на задачу (если агент взял задачу и исчез — она зависает в doing).

**Оценка зрелости:** 2.5/3. Система работает, но не отказоустойчива.

### 3.4. Архитектура данных

**Файловая модель:**
- Markdown + YAML front-matter = источник правды для задач, вопросов, решений, тем, драйверов.
- JSON = машинные срезы (index.json, drivers/index.json, logs/pipeline.json, logs/heartbeat.json).
- SQLite = локальная БД (workbench.db) для поиска и аудита.
- Bash = pre-commit hook, git-flow, queue-claim (атомарность через O_EXCL).

**Плюсы:**
- Версионируется git (всё, кроме SQLite).
- Читаемо человеком (Markdown) и машиной (JSON/YAML).
- Нет vendor lock-in (всё — текстовые файлы).

**Минусы:**
- SQLite — бинарный файл, не версионируется в git (конфликты, дрейф).
- JSON-логи растут — нужна ротация (сейчас нет).
- Файловая шина медленнее, чем in-memory (Redis) — при 10+ агентах будет bottleneck.
- Нет backup-стратегии (если workbench.db повреждён — данные потеряны).
