# Рекурсивное само-улучшение: одна петля из накопленных частей

> Мета-архитектурный слой НАД отдельными подсистемами. До сих пор каждая часть описана
> отдельно: пирамида L1–L4 (`workspace-pyramid-levels.md`), блок-слой (`blocks-layer.md`),
> FINDER→роутер→SOLVER (`finder-solver-pipeline-methodology.md`), конвейер/бригады
> (`workflow-conveyor-policy.md`), adoption-монитор (`tools/adoption.py`), friction
> (`tools/friction.py`), cohort/flow (`tools/cohort.py`, `tools/flow.py`). Этот документ
> утверждает **тезис единства**: все они — не россыпь, а **органы одной рекурсивно-само-
> улучшающейся машины**, и формализует **цикл**, который их связывает. Цель — не описать
> части ещё раз, а показать, что между ними замыкается контур обратной связи, и сделать
> этот контур **запускаемым** (предложение блока `improve` в §7).

## 0. Тезис: система — это контур, а не набор инструментов

Adoption-аудит (`темы/adoption-statistics-2026-06-23.md`) дал диагноз, который и есть отправная
точка: **проверенное работает (≈78% применения), но применяется россыпью**. Каждый инструмент —
исправный «стройматериал», но между ними нет замкнутого контура, который бы заставлял систему
**сама себя чинить и достраивать**. Накопление информации ≠ улучшение: 18 из 23 решений живут как
декларация, 9 инструментов dormant, 4 дока orphan — это не дефекты инструментов, это **отсутствие
петли**, которая бы их подхватила и впаяла.

Рекурсивное само-улучшение — это не отдельная фича, которую надо «дописать». Это **топология
связей** между уже существующими частями: если их соединить в цикл `measure → detect → route →
improve → re-measure`, система начинает уменьшать собственную энтропию без внешнего толчка на каждый
шаг. Ключевое слово — **рекурсивное**: тот же контур применяется к **собственному коду, докам и
решениям движка**, а не только к пользовательским задачам. Движок — первый клиент самого себя.

## 1. Цикл: пять фаз и какие органы их несут

```
                    ┌──────────────────────────────────────────────────────────────┐
                    │                                                                │
                    ▼                                                                │
   ┌───────────────────────┐   приоритизированный   ┌──────────────────────┐        │
   │ 1. MEASURE (adoption)  │   список «что не       │ 2. DETECT (FINDER/    │        │
   │ tools/adoption.py      │──►применяется/сломано»─►│    audit-блок)        │        │
   │ tools/metrics.py       │   (числа, не проза)    │ blocks.py audit       │        │
   │ → коэффициент применения│                       │ friction/assurance/   │        │
   └───────────────────────┘                        │ drift/reconcile       │        │
            ▲                                        └──────────┬───────────┘        │
            │ re-measure: упал ли                                │ структурные         │
            │ dormant/orphan/doc-only?                           │ находки P1..Pn      │
            │                                                    ▼                     │
   ┌───────────────────────┐                        ┌──────────────────────┐         │
   │ 5. RE-MEASURE          │◄───────────────────────│ 3. ROUTE (я,          │         │
   │ adoption snapshot      │   ship когортой        │    оркестратор)       │         │
   │ Δ к прошлому base       │   (cohort/flow гейты)  │ триаж: дедуп/приоритет/│        │
   └───────────────────────┘                        │ классификация/scope   │         │
                    ▲                                └──────────┬───────────┘         │
                    │                                           │ отобранное          │
                    │      ┌──────────────────────┐             ▼                     │
                    └──────│ 4. IMPROVE (SOLVER/   │◄────────────────────────────────┘
                           │    blocks)            │  фан-аут решателей через
                           │ blocks.py self/improve │  конвейер/бригады (cohort)
                           └──────────────────────┘
```

| Фаза | Вопрос | Орган | Выход |
|---|---|---|---|
| **1. MEASURE** | Применяется ли накопленное? | `adoption.py`, `metrics.py` | коэффициент применения, списки dormant/orphan/doc-only |
| **2. DETECT** | Что сломано / недоделано / противоречит? | FINDER-воркфлоу + `blocks.py audit` (validate/generate/friction/assurance/drift/reconcile) | структурные находки `{title, evidence, kind, severity}` |
| **3. ROUTE** | Что из найденного решать **сейчас**? | оркестратор (я) — барьер-роутер | отобранный приоритизированный список под полосу коммита |
| **4. IMPROVE** | Решить отобранное | SOLVER-воркфлоу / build-бригады, гейты `blocks.py self` | готовые артефакты (код/доки/впайка решений) |
| **5. RE-MEASURE** | Стало ли лучше? | `adoption.py` снова, Δ к прошлому base | подтверждение/опровержение → новый виток |

Контур **замкнут**: выход RE-MEASURE — вход следующего MEASURE. Это не пайплайн с концом, а
**аттрактор**: каждый виток должен двигать метрики применения вверх, иначе виток был холостым.

## 2. Почему именно эти пять фаз (а не четыре и не шесть)

Развею, почему контур именно такой формы:

- **MEASURE отдельно от DETECT.** Соблазн слить: «аудит и так находит проблемы». Но это **две
  разные оси**. DETECT (`audit`-блок, FINDER) ищет **дефекты** — то, что сломано или противоречит.
  MEASURE (`adoption`) ищет **неприменённое** — то, что исправно, но лежит на полке. Дефект и
  полка-пыль требуют разных лечений: дефект чинят (fix), полку-пыль **впаивают** (wire). Слить их —
  значит потерять целый класс долга (18 doc-only решений — не баги, их нечего «чинить», их надо
  подключить). Поэтому MEASURE — отдельная голова контура.
- **ROUTE обязателен и неустраним.** Это центральный тезис `finder-solver-pipeline-methodology.md`:
  **не всё найденное надо решать**. Авто-пайп DETECT→IMPROVE решал бы шум — дубли, out-of-scope,
  уже-сделанное, governance-вопросы (которые идут в котёл D-018, не в build). ROUTE — человеко-/
  оркестратор-гейт качества и scope. Без него контур деградирует в генератор busywork.
- **RE-MEASURE замыкает, а не просто завершает.** Без пятой фазы это разомкнутый пайп: «нашли,
  решили, разошлись». Re-measure превращает линию в **петлю с обратной связью**: тот же `adoption`
  снимок против нового base показывает Δ. Если dormant не упал — improvement был иллюзорным
  (например, добавили док, который сам стал orphan). Контур **само-фальсифицируется**.

Шести фаз нет, потому что IMPROVE не дробится дальше на уровне контура — внутри него уже живёт
своя топология (конвейер §3, бригады cohort), но снаружи это одна фаза «решить отобранное».

## 3. Несущая инфраструктура: как фазы исполняются масштабно

Контур — это **что**. Конвейер и бригады — это **как** фазы DETECT и IMPROVE несут много работы,
не упираясь в один последовательный оркестратор:

- **Производство параллельно (конвейер).** `workflow-conveyor-policy.md` §3-bis: FINDER и SOLVER —
  это не один проход, а **поток** воркфлоу. Пока обрабатывается один результат, следующие уже бегут.
  `tools/conveyor.py` — надзиратель, сигналит REFILL/PROCESS/IDLE, чтобы поток не осушался до нуля.
- **Интеграция серийна (полоса коммита).** `agent-capacity-methodology.md`: предел системы — не
  «сколько агентов» (производство масштабируется свободно, флот до 16 агентов/нода), а **полоса
  ОБРАБОТКИ одного оркестратора** — извлечь, перепроверить, закоммитить в одну каноническую историю.
  Поэтому ROUTE отбирает ровно столько находок, сколько IMPROVE успеет влить (§7 finder-solver).
- **Бригады без коллизий (cohort/flow).** `tools/cohort.py`/`tools/flow.py`: когда IMPROVE пишет код
  параллельно, каждый writer — в своём worktree (`agent/<agent>/<task>`), слияние через
  `merge_gate`. Изоляция убирает гонку за `index.lock`, а не очередит на ней (D-017, D-022).
- **Двусторонний конвейер.** §3-quater: узкое место-потребитель тоже параллелится — композиция
  результатов отдаётся интегратор-воркфлоу (composer-агент на каждый output), а за оркестратором
  остаётся только дешёвый write+commit. «Несколько оркестрантов» расширяют полосу обработки.

Итог: контур §1 — логический; конвейер+бригады — физический субстрат, на котором фазы DETECT и
IMPROVE бегут широким фронтом, а серийной остаётся только дешёвая интеграция в одну историю.

## 4. Пирамида L1–L4 как направление улучшения (куда течёт результат)

Контур не просто чинит — он **поднимает материал по пирамиде** (`workspace-pyramid-levels.md`):

```
L4 sandbox/  →  L3 collab/  →  L2 portals/  →  L1 core/
(хаос, вход)    (полилог,       (чистовые        (переносимое
                спор, доказ.)    порталы)         универсальное ядро)
```

Каждый виток контура — это и есть **акт продвижения**: MEASURE/DETECT работают над L3 (история,
доки, решения) и L1 (код `tools/`); IMPROVE впаивает доказанное выше — orphan-док из L3 либо
цитируется (становится cited), либо признаётся мёртвым и опускается; повторно-применённая функция
из L2-порталов поднимается в L1-ядро (`promote.py`/`portal.py` — advisory-шаги pyramid-блока).
**Adoption-метрика — это датчик «насколько хорошо идёт продвижение»:** doc-only решение = застрявший
в L3 материал, который не впаялся в L1-код. Контур — насос, гонящий материал вверх по уровням, а
adoption измеряет, не застрял ли насос.

## 5. Рекурсия: контур применяется к самому себе

«Рекурсивное» — буквально. Те же органы судят **сам контур**:

- `adoption.py` **ловит самого себя**: `blocks.py`/`adoption.py` числятся применёнными, только когда
  подключены (этот док + блок `adoption` дают им вызыватель/ссылку). Если бы их никто не звал —
  монитор показал бы их как dormant, и контур обязан был бы себя впаять.
- `friction.py` F-020 — gate-poison детектор — ловит **собственный** сломанный cross-link
  cohort→friction. Система чинит свою же проводку тем же механизмом, что и чужую.
- `blocks.py self` — единая точка рекурсивной самопроверки: `audit` (над дефектами) + `adoption`
  (над применением) вместе. Это §1-контур, свёрнутый в одну команду для **движка над движком**.

Опасность рекурсии — **бесконечный регресс** (монитор монитора монитора). Граница проста и уже
заложена: рекурсия **измеряется тем же adoption-датчиком и останавливается полосой коммита**. Новый
само-инструмент оправдан, только если он повышает применение или ловит реальный дефект (MEASURE/DETECT
это покажут); иначе он сам станет dormant-строкой в следующем снимке. Контур не даёт себе разрастаться
в абстракцию: всё, что не применяется, всплывает как полка-пыль на следующем витке.

## 6. Ретроспектива: что уже ДОКАЗАНО работающим

Контур не гипотетичен — его части уже измерены работающими (`adoption-statistics-2026-06-23.md`):

- **Конвейер — единственная HOT-подсистема** (sub-hour трейсы): производство реально идёт потоком,
  56% воркфлоу в параллельных окнах, до 4 нод одновременно, бригада до 17 агентов на ноду. Фаза
  IMPROVE масштабируется — это **доказано замером**, не обещано.
- **Блоки собраны и рекурсивны:** `blocks.py self` существует и кластеризует audit+adoption; блок-слой
  перевёл россыпь в кластеры (`blocks-layer.md`). DETECT уже исполняется одной командой.
- **FINDER→SOLVER уже прогонялся:** группа new-problems-2026-06-23 собрана по готовой доке (designs+
  назначения); два-спайн trace, F-020 gate-poison, L2-порталы (1→3) — это **landed-артефакты** прошлых
  витков контура, не план.
- **Adoption-датчик откалиброван:** реальные счёты (grep/git/subprocess/sqlite), а не оценки;
  встроен нюанс manual-cli ≠ dead, прокси нижней границы для решений (5/23 enforced). MEASURE даёт
  числа, по которым RE-MEASURE может посчитать Δ.

**Что ещё НЕ замкнуто (честный долг):** RE-MEASURE как автоматический Δ-шаг пока ручной (нет
«adoption diff base..HEAD»); IMPROVE-фаза не имеет своей одной кнопки, которая бы взяла выход
MEASURE+DETECT и выдала приоритизированный план — её и предлагает §7.

## 7. Предложение: блок `improve` — кнопка, замыкающая петлю

Сейчас `blocks.py` имеет `audit` (DETECT), `adoption` (MEASURE), `self` (DETECT+MEASURE вместе),
`pyramid` (структура). Чего **нет** — блока, который **запускает петлю**: сводит adoption+audit в
**один приоритизированный список** «что улучшать», то есть готовит вход для фазы ROUTE. Это
недостающее звено между MEASURE/DETECT и человеко-роутером.

Готовая запись для словаря `BLOCKS` в `tools/blocks.py` (символ-якорь: dict-литерал `BLOCKS = {`,
вставить новый ключ **после** записи `"self"` и перед `"pyramid"`):

```python
    "improve": {
        "desc": "петля само-улучшения: adoption(применение)+audit(дефекты) -> вход для роутера (что чинить/впаивать)",
        "steps": [
            ("adoption.py", ["--json"], "advisory"),   # MEASURE: dormant/orphan/doc-only
            ("friction.py", ["status"], "advisory"),   # DETECT: known-проблемы по F-реестру
            ("assurance.py", [], "advisory"),          # DETECT: instruction-assurance
            ("drift_check.py", [], "advisory"),        # DETECT: дрейф канона
            ("validate.py", [], "gate"),               # GATE: база валидна (иначе список нерелевантен)
            ("generate.py", ["--check"], "gate"),      # GATE: навигация свежа
        ],
    },
```

Семантика в существующей машине `run_block` (правок кода не требует — `improve` исполняется тем же
раннером): gate-шаги (`validate`, `generate --check`) решают вердикт BLOCK-OK/FAIL — если база
сломана, приоритизировать улучшения бессмысленно (fail-closed). Advisory-шаги (adoption + три
детектора) **собираются**, не валят: их `advisory_flags` и `--json`-хвосты — это и есть сырьё
приоритизированного списка для ROUTE. Параллельный запуск по умолчанию (`threading.Thread`, обход
коллизии `tools/agent_queue.py`↔stdlib `queue`) — кластер бежит конкурентно, как `audit`/`self`.

**Почему `improve` ≠ `self`.** `self` отвечает «здорова ли система целиком» (булев вердикт для
само-проверки). `improve` отвечает «**что** делать дальше» — он наклонён к MEASURE (`adoption --json`
первым, машинно) + добавляет drift, чтобы выдать **материал для приоритизации**, а не просто pass/fail.
`self` — датчик здоровья; `improve` — генератор повестки. Разные вопросы → разные блоки.

**Граница честности.** `improve`-блок готовит вход для ROUTE, но **не роутит сам** — приоритизация
(value×severity, дедуп vs git/канон, классификация build/decision/question, фильтр scope) остаётся
за оркестратором-человеко-гейтом (D-006/D-018). Блок собирает сырьё одной командой; решение «что из
этого решать сейчас» по-прежнему проходит барьер-роутер. Это сохраняет инвариант §2: контур не
авто-пайплайнит DETECT→IMPROVE.

## 8. Итог

Накопленные части — не россыпь, а **органы одной петли**: adoption измеряет применение, FINDER/audit
детектируют дефекты и недоделки, оркестратор роутит отобранное через барьер качества, SOLVER/блоки
улучшают (масштабируясь конвейером и бригадами), adoption измеряет снова — и виток повторяется,
поднимая материал по пирамиде L4→L1. Контур **рекурсивен** (судит сам себя тем же adoption-датчиком)
и **само-ограничен** (полоса коммита + полка-пыль не дают разрастись в абстракцию). Доказано
работающим: конвейер HOT, блоки собраны и рекурсивны, FINDER→SOLVER уже шипил артефакты. Недостающее
звено — блок `improve` (§7), который сводит MEASURE+DETECT в одну команду и замыкает вход петли,
оставляя ROUTE человеко-гейту.
