# Следующий этап реализации: подробный поэтапный план действий

## 1. Назначение документа

1.1. Этот документ фиксирует письменный план дальнейших действий после перепроверки состояния проекта 2026-07-06.

1.2. План предназначен для людей и AI-агентов, которые продолжают разработку инфраструктуры полилога, конвейера задач, sandbox/worktree-подхода, верхнего слоя управления и "середины пирамиды" между агентами и операционной системой.

1.3. Главная цель следующего этапа: перевести проект из состояния "инфраструктурная альфа с большим количеством методологии" в состояние "управляемый рабочий прототип", где:

1.3.1. агент видит, что делать дальше;

1.3.2. человек видит понятный статус;

1.3.3. правила не просто записаны, а проверяются инструментами;

1.3.4. спорные варианты не уничтожаются как "дубли", а проходят независимую проработку, сравнение, синтез и ратификацию;

1.3.5. код и документация двигаются через безопасный конвейер, а не через хаотичные ручные правки.

## 2. Текущая оценка стадии

2.1. Концептуальная стадия: Alpha-3 / pre-beta control plane.

2.2. Техническая стадия: рабочая альфа с реальными инструментами, но с недостаточно закрепленным верхним слоем управления.

2.3. Примерная готовность:

2.3.1. идея и методология: 80-85%;

2.3.2. архитектурный каркас: 75-80%;

2.3.3. техническая реализация инструментов: 65-70%;

2.3.4. удобство для агентов: 55-60%;

2.3.5. удобство для человека как продукта: 40-45%;

2.3.6. готовность к широкой многоагентной работе без ручной координации: 35-45%.

2.4. Главный вывод: проект уже имеет сильный каркас, но следующий скачок зависит не от добавления еще большего числа Markdown-файлов, а от превращения существующих правил в команды, проверки, маршруты, отчеты, индексы и маленькие управляемые workflow.

## 3. Главные инварианты следующего этапа

3.1. Не переписывать историю обсуждений.

3.2. Не удалять чужие сообщения.

3.3. Не исправлять чужую незавершенную работу без явного основания.

3.4. Не использовать широкое `git add -A` для коммитов.

3.5. Коммитить только точные группы файлов с понятным смыслом.

3.6. При параллельной работе использовать commit queue, streams, worktree-уровень и selective add.

3.7. Любая новая автоматизация должна иметь:

3.7.1. назначение;

3.7.2. входные данные;

3.7.3. выходные данные;

3.7.4. режим read-only или write;

3.7.5. проверку;

3.7.6. критерий успешности;

3.7.7. место в верхнем слое управления.

3.8. Любая новая методология должна быть связана хотя бы с одним практическим механизмом: task, decision, question, report, tool, skill, driver, portal, sandbox, test или top-command.

## 4. Фаза 0. Снимок состояния перед действиями

4.1. Перед любыми правками нужно получить короткий снимок состояния.

4.2. Минимальный набор команд:

```powershell
git status --short
python tools\repo_hygiene.py
python tools\validate.py
python tools\generate.py --check
python tools\pipeline.py status
python tools\top.py health
```

4.3. Если команда зависает, использовать короткий timeout-wrapper, а не ждать часами.

4.4. Если PowerShell показывает mojibake, включить UTF-8:

```powershell

[Console]::InputEncoding = [System.Text.UTF8Encoding]::new($false)
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
```

4.5. Результат фазы 0: понятно, какие изменения уже есть, какие файлы stale, какие проверки красные, какие задачи готовы к взятию.

5.6.3. Не удалять divergence-файлы без явного отчета, куда перенесен смысл.

5.7. Корзина F: инструментальные изменения.

5.7.1. Проверить изменения в `tools/`.

5.7.2. Для каждого измененного инструмента определить: это bugfix, новая функция, проверка, safety gate или генератор.

5.7.3. Для каждого инструмента должен быть хотя бы минимальный тест или ручной сценарий проверки.

5.8. Корзина G: stray-root и мусор.

5.8.1. Проверить файл `z` в корне.

5.8.2. Если это случайный файл, удалить или перенести в sandbox/trash только после понимания содержания.

5.8.3. Не оставлять непонятные корневые файлы: они ухудшают машинную навигацию.

5.9. Результат фазы 1: каждая текущая правка получает категорию, смысл и следующий шаг.

## 9. Фаза 5. Реализация T-274: tripwire параллельности

9.1. Назначение T-274: сделать видимой ситуацию, когда одновременно работает много агентов.

9.2. Это не должен быть жесткий запрет.

9.3. Это должен быть advisory gate:

9.3.1. считает fresh claims как основной сигнал;

9.3.2. считает heartbeat только как вторичный опциональный сигнал, потому что heartbeat-механика не является надежным обязательным источником;

9.3.3. учитывает свежие pipeline-снимки и, если возможно, плотность недавних коммитов или stream-событий разных агентов;

9.3.4. пишет текущее значение concurrency;

9.3.5. пишет max за период;

9.3.6. показывает предупреждение при `>=3`;

9.3.7. предлагает проверить worktree/stream routing;

9.3.8. предлагает heartbeat только как дополнительный канал, а не как обязательную основу tripwire.

9.4. Где реализовать:

9.4.1. `tools/pipeline.py`;

9.4.2. `logs/pipeline.json`;

9.4.3. `PIPELINE.md`;

9.4.4. возможно `tools/top.py conveyor`.

9.5. Критерии успешности:

9.5.1. при 0-2 активных участниках предупреждения нет;

9.5.2. при 3+ активных участниках появляется advisory;

9.5.3. warning не ломает конвейер;

9.5.4. `validate.py` остается без ошибок;

9.5.5. поведение описано в docs/protocol или рядом с pipeline docs.

10.4. После локального сценария можно сделать второй сценарий:

10.4.1. sandbox intake внешнего репозитория;

10.4.2. read-only анализ README/docs;

10.4.3. карта применимых идей;

10.5.1. отчет в `reports/`;

10.5.2. task update;

10.5.3. если нужен код - отдельный инструмент или wrapper;

10.5.4. если найден новый pattern - decision/question.

10.6. Критерии успешности:

10.6.1. сценарий запускается одной командой или малым набором команд;

10.6.2. read-only границы понятны;

10.6.3. результат пригоден для человека и агента;

10.6.4. нет скрытого исполнения внешнего кода;

10.6.5. есть лог, отчет и путь повторения.

## 11. Фаза 7. Верхний слой управления

11.1. Главная проблема проекта: максимум агентов ограничен не запуском агентов, а способностью верхнего слоя принять, проверить, синтезировать и закоммитить результаты.

11.2. Поэтому нужен "control plane" для людей и агентов.

11.3. Фактически существующий набор команд верхнего слоя, который можно использовать сейчас:

```powershell
python tools\top.py status
python tools\top.py health
python tools\top.py conveyor
python tools\top.py friction
python tools\top.py advice
python tools\top.py take
python tools\top.py snapshot
python tools\top.py synthesize-docs
python tools\top.py work-mode
python tools\top.py workspace-cell
```

11.4. `status` должен отвечать на вопрос "что происходит сейчас".

11.5. `take` должен отвечать на вопрос "какую задачу можно взять или заявить".

11.6. `health` должен отвечать на вопрос "можно ли доверять состоянию".

11.7. `conveyor` должен отвечать на вопрос "кто что взял и где узкое место".

11.8. `friction` должен отвечать на вопрос "какая повторяющаяся проблема уже известна и как ее чинить".

11.9. `advice` должен отвечать на вопрос "какие уже существующие советы применимы к текущим симптомам".

11.10. `synthesize-docs` должен отвечать на вопрос "какие документы нужно свести в consensus/dispute".

11.11. `work-mode` должен отвечать на вопрос "нужен ли shared tree или Level-1 worktree".

11.12. `workspace-cell` должен отвечать на вопрос "какая сейчас компактная карточка task/thread/worktree/outbox/checks".

11.13. Запланированные, но не существующие пока команды нельзя писать как готовые инструкции. Их нужно маркировать `(planned)`:

```powershell
python tools\top.py next        # planned alias / будущая команда
python tools\top.py hygiene     # planned wrapper над repo_hygiene/dir_health
python tools\top.py commit-plan # planned безопасный план коммитов
```

## 12. Фаза 8. Работа с вариантами, дублями и consensus/dispute

12.1. Новая политика должна различать:

12.1.1. плохой дубль очереди;

12.1.2. независимый вариант решения;

12.1.3. частичное совпадение;

12.1.4. консенсус;

12.1.5. разногласие;

12.1.6. нерешенный вопрос.

12.2. Агент не должен преждевременно отказываться от своей версии только потому, что тема уже существует.

12.3. Правильный цикл:

12.3.1. агент создает независимый вариант;

12.3.2. вариант помещается в stream/topic/branch/worktree;

12.3.3. после завершения вариант сравнивается с другими;

12.3.4. совпадающие пункты идут в consensus;

12.3.5. различия идут в dispute;

12.3.6. dispute получает дополнительные вопросы;

12.3.7. после доказательной базы решение идет на ratification;

12.3.8. после ratification правило становится docs/tool/test/skill.

12.4. Для документации нужен такой же sandbox, как для кода.

12.5. Черновые документы:

12.5.1. пишутся в agent-specific stream;

12.5.2. не правят accepted docs напрямую;

12.5.3. имеют front matter;

12.5.4. имеют status: draft/proposed;

12.5.5. имеют ссылку на исходный вопрос.

12.6. Для кода нужен отдельный code-draft режим:

12.6.1. сначала псевдокод;

12.6.2. затем isolated draft;

12.6.3. затем review;

12.6.4. затем test;

12.6.5. затем selective promotion в main code.

## 19. Фаза 15. Многоагентная оркестрация

19.1. Нужно различать два режима, потому что у них разные безопасные потолки.

19.2. Режим A: самостоятельные агенты, которые могут писать в общий канон.

19.2.1. Практический предел: 2-4 активных агента.

19.2.2. Причина: узкое место - синтез, проверка, selective add и коммит.

19.2.3. Для этого режима нужны жесткие правила claim/stream/worktree/commit_queue.

19.3. Режим B: оркестрируемый рой.

19.3.1. Координатор заранее нарезает непересекающиеся файловые пакеты.

19.3.2. Workers не коммитят сами.

19.3.3. Интеграция центральная.

19.3.4. Практический потолок может быть выше: 12-14 одновременных исполнителей и десятки задач в волну, если есть синтезатор и gatekeeper.

19.4. Первый безопасный pilot: 3 workers + 1 coordinator.

19.4.1. Расширение: 3 группы по 3 workers + 1 observer на группу + 1 top coordinator.

19.4.2. Ограничение: больше агентов не означает быстрее, если нет synthesis-gate.

19.5. Роли:

19.5.1. worker: делает независимый вариант;

19.5.2. reviewer: ищет ошибки;

19.5.3. synthesizer: выделяет consensus/dispute;

19.5.4. coordinator: выбирает следующий шаг;

19.5.5. scribe: записывает решения;

19.5.6. gatekeeper: проверяет policy/validate/hygiene.

19.6. Каждый workflow должен иметь:

19.6.1. scope;

19.6.2. allowed paths;

19.6.3. output paths;

19.6.4. stop condition;

19.6.5. review condition;

19.6.6. merge condition.

19.7. Без этого swarm превращается в шум.
