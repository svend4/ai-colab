## Назначение

Эта политика отвечает на вопрос: как многим людям и агентам работать в одной папке, не блокировать друг друга и не коммитить чужую незавершённую работу.

Коротко:

- Git commit — это mainline snapshot, а не место для полусырых идей всех участников.
- Очередь `tasks/` отвечает за исполнение.
- Темы и вопросы отвечают за обсуждение.
- `streams/` отвечает за промежуточные варианты: уже больше, чем текстовый комментарий, но ещё не commit в основную линию.

## Проблема

Если несколько агентов работают одновременно, появляются три риска:

1. Агент делает `git add -A` и случайно коммитит чужие незавершённые файлы.
2. Один агент первым сделал вариант, и другой вариант исчезает как "дубль", хотя мог быть лучше.
3. Общая mainline начинает содержать смесь готового, спорного и полуготового.

Значит нужен промежуточный формат: маленькие "ручейки" вариантов, которые могут течь параллельно, сравниваться и только потом вливаться в основную линию.

## Термины

| Термин | Значение |
|---|---|
| Mainline | Обычные tracked файлы проекта, которые считаются текущим рабочим состоянием. |
| Commit | Снимок mainline. Коммитить можно только осознанно выбранный набор файлов. |
| Stream | Промежуточная ветка мысли/варианта в `streams/`: proposal, patch, notes, evidence. |
| Variant | Один технический подход внутри общего вопроса. |
| Adoption | Решение перенести stream/variant в mainline. |
| Integration commit | Коммит, который специально собирает несколько потоков или чужих изменений после review. |

## Уровни фиксации

### L0. Message

Обычный комментарий в теме или outbox.

Подходит для идеи, замечания, вопроса, короткой критики.

### L1. Variant note

Отдельный Markdown-файл с вариантом A/B/C.

Подходит, если надо сравнить несколько подходов, но ещё нет кода или патча.

### L2. Stream packet

Папка в `streams/`:

```text
streams/<topic-id>/<stream-id>/
  STREAM.md
  notes.md
  patch.diff              # optional
  files/                  # optional proposed files
  evidence/               # optional small reports
```

Это "полу-коммит": структурированный пакет предложения, но не mainline. Его можно читать, ревьюить, сравнивать и потом принять или отклонить.

### L3. Mainline change

Правка обычных файлов проекта: `docs/`, `tools/`, `drivers/`, `tasks/`, `questions/`, `decisions/`.

Должна быть связана с task/claim или явным запросом человека.

### L4. Git commit

Финальный snapshot выбранной mainline-правки.

Коммит не должен случайно включать:

- чужие незавершённые stream/work files;
- чужие generated files, если они не входят в integration scope;
- half-done tasks другого агента;
- sandbox raw sources;
- runtime logs.

## Правила commit для агентов

### C1. Не использовать широкий commit при грязном workspace

Запрещено делать `git add -A` или `git commit -a`, если в workspace есть чужие или непонятные изменения.

Разрешено:

```text
git add <explicit-file-1> <explicit-file-2> ...
git commit -m "scope: message"
```

Только явный список файлов.

### C2. Перед commit проверять три списка

Агент должен понимать:

```text
git status --short --untracked-files=all
git diff --name-only
git diff --cached --name-only
```

Если shell зависает, commit лучше отложить, чем случайно включить чужую работу.

### C3. Коммитить только свою задачу

Обычный commit должен включать:

- файлы, которые агент изменил для текущей задачи;
- generated indexes, если они прямо нужны этой задаче и не содержат чужие незавершённые изменения;
- done/outbox по своей задаче.

Если в generated files уже смешаны изменения другого агента, нужен один из вариантов:

- не коммитить generated files сейчас;
- попросить другого агента завершить/закоммитить своё;
- сделать отдельный integration commit с явным описанием, что объединяется.

### C4. Чужие half-done файлы не трогать

Если видны чужие новые файлы, например `tools/portal.py`, `D-016`, `T-132`, но задача агента про commit policy, их нельзя добавлять в commit.

Можно ссылаться на них в discussion, но не фиксировать за другого агента.

### C5. Сначала stream, потом adoption

Если изменение спорное, архитектурное или имеет несколько вариантов, сначала создать stream packet или variant note.

Mainline менять только после:

- маленького review;
- сравнения критериев;
- task/decision/adoption note;
- явного выбора варианта.

### C6. Один commit — одна мысль

Коммит должен отвечать на один понятный вопрос. Не смешивать:

- sandbox policy;
- portal implementation;
- generated registry refresh;
- unrelated docs cleanup.

Если нужно смешать, это integration commit, и он должен так называться.

## Формат stream packet

Минимальный `STREAM.md`:

```md
---
id: stream-YYYYMMDD-HHMM-agent-short
topic: topic-id
status: draft
author: agent-id
related: [T-000, Q-000]
adoption: none
---

# Название варианта

## Проблема

Что решаем.

## Вариант

Как предлагаем решить.

## Почему это может быть лучше

Критерии и аргументы.

## Риски

Что может сломаться.

## Проверка

Как доказать, что вариант лучше/хуже.

## Что нужно для adoption

Какие условия должны быть выполнены, чтобы перенести в mainline.
```

Статусы:

- `draft` — автор ещё думает;
- `ready-for-review` — можно сравнивать;
- `adopted` — перенесено в mainline;
- `superseded` — заменено другим stream;
- `rejected` — отклонено с причиной;
- `archived` — сохранено как история.

## Stream forks

Если один stream порождает подварианты, не нужно бесконечно делать глубокие папки. Лучше:

```text
streams/<topic-id>/
  2026-06-21-codex-commit-policy/
  2026-06-21-claude-commit-policy-alt/
  2026-06-21-mavis-commit-policy-risk-review/
```

Связь указывать в front matter:

```yaml
parent_stream: 2026-06-21-codex-commit-policy
variant_of: commit-stream-policy
```

То есть "подфорки" существуют, но как плоские ручейки с ссылками, а не как глубокое дерево, которое трудно читать.

## Как stream вливается в mainline

1. Создать или обновить stream packet.
2. Сравнить с другими вариантами в теме или `Q-*`.
3. Зафиксировать adoption note: почему выбран этот вариант.
4. Создать/взять task на перенос.
5. Внести mainline правки.
6. Прогнать проверки.
7. Commit только явных файлов.
8. В stream отметить `adopted` и ссылку на commit/task.

## Когда нужен отдельный Git branch/worktree

`streams/` не заменяет Git branch. Он нужен для лёгких вариантов и полилога.

Branch/worktree нужен, если:

- меняется много кода;
- нужны длительные эксперименты;
- несколько агентов меняют одни и те же generated files;
- нужна CI-проверка до mainline;
- есть высокий риск конфликтов.

Рекомендуемая будущая модель:

```text
stream packet -> agent branch/worktree -> review -> integration commit
```

Но до полноценной branch/worktree дисциплины `streams/` даёт более дешёвую промежуточную ступень.

## Мнение Codex

Я считаю, что это важный слой для большой компании людей и агентов. Обычный Git слишком жёсткий для раннего размышления, а простой Markdown-комментарий слишком слабый для технического варианта с patch/evidence.

`streams/` должен стать местом, где варианты могут жить параллельно, не ломая mainline. Тогда агент не обязан отказываться от идеи только потому, что другой агент первым сделал похожую карточку. Но и mainline не превращается в свалку полусырых изменений.

Правильная дисциплина: **много ручейков, одна проверенная основная линия**.
