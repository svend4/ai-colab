# Методика «FINDER → роутер → SOLVER»

> Два **больших** воркфлоу и оркестратор **в середине**. Один воркфлоу (FINDER) широким фан-аутом
> сканирует весь репозиторий — код, доки, корпус, решения, вопросы, задачи — и находит **проблемы,
> недоделки, открытые вопросы**. Оркестратор (я) **в середине**: получает список находок, делает триаж
> (дедуп / приоритет / классификация / фильтр) и **перенаправляет** отобранное второму большому воркфлоу
> (SOLVER), где тоже много агентов **решают** проблемы. Затем оркестратор **смотрит результаты**, извлекает
> в канон и зацикливает. Это две стадии продюсер→решатель с **человеко-роутер-барьером** между ними.

Слой НАД `docs/orchestration-architecture-2026-06-23.md`: там producer→integrator один контур; здесь два
БОЛЬШИХ контура (поиск и решение) с осознанным барьером-роутером, потому что **не всё найденное надо
решать** — часть дубли, часть out-of-scope, часть требует ратификации.

## 1. Три роли

```
W1 FINDER (большой, много агентов)        РОУТЕР (я, в середине)         W2 SOLVER (большой, много агентов)
┌──────────────────────────────┐         ┌──────────────────────┐       ┌──────────────────────────────┐
│ ~8 scan-агентов по срезам:    │  список │ триаж:               │ отобр.│ 1 solver-агент на проблему:   │
│ code-stubs · docs-gaps ·      │ проблем │ • дедуп vs уже-done  │ задачи│ design / fix / answer / spec  │
│ questions/decisions · tasks · │ ───────►│ • приоритет value×sev│──────►│ + интегратор сшивает результат│
│ machine-findings · conflicts ·│  (P1..) │ • классификация kind │       │                              │
│ tests · bridge/MCP            │         │ • фильтр scope/ratify│       │                              │
│ → синтез: ранжированный список│         │ • выбор «что решать» │       │ → результаты                  │
└──────────────────────────────┘         └──────────┬───────────┘       └───────────────┬──────────────┘
                                                     │ ◄─── смотрю результаты, извлекаю в канон, commit ──┘
                                                     ▼ зацикливаю (новый FINDER по остатку / по новому слою)
```

- **W1 FINDER** — большой read-only воркфлоу. Фан-аут scan-агентов, каждый по своему срезу репо (см. §3),
  возвращает структурные находки `{title, evidence(file:line), kind, severity}`. Синтезатор дедуплицирует
  и ранжирует → **нумерованный список проблем** `P1..Pn` с `suggested_solver` (что и в каком режиме делать).
- **РОУТЕР (я)** — **в середине**. Не авто-пайплайню W1→W2. Получаю список, делаю триаж и **выбираю**, что
  передать SOLVER'у (§4). Это барьер качества и scope.
- **W2 SOLVER** — большой воркфлоу. Один solver-агент на каждую **отобранную** проблему (design/fix/
  answer/spec), интегратор сшивает результаты. Возвращает готовые артефакты.
- **Я снова в середине** — смотрю результаты, перепроверяю, извлекаю в канон, коммичу (дешёвая серийная
  точка, как в reduce-дереве), и **зацикливаю**: следующий FINDER по остатку или по новому слою проблем.

## 2. Почему РОУТЕР в середине, а не авто-пайп W1→W2

Барьер-роутер оправдан (в отличие от дефолтного pipeline §5 конвейера), потому что между поиском и решением
есть **обязательная человеко-/оркестратор-логика**, которую нельзя автоматизировать слепо:

- **Не всё найденное надо решать.** FINDER даёт и дубли, и уже-сделанное, и out-of-scope, и ложные
  срабатывания. Авто-пайп решал бы шум.
- **Приоритизация — мой выбор.** value×severity, что блокирует больше другого, что дёшево.
- **Классификация по режиму.** build (inline/worktree) vs decision/ratify (котёл D-018) vs question (в
  `questions/`). SOLVER-агент не должен сам решать governance — это человеко-гейт (D-006).
- **Дедуп vs канон.** Многое уже описано/сделано в прошлых доках — роутер отсекает по git log + корпусу.

Поэтому W1→роутер — **барьер** (жду весь список, фильтрую), а роутер→W2 — фан-аут только отобранного.

## 3. FINDER: срезы сканирования (полный охват репо)

Каждый срез — отдельный scan-агент (read-only), может звать `repo_search.py`, grep, Read, и машинные
детекторы. Срезы (ортогональны, покрывают весь репозиторий):

1. **code-stubs** — `tools/*.py`: `TODO/FIXME/не реализован/stub/заглушка`, функции-печатают-«not implemented».
2. **docs-gaps** — `docs/*.md`: разделы «Дальше», `proposed`-не-сделанное, «not yet implemented» (возможно протухшее).
3. **questions/decisions** — `questions/Q-*` (open) + `decisions/` (нератифицированное, висячее).
4. **tasks-backlog** — `TASKS.md`/`board.md`/`tasks/` (todo/doing/blocked) + перспективный бэклог vs git log.
5. **machine-findings** — прогон `assurance.py` / `drift_check.py` / `friction.py status` / `reconcile_state.py check`.
6. **corpus-conflicts** — `topics/` + subsystem-доки + `data/`: синтез-док заявляет связь, которой нет в коде (паттерн F-020).
7. **test-coverage** — `tools/*.py` без `test_*.py`; тесты только happy-path; свежие тулзы без тестов.
8. **bridge/MCP** — `drivers/`/gateway: draft-vs-ready, acceptance-блокеры, `mode:execute` гейты, неимплемент. MCP-инструменты.

Синтезатор: дедуп (отсечь уже-shipped по git log + дубли срезов), ранг по severity×value, нумерация `P1..Pn`.

## 4. РОУТЕР: триаж и редирект (что делает оркестратор в середине)

1. **Принять** список `P1..Pn` от FINDER (структурный, не проза).
2. **Дедуп vs канон/git** — выбросить уже-сделанное (F-020/two-spine/порталы уже зашиплены и т.п.).
3. **Классифицировать kind→режим:** bug/undone→build (inline если мой-чистый, worktree если co-owned),
   open-question→`questions/`, gap/conflict→design, ratify→котёл (D-018), missing-test→test.
4. **Приоритизировать** value×severity; отсечь out-of-scope/заблокированное (напр. assurance.py под QA).
5. **Отобрать** N решаемых сейчас (под полосу обработки — `agent-capacity-methodology.md`: биндит коммит, не агенты).
6. **Перенаправить** отобранные в W2 SOLVER (по одному solver-агенту на проблему + интегратор).
7. **НЕ передавать** в SOLVER: governance/ratify (в котёл), заблокированное премис-сейфти, дубли.

## 5. SOLVER: фан-аут решателей + интеграция

- Один **solver-агент на отобранную проблему**: по `suggested_solver` делает design/fix/answer/spec,
  возвращает структурный результат `{problem_id, result, artifact, status}`.
- **Интегратор** сшивает результаты в один отчёт/набор артефактов.
- Режим контенции (как в конвейере §6): solver'ы read-only/design — свободно параллельны; build-solver'ы —
  worktree или сериализованный коммит; ratify — не в SOLVER, а в котёл.
- Я принимаю готовое → перепроверяю → извлекаю в канон → **батч-commit** (единственная серийная точка).

## 6. Активация (рецепт)

1. **Запустить W1 FINDER** (большой, ~8 scan-агентов + синтез). Зарегистрировать `conveyor.py launch`.
2. **Не ждать впустую** — параллельно держать конвейер (другие ноды), §3-bis конвейера.
3. **На приземлении W1** — РОУТЕР: триаж (§4), отобрать решаемые сейчас.
4. **Запустить W2 SOLVER** по отобранным (фан-аут solver + интегратор). Зарегистрировать.
5. **На приземлении W2** — смотреть результаты, перепроверить, извлечь в канон, **батч-commit**.
6. **Зациклить:** следующий FINDER по остатку/по новому слою (как `topics/new-problems-2026-06-23.md` →
   назначение группы). FINDER может быть **рекуррентной** нодой (само-кормление, §3-bis).

## 7. Сбои и границы

- **Ложные находки FINDER** → роутер фильтрует (барьер для того и есть); solver не тратится на шум.
- **W2 solver частично провалился** → salvage хороших + перезапуск только провалившихся (мелкий фан-аут).
- **Граница — полоса коммита** (`agent-capacity-methodology.md`): сколько результатов W2 успеваю извлечь+
  закоммитить, столько проблем и отбираю в роутере. FINDER находит много — SOLVER берёт ровно посильное.
- **Governance не автоматизируется:** ratify-проблемы роутер уводит в котёл (D-006/D-018), не в SOLVER.

## 8. FINDER под конкурентной мутацией (shared-tree)

FINDER — долгий read-only скан, а ДРУГИЕ агенты (Codex) одновременно коммитят и правят те же
файлы. Это «движущаяся мишень»: (а) scan-агенты видят **несогласованный снимок** (агент A прочитал
файл до чужого сохранения, B — после); (б) находки **stale-on-landing** (заявлено «X не сделано», а
сосед уже починил). Подтверждено замером: за один скан — 1 чужой коммит + ~20 файлов в незакоммиченной
правке, включая центральные для срезов.

Почему не фатально — **барьер-роутер именно для этого**: выход FINDER не авто-правки, а заявки-кандидаты,
которые роутер **пере-verify против реальности-на-момент-landing** перед действием. FINDER не мутирует
сам → худший случай stale-находки = впустую потраченная переинспекция, не плохая правка.

Дисциплина (в порядке силы):
1. **Snapshot-изоляция (правильная починка для НОВОГО FINDER):** запускать скан против ОДНОГО
   неизменного git-ref — worktree на фикс-коммите или агенты читают `git show <ref>:path`. Все агенты
   видят одно состояние; находки внутренне согласованы. То же, что Level-1 worktree-изоляция (D-022),
   но применённое к **чтению**.
2. **Churn-reconcile на landing (обязательно всегда):** до роутинга считать дельту
   `git diff <base>..HEAD` + незакоммиченное (`git status`); пере-verify каждой решаемой находки против
   текущего HEAD+working-tree, приоритет — churned-файлы; **дроп** того, что сосед уже закрыл.
3. **Премис-исключение:** находки на файлах, которые СЕЙЧАС правит сосед, роутер НЕ берёт inline
   (premise-конфликт) — помечает «сосед владеет», ждёт его landing.
4. **Advisory-only / idempotent:** FINDER никогда не авто-мутирует; короткая одна волна сужает окно
   движущейся мишени.

**Итог.** FINDER (широкий поиск) → роутер (я: дедуп/приоритет/фильтр/выбор) → SOLVER (широкое решение) →
я (извлечь+commit) → цикл. Оркестратор всегда в середине как барьер качества и точка редиректа; два больших
воркфлоу несут дорогую работу, серийной остаётся только дешёвая интеграция в одну историю.
