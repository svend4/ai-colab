# Политика коммитов и параллельной работы — консенсус двух агентов

> Чистовой консенсус-документ. Сюда сведено только то, что **оба** агента (Claude — `docs/parallel-work-policy.md`, Codex — `docs/commit-stream-policy.md`) утверждают согласованно, подтверждённое двумя независимыми семантическими проходами. Каждый пункт несёт cross-ref на оба источника. Разногласия и одностороннее покрытие вынесены в отдельный документ расхождений.

## Принцип

Несколько агентов работают в одной папке одновременно. Цель — убрать «ожидание другого агента» и потерю работы при коллизиях, не загрязняя mainline получерновыми изменениями. Достигается дисциплиной коммитов плюс промежуточным/изолирующим слоем перед mainline.

## Консенсус-пункты

### 1. Не коммить то, что не менял осознанно (selective-add)
Запрещён `git add -A` / `git commit -a` при грязном или непонятном workspace. Всегда явный список файлов; агент обязан понимать, что представляет каждый файл, прежде чем стейджить.
- A: `docs/parallel-work-policy.md:67` (анти-паттерн: DO NOT use `git add -A`), также `:124`, `:163`, `:182`
- B: `docs/commit-stream-policy.md:88-99` (C1: запрет широкого commit при грязном workspace)

### 2. Чужую недоделанную работу не коммитить
Незавершённые source-файлы другого агента не включаются в коммит, даже если они видны в `git status`. На них можно ссылаться в обсуждении, но не фиксировать за другого. Не предполагать, что коллега сам закоммитит, — изолироваться, а не ждать и не теребить.
- A: `docs/parallel-work-policy.md:73` (анти-паттерн: не предполагать, что коллега закоммитит; изолироваться)
- B: `docs/commit-stream-policy.md:127-131` (C4: чужие half-done файлы не трогать)

### 3. Перед коммитом проверять состояние рабочего дерева
До коммита агент инспектирует `git status`, `git diff` и staged-изменения (а также `generate.py --check`), чтобы понять состояние и поймать stale/неожиданные изменения. Если shell зависает — лучше отложить коммит, чем случайно захватить чужое.
- A: `docs/parallel-work-policy.md:69` (анти-паттерн: не пропускать `generate --check` перед commit)
- B: `docs/commit-stream-policy.md:101-111` (C2: проверять три списка перед commit)

### 4. Атомарная граница коммита (один commit — одна мысль)
Один коммит отвечает на один понятный вопрос (одна задача / одно решение / один scope рефакторинга). Смешивать несвязанное (sandbox + portal + регенерация реестра + чистка доков) нельзя — кроме явно названного integration commit.
- A: `docs/parallel-work-policy.md:108` (атомарная граница: один commit = один ясный ответ)
- B: `docs/commit-stream-policy.md:144-153` (C6: один commit — одна мысль; смешивание — только именованный integration commit)

### 5. Генерируемые индексы держать синхронными с источниками
Канонические индексы (`TASKS.md`, `DECISIONS.md`, `index.json`) должны соответствовать своим source-файлам. Нельзя коммитить stale-индексы или индексы, загрязнённые чужой half-done работой, — это портит навигацию для остальных. Коммитить индексы только если они отражают **исключительно** текущую задачу и не содержат чужого незавершённого.
- A: `docs/parallel-work-policy.md:68` (анти-паттерн: не коммитить STALE generated files), `:88` (источники + их индексы одним атомарным commit), `:165`
- B: `docs/commit-stream-policy.md:113-125` (C3: generated indexes только если отражают эту задачу и без чужого half-done)

### 6. Волатильные/рантайм-файлы не версионируются
`LIVE.md`, `PIPELINE.md`, `board.md`, heartbeat- и pipeline-логи, рантайм-снимки не стейджатся и не коммитятся в обычных коммитах — это эфемерные средства мониторинга, не исторический record. Если нужна запись состояния — скопировать в постоянный документ (отдельный snapshot-commit с явным сообщением), но не сам волатильный файл.
- A: `docs/parallel-work-policy.md:20` (работа только в волатильных файлах не триггерит worktree; исключить из add), `:89`, `:103`, `:164`
- B: `docs/commit-stream-policy.md:74-84` (L4: коммит не должен включать runtime logs, чужой half-done, sandbox raw sources)

### 7. Спорные/многовариантные изменения — сначала промежуточный слой, потом mainline
Контентные, архитектурные или многоподходные изменения готовятся в лёгкой промежуточной форме (stream packet / variant note / adjacent fork) до интеграции в mainline. Это защищает mainline от загрязнения и даёт структурированное параллельное сравнение. Mainline меняется только после review, сравнения критериев и явного выбора варианта (adoption note).
- A: `docs/parallel-work-policy.md:39` (порог fork-variant; малые doc-варианты — через streams/Level-0), `:90-92` (Вариант-2: adjacent forks для мелких ревью)
- B: `docs/commit-stream-policy.md:133-143` (C5: сначала stream, потом adoption), поток adoption `:225-234`

### 8. Параллельная работа в общих зонах требует изоляции
Когда несколько агентов одновременно правят пересекающиеся зоны или один и тот же файл, нужна некоторая форма изоляции (worktree, variant-stream или явная синхронизация), чтобы не блокировать друг друга. В частности, для same-file правок selective-add недостаточно — нужен изолирующий механизм с последующим сведе́нием.
- A: `docs/parallel-work-policy.md:5-6` (цель: убрать ожидание и потерю работы), `:38`, `:59` (same-file нельзя решить selective-add)
- B: `docs/commit-stream-policy.md:236-246` (branch/worktree нужен, когда несколько агентов меняют одни и те же generated files)

### 9. Аварийный обход — только с одобрением и пост-фактум-синтезом
Только в критических ситуациях (security / data-loss / блокер) допустим обход нормальной эскалации: быстрый путь требует явного одобрения (Stefan/maintainer), логируется и сопровождается документированным пост-фактум-синтезом/решением.
- A: `docs/parallel-work-policy.md:25` (экстренный hot-fix: approval + URGENT merge + post-hoc синтез), `:42`, `:52`
- B: `docs/commit-stream-policy.md:236-246` (branch-путь для случаев, требующих CI-проверки до mainline) — частичное пересечение; см. расхождения
