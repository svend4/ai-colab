## 1. Уровень-1 (worktree) vs Уровень-0 (общее дерево) — триггеры

**Принцип:** Level-1 (per-agent git worktree with isolated index, branch `agent/<agent>/<task>`) is MANDATORY when any of three trigger-conditions are met: (1) uncommitted source-files from coworkers exist in git status, (2) STALE generated indexes detected from coworker tasks, (3) hot-file edits (TASKS.md, PIPELINE.md, tools/top.py, generators, etc.) are planned. Level-0 (selective-add + commit_lock in shared tree) remains the cheap default for isolated work. The decision is binary: detect triggers → enforce worktree OR proceed with Level-0 safeguards.

**Пороги/триггеры:**
- Uncommitted source-file detection: ANY modified file (M-code in git status) in SOURCE_DIRS (tasks/, decisions/, questions/, tools/, drivers/, docs/, topics/) from a non-current-agent triggers worktree-mandatory immediately.
- STALE index threshold: generate --check exit-code != 0 OR output contains 'STALE' or 'устарел' AND stale sources are not from current agent's own staged work → worktree-mandatory.
- Hot-file edit threshold: ANY planned edit to HOT_FILES (TASKS.md, QUESTIONS.md, DECISIONS.md, index.json, PIPELINE.md, tools/top.py, tools/portal.py, tools/generate.py, tools/capabilities.py, board.md, STATUS.md) → worktree-mandatory.
- Task size threshold for large-file risk: changes touch >5 files OR span >3 distinct source-directories AND coworker has active claim (queues/claimed/*.claim.md with timestamp <5 min) → worktree-recommended (escalate if commit_lock BUSY >30s).
- Same-file collision detection: git status shows same file modified under multiple non-staging-area codes AND different claimed agents own those claims → worktree-mandatory.
- Coworker activity timeout: If coworker's last claim ended >10 minutes ago AND no new uncommitted source-files from that zone appear in git status, Level-0 is safe. Refresh check via generate --check before each commit.
- Volatile-file exclusion: LIVE.md, queues/*, *~, *.tmp, .git/* are not commit-scope; their presence in git status does not trigger worktree. Exclude them from add/commit logic.
- Emergency-override approval: Worktree or fast-track merge requires explicit Stefan/maintainer approval. Log override reason and timestamp in commit message.
- Fork-variant threshold: If D-017 parallel variant exists in streams/ or docs/ with status='proposed' or 'ready-for-review' AND current work is <50% rewrite of that file → use Level-0 + stream adoption. Only escalate to worktree if rewrite is architectural.
- Stale-regenerate loop limit: If agent must run `generate.py` >5 times in a single task due to stale-index from coworkers → worktree is now mandatory for remaining work.

**Edge-cases:**
- Merge-conflict on generated files: If worktree-merge detects conflicts in TASKS.md, index.json, or board.md (generated files), merge-gate should re-run generate.py on the merged commit to produce canonical versions, not accept hand-merged generated files.
- Stale-index false-positive: generate --check may flag stale if a coworker just staged+committed but push hasn't propagated. Agent should retry generate --check after 2–3 seconds before escalating.
- Same-file fork (LS-2 case): If both agents have uncommitted changes to one file, neither can use Level-0 safely. Both MUST migrate to worktree or one must pause. No selective-add discipline avoids this collision.
- Worktree-local stale: Agent creates worktree, generates locally (fresh index), but merge-gate re-runs generate and sees different output due to newer coworker commits to source-files. Merge-gate must approve the merged state, not require rebase. This is why merge-gate is final validation.
- Hot-file cascade: If tools/generate.py or tools/top.py changes, nearly all subsequent agent-work may need regeneration. The agent editing hot-files MUST use worktree and signal all coworkers that regeneration is needed post-merge.
- Task with no claim (orphan): If git status shows uncommitted source but no active claim matches, assume it's a stray previous session. Query agent/owner via cohort board; if unknown, do NOT attempt Level-0 commit—escalate or wait for owner to clarify.
- Windows CRLF vs LF in source-files: If coworker committed LF-files and current agent's git config is CRLF, git status may show all files as modified. Use `git status --porcelain` and check actual byte-diffs before deciding on Level-0 vs Level-1.
- Timeout waiting for commit_lock: If commit_lock acquire times out (BUSY >120s from cohort.py), Level-0 is failing due to lock contention. Escalate immediately to worktree to reduce global lock pressure.

**Анти-паттерны:**
- DO NOT use `git add -A` in a shared tree unless this is an explicitly named integration commit with prior approval. Always use selective-add (`git add <file> <file> ...`).
- DO NOT commit generated files (TASKS.md, index.json, PIPELINE.md) if they contain uncommitted changes from coworkers. Either wait for coworker to stage+commit their sources, or escalate to worktree.
- DO NOT skip generate --check before commit. It is the canonical test for index freshness. If it fails, do NOT force-commit; either fix the staleness or use worktree.
- DO NOT treat STALE output as a suggestion—treat it as a blocker. STALE indexes corrupt downstream reading of task/decision state.
- DO NOT create a worktree and then continue working in the shared tree in parallel. Pick one: either worktree-only for the task, or shared-tree-only. Mixing causes index-sync confusion.
- DO NOT merge a worktree without running merge_gate --check first. The gate is not optional; it re-validates freshness, permissions, and test-status at merge time.
- DO NOT assume a coworker will commit their half-done work. If you see their uncommitted source-files, assume they are STILL working and go to worktree. Do not wait and do not nag—just isolate.
- DO NOT use commit_lock acquire in a loop with exponential backoff >10 retries. After 3 failures (BUSY), escalate to worktree. The lock is advisory, not a guarantee.
- DO NOT override hot-file edits by another agent in the same session. If you both need to edit tools/top.py, use different worktrees and merge-gate will signal the conflict.
- DO NOT leave a worktree abandoned without removal. After merge or abort, run `python tools/worktree.py remove <agent> <task>` to clean up the directory and branch.

## 2. STALE-индекс — авто-регенерация vs ожидание

**Принцип:** Agents in a shared repository must avoid blocking each other while preventing accidental commits of half-done work. This requires three layered mechanisms: (1) Level-0: serialized git operations + selective-add discipline in a shared tree, a cheap baseline; (2) Level-1: per-agent git worktrees with isolated generated indexes + merge-gate, activated by specific triggers (Q-015 B); (3) generated file strategy: split canonical indexes (TASKS/DECISIONS/index.json, committed when source changes) from volatile snapshots (LIVE/heartbeat/logs, not committed), preventing false STALE cascades. When two agents modify the same file, worktree+merge replaces content forks when the work is large; Variant-1 (worktree): triggers when multiple source files are involved or merge conflicts are likely (architectural work, large refactors). Variant-2 (adjacent forks): triggers for narrow reviews and small edits (one-file-one-claim, separate docs/<name>-<agent>.md, explicit synthesis later). Variant-3 (accept rewrite + synthesis after): reserved only for specific approved cases where clean overwrite + documented synthesis is cheaper than merge conflict resolution. The STALE-index problem is the crux: Level-0 does not solve shared generated-state coupling. Auto-regenerate + commit-your-own is the cohort-ship standard (not wait), treating canonical vs volatile distinctly.

**Пороги/триггеры:**
- Level-0 remains default for isolated work: one agent, no other uncommitted source changes visible, no hot-file modifications, generated index is fresh (generate --check passes). Use Level-0 for small reviews, documentation edits, isolated refactors.
- Level-1 mandatory trigger (Q-015 B, cohort.guard): if any of {foreign uncommitted source-file + no explicit claim, stale generated index from another agent's task, hot-file concurrent modification} is detected. Do NOT attempt Level-0 commit; go to worktree.
- Same-file fork Variant-1 (worktree+merge): when the change touches 3+ files OR the single file change is substantial (10+ logical changes, architectural, high conflict risk). This is the default assumption when two agents both want to modify one file.
- Same-file fork Variant-2 (adjacent forks): when the change is narrow (1–2 files), tactical (< 5 changes per file), and the review is about comparing approaches. Synthesis is explicit and manual (e.g., Stefan picks one). This is cheaper than merge for small, opinionated changes.
- Same-file fork Variant-3 (overwrite+synthesis): RESERVED for explicit Stefan approval only. Not a default path. Used when sequential generation (A drafts, B rewrites from scratch) is faster than parallel merge conflict resolution.
- Canonical index commit threshold: ALWAYS commit TASKS.md, DECISIONS.md, index.json when you commit the source files they reflect (tasks/*.md, decisions/*.md, questions/*.md, or drivers/*/manifest.json). Omitting canonical index update is a red flag (stale history).
- Volatile file non-commit threshold: NEVER stage or commit LIVE.md, PIPELINE.md, logs/heartbeat.json, logs/pipeline.json (gitignored per T-148/D-012), or any runtime snapshot files (matching docs/runtime-*, agent session logs). Copy to permanent docs for record-keeping; do not commit volatiles. board.md and STATUS.md are NOT in this list — they are canonical generated files (D-022 п.3) and MUST be committed with their sources (see canonical index commit threshold above).
- STALE index tolerance: if generate --check shows STALE state caused by foreign uncommitted work, do NOT proceed with Level-0 commit. Wait <5 min for their commit OR switch to Level-1. Do NOT regenerate-and-commit their half-done state.
- Worktree merge resolution threshold: if a merge_gate detects conflicts between two worktree branches, do not auto-merge. Escalate to integrator or request manual review. Conflicts are a sign that coordination or sequential ordering is needed.
- Stream packet lifecycle: max 7 days in 'draft' or 'proposed' status without adoption decision. After 7 days, stream is archived or escalated to decision (Q/D). Prevents 'graveyard' accumulation.
- Hot-file edit serialization (Level-0 fallback): if forced to stay in Level-0 and hot files are contended, use commit_lock with TTL ~120s. If lock is BUSY >2 times, escalate to Level-1.
- Commit message atomic boundary: one commit = one clear answer (one task, one decision, one refactor scope). Do NOT mix sandbox policy + portal + generated registry + unrelated docs cleanup in one commit. If needed, use integration commit with explicit naming.

**Edge-cases:**
- Nested stale states: My source is uncommitted, foreign source is uncommitted, but foreign source affects my source (circular dependency or cascade). Solution: both agents enter Level-1 independently, resolve in merge_gate or explicit coordination stream.
- Generated index update-during-commit: While I am running git commit, another agent runs generate.py. The regenerated file may be newer than my staged version. Use commit_lock to serialize; the lock wraps generate+add+commit atomically.
- Worktree branch collision: Two agents try to create `agent/codex/T-042` simultaneously. Solution: worktree.py uses `git worktree add --quiet` which fails fast if path exists; agent retries with a unique suffix (e.g., `agent/codex/T-042-b`). Atomic claim in pipeline.py prevents task duplication.
- Merge conflicts with generated indexes: When two worktrees merge, TASKS.md from both have different structure (both regenerated locally). merge_gate re-runs generate.py on mainline post-merge to make indexes canonical. Worktree-local indexes are NOT merged; they are discarded.
- Volatile-snapshot-in-stream: A stream packet includes LIVE.md as evidence of a session state. When stream is adopted, LIVE.md is copied into a permanent doc (e.g., `evidence/session-snapshot.md`), then volatile LIVE.md is not committed.
- Same-file fork with divergent dependencies: Variant-2 (adjacent docs) works when variants are independent opinions. If they have data dependencies (one variant imports data from another), escalate to Variant-1 (merge) or sequential ordering.
- Stale index in pre-commit hook: Hook runs `generate --check`, finds index stale. If stale is due to my uncommitted source, re-run `generate.py` and retry commit (automatic in cohort.py ship). If stale is due to foreign source, hook BLOCKS (by design). Agent must resolve: wait for foreign commit, OR escalate to Level-1.
- Concurrent merge-gate requests: Two worktrees request merge at the same time. merge_gate is single-owner (Stefan/integrator). First request is queued, second must wait. If wait > 5 min, escalate to process review (merge-gate bottleneck, need more integrators or batch merges).
- Worktree branch lingering after merge: A worktree merges successfully, but the branch `agent/codex/T-042` is not auto-deleted. Solution: after merge_gate approval, `git worktree remove` is part of finish sequence; if forgotten, cron job cleans up branches older than 7 days.
- Canonical index cascade: T-045 references D-050, D-050 references Q-100. All three are new. regenerate must order them correctly (topological sort). generate.py assumes index.json defines the order; if circular dependency exists, generate fails (by design). Agent must break cycle with explicit sequencing stream.

**Анти-паттерны:**
- Anti: 'Waiting for foreign commit' in Level-0 when triggers are active (foreign source visible, stale index). Use Level-1 instead. Waiting is the problem Level-1 solves.
- Anti: `git add -A` in shared tree with dirty working directory. Always use explicit file list, even in Level-0. Cohort.py ship enforces this.
- Anti: Committing volatile snapshots (LIVE.md, PIPELINE.md, logs/heartbeat.json, logs/pipeline.json). They become stale immediately and pollute history. Copy to permanent docs for records. (board.md and STATUS.md are canonical generated files and ARE committed with sources — D-022 п.3.)
- Anti: Regenerating indexes when stale is caused by foreign uncommitted work, then committing. This captures foreign half-done state. Instead: wait for foreign commit, or switch to Level-1.
- Anti: Merging two worktrees' regenerated indexes by hand (taking both TASKS.md versions). merge_gate re-runs generate.py post-merge; hand-merging indexes is redundant and likely wrong.
- Anti: Same-file fork Variant-3 (overwrite) without explicit approval and stream documentation. This risks losing one agent's work. Default to Variant-1 (merge) unless specifically approved.
- Anti: Committing source file without committing its canonical index in the same atomic commit (e.g., task/T-100.md committed alone, TASKS.md left stale). This breaks the navigational contract.
- Anti: Creating streams and leaving them in 'draft' status indefinitely without adoption or rejection. Set a deadline (7 days) and archive/escalate if no decision.
- Anti: Multiple agents editing the same task file within Level-0 shared tree, each expecting their edits to merge automatically. Worktree or sequential ordering required.
- Anti: Attempting merge_gate check without running generate.py locally first. merge_gate expects the worktree to have fresh local indexes; otherwise, false STALE reports.
- Anti: Ignoring cohort.guard recommendations. If guard says 'Level-1 required', Level-0 commit will likely hit stale-index hook failure or half-done conflicts.
- Anti: Using Variant-2 (adjacent forks) for substantial refactors (100+ lines, multiple functions). Synthesis overhead grows; Variant-1 (merge) is cleaner. Variant-2 is for reviews and comparisons, not rewrites.
- Anti: Leaving commit_lock locked indefinitely. Always call `commit_lock release` in a finally-block or timeout. Deadlock otherwise.
- Anti: Merging worktree branches with git merge --theirs or --ours without merge_gate review. Both can hide the conflict; gate runs generate to resolve.
- Anti: Treating hot-file (TASKS.md, index.json) edits as low-priority in Level-0. Hot files are high-contention; if you must edit them, use Level-1 or explicit commit_lock coordination.

**Пороги/триггеры:**
- ОБЯЗАТЕЛЕН Level 1, если git status --porcelain показывает незакоммиченные files в tasks/, questions/, decisions/, topics/, drivers/, или streams/*/STREAM.md от других агентов
- ОБЯЗАТЕЛЕН Level 1, если `python tools/generate.py --check` выводит STALE для ANY из (STATUS.md, board.md, TASKS.md, QUESTIONS.md, DECISIONS.md, index.json)
- ОБЯЗАТЕЛЕН Level 1, если задача трогает файлы из HOT FILES группы: tools/top.py, tools/generate.py, tools/pipeline.py, tools/merge_gate.py, tools/cohort.py, _canon/*, core-export/*, portal-specs/*, drivers/index.json
- OPTIONAL Level 0, если git status чист, generate.py --check зелёная, файлы не hot, и это одиночная опечатка/мелкая исправление
- ЗАПРЕЩЕНО в Level 0: `git add -A` в грязном дереве; REQUIRED: явно перечислить files через `git add file1 file2`
- ВОЛАТИЛЬНЫЕ файлы (PIPELINE.md, LIVE.md, logs/pipeline.json, logs/heartbeat.json, logs/heartbeat/*.json) по умолчанию НЕ коммитятся; исключение: явный snapshot-commit со специальным сообщением 'snapshot:...'

- worktree-ветка должна обновляться из мейнлайна перед finish (git rebase или git merge origin/master), чтобы merge была ff или clean
- Stream статус MUST быть one of: proposed, adopted, superseded, rejected, archived. Без статуса stream считается orphan и может быть выпилен

**Edge-cases:**
- Одновременная правка ОДНОГО файла двумя агентами (например decisions/D-018.md): Level 0 merge conflict. Разрешение: раньше коммитивший выигрывает, второй pulls + resolves вручную. Prevention: Level 1 для governance-files.
- Stale index.json из-за того, что только что была создана задача T-14X (например), но ещё не коммичена: `git status` показывает задачу как untracked, generate.py --check краснеет (т.к. не видит T-14X в source). Это нормально и ОЖИДАЕМО. Решение: агент ждёт commit создателя T-14X ИЛИ сам коммитит T-14X (если owner согласен) ИЛИ работает в Level 1.
- Worktree-ветка не заканчивается, потому что merge-gate отклонила (красные тесты). Что дальше: агент фиксит тесты ЛОКАЛЬНОв worktree, новый commit, merge-gate прогон снова. Если не может фиксить (например, тест падает из-за чужого изменения на mainline) → агент pulls origin/master в worktree, разрешает конфликты, снова коммитит локально, merge-gate повторно.
- PIPELINE.md обновилась во время Level 1 работы (другой агент кончил T-X и запустил pipeline.py done). Твой worktree PIPELINE.md старый. При merge: мейнлайн видит финальное PIPELINE.md. Это ОК, потому что PIPELINE.md волатилен, и final state на mainline после merge будет правильным.
- Заблокированный merge-gate: test_*.py падает из-за bug, который не в твоём коде. Escalation: отправляешь сообщение Stefan/review-owner. Можно попросить `merge_gate.py ... --skip-tests` для скоро-исправного-bug или `--manual-approval` (требует human ввода). Иначе wait.
- Случай 'сделать snapshot на конец работы': после finish workflow, перед удалением worktree, ты можешь запустить `pipeline.py snapshot --record` для сохранения конечного PIPELINE.md/logs/ в отдельном файле (например reports/2026-06-22-T-146-complete.json), затем удалить worktree.
- Вопрос: коммитить ли 'пересчитанный' index.json если ничего не изменилось в sources? Ответ: ВООБЩЕ НЕ КОММИТИТЬ. В git diff он будет выглядеть как no-op, и commit будет пусто. merge-gate отклонит пустой commit.
- Volátil race: agent1 запустила generate.py, видит чистый index.json. Agent2 одновременно создал T-14X.md и ещё не коммитила. Agent1 не видит T-14X в git status (т.к. он untracked, а `git status` может быть cached). Потом agent1 коммитит старый index.json. Это маловероятный race, но prevention: перед generate.py запусти `git add -A --dry-run` или `git status` дважды.
- Merge-gate + worktree: если merge-gate запущена на agent1/feature и agent1 потом меняет код В MAINLINE (не в worktree), что происходит? Worktree-ветка отстаёт от mainline. Solution: перед finish — `git rebase origin/master` в worktree, потом merge-gate повторно.

## 4. Same-file параллелизм — Вариант 1 / 2 / 3

**Принцип:** Агенты работают параллельно без блокировки друг друга и без коммита чужой недоделанной работы. Три совмещённых слоя разрывают связку: (1) commit-lock + selective-add сериализует git-операции и защищает от захвата чужих файлов (Уровень 0); (2) worktree+merge-gate изолирует рабочее дерево и генерируемые индексы (Уровень 1); (3) для файлов, которые правят несколько агентов, выбор инструмента зависит от размера работы, типа (code vs doc), роли (author vs reviewer), и механики (mechanical vs substantive edit) — три конкурирующих варианта (worktree+merge / один-файл-один-claim+fork-рядом / accept-rewrite+synthesize-after) активируются разными триггерами и покрывают разные типы коллизий.

**Пороги/триггеры:**
- Level 1 worktree ОБЯЗАТЕЛЕН при ЛЮБОМ из пяти триггеров (Q-015 вариант B): (1) чужие незакоммиченные canonical files в git status; (2) STALE generated index из-за чужой active task (progнoz via tools/top.py work-mode); (3) правка hot files (TASKS.md, index.json, tools/top.py, tools/portal.py, генераторы); (4) явный запрос многоагентной работы; (5) same-file collision prediction.
- Вариант 1 (worktree+merge) используется, когда: размер файла >500 строк, code-фокус, substantive изменения (не review-правки), нет явного claim (или claim-owner одобрил параллельную работу). Может быть обязателен в areas: крупная архитектура, production-инструменты, critical-system-files.
- Вариант 2 (один-файл-один-claim+fork-рядом) используется, когда: 100–500 строк, есть явный owner (claim), review-правки (не новая фича), docs или утилиты (не production-code). Собственник вливает идеи из fork, коммитит сам.
- Вариант 3 (accept-rewrite+synthesize-after) используется ТОЛЬКО, когда: <100 строк, draft-status (не API), быстро развивающийся инструмент, оба агента кооперативны, ОБЯЗАТЕЛЕН синтез-шаг потом (иначе идеи первого агента потеряны). ЗАПРЕТ на production-code и critical-files.
- Commit-lock (Level 0) — TTL ≈ 120 секунд; если агент упал, лок автоматически освобождается. Retry-логика: wait + retry до 3× (не infinite loop).
- Stream-пакеты (полу-формат): status: draft → ready-for-review → adopted/superseded/rejected/archived. Таймаут proposed-stream без adoption: max ≈ 7 дней (потом flag as obsolete). Enforcement: tools/stream.py check (SHIPPED 2026-06-23, commit 686a0fb; tools/stream.py:292, P-11 graveyard detector — флагует stale/broken stream-пакеты).
- Merge-gate (Level 1 finish): validate() + generate --check + permissions-check зелёные = fast-forward либо merge-commit. Merge-owner (Stefan/интегратор) принимает решение о слиянии; автоматический bot только при явной pre-approval и trivial fast-forward.
- Hot-files list (trigger C): TASKS.md, QUESTIONS.md, index.json, PIPELINE.md, LIVE.md, tools/top.py, tools/portal.py, tools/flow.py, _canon/*, генераторы (generate.py, promote.py, capabilities.py), shared registry-файлы. Правка любого → Level 1 worktree обязателен.
- Same-file collision detection (trigger E): если git status показывает файл как modified by agent A и agent B начинает писать в тот же файл → предикция Level 1 обязателен. Tools/top.py work-mode <agent> <task> → should output recommendation.
- STALE generated index detection (trigger B): tools/top.py work-mode или preflight check перед commit → если generate.py --check красный из-за чужого active claim (не своих изменений) → уведомление о Level 1. Не блокировка (агент может рискнуть Level 0), но явное предупреждение.
- Selective-add правило (Level 0 дисциплина): НИКОГДА git add -A в грязном дереве; только git add <explicit-paths>. Проверка: pre-commit hook ЕСТЬ (SHIPPED commit 0f74e61; tools/githooks/pre-commit) — он блокирует коммит на validate.py ERROR + generate.py --check (:45-57). Оговорка: хук НЕ детектит сам факт `git add -A` напрямую (специальной wide-add-пробы пока нет); selective-add остаётся дисциплиной + покрывается gate-poison/F-020, который ловит результат отравленного стейджа.
- Merge-conflict разрешение: при Level 1 worktree merge двух притоков → конфликты разбирает merge-owner (иерархический: Stefan > назначенный интегратор > author if no integrator). Для большого конфликта → возможна rebase/cherry-pick вместо merge-commit (в зависимости от истории).
- Orphan worktree cleanup: worktree не finish'ед >24 часа → tools/flow.py check warn. Рекомендация: finish в одной сессии (не создавать паразитные ветки). Старые orphan можно удалить (git worktree remove <path>) после проверки что не потеряется.
- Claim-система взаимодействие с варiantами: Вариант 2 предполагает наличие claim (owner). Если claim отсутствует, Вариант 2 трансформируется в Вариант 1 (две конкурирующих ветки, потом consensual merge/adoption). Первый коммит файла может установить claim автоматически (если нет явного dispute).

**Edge-cases:**
- Три агента редактируют ОДНОВРЕМЕННО ОДНУ ПАПКУ (например, portals/example/*). Level 0 commit_lock сериализует (один за раз), но общее дерево становится узким местом. Рекомендация: все трое в Level 1 worktree (отдельные ветки на разные subtasks: agent/codex/portal-a, agent/claude/portal-b, agent/third/portal-c). Merge-gate потом сводит три варианта (может потребоваться manual merge, если конфликты в одном файле).
- Файл переписывается ПОЛНОСТЬЮ (>90% строк изменены) без пересечения логики. Вариант 1 merge может быть costly (history-based merge неправильно работает). Альтернатива: Вариант 2 (переписка как форк-предложение, owner принимает/отклоняет целиком) или Вариант 3 если маленький draft (accept-rewrite + синтез потом).
- Generate --check STALE ВРЕМЕННО из-за другого агента, но на ДРУГОЙ branch (не в master). Пример: Codex в ветке agent/codex/T-133, добавил новый task. Claude в master видит STALE? Нет, потому что generate смотрит на текущий checked-out commit. Но если оба в master (Level 0) → да, STALE. Это ещё один аргумент за Level 1 изоляцию.
- Merge-gate КРАСНЫЙ (generate --check fail) после того как оба агента finish. Что делать? (1) Merge-owner смотрит на красный output, видит проблему (обычно missing dependency file или broken syntax). (2) Один из агентов (обычно автор проблемной ветки) заходит в своё worktree, чинит, делает amend/rebase, finish ещё раз. (3) Merge-gate перепроверяет, зелёный, merge проходит. Worktree не удаляется до merge-gate approval (if ever).
- Stream-пакет создан как Вариант 2 (форк-предложение), но потом выяснилось, что это Вариант 1 (полная пересоздание архитектуры). Решение: stream markиров as status: superseded, новая ветка заводится (agent/author/full-rewrite), finish через merge-gate. Старый stream archive/reject.
- Claim КОНФЛИКТ: двое agentов claim'ят ОДНОВРЕМЕННО одно и то же файл (race condition). Решение: queue.py/pipeline.py используют O_EXCL atomicity, первый agenta выигрывает, второму возвращается BUSY (он должен retry или отступить). Документация: docs/claim-resolution-policy.md (exists?).
- Синтез-шаг (Вариант 3 обязательно) ЗАБЫТ: оба варианта в repo, но никто не прочитал. Stream-пакет висит в status: draft, потом superseded (but nobody explicitly decided). Решение: tools/stream.py check (not yet) → flagged как orphan → архивация или требование explicit adoption/rejection.
- Worktree branch diverged слишком далеко (>50 коммитов от master за дни). Merge-конфликты становятся нерешаемы автоматом. Рекомендация: (1) merge-owner запрашивает rebase на current master перед merge. (2) Или cherry-pick нужные commits. (3) Или (редко) accept merge-commit с полной историей (if story matters). Предотвращение: finish worktree в течение часов/дня, не недель.
- Одновременная правка НА РАЗНЫХ ветках (не Level 0, не Level 1 worktree) — два агента на разных named-branch'ах (agent/codex/feature-a и agent/claude/feature-b). Git позволяет, но merge-gate мог видеть конфликты? Нет, потому что каждая ветка независима до pull-request/merge. При merge в master — merge-gate проверяет на основе diff master..feature-branch. Если оба меняют TASKS.md → конфликт виден merge-gate, требуется разрешение.
- Agent упал (процесс убит) во время Level 1 worktree write. Файлы в worktree директории остаются в грязном state. Следующий агент или человек: tools/flow.py check → видит orphan, tools/flow.py clean <agent> <task> → удаляет worktree и ветку (с warning, что несохранённая работа). Или: git worktree remove <path> —force. Важно: orphan detection актуально.
- Stream-пакет format расширен (добавлено новое поле в STREAM.md front-matter). Старые streams-пакеты (от недели назад) не имеют поля. Backwards-compatibility: tools/stream.py должен handle missing field (default value или skip). Forward-compatibility: новые пакеты включают поле, tools требует его при validation. Миграция: инструмент должен понимать обе версии.
- Claim ИСТЕКАЕТ (TTL claim ≈ 48 часов без heartbeat per T-082). Агент мог забыть update heartbeat. Следующий агент может взять claim (override с warning). Первый агент вернулся, видит, что claim потерял. Решение: (1) heartbeat-механизм (agent периодически обновляет claim timestamp). (2) Или manual release. (3) Или LRU-чистка старых claims (>7 дней без обновления → auto-release).
- Файл УДАЛЁН одним агентом, другой параллельно ПРАВИТ. Git merge обычно разрешает это (deletion wins если no conflict в содержимом). Но logically это может быть ошибка. Merge-gate может flagging (file was deleted on branch A, modified on branch B). Solution: merge-owner reviews, принимает решение (restore + merge, или keep deletion). Рекомендация: ЗАПРЕТ на удаление production-file без явного decision/approval.

- АНТИПАТТЕРН: accept-rewrite (Вариант 3) применен к production-code (tools/knowledge.py, 500+ строк). Результат: история первого агента теряется, тесты сломаны, синтез никогда не произошёл. Регрессия. Решение: Вариант 3 ЗАПРЕЩЁН для code >100 строк и production-файлов. Использовать Вариант 1.
- АНТИПАТТЕРН: Merge-gate как единое узкое место (один merge-owner, работает 9-5). Результат: agents ждут merge, потом обходят и коммитят в master соло. Bottleneck. Решение: ротация merge-owner / назначенный интегратор для low-risk (D-021 открытый вопрос).

- АНТИПАТТЕРН: Merge-конфликт разрешён НЕПРАВИЛЬНО (conflict marker'ы остались в файле, никто не заметил). Коммит пошёл в master, build broken. Решение: merge-gate + pre-commit hook должны detect conflict marker'ы (<<<<<<, >>>>>>). Или strict format check (JSON/YAML validation).

Уточнение к `D-017`: для содержательных вопросов, архитектуры, методологии, ревью и больших предложений похожая тема не является основанием остановить агента. Правильная процедура:

2. раскрывает вариант до состояния `ready-for-synthesis`;
3. только после этого observer/synthesizer сравнивает варианты;
4. повторяющиеся пункты становятся candidates для `consensus` / `ratify-build`;
5. расхождения и edge cases остаются в `divergence-detail`;
6. шумовой дубль закрывается только после synthesis, если он не добавил условий, evidence, рисков, вопросов или реализации.

Команда готовности:

```powershell
python tools\stream.py mark <stream-id> ready-for-synthesis "variant completed"
```

Dedup по-прежнему действует для механики: id, generated indexes, locks, manifests, claim-файлы и accepted canonical records.
