# Три пути развития многоагентной коллаборации — единый ответ

*Синтез стратегии для приватного русскоязычного «канона» на одной 4-ядерной машине.*

## 1. Рамка: три пути — не меню, а три поверхности исполнения одного канона

**Три «пути» — это не три конкурирующих продукта, из которых выбирают один.** Это **три поверхности исполнения** одного и того же канона и одной политики.

Канон (`.md`-объекты T/Q/D, `docs/`, `reports/`, `indexes/`), политику (reconcile / не-удаление / precedence, D-026, эпистемику independent-first + кворум судей) и доменные гейты (`validate.py`, `bulk_guard.py --range`, `generate.py --check`) мы пишем **ОДИН раз**. Меняется только **substrate** — на чём проверки запускаются и где лежит источник истины.

Подтверждается самим кодом:
- `work_admission.py` вычисляет слоты от `os.cpu_count()` (`_slots() → max(1, cpu_count − reserve)`, `RESERVE=2`), состояние в `logs/slots/*.slot` **под ROOT машины** → кап **по построению per-host**. Тот же код: 4 ядра → 2 слота (Путь 1), 32 vCPU → 30 (Путь 2). Явный `--slots N` уже есть → кап можно сделать **политикой**.
- `next_id.py` держит атомарность на `O_CREAT|O_EXCL` в **ОДНОЙ ФС** — **единственный узел, который физически ломается** при распределёнке, требует централизации во всех путях.

Правильная постановка — **не** «локально ИЛИ GitHub ИЛИ сервер», а **слоистый гибрид**: GitHub = durable источник истины + серверный гейт; локальная машина = приватная медленная ход-модель поверх клона; выделенный сервер = burst-параллельность и мульти-модельность поверх того же клона.

Два **ортогональных** потолка:

| Потолок | Что это | Кто снимает |
|---|---|---|
| **A — ядра хоста** | сколько тяжёлых агентов тянет машина | сервер (Путь 2: ядер много → слотов много) |
| **B — контеншн общего дерева** | драка за один `.git` / nav-индексы | GitHub (Путь 3: клон-на-агента растворяет дерево) |

**Ловушка: клон-на-агента изолирует ДЕРЕВО, но НЕ ядра.** `work_admission` (Gate B) остаётся по-машинным капом A на каждой поверхности.

## 2. ПУТЬ 1 — Локальный последовательный / низкая одновременность

**Метафора: медленная растянутая визуальная новелла, «play-by-post над версионируемым состоянием мира».** Одна машина; канон = единое «состояние мира». Параллельно максимум 1–2 агента без под-агентов ИЛИ 1 агент с роем. Сверх — сериализуется **во времени (ходы)**: агент А отработал ход и закоммитил; на следующий день/ход агент Б перечитывает состояние, перепроверяет, дорабатывает, передаёт ход.

**Модель хода (turn):** (1) **READ** — читает состояние (`STATUS.md`, `LIVE.md`, повестку, claim'ы, heartbeat, объявление прошлого хода); (2) **ACT** — действует ТОЛЬКО в объявленной зоне; (3) **COMMIT** — фиксирует в канон (grow-only, reconcile); (4) **HANDOFF** — оставляет «ход-записку» (что сделал, что открыто, кому и что проверить). Одновременность = **не потоки, а глубина хода**: 2 лёгких lead ИЛИ 1 lead+рой — оба в кап `cores−2=2`. Состояние — **на диске**, не в памяти сессии (урок `workflows-die-on-compaction`).

Связи: **D-036** (ход нельзя начать без объявления + `zone_overlap` ПЕРЕД захватом); **reconcile** (коллизия ходов → branch-on-collision, не перезапись); **work_admission** (кап 2 не даёт «6 ходов разом» стать нагрузкой — лишний → QUEUE).

**Для кого:** частник/соло, приватный локальный проект без сервера. Ценит полную приватность, нулевую инфраструктуру, неспешный ритм (качество > пропускная способность). Плохо для фирмы с дедлайнами.

**Что доработать (90% из готового):** профиль `LOW_CONCURRENCY` в `work_admission` (явный `--slots 1–2`); поля «ход-записки» (`who_next`/`open_threads`/`verify_next`) в claim/done; тонкая обёртка `turn.py` над pipeline+work_admission+zone_overlap (`turn start/end`); reconcile под «коллизию ходов». Как есть: heartbeat/lease fencing, очередь `queues/`, D-012 tripwire (≥3 = вышли за режим), git как журнал ходов.

**Политика:** кап = политика (≤2 lead), `acquire` обязателен; ход только после эстафеты D-036; состояние на диске; смена хода фиксируется явно (нет молчаливого окончания); коллизия → reconcile, никогда удалением; перепроверка встроена в ритм (D-018); один интегратор на цикл (Q13).

**+** машина не насыщается, ~0 $, полная приватность, устойчивость к смерти сессии, минимум разработки.
**−** низкий throughput, латентность хендовера, **bus-factor НЕ решён** (один диск, near-miss ~11k строк), форс капа advisory, потолок ~2, ядра простаивают.

**Когда:** машина одна/локальная; проект приватный; агентов немного (2–4); throughput не критичен. Дефолтная, самая дешёвая, самая приватная **стартовая точка** — на ней обкатываются эстафета/reconcile/кап, которые потом **включаются**, а не выбрасываются.

## 3. ПУТЬ 2 — Серверный / средний / гибрид

**ПРЯМОЙ ОТВЕТ: «есть ли мощные промышленные системы, где к ОДНОЙ системе подключены СРАЗУ НЕСКОЛЬКО моделей параллельно?» — ДА.** Это зрелая категория **multi-model orchestration**: слой маршрутизирует каждый запрос к подходящей модели, разные узлы работают на разных моделях одновременно.

**Промышленные носители (июль 2026):** AWS Bedrock AgentCore (Intelligent Prompt Routing: Claude Sonnet↔Haiku), Google Vertex AI Agent Builder, Azure AI Agent Service, Microsoft Copilot Studio, IBM watsonx Orchestrate, Salesforce Agentforce 360, ServiceNow AI Agents; enterprise-гейтвеи TrueFoundry, Bifrost (20+ провайдеров за одним API, failover/semantic-cache/native-MCP, в свой VPC); фреймворки LangGraph/CrewAI/AutoGen (model-agnostic); протокол A2A связывает агентов разных фреймворков.

**Разделение труда с фреймворками:**

| Наш примитив | Промышленный аналог |
|---|---|
| `workflow_recover`/`thread_runner`/`conveyor` + урок «workflows die on compaction» | **LangGraph checkpointing** (Postgres/Redis, survives restart) |
| DAG `depends_on` + lead/sub | LangGraph directed-graph, узлы на разных моделях |
| lead+sub с ролями | **CrewAI** роли + Crew Manager |
| «несколько моделей» + tiering | Bedrock IPR / Vertex / TrueFoundry / OpenRouter / ZenMux |
| `workbench.db` + `drivers/sqlite` + reconcile | **Zep** (Context Lake, инвалидирует устаревшие факты) |

**Гибрид (главный тезис):** НЕ выбрасывать канон и НЕ отдавать всё вендору. Фреймворк/роутер берут **ГДЕ/КОГДА/КАКОЙ моделью**; наш код держит **ЧТО проверять** (D-026, недеструктивность, эпистемика/кворум, budget-aware срез, приватная память, ID, кап). Наши 7 MCP-серверов уже MCP → подключаются к native-MCP роутера без переписывания. Сервер снимает A (ядра), фреймворк — B (state-persistence вместо драки за `.git`), роутер — «одна модель».

**Для кого:** большие фирмы, юрлица, крупные совместные проекты — НЕ частник (промышленные платформы под тенант организации; стоимость окупается только при потоке задач и команде).

**Одновременность:** реальные ядра − 2: 16→14, 32→30, 64→62 линейно. LangGraph checkpoint держит длинные прогоны с переживанием рестарта.

**Стоимость:** VM 16–32 vCPU ~сотни $/мес; API per-token (доминирует; tiering снижает 40–70%); фреймворки open-source, managed — подписка; devops-человек.

**Когда:** агентов/людей много (3+) на разных моделях; поток работы; нужны governance/audit/data-residency/SLA или durability длинных прогонов; bus-factor критичен.

## 4. ПУТЬ 3 — GitHub / онлайн (распределённый remote как источник истины)

Приватный GitHub-remote + клон/ветка-на-агента + PR/merge-queue включает **физически невозможное локально**: серверный необходимый энфорсмент, облачные раннеры (offload validate с 4 ядер), офсайт-durability, кросс-девайс.

**Что доступно ТОЛЬКО онлайн:** (1) required status checks на protected `main` — единственный барьер, который агент не отключит локально (`--no-verify` бессилен); (2) облачные раннеры уводят ~2-мин `validate.py`+`generate --check`+`test_all` с локальных ядер (снятие горлышка); (3) **merge queue** сериализует пуши server-side — замена `commit_lock`/`seq_merge`, которые live-lock'ались; (4) офсайт-durability + bus-factor из коробки; (5) доступ с разных устройств/локаций.

**Разработать под онлайн:** Actions-job nav-генерации **ПОСЛЕ** merge (устраняет детерминированный конфликт `STATUS.md`/`index.json`); gh-обёртки поверх Issues/Projects (claim/очередь/доска как проекция); **`next_id` как онлайн-сервис** (`O_EXCL` атомарен только в одной ФС — между клонами молча не сработает → двойная выдача ID); bootstrap-скрипт клона (crdt merge-driver, хуки, `work_admission reserve` по ядрам машины).

**Для кого:** распределённые/кросс-девайс команды (Codex+Antigravity+Claude на разных машинах), любой масштаб; это **prerequisite** горизонтального масштаба. Также соло-оператору ради офсайт-бэкапа/доступа с устройств.

**Одновременность:** потолок НЕ снимается — становится **по-машинным** (`slots = ядра−2` на каждой). Глобально сериализуется только слияние (merge queue). Потолок = (сумма ядер всех машин) + (лимит Actions-минут) + (пропускная merge queue).

**Политика:** ветка-на-агента, прямой push в `main` ЗАПРЕЩЁН; защита `main` (require PR + checks green + up-to-date + linear + CODEOWNERS); merge queue on; **кап ЯДЕР остаётся по-машинным** (ложная вера «PR решил concurrency» запрещена); канон file-native = истина, Issues = проекция; три неделегируемых узла не бросать наивно.

**+** серверный энфорсмент, offload горлышка, merge queue вместо live-lock, горизонталь A, durability/bus-factor, отрицательный оверхед на subsumed-классе (`commit_lock`/`worktree`/`_claims`/`seq_merge` удаляются), приватные репо бесплатны.
**−** не снимает кап ядра; `next_id` ломается ТИХО (самый опасный); данные у вендора; CI-минуты лимитированы; merge queue не сливает по полям (нужен crdt); эпистемику/durability тащить своим кодом.

**Когда:** нужно масштабироваться за потолок одной машины (6 на 4 ядрах = насыщение). Делать **ДО** подключения многих агентов — prerequisite, а не следствие.

## 5. Сравнительная таблица

| Ось | Путь 1 — Локальный | Путь 2 — Сервер/гибрид | Путь 3 — GitHub/онлайн |
|---|---|---|---|
| **Одновременность** | ≤2 (`cores−2`), сериализация во **времени** | линейно с ядрами: 16→14, 32→30, 64→62 | по-машинный кап; глобально сериализуется только merge |
| **Что снимает** | ничего (в потолке) | потолок **A** + мультимодель | потолок **B** + durability |
| **Для кого** | частник/соло | фирма/юрлицо, 3+ на разных моделях | распределённые любого масштаба + соло ради бэкапа |
| **Приватность** | максимум (всё локально) | контролируешь, но админишь (VPC/on-prem) | данные у вендора (даже приватный репо) |
| **Стоимость** | ~0 $; платишь **временем** | VM + API + devops | ~0 $ кап; **CI-минуты + латентность** |
| **Bus-factor** | **НЕ решён** (один диск) | решён | решён из коробки |
| **Throughput** | низкий (день=ход) | высокий (параллельность + tiering) | горизонталь (N машин), offload validate |
| **Форс капа** | advisory (обходим) | серверный CI (required) | серверный required (`--no-verify` бессилен) |

**Правило: стоимость растёт `1 < 3 < 2`; снятый потолок растёт `1 (≤2) < 3 (горизонталь, кап по-машинный) < 2 (вертикаль+горизонталь+мультимодель)`.**

## 6. ГИБРИД: как три сочетаются

**«Один канон — три крана исполнения»:** (1) **источник истины = приватный GitHub-remote** (durable substrate, серверный гейт, merge queue, облачный offload); (2) **локальная машина** = приватный медленный клон для ход-модели (профиль `LOW_CONCURRENCY`, чувствительное не уходит в API); (3) **выделенный сервер** = burst-клон под настоящую параллельность/мультимодель, **по требованию** (тот же remote-клон, `work_admission` даёт 14–62 слота тем же законом).

Все три — **КЛОНЫ одного remote**; слияние в `main` строго через PR→checks→merge queue; nav-деривативы генерятся **только post-merge в одном процессе** (или crdt-driver везде идентично). Три неделегируемых узла — общие MCP-сервисы поверх всех поверхностей.

> GitHub — библиотека-хранилище (истина + гейт); локальная машина — тихий читальный зал (1–2 хода за такт); сервер — конференц-зал (burst). **Книга-истина одна.**

**Триггеры перехода:**
- **Локально (1) → +GitHub (3):** нужен офсайт-bus-factor (почти безусловно, ДО многих агентов) / появился 2-й агент на др. машине / нужен необходимый гейт / validate стал горлышком. GitHub-слой — это durability + substrate, включается **рано и почти всегда**.
- **GitHub (3) → +сервер (2):** нужно >2 тяжёлых агентов разом / несколько моделей / промышленная durability / governance регулируемой отрасли.
- **ВНИЗ можно:** сервер — **эластичный кран** (погасить после burst), GitHub-слой не откатывается.
- **БЛОКЕР миграции:** ПЕРЕД первым 2-м клоном ОБЯЗАТЕЛЬНО развернуть централизованный `next_id` — иначе тихая двойная выдача ID.
- **Tripwire:** D-012 при ≥3 = сигнал человеку «вышли за режим Пути 1».

## 7. Что ОБЩЕЕ (пишем раз) vs специфично

**Общее для всех трёх:** КАНОН (file-native истина; Issues/Zep/Postgres — проекции); ПОЛИТИКА недеструктивности (reconcile/precedence/grow-only/branch-on-collision; D-026; D-036; один интегратор Q13); ДОМЕННЫЕ ГЕЙТЫ (`validate`/`bulk_guard --range`/`generate --check`); ЭПИСТЕМИКА (`independent_first`/`oracle_quorum`/`autonomy_guard`/`risk_gate`/`red_team_gate` — нет у вендоров); MCP-РЕТРИВАЛ + приватная память; ТРИ НЕДЕЛЕГИРУЕМЫХ УЗЛА (ID, кап, приватная память/MCP).

**Специфично (та же политика, разный форс-механизм):**

| Аспект | Путь 1 | Путь 3 | Путь 2 |
|---|---|---|---|
| Вход в кап | явный `--slots 1–2` | по-машинный на клоне | reserve по ядрам сервера |
| Сериализация слияния | во времени (ходы) | merge queue server-side | merge-queue / nav-job после merge |
| Изоляция | advisory worktree | ветка/клон-на-агента | state-persistence фреймворка |
| Энфорсмент | advisory (обходим) | серверный required | серверный required |
| Durability | ход-записка + диск | наш `workflow_recover` | LangGraph checkpoint |
| subsumed-класс | не трогаем | `commit_lock`/`_claims`/`seq_merge` удаляются | state-persistence замещает |

**КЛЮЧ:** канон+политику НЕ дублируем; дублируется только тонкий адаптер активации (CI/hook/agent-cli/MCP). Форс-сила растёт advisory→required→оркестратор без изменения проверяемой логики. **НЕ subsumed никогда:** `work_admission`, эпистемика/reconcile/D-026, `next_id`.

## 8. Рекомендация по этапам (профиль Stefan: приватный, 1 машина, 2–4 агента)

- **ЭТАП 0 (сейчас, безусловно):** включить GitHub-слой как durable источник истины — приватный репо + `bulk-guard.yml` required + branch protection. Закрывает **bus-factor** (главный незакрытый риск). Делать ДО многих агентов. **Блокер:** до 2-го клона развернуть централизованный `next_id`.
- **ЭТАП 1 (дефолт):** жить на Пути 1 ПОВЕРХ GitHub-клона — ход-модель, `LOW_CONCURRENCY`, `turn.py` + поля ход-записки (единственная новая разработка).
- **ЭТАП 2 (по требованию, эластично):** поднимать сервер Пути 2 ТОЛЬКО под burst (>2 агентов / несколько моделей), гасить после пика.
- **НИКОГДА не выбрасывать наш код:** канон/политика/гейты/эпистемика/кап — на всех поверхностях. Вендор берёт ГДЕ+КОГДА+КАКОЙ моделью; наш код — ЧТО проверять.

**Решает человек:** GitHub vs NAS; приватность vs durability; бюджет CI/API; что file-native vs проекция; санкция на смену модели D-036; момент подъёма/гашения сервера.
**Дорабатывают агенты:** `turn.py` + ход-записка; адаптер `work_admission` `LOW_CONCURRENCY`; post-merge nav-job, gh-обёртки, bootstrap; reconcile под коллизию ходов; crdt-driver; централизованный `next_id` (блокер).

**Главное правило гибрида:** канон и политику пишем один раз; форс-механизм наращиваем advisory (локально) → required check (GitHub) → оркестратор+роутер (сервер) — три поверхности исполнения одной истины, а не три конкурирующие истины.
