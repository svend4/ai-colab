# Политика Координации Субагентов (Рой 3:1)

Данный документ описывает фундаментальную политику управления системными субагентами (LLM compute nodes), используемыми главным системным агентом (Antigravity). Эта архитектура устраняет главную уязвимость автономных систем — переполнение контекста у главного оркестратора при большом потоке параллельных результатов.

## 1. Иерархия Координации (Архитектура 3:1)

Во избежание эффекта бутылочного горлышка (bottleneck) вводится жесткая древовидная структура субагентов. Базовая ячейка роя состоит из 4 агентов:

*   **Исследователи (Researchers)**: Активные рабочие узлы (максимум 3 на одну группу). Их задача — собирать данные, парсить код, искать ошибки. Изначально они обладают **только правами чтения (Read-Only)**.
*   **Наблюдатель / Куратор (Supervisor)**: 1 узел. Его задача — собрать сырые отчеты от 3-х исследователей, очистить их от мусора, объединить в единый синтетический документ и передать наверх.
*   **Главный Оркестратор (Antigravity)**: Получает только один чистый, структурированный отчет от Наблюдателя, вместо трех сырых отчетов.

Если задача огромна, можно развернуть несколько групп по принципу фрактала (например, 3 группы по 3 исследователя -> 3 наблюдателя -> 1 старший куратор -> Antigravity).

## 2. Разделение прав и Конвейер (Workflow)

Процесс анализа и внесения изменений делится на этапы. Бесконтрольное изменение кода в чистовике строго запрещено.

### Этап 1. Чтение и Исследование (Read-Only)
*   Начинаем всегда с базовых прав. Исследователи получают задачу "понять проблему".
*   Они не имеют доступа к инструментам редактирования файлов. 
*   Все свои наблюдения они передают Куратору.

### Этап 2. Внесение изменений в Песочнице (Sandbox-Only Write)
Если результаты исследований требуют изменения кода (рефакторинг, исправление багов):
*   Главный агент (Antigravity) копирует нужную часть кодовой базы в изолированную директорию (например, `sandbox/inbox/task_xxx/`).
*   Формируется новая группа субагентов, которым выдаются права на **изменение кода (Write Access)**, но их зона видимости строго ограничена папкой песочницы.
*   Они применяют изменения к скопированным файлам, тестируют их и пишут отчет Куратору.

### Этап 3. Валидация и Слияние (Merge-to-Main)
*   Куратор приносит отчет о сделанных изменениях в песочнице Главному агенту (Antigravity).
*   Antigravity проверяет качество измененного кода (в песочнице).
*   Принимается коллегиальное решение: Antigravity может привлечь других агентов репозитория (Codex, Claude) или запросить аппрув Человека (в соответствии с `D-006` и `D-014`).
*   Если решение принято как полезное (`accepted`), Antigravity переносит код из `sandbox/` в чистовик репозитория и удаляет песочницу.

## 3. Инструкция для Antigravity
Я (Antigravity) должен неукоснительно следовать этому правилу при делегировании объемных задач. Прежде чем порождать хаос из десятков независимых субагентов, я должен выстроить прослойку из кураторов.
