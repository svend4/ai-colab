# Моя НЕЗАВИСИМАЯ версия (sealed) — 2D полу-диффузия текста, мощь видео → многоагентный текст

> Написано ДО чтения выводов роя (independent-first). Сверю после. Грунт — прочитанный код:
> pkg/pseudo/grid.go (Grid.rect→upscaleBilinear→blur→DiffuseFrames), pkg/scene/scene.go (box/text/rect DSL),
> docs/SHARED_WORLD.md (raymeet: Region~100Б/Pose 44Б), ai/BRAIN_PROTOCOL.md (tvcp-ai/1).

## 1. Что делает идею РЕАЛЬНОЙ, а не метафорой
Весь фокус TVCP — «**смысл, не пиксели**»: по проводу идёт крошечное описание, клиент пере-собирает кадр локально.
Для ТЕКСТА это ложится идеально, потому что текст и так смысл-плотный. Прямое отображение видео→текст, которое
ВЫДЕРЖИВАЕТ проверку:
- видео-кадр = 2D-сетка пикселей, восстановленная из компактного кода (`.babe`-блоки);
- текст-«кадр» = 2D-сетка **КАРТОЧЕК**, восстановленная из компактного кода (сид карточки = заголовок + пара
  семантических токенов / одна [[ссылка]]);
- псевдо-диффузия (grid.go): грубый сид → `upscaleBilinear` → `blur` → постепенная резкость. Для текста:
  грубый сид (гист/заголовок карточки) → «upscale» = разворот в под-карточки → «denoise/blur-fade» = раскрытие
  **от общего к частному**. `DiffuseFrames` (шум→цель, blur затухает) = «текст течёт как видео»: карточка
  стартует мутным гистом и проявляется в детали по кадрам.

## 2. Почему 2D — правильный СРЕДНИЙ путь (моё мнение)
- **1D-чат** навязывает строгий временной порядок: читаешь в последовательности произнесения, параллелизм
  схлопывается.
- **3D-видео** расточительно для текста: у текста нет глубины; рендер его как 3D жжёт трафик/счёт на измерение,
  которого у текста нет.
- **2D** — родная размерность текста, как только перестаёшь думать «строки»: страница/канва карточек, где
  ПОЛОЖЕНИЕ кодирует отношение (общее ↖ → частное ↘, или дерево-меню). Так уже работают газеты, дашборды, IDE.
  Новизна — сделать это ГЕНЕРАТИВНЫМ+ПОТОКОВЫМ (карточки появляются/уточняются как кадры) и МНОГОАГЕНТНЫМ
  (каждую карточку может авторствовать свой участник).

## 3. Честный предел аналогии с видео (где я ПОСПОРЮ с формулировкой)
«Текст течёт как видео» соблазнительно, но ценность текста НЕ в движении — пере-рендерить текст 15 раз/с
бессмысленно, прочитаешь один раз. Значит «видео», которое нам нужно, это НЕ высокий FPS, а:
(a) пространственный 2D-параллелизм (много карточек разом = много камер-плиток),
(b) прогрессивное разрешение (диффузионное coarse→fine раскрытие),
(c) провод «смысл не пиксели».
«FPS» для текста — **событийный** (карточка обновляется, когда меняется её смысл), не тактовый.
→ Рекомендация: убрать буквальный «поток на FPS», оставить «2D-параллель + прогрессивное-раскрытие +
смысл-провод». Это защитимое ядро.

## 4. Многоагентность: MMORPG / сетка-камер (моя трактовка)
raymeet уже даёт скелет — Region (авторский кусок ~100–300Б) + Pose (44Б) + presence + chat. Отображение:
- участник (человек ИЛИ агент) = «камера» = владеет одной/несколькими карточками в общей 2D-канве;
- канва = общий «мир» = по сути наш канон;
- «Pose» для текста = на какой карточке фокус/курсор/вьюпорт (дешёвый presence: кто на что смотрит);
- агенты «общаются» = карточки ссылаются на карточки ([[link]] = домино-ребро); агент «отвечает», авторствуя
  соседнюю карточку;
- «сетка наблюдения» = дашборд активных карточек всех участников, каждая — живая плитка (это raymeet «видеть
  друг друга аватарами», но аватар = текущая карточка участника).

## 5. Трудная часть — где ОБЯЗАН включиться наш CRDT (моя рекомендация)
Общий мир raymeet — host-авторский, last-writer: ок для одного режиссёра, СЛОМАН для многих со-авторов. Как
только много агентов+людей правят общую карто-канву конкурентно — нужен наш `crdt_merge`: **OR-Set на МНОЖЕСТВО
карточек** (add-wins → конкурентные новые карточки от разных агентов все выживают) + LWW/diff3 на ТЕЛО карточки.
Критично: баг `inf_crdt.remove_block` (воскрешение удалённого), что я нашёл — карто-сет ОБЯЗАН делать remove
через tombstone, иначе удалённые карточки всплывают. Это и есть технический хребет; диффузия/карточки — это UX
поверх него.

## 6. Оракул-проблема (мой честный caveat)
«Кто диффундирует текст» = кто разворачивает грубый сид в детали? Это LLM = захватываемый оракул. Если один мозг
разворачивает все карточки — единая точка. Урок кворума: высоко-ставочные карточки разворачивают ≥2 мозга с
ВИДИМЫМ расхождением (показать дивергенцию как пометку на карточке), не молча мёржить. Сильную сторону —
ДЕТЕРМИНИЗМ grid.go (seeded, воспроизводимо) — сохранить: РАСКЛАДКА/раскрытие детерминированы; только семантика
зависит от оракула — держать эту границу видимой.

## 7. MVP, который я бы построил первым (рекомендация)
`tools/text_scene.py` — берёт срез канона (переиспользовать `view.py` slice_ids) → раскладывает 2D-сеткой
карточек (карточка = узел канона: заголовок = title, тело свёрнуто) → рендер прогрессивного раскрытия
(переиспользовать `view_html.py` <details>, но пространственно-2D, не только вложенно) → опц. режим «diffuse»:
раскрывает карточки coarse→fine (сначала гист, потом тело) кадрами (аналог DiffuseFrames: печать кадров).
Провод/многоагентность — позже (переиспользовать `crdt_merge` для общей канвы). Первый артефакт — одно-
пользовательский 2D-карто-вид с диффузионным раскрытием; дёшево доказывает метафору.
