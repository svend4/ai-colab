# CARDWIRE / `.babet` — кодек и провод «2D-карточек как смысловых дельт»

> Угол **codec/провод**: НЕ «как генерировать» и НЕ «как мёржить семантику глазами оракула», а
> **что именно идёт по проводу** между много-агентным роем (люди+ИИ), как из крошечной дельты
> локально пересобирается 2D-сетка карточек, и как конкурентные правки сходятся **без потери**
> и **без воскрешения удалённых карточек**. Прямой перенос принципа TVCP «meaning, not pixels»
> (docs__SHARED_WORLD.md: Region ~100Б, Pose 44Б) с пикселей на ТЕКСТ.

## 0. Один абзац

Картина-чат TVCP передаёт по UDP не кадр, а `brain.SceneSpec`/`Region` (~100–300Б), и каждая
машина рендерит локально path-трейсером. CARDWIRE делает то же с текстом: по проводу идёт не
тело карточки и не строки, а **смысловая дельта над множеством карточек** — `CardOp` (add/edit/
move/remove/seed) в JSON-конверте `tvcp-ai/1`. Локально дельта применяется к CRDT-состоянию
(нашими `crdt_merge.merge3` + `seq_merge.merge_lines`), и из него детерминированно пере-рендерится
2D-grid карточек (аналог `Grid.frameSmooth`/`DiffuseFrames`: грубый сид → проявление). Удаление —
не вычёркивание строки, а **tombstone в OR-Set**, поэтому одновременная правка удалённой карточки
другим агентом её НЕ воскрешает.

## 1. Что идёт по проводу (wire format) — «смысл, не строки»

Аналогия точная: TVCP пускает `Region.Encode` (байты сцены), CARDWIRE пускает `Patch` (байты
смысловой дельты карточек). Карточка = `scene.Op{op:"box"/"text"}` из pkg/scene, но содержимым
её является не пиксель, а абзац/визитка/пункт-меню.

### 1.1 Адресуемая единица — Card (визитка/блок/карточка)

```json
{
  "id": "c/7f3a",                 // стабильный CardID (см. §4: hash(seed)+actor, НЕ позиция)
  "gx": 2, "gy": 1,               // место в 2D-сетке тем (как Grid.Rows[y][x], НЕ пиксель)
  "lane": "agent:planner",        // контур/дорожка (как Pose.actor в raymeet — кто «камера»)
  "level": 0,                     // глубина progressive disclosure (0=меню/гист, 2=деталь)
  "title": "Бюджет Q3",
  "body": "...",                  // тело — мёржится как seq_merge.merge_lines (diff3)
  "tags": ["budget","draft"],     // OR-Set list-поле (crdt_merge LIST_FIELDS)
  "vv":  {"alice": 4, "planner": 9}  // version-vector (см. §3)
}
```

`gx/gy` — это в точности роль `Grid.Rows[y][x]` из pkg__pseudo__grid.go: грубая 2D-решётка, по
которой потом идёт «upscale» (раскрытие в детали), а не пиксельная карта. `level` — ось
progressive disclosure (`<details>` в нашем view_html.py: меню→детали уже есть как «карточки от
общего к частному»).

### 1.2 Дельта — CardOp (то, что реально летит)

Полная карточка по проводу не ходит почти никогда. Ходит **op над полем**:

```json
{ "protocol":"tvcp-ai/1", "kind":"cardop",
  "patch": [
    {"op":"seed",   "grid":[["budget","risks","plan"],["q3","q4","hiring"]]},   // §2: грубый сид-сетки
    {"op":"add",    "id":"c/7f3a","gx":0,"gy":0,"title":"Бюджет Q3","lvl":0,"by":"planner","clk":9},
    {"op":"edit",   "id":"c/7f3a","body_diff":[[ "@@",3,1,3,2 ],["+ строка факта"]],"by":"alice","clk":4},
    {"op":"tag",    "id":"c/7f3a","add":["urgent"],"rm":[],"by":"alice","clk":5},   // OR-Set дельта
    {"op":"move",   "id":"c/7f3a","gx":1,"gy":0,"by":"planner","clk":10},           // LWW по (clk,actor)
    {"op":"remove", "id":"c/19bd","by":"bob","clk":7}                               // tombstone, §4
  ] }
```

- `seed` = ровно `pkg/pseudo` `grid`-формат: модель-мозг отдаёт **12×8-подобную решётку тем**
  (несколько токенов), а не текст. Это «сид» псевдо-диффузии текста.
- `body_diff` = unified-diff hunk’и, которые на приёме скармливаются `seq_merge._edits`/`merge_lines`
  (diff3 по строкам тела). По проводу — только изменённые строки, не всё тело (как `Region` шлёт
  описание региона, не геометрию).
- `tag.add/rm` = дельта OR-Set точно как наш `crdt_merge._union_lists` для `LIST_FIELDS`
  (related/tags/...): add-wins, ничего не теряется.

### 1.3 Конверт и транспорт

Тот же `tvcp-ai/1` JSON-over-HTTP (`/v1/decide`) / SSE-стрим (`pkg/stream`) что у мозга и у
raymeet. Новый `kind:"cardop"` добавляется ровно по §12 протокола (extend Capabilities + battery).
Хаб — звезда (как `raymeet`): агент шлёт `Patch` хабу, хаб фанаутит; идемпотентное применение +
ack-хилинг потерь (как ack-set регионов в SHARED_WORLD). `seed`/`add`/`remove` — надёжно (ack-set,
как `Region`); `move`/`pose-курсора` — loss-tolerant (перекрывается следующим тиком, как `Pose`).

## 2. Псевдо-диффузия ТЕКСТА на проводе: сид → проявление

Перенос `Grid.DiffuseFrames` (pkg__pseudo__grid.go: шум→цель, blur затухает) на смысл.
Детерминированно, без GPU.

| pkg/pseudo (пиксели) | CARDWIRE (текст) | что по проводу |
|---|---|---|
| `Grid.Rows[y][x]` = токен цвета | 2D-сетка **тем** (заголовки) | `seed` op: матрица строк-тем (~десятки байт) |
| `upscaleBilinear` (грубое→крупное) | раскрытие темы→карточка→абзацы | `add`/`edit` ops уровня `level` 0→1→2 |
| `blur` 3 прохода (сглаживание) | связки/переходы между карточками | вычисляются ЛОКАЛЬНО, не шлются |
| `DiffuseFrames` alpha 0..1 | поток уточнения: гист → детали | серия `Patch` с ростом `level` |

Ключ: как `blur` и `upscaleBilinear` исполняются **на приёме** и не идут по проводу, так связки,
расположение и «сглаживание» сетки карточек считаются локально из сида+ops. По проводу — только
сид (грубая решётка тем) и адресные дельты карточек. Это и есть «9× меньше» (§5).

Детерминизм: рендер сетки из CRDT-состояния — чистая функция (как `cellsToFrame`); один и тот же
набор ops у всех агентов → байт-в-байт одинаковая 2D-раскладка (как path-рендер из `Region`
у каждого walker’а в raymeet идентичен).

## 3. Конкурентное редактирование без потери (CRDT-слой)

Переиспользуем наш стек 1:1, карточка = «канон-файл с front-matter + body»:

- **множество карточек** = OR-Set по `CardID` (add-wins) — расширение `crdt_merge` с уровня полей
  одного файла на уровень коллекции карточек.
- **скаляры карточки** (`title`, `gx`, `gy`, `level`, `lane`) = `crdt_merge._merge_scalar` 3-way:
  тронул один → его; оба по-разному → конфликт-флаг (НЕ молчаливый LWW). `move` — LWW по
  паре `(clk, actor)` (детерминированный tie-break по имени, как ContractNet ties-by-name в §11
  протокола).
- **list-поля** (`tags`, `related`, `participants`) = `crdt_merge._union_lists` (OR-Set union):
  обе стороны выживают.
- **тело карточки** = `seq_merge.merge_lines` (diff3): непересекающиеся правки двух агентов в теле
  сливаются чисто, маркеры `<<<<<<<` только на пересечении строк.

**Version-vector `vv`** на карточку (`{actor: counter}`) даёт каузальность без base-файла: приёмник
знает, видел ли он уже op (идемпотентность: повторный `add` того же `(id, actor, clk)` — no-op, как
дедуп `ChatSync` по id в raymeet). Где есть git-merge-base — идёт полноценный 3-way (`merge3`);
где состояние живое и базы нет — VV решает «кто новее/каузально позже».

Семантический конфликт (оба переписали тело по-разному) не теряется и не решается тихим LLM-судьёй:
карточка помечается `conflict:true`, оба тела видны под маркерами — это «оракул-проблема» сведена к
ВИДИМОМУ кворуму (человек/второй агент разрешает), а не к одному захватываемому судье.

## 4. Удаление без воскрешения (tombstone — центральная проблема угла)

Наивный «убрать строку из чата» ломается в рое: агент B одновременно правит карточку, которую агент
A удалил → правка «воскрешает» её. Решение — как у OR-Set удаления:

1. `remove` НЕ стирает карточку, а ставит **tombstone**: `{id, removed_by, removed_clk, removed_vv}`.
2. Приходящий позже `edit` карточки сравнивает свой `vv` с `removed_vv`:
   - если `edit` **каузально предшествует** удалению (edit.vv ≤ removed_vv) → правка применяется к
     телу, но карточка остаётся удалённой (правка «в архив», не воскрешает);
   - если `edit` **каузально позже** удаления (видел удаление и всё равно правит) → это осознанный
     **re-add**: только тогда tombstone снимается, явным флагом `op:"add","revive":true,"after":removed_clk`.
3. Дефолт: «remove-wins при конкуренции» (add-wins для добавления новой карточки, но remove-wins
   против конкурентного edit) — это снимает «воскрешение» по умолчанию, оставляя осознанный revive
   возможным. Зеркало того, как `crdt_merge` НИЧЕГО не теряет молча: тело удалённой карточки лежит в
   tombstone, доступно для revive, но в активную 2D-сетку не рендерится.

**CardID стабилен и не позиционен** (`hash(seed_topic + creator_actor + nonce)`), а не «индекс в
сетке». Поэтому `move` (смена `gx/gy`) и удаление соседа НЕ путают идентичность — как `Instance` в
raymeet адресуется именем меша, а не координатой. Это убирает классический баг «удалили карточку №3,
правка прилетела в №3 = в чужую».

Tombstone-GC: компактим tombstones, чьи `removed_vv` уже доминируются `vv` ВСЕХ известных акторов
(никто уже не может прислать конкурентный edit) — стабильный причинный фронт, как ack-set «have»
в SHARED_WORLD прунит то, что все подтвердили.

## 5. «9× меньше трафика» — аналог для текста

raymeet считает «смысл vs пиксели» (~40× в `raypipe`: Region байты UDP vs полный кадр). Для текста
считаем «дельта-карточек vs полный ре-дамп 2D-вью»:

- **baseline (1D чат, TEXT_CHAT.md)**: каждая правка = пере-постинг всего изменённого блока/сообщения
  (бинарный пакет `0x06`: timestamp+sender+полное тело, до 1024Б на сообщение).
- **CARDWIRE**: правка = `edit` op с `body_diff` (только изменённые строки) + `vv` ≈ десятки байт;
  добавление темы = `seed`-строка решётки ≈ как `Grid.Rows` (12×8 токенов).

Грубая оценка на типовой сессии (рой уточняет план из ~30 карточек, средняя правка = 1–2 строки тела
из ~12): полный ре-дамп вью ≈ 30 карточек × ~300Б ≈ 9КБ на тик; CARDWIRE-`Patch` ≈ 1 `edit` ×
(diff ~40Б + конверт ~50Б) ≈ ~90Б. Это и есть порядок **~9–40×**, та же природа экономии, что
«Region вместо кадра»: по проводу идёт ИЗМЕНЕНИЕ СМЫСЛА, а 2D-картинка карточек пере-собирается
локально (как `frameSmooth` строит кадр из `Grid` уже на приёме). seed-решётка амортизируется (шлётся
раз на тему, как `Region` раз на регион), курсоры/presence агентов — loss-tolerant (как `Pose` 44Б).

## 6. Много-агентность / много-контурность (MMORPG-сетка камер)

- **lane = контур** (`agent:planner`, `human:alice`, `agent:critic`): своя «дорожка» карточек, как
  отдельная камера наблюдения в сетке. Все lanes делят одну 2D-grid (общий мир), но автор каждой
  карточки тегирован `lane` (как `Pose.actor`/origin-tag голоса в raymeet).
- **кто что видит**: `view.py`-срез по графу `[[links]]` + `canon_index.py` (FTS5) даёт каждому
  агенту контекст-окно (релевантные карточки), а не весь мир — точная аналогия «host шлёт регион
  ВПЕРЁД по ходу walker’а» (region streaming) и «guest реконструирует локально».
- **агент↔агент**: переговоры о владении карточкой/задачей — `pkg/acl` ContractNet (cfp→propose→
  accept) поверх того же `tvcp-ai/1`: кто берётся уточнять данную тему сетки. Конфликт правок
  разрешается CRDT-слоем (§3), конфликт ОТВЕТСТВЕННОСТИ — ContractNet’ом (lowest bid, ties-by-name).
- **разрешение конфликтов**: данные — детерминированно (OR-Set/diff3/VV, §3–4); смысл — видимый
  кворум (карточка `conflict:true` идёт людям/второму агенту), а не один LLM-судья.

## 7. Как ложится на наш репозиторий (re-use)

| Компонент CARDWIRE | Наш примитив | Что добавить |
|---|---|---|
| OR-Set множества карточек | `crdt_merge.merge3` + `LIST_FIELDS` union | поднять с уровня файла на уровень коллекции (CardID-OR-Set + tombstones §4) |
| тело карточки diff3 | `seq_merge.merge_lines` / `_edits` | `body_diff` по проводу = его opcodes, не весь body |
| git-коллизии карточек | `git_reconcile.py` merge-driver | тот же драйвер на `cards/**/*.md` |
| контекст-окно агента | `canon_index.py` (FTS5) + `view.py`/`view_html.py` | FTS-ранжированный срез = «что видит камера», `<details>` = level-раскрытие |
| поток уточнения (thread) | `thread_runner.py` | шаг треда = `Patch` (seed→add→edit), append шага = новый op в лог |

`.babet`-файл = лог `Patch`’ей (append-only, как rrec-запись raymeet `-record`): реплеится в
2D-состояние детерминированно (`rayplay`-аналог), что даёт offline-воспроизводимость и тест.

## 8. Риски / честные пределы

- **GC tombstones**: при долгоживущем рое с приходящими/уходящими акторами причинный фронт может
  не сходиться → tombstones копятся. Митигейт: периодический «барьер» (как ack-have prune), вне
  барьера revive требует явного флага.
- **Семантический мёрж тела**: diff3 чист только на непересекающихся строках; смысловое «оба
  переписали абзац» остаётся видимым конфликтом для человека/кворума (это фича, не баг, но цена —
  не «всё авто-сливается»).
- **Сид-решётка ≠ полнота**: `seed`-grid даёт грубую 2D-карту тем; если рой уводит тему далеко от
  сида, выгода сжатия падает к ре-дампу (как path-рендер вырождается, если Region плохо описан).
- **CardID-коллизии**: hash(seed+actor+nonce) требует достаточного nonce-пространства, иначе два
  агента породят один id для разных карточек.
- **VV-раздувание**: version-vector растёт с числом акторов; в большом рое нужен prune/делегирование
  (lane-агрегаты), иначе `vv` сам становится трафиком.
- **Порядок применения**: идемпотентность держится на корректном `(id,actor,clk)`; кривой/злонамеренный
  мозг может слать неверный clk — нужен тот же трест-барьер, что §14 протокола (валидируем op как
  `CheckResponse` валидирует Spec).
