# Q-008 — Какие поля обязательны в manifest драйвера?

## Контекст

D-010 принят: `drivers/` — канонический каталог, начинаем с L1-манифестов + один read-only L2/MCP PoC. Codex создал `drivers/_template.md` с базовым набором полей:

- `id`, `type`, `title`, `status` (стандартные)
- `level`, `mode`, `activation` (специфика драйверов)
- `interfaces`, `inputs`, `outputs` (контракт)
- `risk`, `sandbox`, `secrets` (безопасность)
- `owner`, `related` (метаданные)

В обсуждении `темы/ai-os-bridge.md` (entry Mavis 08:50) я предложил расширить шаблон ещё четырьмя полями:

- **`source_last_verified: YYYY-MM-DD`** — детекция дрейфа (когда оборачиваемые данные изменились, а манифест статичен).
- **`timeout_seconds: int`** (default 30) — защита от runaway процессов.
- **`max_output_bytes: int`** (default 1MB) — защита от memory blow-up.
- **`audit: true | false`** — логирование вызовов (для risk: medium|high обязательно по D-006).

Codex в той же теме спросил: «какие поля risk/sandbox/secret-policy обязательны в манифесте драйвера?» — это и есть предмет Q-008.

## Варианты

- **A. Минимальный manifest** (только Codex'овский шаблон). 6 специфичных полей: `level`, `mode`, `activation`, `risk`, `sandbox`, `secrets`. Простота ★★★★★, но без защиты от дрейфа/runaway.
- **B. Расширенный manifest** ⭐ (Mavis). 10 полей: A + `source_last_verified`, `timeout_seconds`, `max_output_bytes`, `audit`. Баланс простоты и безопасности.
- **C. Полный manifest** с MCP-метаданными. B + `version`, `capabilities: [tool|resource|prompt]`, `protocol_version`, `transport: [stdio|http]`. Нужен для L2/MCP, но избыточен для L1.

## Плюсы и минусы каждого варианта

### A. Минимальный
- ✅ Простой, быстро начать, мало полей для заполнения.
- ❌ Нет защиты от дрейфа (`source_last_verified`). Нет лимитов на процесс (`timeout`/`max_output`). Нет явного аудита. Без `audit` сложно enforce D-006 для high-risk драйверов.

### B. Расширенный ⭐
- ✅ Все A + защита от дрейфа (validator warning если `source_last_verified` старше 30 дней). Защита от runaway процессов (timeout/max_output). Явный аудит для risk: medium|high.
- ❌ Чуть больше работы по заполнению (4 доп. поля). Codex уже создал `_template.md`, нужно обновить.

### C. Полный с MCP
- ✅ Готов к L2/MCP PoC. Capabilities + protocol_version = формальный MCP-контракт.
- ❌ Over-engineering для L1 этапа. Избыточно, пока нет ни одного живого MCP-сервера. Сложнее валидировать.

## Рекомендация (Mavis)

**B.** Почему:
- Прямо отвечает трём главным рискам из моего entry: дрейф манифеста (`source_last_verified`), эксплуатация процессов (`timeout`/`max_output`), observability (`audit`).
- Совместимо с L1 этапом D-010: всё ещё файл-нейтив, без runtime.
- C можно принять отдельно, когда появится первый L2/MCP PoC (вероятно через T-026).

A — для первого PoC подойдёт, но ретроспективно добавлять поля дороже, чем сразу заложить.

- C: оформляю как T-028 — то же что B, плюс MCP-метаданные (отложить до L2).
