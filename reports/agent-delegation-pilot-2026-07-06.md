## Почему раньше агенты использовались недостаточно

1. В текущей сессии multi-agent tool не был открыт в явном списке до вызова `tool_search`; поэтому часть работы велась локально.
2. Рабочее дерево смешанное: есть правки Codex, других агентов и восстановительные stubs. Непродуманная параллельная запись увеличила бы риск конфликтов.
3. Были задачи с human-gate (`D-026`, `T-280`, accepted governance), где субагент может готовить `proposed`, но не принимать решение.
4. Локальные команды PowerShell часто зависают на чтении/валидации, поэтому агентов нужно использовать как bounded scouts/workers, а не как хаотичный fan-out.

Вывод: это не должно быть оправданием пассивности. Правильная форма — малые независимые волны: read-only scouts + disjoint workers + синтез главным агентом.

## Границы волны

- Агенты не редактируют файлы в этой волне.
- Результаты считаются `proposed`, не `accepted`.
- Главный агент не повторяет их работу, а готовит интеграцию и проверку.
- Следующая волна может включать workers только с disjoint write-scope.

## Критерии приёмки результатов

1. Есть file:line evidence.
2. Есть конкретные next tasks, а не общие пожелания.
3. Есть разделение: что можно делать агентам, что требует человека.
4. Нет предложений удалять историю или обходить D-026/D-006/D-018.
5. Выводы можно превратить в task/report/tool без потери разногласий.

## Что главный агент делает параллельно

1. Проверяет текущий pipeline.
2. Фиксирует волну делегирования в этом документе.
3. Готовит схему следующего шага: `scout -> synthesize -> worker -> verify -> report`.
4. Не ждёт пассивно всех агентов, а продолжает bounded work по safety/orchestration.

## Предлагаемый постоянный цикл

```text
1. Lead формулирует objective и scope.
2. Lead запускает 2-4 read-only scouts по разным вопросам.
3. Пока scouts работают, lead делает не пересекающуюся подготовку.
4. Lead собирает результаты, отделяет consensus от divergence.
5. На consensus запускаются 1-3 workers с disjoint write scopes.
6. Отдельный verifier проверяет patch/results.
7. Lead пишет outbox/report и закрывает pipeline task.
8. Спорное остаётся proposed/divergence до человека или appointed integrator.
```

## Мнение Codex

Для этого проекта сейчас безопасный рабочий режим: 3 агента в read-only scouting + 1 главный интегратор. Переход к нескольким writer-агентам нужен только после `worktree/merge-gate` или явных disjoint write scopes. Иначе мы снова получим проблему смешанного дерева, stale indexes и риск accidental bulk change.
