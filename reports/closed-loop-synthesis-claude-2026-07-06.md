## 2. Консенсус (по смыслу — совпало независимо)

1. Два слоя: стратегические lead-агенты (обсуждение/формулировка/приёмка) ≠ исполнители (узкий scope, structured report, без стратегических решений, без коммитов).
2. Замкнутый цикл: вопрос → задание → согласование → fan-out → возврат → проверка → синтез → котёл → новые задачи → следующий цикл (A: 16 состояний INTAKE..REFILL; B: 8 тактов — одна и та же машина, A мельче гранулярность).
3. Обязательный письменный brief/пакет ДО fan-out (A §5 ↔ B §3); «если brief не пишется коротко — задача не готова к fan-out» (A §5.3, B: порог ~5 подзадач — одно и то же правило с двух сторон).
4. Человек видит сжатую карту (A: decision board / cauldron-lanes; B: повестка), а не сырой шум.
5. Landed ≠ accepted; цикл нельзя закрывать с сиротскими выходами/незамаршрутизированными кандидатами (A §8.4-8.5 ↔ B такт 4/8 + конформанс-практика).
6. Divergence не стирается — уходит в detail-полосу (D-017/D-024, у обоих).
7. Режимы масштаба и потолки: самостоятельные 2–4 / оркестрируемый рой 12–14 при непересекающихся зонах (A §14 ↔ B §1.2/§7 — это принятая К3).
8. Anti-patterns совпадают попунктно (A §15 ↔ B §8 + уроки К1/К4).
9. Ратификация — только человек, батчем по D-035.

Консенсус покрывает ~85% содержания обоих документов. Это сильный сигнал:
независимые архитектуры сошлись.

## 3. Расхождения (4) и предлагаемый синтез

**Р1. Где живёт brief/пакет и его статусы.**
A: `topics/<topic>/brief.md` или tmp-work (лёгкий, без машинных статусов).
B: `kotel/packages/PKG-*.md` с front-matter статусами (draft→…→closed), зонами, риском.
*Синтез:* один файл — brief-схема A **плюс** машинный front-matter B (status,
risk, zones, agreed_by, deadline); расположение A (`topics/<topic>/brief.md`) —
не плодить новый каталог. Статусы нужны машинно: advisory «in-swarm старше N
дней» и «зоны пересекаются» без них не построить.

**Р2. Формализация согласования.**
A: состояние AGREED есть, но правила не заданы («человек/агенты согласовали»
— как, когда можно без ожидания?). B: явные риск-правила (low → без
согласования, post-factum; medium → окно молчания 12ч ИЛИ ok одного агента,
veto останавливает; high → только человек, по D-027).
*Синтез:* вставить риск-правила B внутрь состояния AGREED варианта A — это
закрывает главный практический вопрос «сколько ждать» и снимает бутылочное
горлышко такта 2.

**Р3. Витрина для человека.**
A: существующие `two_track.py board` + `cauldron-lanes` + synthesis-отчёты.
B: новый генерат `kotel/agenda.md` (пакеты+вопросы+демонстрации).
*Синтез:* основа — A (переиспользование выигрывает: инструменты уже есть и
работают); agenda-слой B добавлять ТОЛЬКО если одновременных пакетов станет
больше ~5 и понадобится сводка зон. До тех пор зоны видны из brief-файлов.

**Р4. Порядок следующего шага.**
A: сначала T-276 (materializer), потом демонстрационный цикл.
B: пилот на T-273 немедленно, инструменты — по итогам.
*Синтез:* параллельно, но пилот не ждёт: T-273 стартует сразу (материализация
задач вручную через next_id — отработана волнами), а T-276 строится по итогам
пилота, когда станет видно, ЧТО именно материализуется чаще всего. Пилот даст
T-276 реальную спецификацию вместо предположительной.
