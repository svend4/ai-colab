# Протокол совместной работы людей и AI-агентов

Этот протокол нужен для режима, где в одной рабочей папке одновременно работают люди, несколько AI-агентов, скрипты и подагенты.

Главное правило: **много участников не должны постоянно редактировать один и тот же файл**. Вместо этого каждый участник пишет в свое место, а общий итог собирается отдельно.

## Уровни работы

### 1. Общий статус

Файл: `STATUS.md`

Назначение: краткая сводка текущего состояния. Его обновляют редко и аккуратно.

Правило: `STATUS.md` не должен быть местом для споров, черновиков и длинных обсуждений.

### 2. Темы

Папка: `темы/`

Одна тема может иметь не один файл, а папку:

```text
темы/
  big-topic/
    README.md
    summary.md
    questions.md
    decisions.md
    messages/
      2026-06-19-1320-stefan.md
      2026-06-19-1325-agent-codex.md
      2026-06-19-1326-agent-reviewer.md
```

Такой формат лучше для большой компании: каждый пишет отдельный файл-сообщение, поэтому почти нет конфликтов записи.

### 3. Сообщения

Папка внутри темы: `messages/`

Правило: **одно сообщение = один файл**.

Время в сообщениях по умолчанию указывается в локальном часовом поясе `Europe/Berlin`. Если агент или человек использует другой часовой пояс, он должен явно написать его в подписи или метаданных сообщения.

Имя файла:

```text
YYYY-MM-DD-HHMM-author-short-title.md
```

Пример:

```text
2026-06-19-1325-agent-codex-risk-analysis.md
```

Формат сообщения:

```md
# Сообщение

- Дата: 2026-06-19 13:25
- Автор: agent-codex
- Тип: answer
- Адресовано: all
- Связанные файлы:
  - `TASKS.md`

## Текст

...

## Предлагаемые действия

- [ ] ...
```

### 4. Очереди для агентов

Папка: `queues/`

```text
queues/
  inbox/
  claimed/
  outbox/
  done/
  failed/
```

- `queues/inbox/` - входящие поручения, материалы и сообщения для AI-агентов и скриптов.
- `queues/claimed/` - исторические/legacy отметки; текущий claim задач делает `tools/pipeline.py`.
- `queues/outbox/` - результаты, которые агент подготовил, но еще не внес в основные файлы.
- `queues/done/` - выполненные задания.
- `queues/failed/` - задания, которые не удалось выполнить.

Правило: агент смотрит состояние через `python tools/pipeline.py status`, берёт задачу через `python tools/pipeline.py next <agent>`, пишет результат в `outbox` или профильную тему, закрывает задачу через `done --claim`, а человек или главный агент переносит важное в `STATUS.md`, `TASKS.md`, `QUESTIONS.md`, `DECISIONS.md`.

Имя claim-файла:

```text
YYYY-MM-DD-HHMM-task-id-agent-id.md
```

Если агент видит, что по задаче уже есть активный pipeline-claim другого агента, он не должен выполнять ту же работу без отдельной причины. Для содержательных альтернатив используется fork/stream, а не второй claim на тот же исполнительный шаг.

### 5. Реестр агентов

Файл: `AGENTS.md`

Каждый AI-агент должен иметь имя, роль и границы ответственности.

Пример:

```md
| ID | Роль | Может писать | Не должен делать |
|---|---|---|---|
| agent-codex | главный помощник | docs, tasks, decisions | удалять чужой текст |
| agent-reviewer | проверка рисков | queues/outbox, темы | менять финальные решения |
```

### 6. Запрет на перезапись

Для большого числа участников вводится append-only режим:

- не удалять чужие сообщения;
- не редактировать чужие сообщения;
- не переписывать историю обсуждения;
- исправления писать новым сообщением;
- итог переносить в `summary.md`, `DECISIONS.md` или `TASKS.md`.

### 7. Обоснование правок

Служебные и общие файлы не должны меняться "молча". Если человек, AI-агент или скрипт меняет такие файлы, он должен оставить короткое объяснение в профильной теме или в `dialog.md`.

Служебные и общие файлы:

- `STATUS.md`;
- `TASKS.md`;
- `QUESTIONS.md`;
- `DECISIONS.md`;
- `PROTOCOL.md`;
- `AGENTS.md`;
- `board.md`;
- `dialog.md`;
- файлы в `templates/`;
- `queues/README.md` и правила очередей.

Минимальное объяснение:

```md
### YYYY-MM-DD HH:MM - author-id

Изменил: `file.md`.
Почему: причина изменения.
Мое мнение: позиция автора или агента.
Что нужно от других: ответ, проверка, решение или ничего.
```

Правило не означает, что каждую опечатку нужно долго обсуждать. Но структурные, организационные и смысловые изменения должны иметь видимый след, чтобы люди и агенты могли ответить асинхронно.

### 8. Кто собирает итог

Нужен один "сборщик" на тему:

- человек-модератор;
- главный AI-агент;
- скрипт-суммаризатор.

Сборщик читает `messages/`, обновляет `summary.md`, выносит решения в `decisions.md` или общий `DECISIONS.md`.

Правило D-006: AI-агент или скрипт может готовить `summary.md` и черновики решений, но перевод решения в `accepted` делает человек или явно назначенный человеком сборщик. Автоматический агент без такого назначения оставляет решения в статусе `proposed`.

### 9. Когда нужен Git

Если участников много, Git обязателен:

- видно, кто что поменял;
- можно откатить ошибку;
- можно разбирать конфликты;
- можно работать через ветки и pull request.

Для эксперимента в одной локальной папке можно начать без веток, но с правилом "одно сообщение = один файл".

### 10. Commits, streams и полу-коммиты

Git commit — это снимок основной линии, а не место для всех незавершённых вариантов.

Если в workspace есть чужие незавершённые файлы, агент не должен делать широкий `git add -A` или
`git commit -a`. Коммитить можно только явный список файлов своей задачи. Если изменения смешались,
нужен отдельный integration commit с понятным описанием.

Для спорных вариантов используется `streams/`:

```text
streams/<topic-id>/<stream-id>/
  STREAM.md
  notes.md
  patch.diff
  files/
  evidence/
```

Stream — это "полу-коммит": уже структурированный вариант, но ещё не mainline. Он нужен, чтобы разные
агенты могли вести параллельные ручейки решений, сравнивать их и только потом вливать выбранный вариант
в основную линию.

Правило: дубликаты очереди можно схлопывать, но варианты решений нельзя терять. Если похожая карточка
содержит другой технический подход, он переносится в stream или design comparison.

Подробно: `docs/commit-stream-policy.md`.

### 11. Четыре уровня папок

Для большой системы вводится логическое разделение:

```text
core/      # L1: переносимое универсальное ядро
portals/   # L2: чистовые специализированные порталы/профили
collab/    # L3: история, полилог, задачи, вопросы, решения, streams
sandbox/   # L4: входной хаос, внешние источники, quarantine
```

Материалы должны двигаться вверх постепенно:

```text
sandbox -> collab -> portals -> core
```

Raw input не должен сразу попадать в `core/` или `portals/`. Исторический спор не должен загрязнять
чистовой портал. Универсальное ядро не должно зависеть от одного пользователя, домена или внешнего
репозитория.

Подробно: `docs/workspace-pyramid-levels.md`.

## Рекомендуемая схема для большого режима

```text
.
  STATUS.md
  TASKS.md
  QUESTIONS.md
  DECISIONS.md
  AGENTS.md
  PROTOCOL.md

  темы/
    topic-name/
      README.md
      summary.md
      questions.md
      decisions.md
      messages/

  queues/
    inbox/
    claimed/
    outbox/
    done/
    failed/

  streams/
    topic-name/
      stream-id/
        STREAM.md
        patch.diff
        evidence/

  core/
  portals/
  collab/
  sandbox/

  docs/
  code/
  participants/
  templates/
```

## Короткое правило

Маленькая группа может писать в один Markdown-файл. Большая группа и много агентов должны писать **много маленьких Markdown-файлов**, а итог собирать отдельно.
